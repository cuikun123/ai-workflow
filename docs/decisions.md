## 核心工作流

**需求与起步 → 任务计划 → 执行与协作 → 验证与审查 → 用户验收 → 恢复与下一轮**

以下顺序用于阅读，跨环节规则仍按各决定规定的时点生效；例如方案审查发生在实现前，执行中的验证和调试也不会推迟到交付时。

### 需求与起步

详细设计：[第一次开始项目](design/workflow.md#第一次开始项目)。资料缺项规则 D50 同时适用于后续各环节。

| 编号 | 主题 | 决定 |
| --- | --- | --- |
| D49 | 使用者与 AI 分工 | 开发者可只提出想法，无需先决定技术细节；AI 主动调查业务开源方案、比较语言与技术路线，解释推荐和取舍，并纳入用户技术偏好。关键选择沿用 D05；业务调研与 D33 的框架能力融合并存，验证技术栈不成为所有项目的固定选型。 |
| D50 | 资料不完整 | 在已有授权内主动补查可查信息，不重复提问；关键业务意图用业务语言澄清，不将现有代码当成用户期望。用户拿不准时提供选择、推荐与影响，建议不自动成为要求。独立可做部分继续推进，受缺项影响的结论保留，不强制补齐整套文档或把部分检查写成整体通过；原有操作边界保持。 |
| D19 | 地基要求 | 地基包含安全与数据、DoD、最低可观测性，必须进行实际工程验证。 |
| D53 | 首次项目起步 | 澄清目标、调查开源、比较技术并考虑用户偏好；将起步范围、方案、任务和验收方式在已有设计与计划确认中一并确定。确认后建立最小工程，完成必要组件连通、基础检查及工程约定，审查并逐任务验收；地基完成后进入首轮业务迭代。内容按项目需要选择，不增设重复审批点。 |

### 任务计划

计划中的验收与检查要求关联下文的[验证与审查](#验证与审查)、[用户验收](#用户验收)。任务计划的方法融合已确认 D55，见[开源能力复用](#开源能力复用)。

| 编号 | 主题 | 决定 |
| --- | --- | --- |
| D40 | 任务粒度 | 按可验收成果拆任务，再拆技术子步骤。普通功能对应最小完整使用场景，不按单个文件、按钮、数据表或技术层机械拆验收，也不把多个独立成果笼统合并。子步骤在当前目标与授权内自主推进，不逐项等待验收；关键变化仍确认。可独立交付和验收的接口、工程、文档也可成任务，不要求有页面。任务提交仍按 D39 等待。 |
| D41 | 安排与调整 | 实施前随设计和计划展示整轮任务的成果、边界、验收要点、依赖与顺序，一并确认；任务开始时简述成果与边界，前置和授权具备即执行。内部步骤自主调整，原目标遗漏或修复留在当前任务。影响成果、验收或交付次序的拆分、合并、依赖及顺序调整，先说明原因、前后对比和影响，获确认再执行；不合并任务绕过等待或移出未满足要求后宣称完成。tasks.md 记安排、进度与调整原因，verification.md 留依据。 |

### 执行与协作

详细设计：[工作流](design/workflow.md) · [多 Agent 协作](design/multi-agent.md)。独立调用的操作边界见[独立审查与诊断](#独立审查与诊断)，方法融合见[开源能力复用](#开源能力复用)的 D56。

| 编号 | 主题 | 决定 |
| --- | --- | --- |
| D05 | 确认边界 | 关键节点由用户确认，阶段内部自主执行；小变更可合并确认点，重要变化重新确认。 |
| D06 | 迭代并发 | 默认同一时间推进一轮迭代；可保存后暂停切换，轮内允许多 Agent 协作。 |
| D07 | Agent 分工 | 主 Agent 统筹，子 Agent 按任务创建，默认最多三个，不默认递归委派。 |
| D08 | 调用方式 | 统一入口引导全流程，也支持独立调用阶段或专项能力，并检查必要前置条件。 |
| D32 | 调试闭环 | 优先适配 systematic-debugging：明确症状并复现取证，对比正常路径，以最小实验验证原因；在授权内修复，回归并审查后返回原任务。支持流程内自主调试与独立调用；事实、假设和已验证原因分开，无法复现或验证如实说明，无新证据时停止叠加补丁。 |

### 验证与审查

详细设计：[任务检查与验收](design/workflow.md#3-逐任务实现检查和验收)。审查、调试等方法的来源见[开源能力复用](#开源能力复用)。

| 编号 | 主题 | 决定 |
| --- | --- | --- |
| D34 | 测试职责 | 流程内置且可独立调用：按需求、验收与影响确定必要验证，按需维护正常、边界和异常用例，实际执行、失败后调试重验，并报告范围、结果与证据。检查组合随项目确定，必要检查失败或未执行不能宣布任务全部完成。 |
| D35 | 检查选择 | AI 依据需求、验收、DoD 和实际影响提出并简述必要检查，在已有目标、规则和授权内自主执行，不让用户逐条选择技术检查。业务预期不清、需改验收标准，或涉及重要环境、数据、安全与成本变化时请用户决定；不得为通过检查降低标准。 |
| D36 | 验证受阻 | 先查原因，在已有授权内处理可解决的准备问题；重要环境变更、额外费用、凭据或真实数据缺乏授权时，说明条件和影响并请用户决定。仍受阻则继续独立检查，记录受阻项、原因、补齐条件与下一步。模拟不能冒充真实集成验证，实现与验证状态分开，必要检查未完不称全部完成。 |
| D37 | 验证记录 | 对话给简短结论，verification.md 留详细依据，tasks.md 更新进度。区分通过、失败、未执行、不适用，后两者说明原因；保留执行方式、必要环境、关键证据及未解决问题、补齐条件和下一步，无需粘贴完整日志，不另建平行报告。结论仅覆盖实际验证范围。 |
| D51 | 审查安排 | 实现前检查关键方案；普通功能任务验收前默认一次独立审查，低影响修改可简化，高风险按需专项检查，整轮再审跨任务衔接。审查使用全新独立上下文，交接只给需求及相关改动，不传开发对话或实现推理；审查者可只读项目规范、必要调用方与依赖代码。审查者读取原始依据及实际产物，核对需求与质量，主 Agent 管理状态。发现有位置、条件、影响和证据，分必须修复、改进建议、待核实，不设数量指标或把关键未知记为通过；非必要命名偏好、未要求的重构或额外优化不进入修复列表、不阻塞合入。经核验、有效修复、重验和复查后关闭；技术分歧凭证据解决，重要业务取舍请用户决定。同一问题连续两轮无新证据或反复回退时停止重复修改、重新调查，仍未解决则报告阻塞，不因轮数自动通过。内容变化后重查受影响结论，回归修复后重新验收；逐任务等待及记录分别按 D39、D37。 |

### 用户验收

任务粒度与安排见[任务计划](#任务计划)，证据和进度的文件职责见[文档与状态](#文档与状态)。

| 编号 | 主题 | 决定 |
| --- | --- | --- |
| D38 | 最终完成 | 用户逐任务验收是最终完成的重要依据；实施、AI 检查和用户验收分别记录，未经用户明确通过不得记为已验收或最终完成。用户验收也不能把失败或未执行的必要检查改为通过。 |
| D39 | 提交与等待 | 实施并完成必要检查后，主动提交成果、体验入口或可查产物、准备与步骤、预期结果、已知限制及未验证项，并附检查证据。提交后暂停下一任务，等待用户明确通过；沉默、自检或阶段授权不替代验收。未通过则在原范围与授权内处理反馈、重验并重交，实质变化另行确认。 |

### 恢复与下一轮

反馈与发布见[发布运行与反馈](#发布运行与反馈)；Git 层面的暂停、切换和恢复策略仍待专题确定。

| 编号 | 主题 | 决定 |
| --- | --- | --- |
| D29 | 恢复当前迭代 | 从项目导航定位并核对当前迭代、任务、实际文件和确认，先报告目标、位置与下一步；目标明确、前置满足且授权适用时接续。冲突、歧义或关键待确认事项先处理；不按目录编号或聊天新旧猜测，不把含糊的“继续”当成批准。明确的新指令优先核对处理。 |
| D54 | 无当前迭代与查询 | 下一目标明确时按已有确认和授权接续；未定时根据项目目标与待办推荐候选及理由，由用户选择；无候选则主动问清目标。选定后沿用澄清、设计和计划，不自动批准未展示的实施方案。只查询进度时核对并报告状态、问题和下一步，不启动新工作或改写状态；已有迭代按 D29。 |

## 专项能力与交付

### 独立审查与诊断

与[执行与协作](#执行与协作)、[验证与审查](#验证与审查)共用能力，独立请求按本节边界处理。

| 编号 | 主题 | 决定 |
| --- | --- | --- |
| D30 | 仅请求审查 | 检查并报告问题及建议；明确要求修复或已有适用授权时才改代码，已有授权不重复询问。越出请求或授权的写入、环境变更按既定规则处理。 |
| D47 | 审查范围 | 优先采用用户指定范围；未指定时结合当前任务与实际改动定位并简短说明。范围明确、前置和授权满足时直接检查；多个合理目标或歧义时先问清。操作边界按 D30，资料缺项按 D50。 |
| D52 | 独立诊断 | 仅查原因时，在已有授权内读资料、代码与日志，并可在不影响实际项目和真实业务的隔离环境中复现，报告依据、未知项及修复建议。代码、配置和真实数据等改动依修复请求与已有授权处理；无授权先说明操作与影响，请用户决定。诊断实验也逐步核对副作用；流程内调试和线上故障分别按 D32、D44。 |

### 发布、运行与反馈

详细设计：[发布与后续工作](design/workflow.md#发布与后续工作)。

| 编号 | 主题 | 决定 |
| --- | --- | --- |
| D42 | 发布失败 | 先按事前明确且本次授权覆盖的方案回滚并核验，再报告问题、原因依据、回滚结果、当前状态和解决建议，由用户决定是否重试。原因未知时区分事实与假设；回滚无法执行或失败则报告，不称已恢复、不继续盲目操作。不得自动重试或重新部署，建议不等于修复或再发布授权，一般阶段或部署授权也不越过重试等待点。按项目核对数据恢复，代码回退不代表数据已恢复。此规则取代早先“不自动回滚”的解释。 |
| D43 | 发布方式 | 首版采用方式 C，按环境、风险和授权处理：支持准备发布；部署路径明确、可恢复且授权适用时由 AI 部署并上线检查。新环境、费用、重要数据迁移或授权不清时先给方案，由用户决定是否推进及由谁执行。用户亲自执行时提供产物、配置、步骤和检查方法，协助核验；无法核验如实记录。失败按 D42，本决定不构成真实环境授权。 |
| D44 | 线上故障 | 先主动询问必要信息、明确问题和范围，再在已有访问授权内调查；不得先查、遇缺项才问。报告问题、原因依据、未知项与方案，经用户同意后修复；故障反馈、调查请求或一般调试授权不替代修复确认，已同意的具体方案和适用授权不重复确认。修复后沿用验证、验收与发布规则；D42 不自动扩展为所有线上故障立即回滚。 |
| D45 | 使用反馈 | AI 主动澄清使用场景、问题和期望结果，不要求用户先写完整需求，也不把模糊感受补成确定功能。改进事项沿用 backlog、范围和确认规则；理解或记录反馈不等于批准开发。 |

### 开源能力复用

详细设计：[来源与适配](design/capability-reuse.md)。具体采用范围、版本及验证仍见下方待定事项。
