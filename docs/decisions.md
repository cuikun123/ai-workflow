# 决策记录

本页收录长期有效的规则与原则，按类别组织；被取代的规则以新主题为准。“已确认”表示用户认可，不代表已经实现；实际运行、验收与缺口见[当前交接](handoff.md)和[验证记录](../tests/README.md)。框架规则不自动授予真实项目或环境的操作权限。

## 定位与范围

| 主题 | 决定 |
| --- | --- |
| 用途 | 自建符合个人习惯的 AI 开发框架，兼顾个人与工作场景。 |
| 首版边界 | 首版聚焦 Codex 和从零建立的个人 Web 项目；接手既有业务项目不在范围内。 |
| 技术栈 | 核心流程技术栈无关；Java、React、MySQL 仅为熟悉的首个验证方向，具体方案未选。 |
| 生命周期 | 覆盖项目地基、持续小迭代和发布，不要求预先理清全部需求。 |
| 能力范围 | 覆盖需求、产品体验、架构、工程、安全、开发、测试、调试、审查、部署及反馈迭代。 |
| 名称与许可 | 框架名称为 Iterlane（迭序），包名与命令为 `iterlane`，整体采用 MIT 许可，版权署名 TY，保留所有第三方原许可。 |

## 核心工作流

### 需求与起步

| 主题 | 决定 |
| --- | --- |
| 使用者与 AI 分工 | 开发者可只提出想法，无需先决定技术细节；AI 主动调查业务开源方案、比较语言与技术路线，解释推荐和取舍，并纳入用户技术偏好。关键选择沿用 「确认边界」；业务调研与 「融合与交付」 的框架能力融合并存，验证技术栈不成为所有项目的固定选型。 |
| 资料不完整 | 在已有授权内主动补查可查信息，不重复提问；关键业务意图用业务语言澄清，不将现有代码当成用户期望。用户拿不准时提供选择、推荐与影响，建议不自动成为要求。独立可做部分继续推进，受缺项影响的结论保留，不强制补齐整套文档或把部分检查写成整体通过；原有操作边界保持。 |
| 地基要求 | 地基包含安全与数据、DoD、最低可观测性，必须进行实际工程验证。 |
| 首次项目起步 | 澄清目标、调查开源、比较技术并考虑用户偏好；将起步范围、方案、任务和验收方式在已有设计与计划确认中一并确定。确认后建立最小工程，完成必要组件连通、基础检查及工程约定，审查并逐任务验收；地基完成后进入首轮业务迭代。内容按项目需要选择，不增设重复审批点。 |

### 任务计划

| 主题 | 决定 |
| --- | --- |
| 任务粒度 | 按可验收成果拆任务，再拆技术子步骤。普通功能对应最小完整使用场景，不按单个文件、按钮、数据表或技术层机械拆验收，也不把多个独立成果笼统合并。子步骤在当前目标与授权内自主推进，不逐项等待验收；关键变化仍确认。可独立交付和验收的接口、工程、文档也可成任务，不要求有页面。任务提交仍按 「提交与等待」 等待。 |
| 安排与调整 | 实施前随设计和计划展示整轮任务的成果、边界、验收要点、依赖与顺序，一并确认；任务开始时简述成果与边界，前置与授权具备即执行。内部步骤自主调整，原目标遗漏或修复留在当前任务。影响成果、验收或交付次序的拆分、合并、依赖、顺序调整，先说明原因、前后对比与影响，确认后再做；不合并任务绕过等待，或把未满足的要求移出后宣称完成。tasks.md 记安排、进度与调整原因，verification.md 留依据。 |

### 执行与协作

| 主题 | 决定 |
| --- | --- |
| 确认边界 | 关键节点由用户确认，阶段内部自主执行；小变更可合并确认点，重要变化重新确认。 |
| 迭代并发 | 默认同一时间推进一轮迭代；可保存后暂停切换，轮内允许多 Agent 协作。 |
| Agent 分工 | 主 Agent 统筹，子 Agent 按任务创建，默认最多三个，不默认递归委派。 |
| 调用方式 | 统一入口引导全流程，也支持独立调用阶段或专项能力，并检查必要前置条件。 |
| 共享工具门槛 | 不同客户端复用同一套操作前置判定，按实际参数和既有记录核对。内核只读，客户端负责执行拦截；证据不足不能放行，不新增授权账本。接口和支持边界见[共享工具门槛设计](design/tool-guard.md)。 |
| 调试闭环 | 优先适配 systematic-debugging：明确症状并复现取证，对比正常路径，以最小实验验证原因；在授权内修复，回归并审查后返回原任务。支持流程内自主调试与独立调用；事实、假设和已验证原因分开，无法复现或验证如实说明，无新证据时停止叠加补丁。 |

### 验证与审查

| 主题 | 决定 |
| --- | --- |
| 测试职责 | 流程内置且可独立调用：按需求、验收与影响确定必要验证，按需维护正常、边界和异常用例，实际执行、失败后调试重验，并报告范围、结果与证据。检查组合随项目确定，必要检查失败或未执行不能宣布任务全部完成。 |
| 检查选择 | AI 依据需求、验收、DoD 和实际影响提出并简述必要检查，在已有目标、规则和授权内自主执行，不让用户逐条选择技术检查。业务预期不清、需改验收标准，或涉及重要环境、数据、安全与成本变化时请用户决定；不得为通过检查降低标准。 |
| 验证受阻 | 先查原因，在已有授权内处理可解决的准备问题；重要环境变更、额外费用、凭据或真实数据缺乏授权时，说明条件和影响并请用户决定。仍受阻则继续独立检查，记录受阻项、原因、补齐条件与下一步。模拟不能冒充真实集成验证，实现与验证状态分开，必要检查未完不称全部完成。 |
| 验证记录 | 对话给简短结论，verification.md 留详细依据，tasks.md 更新进度。区分通过、失败、未执行、不适用，后两者说明原因；保留执行方式、必要环境、关键证据及未解决问题、补齐条件和下一步，无需粘贴完整日志，不另建平行报告。结论仅覆盖实际验证范围。 |
| 真实形态验证 | 判定外部系统行为的工具（Git、文件系统、平台、客户端入口）必须有跑在真实形态上的用例：真实 worktree、真实仓库配置文件、真实客户端调用路径。临时初始化的空仓库只证明逻辑分支，不证明能用；缺真实形态证据时按未验证报告，不写成已实现或已保护。 |
| 自举验证 | 框架自身工具交付前，必须在框架仓库上实跑一次完整调用，用它的真实分支、worktree 和工作区规则。连框架仓库都判不了、或要求用户改掉自己的仓库配置才能用时，不算交付完成；差异按必须修复处理，确实不支持的写入支持范围并在交付时说明。 |
| 审查安排 | 实现前先查关键方案；普通任务验收前默认一次独立审查，低影响可简化、高风险加专项，整轮再审跨任务衔接。审查用全新独立上下文，只交接需求与相关改动、不传开发推理；审查者读原始依据与实际产物核对需求和质量。发现按必须修复、改进建议、待核实分类，不设数量指标、不把关键未知记为通过，非必要的命名偏好或重构不阻塞合入。经核验、修复、重验、复查后关闭；技术分歧凭证据，业务取舍请用户定。同一问题连续两轮无新证据就停止反复修改、重新调查，仍解决不了就报告阻塞。 |

### 用户验收

| 主题 | 决定 |
| --- | --- |
| 最终完成 | 用户逐任务验收是最终完成的重要依据；实施、AI 检查和用户验收分别记录，未经用户明确通过不得记为已验收或最终完成。用户验收也不能把失败或未执行的必要检查改为通过。 |
| 提交与等待 | 实施并完成必要检查后，主动提交成果、体验入口或可查产物、准备与步骤、预期结果、已知限制及未验证项，并附检查证据。提交后暂停下一任务，等待用户明确通过；沉默、自检或阶段授权不替代验收。未通过则在原范围与授权内处理反馈、重验并重交，实质变化另行确认。 |

### 恢复与下一轮

| 主题 | 决定 |
| --- | --- |
| 恢复当前迭代 | 从项目导航定位并核对当前迭代、任务、实际文件和确认，先报告目标、位置与下一步；目标明确、前置满足且授权适用时接续。冲突、歧义或关键待确认事项先处理；不按目录编号或聊天新旧猜测，不把含糊的“继续”当成批准。明确的新指令优先核对处理。 |
| 无当前迭代与查询 | 下一目标明确时按已有确认和授权接续；未定时根据项目目标与待办推荐候选及理由，由用户选择；无候选则主动问清目标。选定后沿用澄清、设计和计划，不自动批准未展示的实施方案。只查询进度时核对并报告状态、问题和下一步，不启动新工作或改写状态；已有迭代按 「恢复当前迭代」。 |

## 专项能力与交付

### 独立审查与诊断

| 主题 | 决定 |
| --- | --- |
| 仅请求审查 | 检查并报告问题及建议；明确要求修复或已有适用授权时才改代码，已有授权不重复询问。越出请求或授权的写入、环境变更按既定规则处理。 |
| 审查范围 | 优先采用用户指定范围；未指定时结合当前任务与实际改动定位并简短说明。范围明确、前置和授权满足时直接检查；多个合理目标或歧义时先问清。操作边界按 「仅请求审查」，资料缺项按 「资料不完整」。 |
| 独立诊断 | 仅查原因时，在已有授权内读资料、代码与日志，并可在不影响实际项目和真实业务的隔离环境中复现，报告依据、未知项及修复建议。代码、配置和真实数据等改动依修复请求与已有授权处理；无授权先说明操作与影响，请用户决定。诊断实验也逐步核对副作用；流程内调试和线上故障分别按 「调试闭环」、「线上故障」。 |

### 发布、运行与反馈

| 主题 | 决定 |
| --- | --- |
| 发布失败 | 先按事前明确、且本次授权覆盖的方案回滚并核验，再报告问题、原因依据、回滚结果、当前状态和建议，由用户决定是否重试。原因未知时区分事实与假设；回滚做不了或失败就如实报告，不称已恢复、不盲目继续。不自动重试或重新部署；建议不等于修复或再发布授权。按项目核对数据恢复——代码回退不代表数据已恢复。 |
| 发布方式 | 首版采用方式 C，按环境、风险和授权处理：支持准备发布；部署路径明确、可恢复且授权适用时由 AI 部署并上线检查。新环境、费用、重要数据迁移或授权不清时先给方案，由用户决定是否推进及由谁执行。用户亲自执行时提供产物、配置、步骤和检查方法，协助核验；无法核验如实记录。失败按 「发布失败」，本决定不构成真实环境授权。 |
| 线上故障 | 先主动询问必要信息、明确问题和范围，再在已有访问授权内调查；不得先查、遇缺项才问。报告问题、原因依据、未知项与方案，经用户同意后修复；故障反馈、调查请求或一般调试授权不替代修复确认，已同意的具体方案和适用授权不重复确认。修复后沿用验证、验收与发布规则；「发布失败」 不自动扩展为所有线上故障立即回滚。 |
| 使用反馈 | AI 主动澄清使用场景、问题和期望结果，不要求用户先写完整需求，也不把模糊感受补成确定功能。改进事项沿用 backlog、范围和确认规则；理解或记录反馈不等于批准开发。 |

## 支撑机制

### 文档与状态

| 主题 | 决定 |
| --- | --- |
| 文档结构 | 业务文档采用已批准结构；上游必要产物无法归属时，重新讨论结构。 |
| 空文档 | 初始化先建立固定空文档，由地基及各轮迭代按阶段填充、更新。 |
| 最小有效内容 | AGENTS.md 与 state.yaml 必须有最小有效内容；空文件不能当成已有结论。 |
| 内容与历史 | 当前有效资料、每轮变更历史、发布记录分别管理；spec 与迭代是多对多关系。 |
| 状态职责 | state.yaml 只作导航和进度书签，不复制需求、任务与验证历史。 |
| 文档拆分 | 公共约束按职责组织，业务规格按主题按需拆分，不机械按行数切分。 |
| 轻量规格 | 采用目的、范围、需求与场景的写法；稳定需求编号作为关联建议。 |
| 资料归属 | 模板属于框架仓库；生成后的真实项目内容属于业务项目仓库。 |

### 接入与版本

| 主题 | 决定 |
| --- | --- |
| 完整能力包 | 每个业务项目保存所需 Skills、脚本、模板与检查规则；布局和技能入口按 「顶层布局」、「技能安装」。 |
| 版本与升级 | 项目固定框架版本，日常不自动跟随新版；用户主动升级，升级前检查差异和兼容性，保留业务资料与迭代进度。升级对业务项目的影响边界按「框架升级与业务变更的边界」。 |
| 顶层布局 | .ai-workflow/ 保存框架资源与版本信息，.agents/skills/ 接入技能，根 AGENTS.md 提供协作说明和导航，docs/ 保存既定业务文档、迭代与状态。 |
| 技能安装 | 采用方案一：完整说明安装到 `.agents/skills/<skill>/SKILL.md`，公共脚本、模板和版本信息放 `.ai-workflow/`；两处共同组成完整能力包，统一管理版本。 |
| 重复初始化 | 同版本重跑保留已有内容和进度，先列缺失与冲突再决定修复；升级使用独立流程，初始化不自动升级。 |
| 失败恢复 | 资源先在临时位置准备、检查后安装，保留业务资料与用户修改。只尝试还原本次已授权、归属明确且未被外部修改的安装写入；冲突或归属不明时保留现场并按 「重复初始化」 处理。未完成接入须标记，下次核对实际文件并通过完整检查后才能标记成功。 |
| 接入验收 | 真实目标工具须完成一次正确读取项目状态、不修改业务内容的入口调用；按锁定版本和受管理清单检查完整性与变化，差异先报告。结构与运行结果分开记录，两者通过才算接入成功。入口失败先定位，不因网络或登录问题一律回滚；必要恢复按 「失败恢复」。 |

### 开源能力复用

| 主题 | 决定 |
| --- | --- |
| 复用原则 | 保留自身工作流与文档体系，优先吸收、适配成熟开源能力；不整包照搬，也不只作外层路由。 |
| 审查来源 | 优先评估 Superpowers 的发起审查、模板与反馈核验方法，BMAD 部分视角为补充候选。框架管理时点、范围、授权、修复验证及记录；来源方向不等于强制每项任务委派，审查安排另按 「审查安排」。 |
| 融合与交付 | 框架维护阶段选取来源、固定版本、适配和验证后随能力包提供；日常使用已接入能力无需再临时查找、搬入或整包安装上游。沿用本框架文档、范围、授权和状态规则，保留来源与许可追溯；外部工具或服务依赖预先声明并核对，不能把“已融合”当成运行条件齐备。 |
| 反馈澄清来源 | 以 Superpowers brainstorming 的提问和理解核对为主，Spec Kit clarify 作为已有规格歧义检查的补充候选。框架管理入口、阶段、文档、授权和状态，输出沿用 backlog 及适用 scope、spec；不带入平行文档体系、自动提交、强制委派或澄清后自动设计开发。记录反馈不等于批准开发。 |
| 首次引导来源 | 以 Superpowers brainstorming 为主，利用已有信息问清目标与限制、核对理解、比较方案，设计确认后衔接计划。框架负责接入、地基、文档和验收；不照搬上游目录、提交及委派规则。起步流程另按 「首次项目起步」，具体版本与文件仍待适配。 |
| 任务计划融合 | 提供任务计划技能：融合 Spec Kit 的成果组织与覆盖检查、Superpowers 的技术步骤细化。读既有范围、方案、规格、公共约定和任务进度；任务安排写当前迭代 tasks.md，检查依据沿用 verification.md，保留已有进度与验收事实。按本框架的文档、测试、确认与接续规则运行，不带入上游的平行文档、进度系统或自动 hooks。 |
| 执行与协作融合 | 提供执行与协作技能：融合 Superpowers 的执行核对、子代理开发、任务交接与修复复查、完成前证据判断。核对当前任务、计划确认、授权与依赖，主 Agent 自己执行或按需委派，组织必要验证、独立审查与修复闭环，把成果交用户验收并等待。进度与依据沿用 tasks.md、verification.md；不带入上游的自动提交、平行进度、越过验收或“修到限即记完成”的规则。未实现的能力不写成可调用依赖。 |
| 审查与反馈核验融合 | 提供专项审查能力，融合 Superpowers 的发起审查、审查模板与反馈核验方法，可独立调用、也供执行流程使用；BMAD 视角留作后续候选。按原始要求与实际产物审查需求符合性、实现质量和测试证据，核验反馈是否成立，为修复和复查提供依据。execute-task 组织执行、修复与验收，专项提供检查方法与结论，二者协调、不重复规则。仅请求审查不自动改代码，也不新增平行报告或状态体系。 |
| Skill 文件结构 | 技能统一采用 SKILL.md 与 NOTICE.md 两文件结构；完整方法、必要参考放在主说明，来源、版本、适配范围及完整原许可放在 NOTICE。文件数量限制已取消，允许必要参考、模板和脚本随完整资源包提供；共同规则在 `skills/_shared/` 单一维护，构建时展开到各技能。技能包检查验证文件结构、引用和许可。 |
| 调试专项融合 | 提供 debug-issue：吸收 Superpowers 的系统调试、根因追溯、条件等待与分层校验，支持独立诊断、授权修复及在 execute-task 内调用。按证据查原因、逐操作核对授权，修好后重验并接入审查与验收；默认只诊断、不改真实项目。不另建执行流程或审查，随包保留来源与许可（SKILL.md + NOTICE.md）。 |
| 统一测试能力融合 | 提供 test-work：单元、接口、集成、端到端测试的统一入口，按需求、验收、改动和风险选必要组合，不按类型拆多个技能、不强制全跑。以 Superpowers 的测试质量方法为主，吸收“先证明用例能暴露问题、修好再重验”的做法，开发顺序沿用项目约定。工具可用性与实际验证分别核对；失败时衔接 debug-issue，审查由原流程组织。证据和进度沿用 verification.md、tasks.md，不另建报告体系。 |
| 需求澄清与方案设计融合 | 提供 clarify-design：统一处理新项目想法、功能需求和反馈，推进到澄清、方案或计划交接。以 Superpowers brainstorming 为骨架，吸收 grilling 的决策追问、Spec Kit 的歧义与缺项检查、BMAD 的 UX 与架构视角。AI 主动调查开源方案并解释推荐，已有决定不重复问、普通细节自主处理、关键取舍按确认规则；不遍历所有问题、不强制委派。对话澄清、backlog、本轮 scope/design 与有效规格各按职责分开，tasks 交 plan-tasks，设计与计划可一起准备和确认，但不自动批准实施。 |
| 非 Git 生命周期能力融合 | 按用户要求融合统一入口与恢复、工程地基、发布、线上排障、现有能力增强和多视角讨论：新建 workflow-guide、build-foundation、release-work、handle-incident、discuss-design，并给既有能力补交接、验收和风险检查。全部适配本框架的文档、确认、范围和验收规则；主 Agent 统一记录，入口只定位交接，专项给方法与结果，不互相递归、不重复审查、不争写状态。来源固定、许可核对、隔离验证按既有流程，创建与检查不替代用户验收。Git 属独立专题。 |

### Git 管理

Git 相关规则集中在本节（分支、工作树、提交、合并推送、标签、工作区保护、线上修复基线等），不在其他能力里另行定义。

#### 日常流程

| 主题 | 决定 |
| --- | --- |
| 任务起步：整理工作区 → 同步主线 → 建分支/worktree | 开始新任务前先整理工作区：保存未提交改动、确认干净再动手（检查范围限本次用到的目录，不涉及其它目录；“干净”不等于清空，也不授予删除权）。之后每个新任务先 fetch 指定远端主分支、本地一致则保持、仅落后则快进，确认与远端一致后建独立任务分支和 worktree；本地分叉先查原因、不覆盖本地提交、远端确认不了就不基于旧版本起步。任务改动 commit 后才算开发结束（是开发阶段结束的必要条件，但不代表已推送、合并、发布或最终完成）。 |
| 分支与目录命名 | 用 Git worktree 给每个任务一个独立工作目录。分支用 `task/<迭代标识>-<任务标识>-<简短英文描述>`；worktree 子目录用同名主体（去掉 `task/`），放在主仓库同级 `<项目名>-worktrees/` 下，主目录维护主分支。标识沿用已有任务记录、不另建编号（示例 `task/003-demo-login` 只是格式）；换方案另开分支加 `-r2`/`-r3`，仍关联原任务，普通修复用原分支。任务完成后只清理对应子目录。 |
| PR、验收与合入 | 开发提交完成、产品验证和独立代码审查及必要修复通过后，在交用户验收时创建 PR。合入前必须过 AI 集成检查：核对最终待合入版本与当时主分支的衔接、规格与记录一致性、必要测试与审查证据（不拿旧审查替代本轮判断）。顺序：AI 产品验证、独立审查、必要修复 → 用户明确验收 → 补规格与记录收尾 → 再合入。合并用 Squash：把最终改动压成主线上一条正式提交、每条对应一个完整任务，过程提交保留、不预先改历史。行为变化要重验重验收，检查失败或关键未知不合入；合入触发上线需有部署授权。 |
| 合入后清理 | PR 实际合入主分支后才清理该任务的本地和远端开发分支。清理前确认任务已验收、检查和记录收尾完成、PR 确已合入；停止相关 Agent 和本任务进程，核对并先保存要留的未提交、未跟踪、忽略文件；再从主目录 `git worktree remove` 移除 worktree，成功后再清理两端分支。仍被使用、有未保存资料或受阻时保留现场、不强行清理。 |
| 正式提交消息格式 | 正式提交消息用“类型(范围): 中文成果摘要”：类型区分功能、修复、文档等，范围可省；摘要说明完整任务实际交付的成果，正文按需补原因和任务关联。示例 `docs(git): 明确任务分支的保存与清理规则`。 |

#### 保存与中断

| 主题 | 决定 |
| --- | --- |
| WIP 保存 | 触发：必须人类决策才能继续的阻塞，或用户明确暂停、切换（如“今天到这里”）。有未保存改动时先核对归属、精选可入库的文件或改动块、核对暂存区，建本地 WIP 提交、记断点，不默认 `git add .`；远端与推送授权明确时自动备份并核对，失败就保留本地、报告“本地已保存、远端未备份”。没改动不建空提交；未解决冲突按冲突规则保留现场。WIP 只存进度，不代表完成、验证或验收通过。 |
| 替代方案与合并冲突 | 新方案替代旧方案：关闭旧 PR 并注明替代关系（防误合入），旧分支和 WIP 先保留；替代方案验收合入、确认旧方案无需保留后再清理。合并冲突需要用户决定时：保留该 worktree 的冲突状态和已完成处理、暂停该目录写入，记录冲突位置和恢复依据，等用户答复后从原处继续；不自动中止合并、清理目录或挪作他用，也不把冲突标记当已解决来保存。 |
| 其他来源改动与操作报告 | 手动修改或其他工作留下的改动，按所属任务和授权保存到对应分支：属于当前任务且可入库的一起保存，属于其它任务的单独处理、不混入当前提交。每次 Git 操作后报告实际做了什么（项目、任务、动作与结果、可定位的提交或 PR 或分支、未完成事项）；只读可汇总，未执行或未知不写成成功。再收到相同请求先核对真实状态：已完成给结果、部分完成只接续剩余获准步骤、状态不明先查证。 |

#### 发布与线上修复

| 主题 | 决定 |
| --- | --- |
| 线上修复与补丁发布 | 线上故障以当前线上实际运行版本对应的提交为起点（按发布记录核实、不猜最新主线），另建修复分支和 worktree；补丁只含该线上版本和必要修复，主线其它未发布改动保留、不随补丁上线。顺序：先发布补丁并确认线上恢复 → 再确保主线覆盖同一修复 → 最后清理。补丁先过测试、独立审查、用户验收，具部署授权后发布并做上线检查；用固定发布标签（固定、不改指）保留实际发布的提交，别只记提交号就删唯一引用。发布失败按发布失败规则回滚并等重试决定。 |
| 线上问题分级 | 紧急问题单独开小修复迭代、只含必要修复，先保存暂停当前迭代；修复完成验收、发布、主线处理和清理后，按预先约定恢复原迭代（原任务在等验收就仍等验收、不补记）。不紧急的问题默认进 backlog、排后续迭代；属于当前任务没满足原要求的，留在原任务修、不推后。 |

#### 项目与升级

| 主题 | 决定 |
| --- | --- |
| 框架升级 | 框架升级作为独立任务，沿用设计、计划、验证、逐任务验收和 Git 流程。普通升级只更新框架管理的资源和必要导航，不改业务代码；业务内容、用户修改和迭代进度保留，模板更新不覆盖已有业务内容。默认等当前任务验收并收尾后再升级、不自动追随新版；在既有文档记录升级前后版本（计划与已生效分开、核不了就保留未知）。安装器、升级迁移和回退机制尚未实现。 |
| 新个人项目默认约定 | 新个人项目默认：远端平台 GitHub、新建仓库私有（只有明确要求才公开）、远端名 `origin`、主分支 `main`；已有项目沿用现配置、不自动改名，框架保留适配其它平台的空间。选平台或命名不等于已接入或有真实仓库权限。 |
