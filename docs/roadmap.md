# 开发路线

当前进度见[交接](handoff.md)。本页只列尚未完成的计划。

## 真实使用驱动的框架升级计划

本计划记录目标、顺序和成功条件，是待实施的计划，不代表已提供的能力或可直接运行的命令，也不授予实施、升级或 Git 写操作权限。

### 目标与范围

框架应让真实 AI 客户端自行完成任务内部步骤，在正确位置等待用户，并能在功能合入 main 后接受改进、完成下一轮迭代。现有项目应能升级后继续工作，业务、约定和历史得到保留。

依据既有安装和真实使用评测，重点是让 AI 自行衔接整条流程，而不是由测试控制器代做关键步骤。

沿用 Node.js 24、JavaScript ESM、现有 CLI 与技能、共享规则和项目级客户端接入。具体客户端版本、工具集合、上游来源、许可、写入范围和新协议在对应任务实施前核对；目标新版本及准确来源另行固定。

### 主场景 A：首次交付与下一轮功能迭代

演练采用同一个本地小应用，例如先保存收藏，合入后再增加标签与筛选；这是测试示例，不是真实业务需求。测试初始资料、地基和授权明确标识；不能由测试控制器代做当前任务的登记、绑定、启动、审查或收尾。

| 节点 | AI应自行完成 | 用户参与和可观察结果 |
| --- | --- | --- |
| 第一轮规划 | 核对项目、地基、状态和授权，调查可查信息，澄清关键问题，设计并规划完整成果 | 用户回答关键业务问题、确认已展示方案和计划；未确认不实施 |
| 第一轮执行 | 保存相关改动、同步main、建立任务分支/worktree，登记任务、绑定依据，实施、检查产品效果、独立审查及必要修复复查 | 普通内部步骤自动推进；实际进度、文档和工具记录一致 |
| 第一轮交付 | 必要检查通过后创建PR，提供成果与证据，登记等待 | 用户验收或反馈；验收前main不纳入该成果 |
| 第一轮收尾 | 验收后同步已交付规格及记录、补必要检查、Squash合入、核对清理结果 | 同范围Git授权具备时正常收尾自动完成，不逐步重复询问 |
| 提出改进 | 读取已交付规格、公共约定和历史，识别增量，准备下一轮及任务 | 用户确认新方案和计划；原任务遗漏仍留在原任务修复 |
| 第二轮执行与交付 | 使用新任务、新绑定和任务分支，完成实施、检查、独立审查、修复复查及PR | 用户验收第二轮；不复用第一轮绑定，不用旧验收批准新增行为 |
| 第二轮收尾 | 更新对应规格并合入main，保留旧需求、编号、验收和未修改行为 | 第二轮实际成果、main与记录一致；未批准的新目标不自动继续 |

正常路径每轮主要有方案/计划确认与成果验收两个暂停点；已有适用确认不重复询问。关键范围、设计、数据、安全、成本、权限变化或用户必须判断的冲突另行确认。普通技术问题在已有授权内处理，必要检查受阻时保留缺项和现场，独立可做部分继续。

### 衔接性是整体验收必过项

验收的是上一节点真实产出的内容能被下一节点正确使用，不是各模块单独通过的总和。连续运行两轮，不能靠用户提醒“登记、绑定、审查、建PR、同步规格”或测试脚本修补才能继续。

| 衔接 | 成功条件 |
| --- | --- |
| 计划确认→启动 | 实际获批范围、计划和依赖被用于当前任务，未重新编造要求 |
| 启动→实施 | 按当前任务边界和公共约定修改；真实进度、状态和文档对应 |
| 实施→检查/审查 | 检查与全新审查针对实际候选，遗漏和失败返回当前任务 |
| 修复→复查→PR | 新候选补受影响检查及复查，同一PR展示实际最终候选 |
| PR→验收 | 体验入口和证据对应PR，保持等待；“继续”不改变验收事实 |
| 验收→规格收尾→main | 验收对应具体成果，实际变化同步，最终检查及Git条件满足后合入 |
| 第一轮main→第二轮规划 | 以已交付规格和历史形成增量，保留旧规则和身份，正确启动新轮 |

每次交接沿既定tasks/verification记录实际输入、输出、内容版本、命令结果和未完成项；state只作导航。用户确认、候选提交、审查上下文、PR与main结果可定位。演练中的用户消息注明测试输入，不能记为业务项目真实验收；工具不认证消息真实性、模型理解或外部操作身份。

### 主场景 B：现有项目升级后继续完成任务

本场景验证一个已接入的真实项目能升级到新版本、完成任务并回退。安装身份以项目manifest的完整摘要为准，不承诺任意历史版本或所有同版本来源兼容。

1. **核对并保存现状。** 固定安装来源、业务文件、配置、文档、分支和日志；先在脱敏副本验证迁移，不反复操作真实云数据。
2. **受控整理旧记录。** 依据真实消息、文件、提交、检查和PR修正矛盾，保留该任务的身份及有效证据。补记注明事后整理，不倒填当时已绑定、已审查或已验收，不靠刷新摘要伪装收尾。
3. **完成当前任务必要收尾。** 补最终候选必要检查与复查，用户明确验收后完成适用收尾。默认此后升级；中途升级须明确暂停与迁移安排，保留原未验收状态。
4. **预览独立升级任务。** 重新核对准确来源与当前revision，列出框架资源、入口和配置变化。业务代码、foundation、overview、规格、任务正文及历史不作为覆盖对象；用户修改发生冲突时保留处理。
5. **升级并验收。** 按明确项目授权更新受管理资源及必要入口，核对资源、文档、状态和客户端接入；继续完成一个任务并合入main，以证明现有项目能接续工作。
6. **保留并验证回退。** 回退恢复框架资源和配置，保留期间新增业务成果、记录、revision和验收事实。旧工具不能处理新记录的限制及可行处理方式在升级前说明并验证；不能只证明旧文件可复制回来。

实际升级、项目Git及生产操作依各自具体授权执行。版本工具如何与独立升级任务记录协作、受控旧任务纳管接口、协议兼容和中途迁移细节在实施前落实，不从当前错误书签推断前置满足。

### 剩余工程成果及验收

编号沿用原计划，未列入的成果不在此重复。顺序按复杂度和依赖安排：3—7完善规划、状态、文档、Git与审查闭环；8—10接入客户端；11验证迁移；12最后整理文档。每项完成必要检查、适用独立审查和用户验收后再按前置接续；归档不代替验收或实施授权。

#### 3. 设计、计划与迭代增量衔接

**验收方法：**运行A的两轮自然需求规划，核对方案、任务与需求前后对照。

**成功条件：**关键选型、范围、验收和必要约束明确，缺项保留；任务按完整成果拆分并规划规格收尾。第二轮引用已有规格，明确增量和保留行为；正确区分修复与额外需求，新方案未确认不实施，不重复询问旧决定。交付两轮方案/计划和行为对照。

#### 4. 任务登记、绑定与状态推进

**验收方法：**让真实AI从获批计划自行准备任务，在相关节点加入缺绑定、地基变化及“继续”。

**成功条件：**自行登记、选择、绑定并启动；缺任务、确认或过时绑定不能通过受控流程启动。第二轮有自己的任务和绑定；交验收后等待准确，“继续”不变验收；小修改不机械制造业务迭代。交付实际转换和事件，控制器不代做。

#### 5. 文档全流程一致性与恢复

**验收方法：**在A的规划、实施、审查、验收及main节点核对文档；隔离副本加入一次依据变化和代表性部分写入中断。

**成功条件：**scope/design/tasks的成果、边界、依赖及验收对应，tasks/verification/state反映真实阶段，检查审查对应候选，specs只含实际验收变化。公共约定变化重核受影响依据和确认；中断冲突可发现并恢复，历史、用户修改和等待保留。工具核对身份、引用、摘要和状态，AI另外核对正文含义，哈希一致不当作语义一致。交付节点核对及恢复前后对照。

#### 6. Git与提交前安全门槛

**验收方法：**隔离仓库正常交付，加入只授权推送、未验收、可见性不符和已定义敏感内容等负例。

**成功条件：**开发在任务分支，验收前main不纳入成果；推送授权不取消PR/审查/验收。可见性不符合已确认要求或未知时不继续依赖它的推送；定义范围内敏感内容被发现并阻止，未知类别不称全面保护。验收且权限满足后正常合入自动完成，恢复不擅自强推，清理限定对应任务。交付PR、main引用、实际操作及拒绝原因。

#### 7. 自动独立审查及修复复查

**验收方法：**真实AI自行组织全新审查，以一个有明确影响的问题观察必要修复、复查及候选变化处理。

**成功条件：**无需提醒主动安排；审查取得原要求和实际候选，不继承实施推理。必要问题在原授权内核验修复、重验及独立复查，非必要偏好不扩成阻塞。候选变后不直接复用受影响旧结论；审查缺失或关键未知未解不称可验收。交付上下文、候选身份、处理和复查证据，不凑发现数量。

#### 8. 共享客户端接入底座与Codex核对

**验收方法：**核对配置保留、加载和能力诊断，在真实Codex使用共同主线，分别观察已声明节点。

**成功条件：**使用共同规则与状态契约，用户配置及其他入口保留。安装、自动加载、阶段校验及独立审查能力分别报告；保障有证据，未知工具和拦截路径明确，缺加载或异常不显示保护正常。客户端未完整通过A时不宣称与完整场景同等支持。交付固定版本及支持范围。

#### 9. Pi真实连续迭代闭环

**验收方法：**在用户实际Pi使用环境和工具集合完整运行A，在适当节点换会话、变更依据、保持等待。

**成功条件：**两轮自行完成登记、绑定、实施、检查、审查、PR及收尾，用户只处理关键决定、方案确认与成果验收。自然改进进入正确下一轮；恢复不丢历史或越过等待。声明支持的工具路径符合规则，扩展关闭、异常和未知工具不误报受保护。交付两轮PR/main及消息与自动操作对应记录；原生Pi与实际宿主形态分别核实，不借原生测试推断任意SDK/RPC或宿主支持。

#### 10. Claude Code真实接入

**验收方法：**复用同一小应用和A，单独观察固定Claude版本的配置加载、原生事件和两轮运行。

**成功条件：**两轮主流程成立，新会话、跨任务及地基变化正确，原配置及其他hooks保留；异常限制如实报告，不借其他客户端结果验收。交付Claude实际证据，未变化共享代码的检查复用。

#### 11. 现有dev.12升级、回退与交付

**验收方法：**先用Hairdressing脱敏副本验证B及故障分支，再在用户明确授权时升级实际项目。

**成功条件：**准确来源匹配、错误来源拒绝；异常旧书签不能当初始项目升级，必要补记不伪造历史。预览与实写一致，业务/约定/历史和用户修改保留；冲突、中断、重复请求有确定处理。升级后能完成任务至main；回退保留期间业务成果，旧工具与新记录限制提前说明并验证。交付固定包、来源、前后对照和回退说明。

#### 12. 最终文档内容优化

**验收方法：**独立读者只根据最终文档定位并理解A、B的操作；维护者从交接准确接手。

**成功条件：**下一步、预期、确认与验收清楚，安装/任务/迭代/升级/异常说明可用；维护状态、缺项和下一步可找。重复规则有明确归属，过时说明删除或标适用版本，术语和技术字段按读者需要放置，能力声明与交付一致，无已知矛盾或关键操作缺口。交付文档与读者反馈，链接正确不代替可读性。

### 共享工具门槛实施安排

维护者按以下安排交付共享判定内核，之后再接客户端。本安排依据[共享工具门槛设计](design/tool-guard.md)。当前进度与适用授权见[交接](handoff.md)；本页不替代真实项目接入或 Git 写操作授权。

本轮沿用仓库既有运行环境、依赖和文档归属。主 Agent 顺序实施，不默认并行委派；每项成果完成必要检查和独立审查后交用户验收，后续按既有前置接续。所有验证使用隔离文件与临时本地仓库，不调用真实模型或远端平台。

#### 交付机器契约与共用前置校验

这一成果提供严格请求结构和可复用的任务、确认及候选检查，保持原状态操作含义。

| 文件 | 处理 |
| --- | --- |
| schemas/guard-request.schema.json、schemas/guard-result.schema.json | 新建请求与返回结构 |
| schemas/workflow-record-v2.schema.json | 增加可选 guard_policy、operation_scope 和 check.operation_context |
| src/guard-request.mjs | 新建严格 JSON 解析与结构校验 |
| src/guard-declarations.mjs | 共用范围、路径和 Unicode 声明校验 |
| src/workflow-prerequisites.mjs | 提取共享确认、任务前置和候选检查 |
| src/workflow-transitions.mjs、src/verification-policy.mjs、src/workflow-docs.mjs、src/spec-deltas.mjs | 接入共用检查及新增字段的声明、修订和确认失效判断 |
| tests/runtime/guard-contract.test.mjs | 验证结构、兼容和确认绑定 |
| tests/fixtures/workflow-record-before-guard.schema.json | 保留改动前的严格结构作为兼容检查依据 |

接口约定：parseGuardRequest(text) 返回已校验的 GuardRequest；validateGuardRequest(value) 校验已解析对象。共用模块提供 inspectConfirmations(view, options)、inspectTaskPrerequisites(view, options) 和 inspectCandidatePrerequisites(view, options)，均返回 issues 与实际核对对象，不写文件。候选检查通过 requireAcceptance 明确是否要求用户验收。

1. 先为严格结构、错误字段、请求大小、字段修订、旧记录保留和计划摘要失效写失败用例。
2. 运行新增用例，确认失败来自尚未实现的契约；保存原有状态、绑定和验证政策检查的基线。
3. 实现契约与共用检查，保留既有错误类别和拒绝语义，不改操作日志协议。
4. 验证新增字段由语义修订处理，修改后原计划确认和绑定不能直接复用；旧结构检查拒绝新字段。
5. 回归原状态转换、绑定与验证政策，核对同一输入的允许或拒绝行为没有改变。

实施后在框架仓库运行：

~~~powershell
node --test tests/runtime/guard-contract.test.mjs tests/runtime/workflow-transitions.test.mjs tests/runtime/context-binding.test.mjs tests/runtime/verification-policy.test.mjs
~~~

预期新增契约及原流程检查均通过。失败时先定位是新字段、共用检查还是原行为变化，不降低旧检查标准。验收时展示字段落点、接口结果及兼容边界。

#### 交付文件与工程命令判定

这一成果提供不依赖客户端的 inspectOperation 与 revalidateOperation，覆盖文件、已识别的框架操作及工程命令。

| 文件 | 处理 |
| --- | --- |
| src/operation-guard.mjs | 新建判定入口、读取依据和统一返回 |
| src/operation-files.mjs | 新建路径、前像、范围与机器记录保护检查 |
| src/operation-command.mjs | 新建实际可执行文件、参数和声明范围检查 |
| src/workflow-docs.mjs | 保留原记录文档容量，复用解析器检查较大的普通 Markdown 全文 |
| tests/runtime/operation-guard.test.mjs | 验证阶段、正文、命令、独立请求和无写入 |
| skills/_shared/references/work-contract.md、spec-runtime.md | 说明新增门槛字段与原有记录的关系 |

接口约定：inspectOperation(projectRoot, request, options) 返回 GuardResult；revalidateOperation(projectRoot, request, previousResult, options) 重新检查并核对参数与事实。options.independentRequestObserver 和 options.preparationRequestObserver 只由受控宿主配置，其字段与限制以共享工具门槛设计为准。

1. 为无任务写代码、有效绑定、verify 中修复、待验收修改、跨任务和陈旧结果写失败用例。
2. 补路径越界、链接、别名、移动两端、直接改机器记录、不透明 Markdown、请求大小和命令可执行文件变化的用例。
3. 实现规划、输入准备、任务执行和普通文档收尾的独立分支；前两类不要求尚未存在的任务或绑定，也不取得业务代码许可。
4. 验证独立文案请求不创建迭代；缺宿主观察返回 unknown。伪报操作类型、任意 shell 和未声明命令不能放行。
5. 对 allow、deny、unknown、格式错误、observer 异常和重新校验逐项比较前后文件与状态，确认无写入。
