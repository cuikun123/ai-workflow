# 框架开发路线

本页保存2026-11-13首版补齐方案。**D112已授权第1步工程、资源包及校验基础；客户端未结问题继续作为接入验收和发布门槛，第0步不补记全部通过。** D113已选择Iterlane（迭序）、MIT与版权署名TY；未明确采用的数值预算与后续实现细节保持建议。设计不是实现、运行验证或用户验收事实。当前源码和检查事实见[交接](handoff.md)、[验证记录](../tests/README.md)，有效规则见[决策记录](decisions.md)。

## 首版交付目标与边界

建议首版达到：使用者依照快速开始取得固定版本，通过正式入口安装到新项目；真实客户端能发现并调用；状态可检查、暂停后可恢复；重复执行、写入失败和版本升级不静默损坏已有资料；全部声明能力都有可复现的框架级证据。

- 保留已确认的Codex、新建个人Web项目和既定业务文档结构；多Agent并行调度、跨会话编排与强制资源隔离继续后置。现有独立审查要求不因此取消，使用宿主已有能力时单独实测。
- 建议首版保证Windows环境，冻结实际支持的系统、Node、Git、Codex客户端及模型版本组合。其他系统可做核心工具兼容检查，但不能据此声明完整宿主支持。具体客户端形态在第0步锁定，不笼统宣称整个Codex产品线已适配。
- 保留发布和维护工作流：在专用测试仓库、可丢弃部署环境验证相应行为；生产平台、真实业务数据及跨技术栈兼容性单独声明。沙箱部署结果不写成生产验证。
- 建议首版具备可分发产物及基本开源资料。名称、包名与MIT按D113落实，上游许可及署名继续保留。本方案不授权发布包、创建远端或操作生产环境。
- 首版不是所有生态能力齐备；也不能通过排除已承诺的必要能力，把未完成项改写为通过。

## 推荐实现形态与需调整的旧约束

建议采用轻量命令工具、现有Skills和一个经过实测的Codex接入方式。确定性代码负责安装、文件清单、校验、状态写入、诊断及升级恢复；Agent负责业务判断、方案和工具调用。暂不建立独立Agent运行平台。

继续纯手动方法包无法补齐已核实的运行缺口；先建设完整编排平台会扩大范围，并与多Agent后置冲突。轻量工具方案能沿用现有方法和文档，同时提供独立可测的运行基础。

包结构和状态写入原则已按D110确认，具体实现待定；工具形态及技术分发继续作为第0步推荐：

| 项目 | 建议 | 原约束或关联 |
| --- | --- | --- |
| 包结构 | 取消固定两文件数量限制；主说明保留触发、边界、必要步骤，长参考和模板按需加载，必要脚本进入受管理资源 | D110已确认原则；当前源码仍为两文件包，保留完整来源与许可 |
| 状态写入 | 建立正式schema及受校验的读写入口，Skill调用工具维护；状态仍是书签和引用，不复制整套任务与证据历史 | D110已确认原则，保留D13、D15；具体结构见文档设计的第0步建议 |
| 工具入口 | 提供小型真实CLI；建议操作为init、check、status、doctor、recover、upgrade、rollback、validate，名称是拟议接口，不是现有命令 | 细化P01、D22—D28；不创建空壳命令充数 |
| 技术与分发 | Node.js、JavaScript ESM及npm包，复用现有Node测试；仅引入必要解析、校验依赖，固定版本和锁文件 | D111认可、D112已实施第1步；名称及许可按D113确定，完整支持基线仍待验证 |

资源仍按D24、D25归属：技能及其专属参考在`.agents/skills/<skill>/`；公共脚本、模板、版本和安装恢复元数据在`.ai-workflow/`；业务资料沿用`docs/`。状态、安装记录和验收依据各司其职，不能把安装成功写成任务验收通过。

## 实施顺序及每项验收标准

表中0是进入实现前的准备，其余1—8均建议作为首版必须交付的成果。顺序表示依赖；测试、诊断和使用说明随对应能力一起编写，不能全部拖到最后。通常逐项检查后交用户验收；本轮D115调整第2、3步为第三步完成后的最终联动验证及联合用户验收，各步必要检查仍随实施运行，其他任务的等待规则不自动改变。

| 顺序 | 必须交付什么 | 验收标准 |
| --- | --- | --- |
| 0. 范围与契约 | 冻结支持矩阵、名称与许可、命令及输出约定、受管理文件清单、状态字段与合法转换、写入归属、恢复边界和测试断言 | 每项声明能力能对应后续任务及可观察断言；正式schema不再是字段示例；安装、状态、验收各自有明确事实来源。先核对官方宿主机制并完成真实只读入口可行性验证，失败则保留阻塞，不按假定hook继续建设。此步通过仅表示设计和接入路线具备实施依据 |
| 1. 工程、资源包与CI | 可执行工具基础、可打包资源、依赖锁定、整体LICENSE与上游NOTICE；取消两文件硬限制；建立自动检查和证据输出 | 从干净检出构建真实安装产物；包包含全部资源和许可，脱离源码仓库可定位资源；非法参数、缺依赖及损坏资源返回明确失败。当前41项检查按职责保留或适配，增加真实工具断言。代码、Skill、模板及schema变化触发CI；故意破坏样例能使检查失败，零测试或必测项跳过不得显示整体通过 |
| 2. 安装与初始化 | 固定版本安装、AGENTS管理区块、有效起始state、受管理清单和摘要、同版本重跑保护及中断恢复基础 | 空目录初始化成功；同版本重跑不改变业务资料、已有进度和非框架Skills；缺失、冲突、未知版本准确报告，修复不偷换为升级。中文、空格路径可用；目录穿越和重解析点越界不得写出目标范围。逐写入阶段注入失败或终止后，保留资料、识别未完成安装；重新运行能按明确策略继续或有限还原，不能误报成功 |
| 3. Codex接入与按需加载 | 经实测的规则加载、入口路由、专项显式调用及最小状态查询；保留其他Skills共存 | 在新会话、仅依赖已安装产物的项目中，不提供框架源码路径或开发聊天，客户端能找到正确技能；开始、继续、查询及专项请求路由正确，不相关请求不误启动工作流；只读查询不改文件；显式调用提供可复现兜底。实际读取范围可观察，不默认读完11项；遗漏必需参考必须被发现。客户端连接失败与安装损坏分别报告 |
| 4. 状态、文档校验与恢复 | status及受校验的写入/恢复入口；正式状态schema、修订冲突检测和单写入保护；最低限度规格与记录校验 | 覆盖未开始、执行中、待验收、被阻塞、暂停、已验收但未收尾及已完成；新会话恢复到正确任务，待验收仍等待。状态过时、引用缺失、两份依据冲突不得自行猜测；旧revision写入被拒绝；两个进程不会互相覆盖，残留锁可诊断。修改与验收绑定的内容后原结论不得继续冒用。检查重复需求编号、坏引用、必需记录缺失和非法转换，合法空文档按阶段接受；无法程序判断的业务语义明确交由审查。schema通过不证明验收真实，禁止从字段存在推定用户批准 |
| 5. 框架诊断 | doctor只读诊断及recover的受控恢复；每个故障给原因类别、证据、影响和下一步 | 可区分资源缺失、摘要变化、版本混用、状态损坏或过时、残留锁、权限/运行依赖不足及客户端连接问题；诊断前后业务文件一致。不把网络错误当作安装损坏；修复只处理已授权、归属明确的写入。恢复书签不自动重试部署或清理现场；无法安全恢复时保留现场并返回阻塞 |
| 6. 版本升级与回退 | 项目锁版、差异预览、用户主动升级、兼容迁移、上一个可恢复版本的回退路径 | 用两个真实可安装的测试版本验证旧→新→回退，核对资源、schema和进度；同版本重复操作不破坏状态。混合版本、用户改动、失败写入和不兼容迁移都有用例；回退前后保留后来产生的业务修改。无法安全逆迁移时明确拒绝，不能声称已回退。没有版本依据的旧手动副本不自动认领覆盖；不承诺任意历史版本迁移 |
| 7. 行为评测与完整联动 | 可重复运行的真实Agent场景、必要的观察与判定工具；覆盖所有首版声明的Skills及跨阶段接口 | 按下文统一门槛覆盖正向、反向、失败和恢复；记录模型、客户端、包摘要、输入、工具行为与结果。必须证明实际读取并使用安装包，不靠Agent口头自评。GitHub PR与合入清理在获准测试仓库真实执行；发布、失败回退和修复返回在可丢弃环境真实验证。涉及界面的产品检查提供实际操作证据；现有独立审查要求使用宿主真实能力，角色扮演不算 |
| 8. 使用与发布交付 | 快速开始、可复现示例、支持及限制说明、基本贡献/安全/发布说明、可定位测试证据和版本产物 | 按快速开始在干净目标环境从分发产物安装，无作者机器路径和临时手工补件；示例生成过程可复现，示例需求不污染业务模板。发布候选内容与已测摘要一致；真实CI成功记录可查；发布说明列已支持、未支持及已知限制，必测项无未结失败或未验证。正式名称和整体许可不再暂缺；发布、Git及用户验收仍分别核对授权 |

第0步的schema、管理清单和错误约定先定义，第1步加入校验工具，第2步只生成有效起始状态，第4步再完成状态转换与恢复；避免初始化器和状态运行时各自发明一套协议。升级复用安装和恢复能力，不重复造另一套写入逻辑。

**最先做0—3，先形成可安装、可发现、可调用且受检查保护的基础；随后4—6补齐可持续使用和维护能力；7—8汇总行为、联动及发布证据。** 前几项的单项验收不代表整个首版已验收，行为用例从第1步开始持续加入。

## 首版统一验收门槛

目标：形成可独立运行、可打包和可验证的确定性基础。主Agent按executing-plans内联执行；沿用已认可的接入/状态设计与既有文档，不另建计划目录。本轮不创建Git分支或提交，保留工作区已有改动。

- [x] 工程与状态校验：新增`package.json`、锁文件、`bin/iterlane.mjs`、`src/`及`schemas/state-v1.schema.json`。`check`只校验自身资源包；`validate --state <file>`只做严格YAML/状态结构校验，不推定授权、实际引用或用户验收。只实现已有行为，不加空壳安装/恢复命令。
- [x] 完整资源包：`scripts/build.mjs`打包运行库及全部技能、模板、schema、来源和许可；生成相对路径/SHA-256清单，拒绝越界、链接、缺失、未知文件及摘要变化。`tests/runtime/distribution.test.mjs`在中文空格临时目录解包，脱离源码、全局依赖和网络运行，再故意破坏资源确认失败。
- [x] 检查与交付准备：取消测试的固定两文件限制、保留发现/本地资源/许可断言；加入`.github/workflows/check.yml`和必测项/跳过检测。已执行完整测试、真实构建和本地CI等价命令，独立审查问题已修复并回归；结果与限制见[验证记录](../tests/README.md#第1步工程资源包与校验基础)。远端CI未运行，用户验收待进行，不进入第2步。

实施接口：`validateStateYaml(text) -> state`失败抛带固定code的错误；`checkPackage(root) -> {version,files}`核对完整清单及与本运行时相同的包身份和schema；不替代跨版本兼容或来源签名检查。CLI的JSON输出为`{ok,command,version,data}`或`{ok:false,error:{code,message,details}}`。退出0为成功，2为参数无效，3为环境不支持，4为资源包损坏，5为状态无效，6为读写/构建失败。所有查询不写项目文件。D113已落实Iterlane/MIT/TY及整体LICENSE，当前仍为private内部包，禁止发布。

重点用例：未知字段、重复YAML键/标签/别名/多文档/非JSON数据、非法状态组合、路径穿越/Windows设备名/大小写冲突/重解析点、损坏清单/资源缺失/额外文件、缺依赖、非法CLI参数、打包遗漏许可、零测试或必测跳过。状态结构检查不冒充状态机或外部引用验证。

### 第2步执行计划（D114）

目标：从固定分发包向明确的新项目目录安装资源，生成有效导航/state，保护重复执行、冲突和初始化中断。设计依据：[第2步方案](design/integration.md#第2步安装与初始化方案d114已确认)。主Agent内联执行，完成后一次只读独立审查；不委派实现、不另建计划/报告目录、不执行Git写操作。D114已确认方案与第1步验收，本计划状态不冒充已有安装能力。

统一约束：沿用Node 24.18.0、Windows本地测试基线及现有锁定依赖，不引入新运行库；正式名称Iterlane、MIT/TY、private内部包保持。第2步工具拟采用0.3.0-dev.1，固定区别第1步产物；包名/锁文件同步，先核对并保留已生成旧包，不能借版本改变覆盖未知目录。第0步客户端门槛不解除，第1步验收不自动补记。各项在同一安装任务内实施、回归后统一交付，内部技术步骤不单独请求验收。

关注的风险：安装版与分发版入口定位不同；管理区块之外的并发修改；日志被改造成跨目录写入指令；终止发生在文件替换与日志更新之间；state和模板属于业务资料而不随资源修复重置。下面每项将这些风险纳入实际测试。

### 三类证据分别成立

1. **确定性工具证据**：正常、冲突、越界、版本混用、并发写入及中断恢复断言通过；故意破坏输入能被检查捕获。
2. **真实Agent行为证据**：既能选择并执行适用流程，也能在未获验收、只读请求、证据缺失或权限不足时保持边界。关键边界每场景建议至少3次独立新会话，所有必测断言通过；记录全部运行，不能只保留成功重试。有限次数结果不构成普遍可靠性保证。
3. **完整联动证据**：从固定产物安装、客户端调用、需求和地基、计划执行与检查、用户验收、规格收尾、暂停恢复到发布维护，并覆盖版本升级与异常恢复。按预定断点重启会话，核对数据与授权边界。小业务项目只是其中一个载体。

测试场景可预置确认作为显式测试输入，但不能把测试输入或Agent自报当作真实用户验收。没有人工或可信宿主的确认依据，工具不得把任务标为已验收；记录与内容版本绑定的具体接口在第0步明确，普通YAML文件不构成防篡改权限沙箱。

### 防止业务成功掩盖框架缺口

- 评测从分发产物安装，正式复验不访问框架开发对话、源码目录或未声明的全局资源。
- 准备最小正向、未验收不得继续、只读不得写入、检查失败不得完成、状态歧义、安装中断、升级冲突及修复返回等独立场景；不能只检查最终业务页面。
- 测试中如果需要手动复制资源、补命令或修改提示来救场，记录原失败；修复框架并生成新候选后重新验证受影响场景。正常业务决策和明确批准依旧允许，不要求无人参与。
- 选择有代表性的场景，用相同模型和工具条件做有框架/无框架对照，判断规则遵循、恢复能力及上下文代价；不以业务完成一例推断框架增益。
- 首版按需加载预算建议为入口主说明不超过2000 tokens、单项主说明不超过5000 tokens，以固定计数方式检查并记录实际读取轨迹。必要边界不能为达标而删除；超预算先拆分参考或调整设计，禁止CI悄悄放宽。计数预算是工程约束，不冒充客户端实际计费。

### CI与证据保存

- 无凭据的确定性测试在每次相关变更运行；有账户或模型成本的真实客户端评测按受影响能力及发布候选运行。普通CI成功不替代这些评测；必要真实评测未运行则候选不能发布为首版完成。
- 不给不可信外部PR暴露模型或发布凭据。真实评测失败、环境受阻和未执行分别记录；重跑保留原结果。
- 测试输入、判定及运行脚本留在既有`tests/`；简短结果和证据索引沿`tests/README.md`维护。完整脱敏日志作为CI产物和对应发布证据附件保存；候选发布时固定保留版本、摘要、命令、环境及结果，不只留会过期的临时文件。
- `%TEMP%`仍可用于隔离运行，不再作为唯一证据存放处；不新建第二套正式状态或报告体系。
- 文件存在、格式检查、运行验证、用户验收分别记录。必要项失败或未验证不能靠总体通过率抵消；所有必交成果经过必要检查和用户明确验收，才能称首版完成。
