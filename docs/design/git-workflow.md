# Git 工作流

本页说明**保存改动、任务开发、PR 验收、合入清理和发布版本**。确认依据见[决策记录](../decisions.md)，完整开发主线见[开发流程](workflow.md)。

## 适用范围与基本概念

框架与业务项目分别使用 Git。执行前核对具体项目、仓库、远端、主分支、工具和权限；业务项目规则不自动授权操作框架仓库。

| 名称 | 用途 |
| --- | --- |
| 主分支 | 保存已验收并收尾的任务成果，本文用 `main` 表示 |
| 任务分支 | 保存一个任务的开发、修复和文档过程 |
| worktree | 同仓库的独立工作目录，不自动隔离进程、数据或权限 |
| WIP 提交 | 保存未完成断点，不表示检查或验收通过 |
| PR | 集中查看候选改动、申请合入主分支的入口 |
| Squash | 将一个完整任务的最终改动压成主分支上的一条正式提交 |
| 发布标签 | 固定指向准备发布的具体提交，保留实际版本 |

**新个人项目默认**：GitHub、私有仓库、远端 `origin`、主分支 `main`。明确要求公开时才公开；已有项目沿用实际平台、可见性与命名。

多个远端时分别明确同步、推送和 PR 目标，不能只凭名称推定。主 Agent 使用宿主真实工具执行，不另建 Git Skill 或运行服务；多 Agent 调度升级后置。

## 文档与代码一起保存

- 当前工程约定和业务规格保持稳定文件名，Git 保存版本，不另建 `engineering-v1` 一类平行文档。
- 业务变化的原因、范围、方案和验证归迭代资料；验收后同步实际交付的当前规格。
- 公共约定按确认、落实和生效时点更新，不能保留冲突的有效规则。
- 错字或排版整理保留 Git 历史即可，不借整理改变已确认含义。

代码、适用测试、文档与迭代记录可作为一组关联修改。实质变化重新确认受影响部分；确认与提交版本的精确绑定机制仍待设计。文件职责见[文档管理](documents.md)。

## 普通任务的完整顺序

| 阶段 | 顺序 |
| --- | --- |
| 起步 | 保存已有改动 → 同步主线 → 建任务分支和 worktree |
| 开发 | 实现并持续测试 → 提交最终候选版本 |
| 验收 | 产品验证、独立审查及必要修复 → 创建 PR → 用户验收 |
| 合入 | 更新规格与记录 → 更新同一 PR → 最终集成检查 → Squash |
| 清理 | 确认合入成功 → 移除任务目录 → 清理两端任务分支 |

开发提交完成才结束开发阶段；任务最终完成仍需用户验收及适用收尾。线上补丁使用[单独的基线和发布顺序](#发布版本与线上补丁)。

### 开始前检查哪些目录

只检查本次需要保存、同步、切换或使用的目录：

- 主目录：同步主分支前检查。
- 暂停的旧任务目录：保存进度时检查。
- 新任务目录：开始工作前检查。
- 其他涉及目录：按本次实际用途检查。

检查暂存与未暂存改动、新文件、未解决冲突及其归属。同属当前任务且允许入库的不同来源改动可以一并保存，其他任务分开处理。

> 归属或保存许可不清时保留现场，只澄清该部分。保存其他任务不启动其开发。

未涉及目录不要求整理；已保存暂停目录、需保留冲突及按约定忽略的依赖或缓存可以保留。“干净”不等于清空，也不授予删除权限。

### 同步主分支并创建任务

1. 保存已有改动，确认本次工作区满足起步条件。
2. 获取指定远端主分支最新状态（fetch）。
3. 核对本地主分支：一致则保持，仅落后则快进。
4. 确认本地与本次获取的远端提交一致，再创建任务分支和 worktree。

| 异常 | 处理 |
| --- | --- |
| 本地领先或双方分叉 | 先查原因，不覆盖本地提交，也不为同步制造合并提交 |
| 网络或访问受阻 | 在授权内处理；仍无法核实远端时暂停起步，不以旧版本冒充已同步 |

获取、更新、建分支分别核对结果。

**目录与命名：**

```text
my-app/                         # 主目录维护主分支
my-app-worktrees/
  003-t02-login/                 # 对应 task/003-t02-login
```

- 分支：`task/<迭代标识>-<任务标识>-<简短英文描述>`。
- 目录：使用同一主体，去掉 `task/`，放在主仓库同级的 `<项目名>-worktrees/` 下。
- 标识沿用任务记录，示例不规定全项目编号或机器路径。
- 创建前核对合法性、唯一性、归属及工具对同级目录的访问能力。
- 普通修复留在原分支；另开替代方案时才同时追加 `-r2`、`-r3` 等后缀。

### 开发期间同步主线

准备集成检查时，任务分支若未包含主线新提交，先保存改动、核对版本与目录，再普通 Merge，保留过程历史。已经包含的更新不重复合并。

| 方向 | 方式 |
| --- | --- |
| 远端主分支 → 本地主分支 | 仅落后时快进，本地独有提交先查原因 |
| 主分支 → 普通任务分支 | 普通 Merge，不默认 Rebase |
| 交付 PR → 主分支 | 满足验收和最终检查后 Squash |

同步成功与验证通过分别记录。内容、环境或基线变化后补受影响测试与审查；影响已验收行为时重新验证并验收。线上补丁不机械合入全部最新主线。

## 暂停、阻塞与方案替换

### 保存未完成进度

**触发条件**：用户明确暂停、切换，或出现需要用户决定的阻塞。普通可自主解决的技术问题仍留在原任务处理。

1. 核对归属，精选允许入库的文件或改动块，检查暂存区。
2. 有新改动才创建本地 WIP，不创建空提交。
3. 远端和推送授权明确时，自动推送对应任务分支并核对。
4. 在原 `tasks.md`、`verification.md` 记录断点、未完成事项及恢复条件，简短报告后等待。

| 保存结果 | 如何说明 |
| --- | --- |
| 本地提交和推送均成功 | 本地已保存，远端已备份 |
| 提交成功、推送失败 | 保留本地提交，报告远端未备份 |
| 无法安全选择或保存失败 | 保留现场，不声称进入 Git 历史 |
| 条件缺失或结果未知 | 如实说明缺项与下一步 |

暂存只组织提交，不是分支独立存档；WIP 和备份均不改变开发、验证及验收状态。

### 合并冲突需要用户决定时

- **保留**：原 worktree 中的冲突和已完成处理，暂停该目录继续写入。
- **记录**：冲突位置、相关分支、双方提交、待决定事项及恢复依据。
- **恢复**：用户答复后核对实际现场，继续解决，再补受影响检查和验收。

不自动中止合并、清理目录或交给其他任务。普通技术冲突在已有授权内处理，只有业务或关键取舍才等待用户。

未解决冲突不能创建普通提交，也不能为保存而盲目标记已解决。合并前提交、远端备份与本地冲突现场分别报告；记录本身也受冲突影响时，先在对话交接，不强写冻结现场。

### 方案确定替换时

1. 核对新方案已有适用确认，或属于原授权内的普通调整。
2. 关闭已有旧 PR，注明替代关系。
3. 核对工作区、同步主线，另建分支与 worktree。
4. 在原任务资料关联新旧方案，不另造平行任务或迭代。

**旧方案保留到**：替代方案完成必要验证、验收、规格记录收尾和合入，且确认旧资料无需保留，再清理旧两端分支、WIP 和相关目录。

关闭 PR 不等于删除分支、验收或合入；只处理明确替代的对象，未覆盖权限和工具条件仍须核对。

## 候选版本、PR 与用户验收

### 验收前检查

最终候选提交须完成：

- 实际产品效果验证，含适用页面操作、动态流程和数据结果。
- 全新独立上下文代码审查，以及必要修复、重验和独立复查。
- 适用的自动化测试。

开发中的持续测试保留。有效测试事实可以复用，旧审查不能代替本轮独立判断；WIP、截图或执行者自查不能冒充完整交付证据。

缺工具、环境或独立上下文时保留缺项；非必要优化不阻塞交付，必须修复项和关键未知仍须处理。审查方法见[独立审查与反馈处理](multi-agent.md#独立审查与反馈处理)。

### 创建 PR 并等待用户

开发提交和上述必要检查通过后，在交付用户验收时创建 PR。核对账户、仓库、工具和权限，已有明确 PR 授权不重复询问。

> **用户明确验收前不合入、不推进下一任务。** 沉默、继续检查、测试通过或 PR 已创建，都不代表验收通过。

提供可实际体验或检查的材料，要求见[任务验收](workflow.md#3-逐任务实现检查和验收)。

### 验收后的自动收尾

**条件**：用户明确验收对应成果，仓库、远端、主分支和执行权限明确。

主 Agent 连续完成同一范围的正常收尾，无需逐项再问：

1. 核对检查与审查，更新对应规格和记录；无业务变化不机械改规格。
2. 提交、推送本任务收尾改动，更新同一 PR。
3. 核对与当前主线的衔接、记录和证据；未包含主线更新时先 Merge，再补必要检查。
4. 必要检查通过、必须修复项关闭、验收和记录齐备后，Squash 合入。
5. 确认实际合入成功，再移除对应 worktree 和清理两端分支。

仅文档收尾补一致性检查；行为变化重验并重新验收受影响部分。检查失败、未执行、证据失效或关键未知未排除时不合入；在授权内处理，仍受阻则暂停相关操作并报告。

**权限不包含**：强制推送、改写主分支历史、丢弃无关改动、修改保护规则或生产部署。合入触发上线时，仍须有适用部署授权；项目或目标不明时不执行。

**正式提交消息**：`类型(范围): 中文成果摘要`，范围可省略，正文按需补原因和任务关联。例如 `docs(git): 明确保存与清理规则`。

每条正式提交对应完整任务的代码、适用测试和文档；过程提交保留至清理，不为 Squash 预先改写历史，也不混入替代旧方案。

## 合入后的目录与分支清理

主 Agent 只清理对应任务，保留主目录及其他任务。

### 清理前确认

- 验收、必要检查和记录收尾齐备，PR 确已合入目标主分支。
- Squash 按真实 PR 结果和内容核对，不只看普通分支合并标记。
- Agent 已停止使用目录，本任务独占的开发或测试进程已停止。
- 未提交、未跟踪及忽略文件中，需要保留的资料已保存并核验。
- 替代旧方案、线上补丁的额外保留条件均满足。

### 清理顺序

1. 从主目录执行 `git worktree remove`，移除对应目录及登记。
2. 成功后清理对应本地和远端任务分支；远端已自动删除则只核对。
3. 分别报告合入、目录移除和两端分支结果，部分成功只报告部分成功。

> 目录仍被使用、资料未保存或清理受阻时保留现场，不强行删除；不能把整个 `<项目名>-worktrees/` 当成单个任务目标。

复用有效证据，不仅为清理重跑完整测试或扫描无关仓库；新变化或证据失效才补必要核对。下一任务从更新主线新建分支与目录。

`git status` 干净不足以授权删除；切换分支不证明新文件、忽略文件和构建产物已隔离，删除分支也不等于立即销毁提交对象。

## 发布版本与线上补丁

### 用固定标签保留实际发布版本

1. 为已验证、准备发布的具体提交建标签，并保存到项目远端。
2. 发布使用该标签对应的版本和产物。
3. 代码变化后用新标签，不移动同名标签；版本号沿项目约定。

标签创建、远端保存、部署和上线检查分别核对，实际成功、失败或回滚写入发布记录。标签存在不代表上线成功，推送标签会触发部署时须有发布授权。

### 从线上实际版本修复

紧急问题按[线上故障流程](workflow.md#线上故障处理)单独开小修复轮，先保存暂停当前开发，并约定修复收尾后返回。非紧急问题默认进待办；原任务未满足的要求仍在原任务修复。

- 从发布记录核实环境当前运行的提交或标签，再创建修复分支和 worktree。
- 基线未知先核实，不猜最新主线或最新标签。
- 线上与主线相同时起点重合；否则补丁只含线上版本及必要修复。
- 保留主线未发布改动，不为同步要求或补丁回主线而把全部最新主线上线。

### 先恢复线上，再确保主线保留修复

1. 补丁完成必要测试、独立审查、用户验收和记录，保留固定标签。
2. 在适用部署授权内发布指定补丁版本，确认线上恢复。
3. 核对主线对同一修复的覆盖，按下表处理。
4. 线上恢复、主线覆盖且实际发布提交与必要产物可恢复后，再清理临时目录和分支。

| 主线情况 | 处理 |
| --- | --- |
| 已解决相同问题 | 核验留证，不造重复提交或 PR |
| 可直接合入补丁 | 原修复分支向主线提 PR |
| 有实际冲突或代码不兼容 | 从最新主线建适配分支，只处理该修复必要差异 |

需要合入的内容仍完成适用验证、审查、验收和最终 PR 检查，再 Squash。主线处理属于同一次修复收尾，不默认多开一轮或额外分支，不固定 cherry-pick，也不逐一适配全部未发布提交。

**版本保留**：补丁标签始终指向实际发布提交，不改指后来 Squash 的提交；保留固定标签和必要产物，文字提交号不能代替真实引用。

**异常与返回：**

- 发布失败：按[获准方案回滚并核验](workflow.md#发布失败处理)，报告后等待重试决定，不自动重部署或进入清理。
- 线上恢复、主线受阻：分别报告并保留现场，不宣布整体修复完成。
- 回合主线触发部署：核对授权，不能夹带未获准上线的其他功能。
- 已约定返回原轮：全部收尾后核对原状态和授权；无新指令或阻塞、前置满足时直接恢复，待验收则继续等待。
- 无返回约定或条件不足：按实际情况处理，不推定已恢复。

## 操作报告与重复请求

每组操作完成或因失败、中断停止后，简述：

- 项目、任务、实际动作和结果。
- 可定位的提交、PR 和分支。
- 未完成事项及恢复条件。

只读检查可汇总；提交、备份、合入、发布和各处清理分别说明，失败、未执行或未知不能写成成功。记录沿既有资料归属保存。

再次收到同一请求时，先核对真实仓库、必要远端或 PR 及记录：

| 实际状态 | 接续方式 |
| --- | --- |
| 已完成 | 给已有结果，不重复操作 |
| 部分完成 | 只做仍需且获准的步骤 |
| 有新改动 | 重新核对范围与权限 |
| 状态不明 | 先查证，不凭聊天、旧记录或同名分支推定 |
