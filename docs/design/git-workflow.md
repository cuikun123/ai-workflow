# 文档版本与 Git 工作流

## 已确认的方向

框架仓库与各业务项目分别使用 Git。正式文档和相关代码共同保存历史，以迭代记录说明原因、范围、确认与验证。

工程规则和业务规格保持稳定文件名；通常不另建 engineering-v1、expenses-v2 等平行当前版本。

expenses.md 表示某项业务能力当前规格；具体一次修改放进对应迭代资料。

## 修改流程方向

业务行为变化：在本轮范围中描述 → 按需要确认设计与验收标准 → 实现并验证 → 用户验收 → 同步当前规格。

公共约定变化：记录原因与影响 → 确认重要规则 → 落实代码或工具 → 更新当前约定并明确生效时点。影响本轮执行的规则不能留下冲突的生效版本。

代码、相关当前文档和迭代记录可以作为一组关联修改提交。小型错别字和排版修改保留 Git 记录即可，不能借整理改变含义。

确认针对当时的具体内容；实质变化重新确认。如何绑定 commit 或内容版本仍待设计。

新任务开始前先妥善保存已有未提交修改、核对工作区已干净，再开展新任务，已确认 D67。中断保存与替代方案分支处理已由D76替代D75，主动暂停或切换时的WIP保存按D97；其他来源改动的保存归属按D98，干净的检查范围按D99，其他常规Git自动权限尚待确定。

D99将检查限定为本次实际涉及的目录：主目录在同步主分支前检查，准备暂停的旧任务目录在需要保存进度时检查，新任务目录在开始工作前检查；其他需要保存、切换或使用的任务目录同样纳入。检查未提交修改（含暂存区）、未处理的新文件和未解决冲突，按D76、D97、D98保存和核对归属，冲突按D89处理。未涉及的任务目录无需一并检查整理，已保存暂停的目录及按规则保留的冲突现场继续保留；按项目约定忽略的依赖、缓存等可以保留。检查不等于清空目录，实际删除仍按D85核对全部需保留资料。此范围规则尚未落实到Skills或运行接入。

每个新任务开始前同步一次远端主分支，任务改动commit后才可认为开发阶段结束，已确认 D68。按D67先整理工作区；开发结束仍须满足已有必要检查与审查，任务最终完成继续需要用户验收和规格收尾。同步方式及受阻边界按D83；远端及主分支默认命名按D102，实际项目目标和异常解决方案仍待落实。提交验证和WIP保存沿已确认的D74、D76、D78、D97，未覆盖动作按实际场景核对既有授权，不重复询问已确认规则；验收后文档收尾的提交、推送和合并权限按D81。

D83已确认先同步本地主分支，再从它创建新任务分支：妥善保存已有改动并确认工作区干净后，fetch项目指定远端主分支的最新状态；本地主分支已与其一致则保持，仅落后时通过快进更新到该版本。核对本地主分支与本次获取的远端主分支提交一致后，再从本地主分支创建独立任务分支。直接从远端主分支开任务分支的备选方式未采用；默认命名按D102，具体操作仍须核对项目指定的远端和主分支，已有项目沿用实际配置。

线上故障修复的基线按D90作为例外：从当前线上实际运行版本对应的提交起步，不能将本地主分支已更新到最新版本当作必须从其创建线上补丁分支的理由。普通任务继续沿用D83。

D84已确认采用Git worktree为任务提供独立工作目录，考虑后续多Agent协作需求；任务分支与基线仍按D69、D83，提交、验证、验收和合入规则继续沿用。任务合入后的worktree移除流程按D85，目录布局按D86，任务目录与分支命名按D87，多Agent与目录的分配尚待细化，不把工作文件分目录视为进程、数据库、端口或权限已经隔离。完整协作升级仍按D66后置，当前未创建worktree或实施运行能力。

D86已确认任务worktree放在项目旁边：主仓库与`<项目名>-worktrees/`目录同级，各任务使用后者下面的独立子目录；主目录继续维护主分支。例如主目录为`my-app/`时，任务目录可表示为`my-app-worktrees/<任务目录>/`，示例不指定统一机器路径或任务编号格式。实际使用须核对项目路径、目录归属及工具能否访问同级目录；任务目录与分支命名关联按D87。按D85只移除对应任务worktree子目录，保留其他任务目录，不将整个`<项目名>-worktrees/`目录作为当前任务的清理目标；当前未创建这些目录。

D87已确认命名方式：分支采用`task/<迭代标识>-<任务标识>-<简短英文描述>`，worktree子目录使用相同名称主体并省去`task/`前缀。例如`task/003-t02-login`对应`<项目名>-worktrees/003-t02-login/`；003表示示例迭代，T02表示其中的登录任务，不是同一任务的开发或审查轮数。迭代与任务标识沿用项目已有记录，不另编一套任务号，也不要求已有编号统一改成示例格式。具体名称合法性、路径归属和唯一性须在落地时核对。

同一任务更换方案、按D76需要另开分支时，在名称主体后追加`-r2`、`-r3`等后缀，分支和worktree目录同步对应，仍沿原任务记录替代关系。普通修复保留原分支和目录，不因一次报错、审查或重验就创建新编号；旧方案保留和清理按D79、D85，重复请求先按D82核对实际状态。当前仅确认命名约定，未创建或重命名分支和目录。

本地主分支存在远端没有的提交，包括本地领先或双方各有提交时，先查明原因，不自动覆盖本地提交，也不为了同步生成合并提交。网络或访问等问题先在已有授权内处理，仍无法确认远端最新状态时如实报告并暂不基于旧版本开始新任务。fetch成功、更新本地主分支和创建任务分支分别核对实际结果；重复请求按D82核对当前任务与分支，已完成的步骤不重复执行。具体异常解决方案、自动操作权限和运行验证仍待落实，当前未执行同步或分支操作。

每个任务使用独立开发分支，PR实际合入主分支后清理该任务的本地和远端开发分支，已确认 D69。验收后自动清理的权限及异常边界按D81，先移除任务worktree再清理分支的顺序与检查按D85，操作报告和重复请求核对按D82，具体工具和运行验证仍待落实。PR流程与用户验收、规格收尾的时序按D73，不能凭PR状态补记验收。

D73已确认顺序，并由D103补充PR创建时点、D85补充目录清理：任务开发提交完成，AI产品验证、独立代码审查及必要修复检查通过 → 创建PR并交用户验收任务分支的候选版本 → 用户明确通过后完成对应规格和相关记录收尾，更新同一PR并通过最终检查 → PR合入主分支 → 按D85移除任务worktree并清理本地与远端任务分支。验收后的文档收尾补必要一致性检查，功能变化则重新验证并验收受影响部分；最终待合入内容和证据仍须满足D70。提交版本验证定位按D74，验收后的自动收尾权限按D81，具体检查组合、工具及其他操作授权仍待讨论。

D103确认在任务开发提交完成、AI产品验证和D71全新独立代码审查及必要修复检查通过后，交用户验收时创建PR，集中提供候选改动的查看入口；验收后的规格和记录收尾继续更新同一PR，再按既定门槛检查和合入。创建PR不替代用户验收，不允许在验收、收尾及最终检查完成前合入。线上补丁发布与主线处理顺序沿D90–D92保持，不因本条提前回合主线。用户指出PR自动执行权限已讨论，创建动作按已有适用授权执行，不再单列重复确认；实际项目的账户、仓库目标、工具及运行条件仍须核对。当前未创建PR、推送或实施Git能力。

D74已明确最终commit版本的必要验证以D71真实产品效果验证与全新独立代码审查为主体，必要自动化测试提供支撑；检查对应最终提交内容，通过后交用户验收。开发阶段仍按D34、D35持续测试，中断保存按D76、D97；WIP不是最终交付提交，不触发开发完成或验收通过的结论。仍适用的测试事实可复用，但旧审查结论不替代该轮新独立判断。内容、环境或合入基线变化后补受影响检查，实际验证与工具接入仍须落实。

D76已确认替代D75，并由D78、D79补充远端备份和旧方案处置：需要人类决策的必要阻塞 → 精选本任务允许保存的内容并核对暂存区 → 本地WIP保存提交 → 按D78同步对应远端任务分支并核对结果 → 主Agent记录断点、说明阻塞并等待 → 新方案确定替代旧方案后按D79关闭已有旧PR、注明替代关系，核对工作区、同步主分支并另建任务分支 → 替代方案验证、验收、收尾及合入 → 确认旧方案无需保留后清理本地及远端旧分支。存在未解决合并冲突时按D89保留冲突现场，不机械执行普通WIP提交；普通可自主处理的问题仍沿D32在原任务内解决，不把每个中途报错都当作需要人类决策的阻塞。

D97将WIP保存扩展到用户明确主动暂停或切换任务，例如“今天到这里”或“先切换任务”。有未保存的任务改动时，沿D76核对归属、精选允许入库的改动并核对暂存区，再创建本地WIP提交、按D78核对远端备份并记录断点；没有新改动不创建空提交。未解决合并冲突仍按D89保留现场；保存失败保留实际状态，本地与远端结果分别报告。本决定仅扩展触发情形，不扩大保存内容、远端权限或验收含义，尚未落实到Skills或运行接入。

D98确认其他来源的改动按所属任务和已有授权保存到对应任务分支：来源不同但属于当前任务且允许入库的可以一起保存，其他任务的改动单独处理。归属或入库许可不清时保留现场，只澄清受影响部分，不混入当前提交。保存不表示恢复推进另一任务或通过验收，已有备份、冲突与报告规则保持；该方法尚未落实到Skills或运行接入。

WIP记录当前未完成进度，本地保存成功、远端备份结果与开发完成、测试审查通过、用户验收分别记录；主Agent沿原tasks/verification记录提交断点、未完成事项及恢复条件。提交实际失败或无法安全选取保存范围时保留现场，如实报告保存受阻，不宣称已进入Git历史。暂存用于组织提交，不默认收进用户无关改动或未获准保存的内容。

D78已确认本地保存后同步远端：项目已明确远端和推送授权后，每次按D76或D97成功创建本地WIP提交，自动推送到对应远端任务分支并核对备份结果。推送失败时保留本地提交，明确报告“本地已保存、远端未备份”；远端或授权条件不具备、结果无法确认时如实记录，不将本地保存当成远端备份成功。备份不表示开发完成、验证或用户验收通过，不改变D77的主分支每任务一条正式提交规则。具体远端、工具接入和运行验证仍待落实，本次不执行当前仓库的提交或推送。

新方案须已有适用确认或属于原任务授权内的普通调整；核对工作区后按D83先同步本地主分支，再从其建立新任务分支。新旧分支关联原任务及方案替换依据，不另建平行任务或迭代。D79已确认新方案确定替代旧方案后，关闭已有旧PR并注明替代关系，避免误合入；旧本地及远端分支和WIP继续保留到替代方案按D70、D73完成必要验证、用户验收、规格记录收尾及合入，再核对旧方案确已无需保留后清理两端旧分支。正常合入的新任务分支仍按D69清理本地和远端；旧方案处置仅限被明确替代的对象。关闭PR不等于删除分支，也不代表旧方案已合入或通过验收；两端清理结果分别核对，不将本地分支删除视为远端已处理。验收合入后的自动清理按D81，报告与重复请求按D82；此前关闭旧PR的具体执行权限、工具和运行验证仍待落实，当前未执行关闭或清理。

D77已确认PR采用Squash（压缩合并）：在D70检查及D73验收、收尾满足后，将当前来源分支的最终任务改动形成一条正式提交合入主分支，每条记录对应一个完整任务，包括实际交付的代码、适用测试和相关文档。开发分支在清理前保留WIP、修复与文档收尾等过程提交，不为压缩合并预先改写开发历史；压缩的是当前交付PR的最终改动，不把被替代旧方案分支并入。合入成功后按D69清理当前任务分支，旧方案分支按D76的条件另行清理。

D80已确认Squash后的正式提交消息采用`类型(范围): 中文成果摘要`。类型区分功能、修复、文档等，范围可省略；摘要说明完整任务实际交付的成果，正文按需补充变更原因和关联任务。例如：`docs(git): 明确任务分支的保存与清理规则`。该格式用于D77进入主分支的正式提交，不改变已有验证、验收和合入条件；当前尚未实施自动消息生成或检查。

D81已确认有条件的自动收尾权限：项目的仓库、远端、目标主分支已明确且执行权限具备，用户明确验收对应任务成果后，主Agent可连续完成对应规格和记录收尾、核对并提交推送本任务收尾改动、更新PR和最终检查；满足D70、D73后，按D77、D80执行Squash合并，确认合入成功且没有需保留的新改动后按D85先移除任务worktree，再按D69清理两端任务分支。旧方案目录和分支仍须满足D79才可清理。上述同一范围的正常收尾不再逐项询问提交、推送、合并、移除任务worktree或删除分支；“继续检查”等指令不替代明确验收，项目与目标不明时不执行。

验收后仅文档收尾则补一致性检查；修改影响已验收行为时重新验证并验收受影响部分。主分支变化时按D88将尚未包含的主线更新同步到任务分支，再核对衔接与受影响检查，不能用过时结论直接合入。必要检查失败先在已有授权内处理，仍不满足条件则不合入；无法解决或涉及关键取舍时暂停相应操作并报告。D81不包括强制推送、改写主分支历史、丢弃无关改动、修改仓库保护规则或生产部署；若合并触发自动上线，须核对适用部署授权。合并成功、清理失败等部分结果分别记录；工具与运行验证仍待落实，规则确认不启动当前仓库Git写操作或补记验收。

D88已确认主线更新以普通Merge同步到任务分支。任务开发期间主分支出现新提交，准备集成检查时发现任务分支尚未包含这些更新，先妥善保存当前改动，核对所获取的主线版本、任务分支及其worktree，再把主线更新合并到任务分支；保留已有提交，必要时新增合并提交，不采用Rebase作为默认同步方式。主线更新已经包含在任务分支时，按D82核对后保持，不重复制造合并。线上补丁分支按D90保留线上版本基线，不机械合入最新主线的全部更新。需要用户决策的冲突按D89保留现场；其他具体处理与运行验证仍待落实，当前未执行同步。

D89已确认需要用户决策的合并冲突保留现场等待：保留任务worktree内的未解决冲突和已完成的处理，暂停该目录的继续写入，不自动中止合并、清理目录或用于其他任务。主Agent记录冲突位置、待决定事项及恢复依据（包括相关分支和合并双方的提交），向用户说明状态；用户答复后先核对实际现场与已有处理，再继续解决原合并，完成后按D88核对受影响验证、审查和验收。普通技术冲突在已有授权内自主处理，不因出现冲突标记就一律等待用户。
