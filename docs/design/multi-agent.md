# 多 Agent 协作

本页说明**何时分工、怎样交接、如何独立审查**。分工依赖宿主实际具备的Agent能力，框架提供交接方法和返回约定，不提供独立调度器或进程、端口、数据的强制隔离。方法与检查范围见[能力索引](../../skills/README.md)和[验证记录](../../tests/README.md)。

## 分工原则

| 角色 | 责任 |
| --- | --- |
| 主 Agent | 统筹当前任务、核验结果，统一更新正式状态和记录 |
| 执行者 | 实现、测试、自查，处理核实后的必要修复 |
| 审查者 | 读取原始依据与实际产物，返回有证据的发现，独立复查修复 |

- 子 Agent 按任务创建，不固定全角色常驻；默认最多三个同时运行，可按需调整。
- 首版不默认递归委派，需要协助时交主 Agent 判断。
- 普通讨论或文档登记不自动委派；已有协作工具不代表必须并行。

## 并行前提与工作目录

开始前核对：

- 目标、输入、验收与依赖清楚，前置已经满足。
- 修改范围可隔离，文件负责人明确。
- 工具真实可用，环境和操作权限适用于本次任务。

任务使用独立 worktree，具体命名、目录位置、Merge 同步和 Squash 合入见[Git 工作流](git-workflow.md#普通任务的完整顺序)。Agent 与分支、目录的具体分配机制仍待设计。

**目录使用约束：**

- 文件分目录不等于进程、端口、数据和权限已隔离。
- 需要用户决定的合并冲突保留在原目录，暂停继续写入，不挪给其他任务或自动清理。
- 清理前确认相关 Agent 停止写入、本任务独占进程停止、必要资料已保存。
- 线上补丁沿用实际发布版本基线，恢复、主线覆盖与清理顺序见[补丁规则](git-workflow.md#发布版本与线上补丁)。

## 交接与返回

| 主 Agent 交出 | 子 Agent 返回 |
| --- | --- |
| 项目、成果、请求模式与返回位置 | 完成内容与实际修改范围 |
| 目标内容或运行版本、原始要求及确认 | 检查结果和可定位证据 |
| 必读资料、可修改范围、允许操作 | 未解决问题和待决定事项 |
| 依赖、已有证据、验证与阻塞要求 | 接续条件或阻塞原因 |

信息按任务需要提供，不用完整表单代替事实。主 Agent 核验产物与证据，再安排必要联调、审查和整体验证；子 Agent 自报完成不等于通过。

专项完成后返回原任务，不递归启动另一套执行流程、不争写正式状态。缺能力时交付材料并说明条件，不伪称已调用。

## 独立审查与反馈处理

### 什么时候审查

- **实现前**：检查关键方案，重要设计按需引入独立视角。
- **任务验收前**：普通功能默认一次独立审查；低影响修改可按实际影响简化，高风险按需专项检查。
- **整轮交付前**：检查跨任务衔接，不能只汇总各任务结论。

执行者的测试和自查始终保留，不能只按行数降低要求。

### 怎样保持独立

PR 合入前的代码审查使用**全新独立上下文 Agent**：

1. 只交接需求及相关修改、新增，不传开发对话或实现推理。
2. 审查者自行读取原始依据、实际产物及必要规范、调用方和依赖；摘要只作导航，不能代替检查。
3. 默认只读代码与正式文档。运行检查前核对环境、临时写入和副作用。
4. 审查期间保持目标内容稳定；变化后重查受影响结论。

不要求用户代为整理技术材料。工具不能提供独立上下文时保留缺项，不以执行者自查冒充独立审查。

### 发现怎样交回

每项发现说明**位置、触发条件、预期与实际差异、影响及依据**。可复现时给最小复现；静态推导说明路径。不设最低发现数量。

| 分类 | 处理 |
| --- | --- |
| 必须修复 | 有依据的需求、验收、质量、安全或数据问题；核验关闭前不具备对应交付条件 |
| 改进建议 | 未违反当前要求的命名、重构或优化；默认不改、不建任务、不阻塞交付 |
| 待核实 | 定向补查，关键验收、安全或数据疑点未排除时不能判通过 |

可能继续造成损害的问题，先停止受影响操作并报告。仅请求审查时只检查和报告，修复依已有适用授权处理。

### 修复怎样闭环

1. **筛选与核验**：审查者先筛必要性，主 Agent 按原始要求、明确规范和实际影响核验；误报须有可核验依据。
2. **修复与重验**：在原授权内处理有效问题，重跑失败场景及受影响检查。
3. **独立复查**：聚焦原问题和修复影响；新增发现遵循相同必要性标准，执行者自报修好不足以关闭。
4. **形成结论**：必要范围已检查、必须修复项关闭、关键未知已处理且证据适用，才可判通过；否则说明需修复或证据不足。

技术分歧优先用要求、代码和最小实验核对，必要时增加另一视角；重要业务取舍交用户决定。

> 同一问题连续两轮无新证据或反复回退时，停止重复修改、重新调查；仍未解决则报告阻塞。轮数、时间或预算不足都不降低通过标准。

主 Agent 向用户简述最终结论、必要修复结果、未结项和关键取舍；详细核验与复查证据归原 `verification.md`，进度归 `tasks.md`。无适用迭代时在对话交付，不另建报告体系。

审查不替代测试和用户验收。整轮审查影响已验收成果时，保留历史验收事实，修复、重验并重新验收受影响部分。

## 多视角讨论

`discuss-design` 按议题选择相关角度、相互质疑，给有条件的推荐并保留分歧与未知。

- 默认可由同一 Agent 分角度分析，须透明说明。
- 只有用户或适用协作要求明确需要，且工具可用时，才实际委派。
- 讨论不等于独立审查或并行执行，建议不代替用户确认。
- 结论按确认结果进入已有需求或设计，不默认生成永久会议文档。

`execute-task` 提供交接与结果核验方法，`review-work` 提供审查及反馈方法；已被委派的审查者读取后自行检查，不再次委派。源码中的方法不构成宿主权限保证。
