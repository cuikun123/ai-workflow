## 接入负责什么

| 层次 | 目标 |
| --- | --- |
| 框架接入 | 把完整能力、入口和导航放入目标项目，并验证可用 |
| 项目地基 | 澄清业务方向，建立并实际验证最小工程 |
| 持续迭代 | 开发业务能力，维护当前资料和每轮历史 |

接入成功不等于地基完成。首版方向是 Skills 加轻量脚本，保留以后演进为 CLI 加 Skills 或插件分发的空间。

当前用户已明确要求补齐安装与接入、状态与恢复、框架行为评测和问题诊断，多 Agent 协作升级继续后置。第1步确定性工具按D112实施，后续安装接入仍需落实；手动复制可用于内部实验，不作为安装能力已交付的依据。各项实现配套验证，完整项目验证再检验联动；范围及剩余任务见[开发路线](../roadmap.md)。

### 技术路线、替代项与依赖

推荐Node.js、JavaScript ESM及必要JSDoc类型说明，使用内置文件、路径、摘要、参数解析与`node:test`能力。仓库已有Node测试，业务栈与框架运行时分离；Java/Python无需成为框架安装前置。TypeScript可改善静态检查，但首版主要风险是文件与状态的运行时一致性，正式schema和行为测试仍不可省；当前建议先沿用JavaScript，避免新增编译链作为开发必经步骤。

| 用途 | 推荐 | 理由与进入实施前须补齐的检查 |
| --- | --- | --- |
| 状态表达 | YAML 1.2可读文件，解析后限制为JSON兼容数据；正式校验使用JSON Schema 2020-12 | 保留既定state.yaml路径和可读性；不再靠正则判断结构。拒绝重复键、自定义标签、别名/合并及未知字段，避免多种解释 |

| schema校验 | [Ajv 8.20.0](https://registry.npmjs.org/ajv/8.20.0)，MIT | 已核对4项运行依赖及版本范围，隔离验证2020-12 schema、无类型强转和拒绝额外字段；只编译可信随包schema，不启用任意远程加载或用户代码。此次不是state v1运行测试 |

### 分发与项目内调用

推荐一个精确版本的npm分发包同时包含初始化入口、十一项Skills、参考资源、模板、schema、预构建运行工具及许可。首次取得包可联网；在指定新项目安装完整资源后，日常调用项目内固定运行工具，不每次通过浮动版本重新下载。D113已选择包名和命令`iterlane`；当前内部包只有check/validate基础，尚无初始化入口。

- 项目内运行工具建议放`.ai-workflow/runtime/`，与技能共同锁定版本；包完整时，check/status/doctor/validate/recover不依赖网络、源码仓库或全局npm缓存。
- 本地已安装版本是日常行为依据。用于安装或升级的外部工具遇到目标已有不同版本时停止并报告，不用外部新工具直接改旧状态；版本迁移走显式兼容路径。
- 业务项目已有package.json不因接入被自动加入框架依赖，不替换已有AGENTS说明、技能或业务文档。
- 版本清单建议放`.ai-workflow/manifest.json`：记录清单版本、安装标识、框架包名/精确版本、来源产物摘要、兼容状态schema、受管理资源路径/摘要及AGENTS管理区块。清单自身不递归记录自己的摘要；来源真实性另由可信分发来源及产物记录核对。
- 框架资源和清单可随项目Git保存；`state.yaml`与业务记录沿既有业务资料保存。机内锁、操作日志和恢复备份统一放`.ai-workflow/.local/`并在接入计划中明确其Git忽略处理，不将它们当跨机器正式状态。
- 业务模板一经生成即属于业务项目，不纳入框架资源固定摘要更新；后续升级不重新铺设模板。框架安装记录不重复充当业务进度文件。

拟议接口中check、status、doctor、validate为只读；init、状态转换、recover、upgrade、rollback的写操作均先核对计划、归属与适用授权，已有授权不重复询问。第1步已实现`--help`、`--version`、`check [--package <dir>] [--json]`及`validate --state <file> [--json]`，错误与退出码见[执行计划](../roadmap.md#第1步执行计划d112)。其他命令尚未创建。

## 第0步：恢复边界

恢复覆盖框架自己管理的文件写入与工作书签，不构成整个业务项目或生产环境的事务系统。状态结构和验收依据见[文档设计](documents.md#第0步状态结构与转换)。

### 写入的一致性方案

推荐每个项目工作目录一把独占写锁，配合revision及文件摘要；不引入数据库、后台服务或多Agent调度。独占锁覆盖本框架工具的写入；不同worktree仍有各自文件，不能把此锁宣称为跨worktree或外部编辑器的强隔离。

1. **先核对**：解析目标根及实际路径，拒绝越界和不支持的文件系统；检查未完成操作、期望revision、当前内容摘要及授权，列出本次具体写入。
2. **持久化准备**：在项目内保存操作标识、目标版本、每项写入前后摘要、归属和必要备份；临时资源校验通过才进入写入。未完成准备时不改目标文件。
3. **逐项写入**：每次写前再核对，先写同目录临时文件、刷新并校验，再执行文件替换；更新操作记录。Windows占用、权限和替换失败均按失败保留现场，不先删目标文件再赌写入成功。
4. **最后提交状态**：相关业务记录更新并回读后，才写新的state revision；安装或升级的有效版本标记在资源校验后提交。中间阶段始终由未完成操作标记阻止误报成功。
5. **回读结束**：全部目标、摘要和状态引用核对一致后标记操作完成，释放锁。启动时先检查未完成日志，不能单凭版本清单或state存在就假定上次成功。

这是一套可检测并恢复的多文件写入协议，不承诺跨目录瞬间原子提交、磁盘损坏恢复或断电绝对不丢数据。非协作编辑器仍可能写入；本框架靠前后比对发现冲突并停止，不声称锁住所有外部进程。

### 哪些可以恢复，哪些必须停止

| 情况 | 推荐处理 |
| --- | --- |
| 只读查询发现状态过时 | 返回过时原因和实际依据，不借查询修复文件；独立恢复在适用授权内执行 |
| 同版本初始化中断 | 依据本次操作日志核对已写/未写项；原授权适用、归属和摘要匹配时继续或有限还原；未知文件不自动认领 |
| 当前文件仍等于本次写入后的内容 | 可按本次已授权范围恢复前像；本次新建且内容未变化的文件才可作为有限还原对象 |
| 文件被用户或外部程序修改 | 停止覆盖与删除，保留当前文件、备份和差异；AGENTS仅比较并恢复本框架区块，保留区块外修改；区块内冲突同样停止 |
| 锁残留或进程异常退出 | 结合操作标识、进程身份和日志判断；不能仅凭锁文件年龄或PID直接删除。无法确定所有者已结束时报告阻塞 |
| state损坏、两份记录矛盾或缺失确认依据 | 不按目录编号/mtime推定；能从已核实的任务、证据及操作记录唯一重建时提交恢复计划，否则保留未知 |
| 升级中断 | 有日志和完整旧资源时恢复一致版本，或在明确兼容及适用授权下继续；禁止混合版本继续工作 |
| 升级后已有新任务或新数据 | 回退先验证旧schema可表达当前状态，保留后来业务修改；不能为了回退框架而恢复整个项目快照 |
| 不可逆迁移或旧版不理解现有状态 | 明确拒绝自动回退，交付差异和可选方案；首版只支持经过测试的相邻兼容版本路径 |
| Git冲突、提交/推送、部署、数据库及生产副作用 | 继续沿既有Git和发布规则；recover不执行reset/clean、自动合并、重新部署或数据库恢复，不把状态恢复当外部动作已撤销 |

备份只覆盖本次管理写入，不备份整个业务目录；未解决操作的日志和前像必须保留，最近一个可回退版本保留至后续成功版本替代且无未结恢复引用。清理由明确的框架管理范围及操作条件决定，不按“临时”二字自动删现场。

恢复后的阶段必须与真实证据一致：原来待验收则仍待验收；已验收但规格未同步则回到收尾；恢复书签不自动重试曾失败的部署。必要恢复无需重复索取已适用授权，但不能从日志中的一段文字发明新的权限。

### 写入、中断与有限恢复

1. 只读预检包、现有目录、每级路径、目标冲突及历史操作；拒绝UNC、链接/重解析点越界、大小写/Unicode路径冲突和无支持依据的目标。临时资源准备和校验完成后才进入目标写入。
2. 项目内`.ai-workflow/.local/write.lock`用独占创建；记录操作UUID、该操作稳定的随机nonce、当前持锁PID和时间。恢复重取锁沿用同一操作nonce，避免新锁与旧日志交接中断后永久不匹配。另一工具进程直接失败；残留锁不能按年龄删除。只有关联日志合法且原PID确定不存在时，显式resume/undo才可核对并处理；PID仍存在或权限导致不可判断时保留锁并报告。PID复用导致保守停止，不冒险认定原进程已退出。
3. `.ai-workflow/.local/operations/<uuid>/journal.json`保存日志版本、项目绑定、包身份和源摘要、实际创建目录、逐文件前/后像及状态；以Base64保存本次前/后像，并逐字节与源/当前文件比较，不备份整个项目。日志字段和所有路径严格检查，不从日志中的权限文字推断新授权。
4. 先写可恢复日志和前像，再逐项核对当前内容。目标临时文件路径绑定操作UUID；日志在创建临时文件前登记当前临时写入的路径、镜像、字节数及SHA-256，flush、回读、替换后更新状态。恢复时仅清理该已登记文件且其内容等于完整预期镜像或一次未完成写入的前缀；其他变化停止保留。日志自身未发布的临时文件留在本次`.local/operations/<uuid>/`，后续使用新临时路径，不把机内残留当资源或自动删除。替换失败不先删除原文件；每次处理AGENTS/忽略区块前重新读取外部内容，保留区块外修改，区块内冲突停止。
5. 先写资源和业务骨架，再生成并回读初始state；最后在全部资源/区块及状态检查通过后写正式安装清单并提交操作。操作未提交时check返回INCOMPLETE，清单存在也不能掩盖未完成日志。
6. resume把实际文件与前/后像核对：等于后像则保留，等于前像或本来不存在且尚未写入则继续，其他变化均停止。undo只还原后像仍匹配的本次写入；本次新建且未改的文件才允许删除，新建目录仅在日志归属明确且为空时移除，业务新增内容和项目根始终保留并报告残留目录。部分undo只能继续undo，不能被resume重新创建。撤销未完成repair会回到原安装的不完整状态，不谎称已卸载；正常已结束操作再次resume/undo拒绝，不重写文件。资源已提交但锁清理中断时只完成已核对的锁清理，不重置业务state。

自动resume/undo的起点是完整准备日志已持久化。此前只允许创建机内元数据目录/锁，不允许写资源、管理区块、业务骨架或state；若在此阶段终止且没有有效归属日志，下一次返回未识别残留/阻塞并保留现场，不能自动认领或清理。这个启动断点单独测试，不能冒充已自动恢复；这是沿D27选取的保守恢复边界，方案确认时一并展示。

本轮实现初始化操作的继续/有限还原，不实现通用state转换、doctor、升级或回退。锁只约束本工具进程；外部编辑的检查与替换仍可能竞争，不宣称强隔离或跨目录原子事务。强制终止、写入错误和占用分别实测，断电/磁盘损坏不作绝对恢复保证。

### D118：Git行尾兼容修复（已授权）

用户已要求按最小方向修复。选择在项目`.gitattributes`中追加独立管理区块，通过`-text`保留指定路径的原始字节；不改全局`core.autocrlf`，不放宽摘要或归一化后冒充原字节。已有区块外内容逐字节保留，外来Skills和其他业务代码沿原Git规则处理。仅对指定路径的文本转换设置形成项目内明确覆盖，其他属性与规则不改。

保护范围为`.ai-workflow/**`、十一项框架Skill各自目录、`AGENTS.md`、`.gitignore`、`.gitattributes`自身、`docs/workflow/state.yaml`及初始化state的四项basis路径（overview、scope、tasks、verification）。不把整个`.agents`或业务`docs`树设为二进制；未来任意状态依据路径仍须在对应状态任务处理。自定义filter、working-tree-encoding或更高优先级/子目录属性仍可能改变内容，严格check不能因此放行。损坏、重复或未知管理区块停止并保留。

沿现有manifest/journal协议登记第三类`attributes`区块，纳入只读preview、缺失区块显式repair、日志断点resume/有限undo；恢复核对来源、前后像及区块外内容，禁止把未知文件认领为受管理资源。新候选0.3.0-dev.3区分旧冻结包；不自动迁移旧dev.2安装或覆盖其进度，旧CLI/包仍按原版本检查与恢复。

独立审查发现区块追加并非可逆映射：补LF会使不同末尾换行的前像得到相同后像，空文件与不存在也可能得到相同后像。dev.3日志增加`before_sha256`，以null区分不存在与空文件摘要，在任何恢复写入前核对；区块写入根据当前外部内容重取前像时同步更新摘要。它检测前像单字段损坏，不构成对整份日志协调篡改的认证或权限沙箱。

实施计划由主Agent内联推进，临时台账留在隔离证据，不新建正式报告体系：

1. 新增真实Git回归：从真实包初始化，在`core.autocrlf=true`及既有`* text=auto`条件下本地保存后重新检出，断言严格check、管理区块/状态/basis原字节保持，外来技能及普通代码继续转换；先观察RED。

3. 覆盖preview无写入、重复init、区块删除repair、改动/坏标记拒绝、attributes写入中断resume及undo保留既有/新增规则，增加CI必测；独立审查关注区块前像、路径越界、过宽Git规则及旧版本保护。
4. 执行主目录与干净副本CI、真实npm打包/离线运行和Git检出复验，保留原失败、新包、源码及检查事件，更新既有交接/验证/变更记录。框架仓库提交/推送仍未授权。

## 项目安装布局

**已确认：每个业务项目保存完整能力包，技能说明直接安装到原生入口。**

```text
业务项目/
├── .ai-workflow/               # 公共框架资源、模板、脚本和版本信息
```

**选择直接安装的原因**：首版聚焦 Codex，可减少读取另一份主流程的步骤，便于核对实际生效内容。引用入口和目录链接备选未采用，不维护第二份相同主说明。

新个人项目的 Git 默认平台、可见性及命名见[Git 基本约定](git-workflow.md#适用范围与基本概念)。实际账户、仓库和权限仍须落实，默认值不授权建仓或修改已有配置。

## 初始化与失败恢复

### 初始化顺序（草案）

1. 检查目标目录、已有规则、工作区和接入状态。
2. 准备并安装指定版本的完整资源。
3. 用可识别的管理区块接入 `AGENTS.md`，保留原有内容。
4. 建立固定空文档与最小有效导航。
5. 检查资源、引用、状态结构，并实际验证入口。

统一入口拟支持开始、继续和状态；专项只补必需前置。`myflow`、`$myflow`、`myflow init/check/status/update` 都是讨论示意，不是现有命令或正式产品名。

### 重复执行与冲突（已确认）

| 情况 | 处理原则 |
| --- | --- |
| 同版本重复初始化 | 保留已有内容和项目进度 |
| 文件缺失或内容冲突 | 先列问题，再决定修复；列出不授权补建、覆盖或合并 |
| 发现有新版 | 初始化不自动升级，使用独立升级流程 |

版本识别、文件归属、冲突检测及修复执行方式仍待设计。

### 中途失败怎样恢复（已确认）

1. **先准备再写入**：框架资源与本框架拥有的技能子目录先在临时位置检查，按计划安装；已有版本保留恢复依据。
2. **保护业务内容**：业务文档、进度和用户修改保留；`AGENTS.md` 的管理区块单独处理。
3. **有限还原**：只尝试还原本次已授权、归属明确且未被用户或外部修改的写入。
4. **保留冲突现场**：归属不明、内容变化或还原失败时保留现场及备份，报告后决定修复。
5. **重新核对**：标记接入未完成；下次核对实际文件，通过完整检查后才能标记成功。

> 不能整体替换 `.agents/skills/`，其中可能有其他来源的技能。单目录替换不等于跨目录事务保证。

恢复需保留成功项、失败项、写入位置和原因。第2步已实现初始化日志与有限恢复；通用业务状态及升级恢复仍属后续任务。强制终止、Windows只读目标及文件占用已有对应检查，断电与磁盘损坏不因此获得绝对恢复保证。

## 接入成功怎样判断

### 已确认的通过条件

**结构检查与真实入口调用都通过，才算接入成功。**

| 检查 | 必须证明 |
| --- | --- |
| 结构与版本 | 按锁定版本、受管理文件清单检查完整性与变化，发现差异先报告 |
| 最小调用 | 在真实目标工具中正确读取项目状态，不修改业务内容 |
| 结果记录 | 结构和运行分别记录通过、失败或未验证 |
| 失败处理 | 先定位原因；入口失败不一律认定安装损坏，网络或登录问题不自动触发文件回滚 |

最小调用只证明这条入口路径，不证明全部技能或完整工作流。业务占位文档仍可为空，接入检查也不验收项目地基。

### 最小调用场景（建议）

在真实目标客户端和项目目录中，显式调用实际存在的只读入口：

1. 客户端找到技能，读取完整 `SKILL.md`。
2. 技能读取最小有效导航，返回当前阶段、下一任务或尚未开始。
3. 整个过程不创建、覆盖或修改文件。

若实现没有只读状态技能，需设计等价的无写入场景，不虚构产品入口。技能名称、提示和结果格式待定，参考[Codex Skills 文档](https://developers.openai.com/codex/skills/)并验证实际客户端。

### 版本检查方式（建议）

在 `.ai-workflow/` 保存锁定版本及受管理文件清单，覆盖技能、公共资源和未生成的模板资源，记录相对路径与摘要。第0步推荐SHA-256，尚未确认实现；模板生成的业务文件不因此成为可覆盖资源。

| 结果 | 解释与处理 |
| --- | --- |
| 版本与摘要吻合 | 受管理内容与锁定包一致 |
| 版本相同、摘要不同 | 可能是用户修改或损坏，先报告，不覆盖 |
| 管理文件缺失或管理范围内有未登记文件 | 先报告，按冲突规则决定修复 |
| 版本缺失或不可读 | 版本未知，不推定已匹配 |

只检查本框架管理范围，不把其他来源技能当冲突。清单和文件若能同时被修改，摘要不能证明来源真实性；签名与可信来源校验留待发布和安全设计。

### 调用失败或无法运行

- **实际调用失败**：记失败，保留错误与现场，定位原因；不能降格为未验证。
- **缺客户端、权限或环境**：记运行未验证，结构结果单独报告。
- **涉及安装恢复**：按前述有限还原规则处理，不因网络或登录问题一律回滚。
- **修复后**：重跑结构检查和同一最小调用，两者通过才标记接入成功。

具体状态字段、枚举、存储、错误分类和检查清单尚未确定；上述状态含义不是已实现的运行协议。

## 框架升级

**已确认：项目固定版本，升级由用户主动触发，作为独立任务。**

### 什么时候升级

- 默认当前任务验收并完成适用收尾后，再安排升级。
- 待验收时保持等待，不自动追随新版。
- 用户新指令或必要调整改变安排时，按确认及暂停恢复规则处理。

### 升级改哪些内容

| 内容 | 边界 |
| --- | --- |
| 框架管理资源及接入导航 | 在确认的升级范围内更新 |
| 业务说明、用户修改、业务资料与迭代进度 | 保留 |
| 模板生成的真实项目内容 | 属于业务项目，更新模板资源不授权覆盖 |
| 业务代码、依赖或构建配置 | 先说明原因、范围和验证方式，确认后处理 |

新版规则可能影响之后的开发与验证，不能承诺零影响。

### 如何核对结果

1. 升级前检查差异与兼容性，明确范围、前置和授权。
2. 沿用设计、计划、验证、逐任务验收及 Git 流程。
3. 在原任务和验证记录中保留实际前后版本，区分目标与已生效版本；无法核实保持未知。
4. 冲突与失败沿初始化的保留、报告及有限恢复原则处理，不另建版本历史体系。

版本标识、锁定信息、文件清单、迁移与回退机制仍待设计。文字版本记录不能替代运行检查或用户验收。
