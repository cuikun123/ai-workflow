## 接入负责什么

| 层次 | 目标 |
| --- | --- |
| 框架接入 | 把完整能力、入口和导航放入目标项目，并验证可用 |
| 项目地基 | 澄清业务方向，建立并实际验证最小工程 |
| 持续迭代 | 开发业务能力，维护当前资料和每轮历史 |

接入安装运行工具和技能，不生成已完成业务或批准。项目地基和业务能力按实际需求另行建立和验收。

使用真实init入口安装完整固定包；手动复制技能不是完整项目安装。跨项目调度和更多环境的支持范围见[开发路线](../roadmap.md)。

## 环境与分发

运行工具使用 Node.js 24 和 JavaScript ESM，依赖版本由锁文件固定。已测环境见[快速开始](../quickstart.md)；其他平台、模型服务稳定性及生产能力不据此推定可用。

分发包包含运行工具、十一项技能、模板、结构定义和来源许可。`resource-manifest.json`记录包身份及各文件的路径、大小和SHA-256，与项目安装记录`.ai-workflow/manifest.json`职责不同；文件摘要不是来源签名。

模型和账户使用宿主现有配置，框架不自建模型服务。连接失败、未知上游身份等证据留在[验证记录](../../tests/README.md)，不复制进使用步骤。

名称为Iterlane，包名和命令为`iterlane`；整体MIT与TY署名及第三方许可随包保留。

## 框架诊断与受控恢复

诊断聚合安装、状态、日志与写锁信息，受控恢复使用同一写入和日志机制，不自动迁移项目或重试业务。

### 只读doctor

接口为`doctor --project <dir> [--package <fixed-source>] [--client-evidence <json>] --json`，安装入口也可按自身位置定位项目。默认只读本项目文件、受管理资源和本机进程存活情况，不发网络请求、不读全局凭据、不执行安装/状态恢复或Git操作。

返回report_version=1、运行工具/项目、environment、client、local_valid、findings及recovery_candidates。每条finding含稳定code/category、severity、已知证据（路径、摘要、操作ID或受控错误码）、影响和下一步；只输出定位所需字段，原日志、消息、凭据和整份业务正文不复制进报告。doctor完成诊断时退出0；local_valid表达本地检查结果，成功诊断不等于环境健康或用户验收。无法启动工具时仍按既有ENVIRONMENT/PACKAGE_INVALID错误和退出码报告，不能伪称已完成doctor。

| 类别 | 必须区分 |
| --- | --- |
| installation/resource/version | 尚未安装、manifest无效、受管理文件/区块缺失、字节摘要改变、外来文件、运行版本与安装版本混用；旧版记录不凭新版本检查误记损坏 |
| state/document | 缺失/损坏state、过时basis、记录/引用或任务进度不一致；初始空文档合法，初始化尚未提交时不推断进度丢失 |
| operation/lock | 安装与状态两类日志、未完成/已提交遗留锁、未知或坏所有者、仍存活/已结束/无法确认的进程、多个未完成操作及被改目标；不按时间戳选日志或删除锁 |
| environment/path | Node支持范围、路径/权限/运行依赖错误，无法核实时保留unknown；不把路径错误等同资源摘要改变，其他平台不因此获得完整支持声明 |
| client | 默认为not_probed；明确提供的本地连接观察区分transport/authentication/timeout/ui_control/unknown，客户端问题与本地资源检查独立 |

client-evidence为有界严格JSON v1，含project_root、observed_at（规范UTC时间戳）、client名称、status（connected/failed/unknown）及failure（transport/authentication/timeout/ui_control/unknown或null）。只接受对应项目；它是调用方提供的观察声明，输出source_authenticity_verified=false，不认证其来源、不直接引用自由文本，也不由turn.started推定完整成功。无证据则不猜连接状态，doctor不会复验用户要求跳过的旧模型基线。

recovery_candidates仅列已识别操作及所需条件，不代表已授权或完整恢复前置通过；未知/损坏日志、锁归属不明、多个未完成操作或版本不匹配时不给自动写入建议。资源修复需要相同来源包，旧版使用匹配工具；不会把客户端错误转成回滚安装的建议。

### recover写入及预览

接口均支持`--project <dir>`及`--json`，一次只选一项动作：

- `recover --repair --package <fixed-source> [--preview]`：复用同版本显式repair，只补已归属缺失资源/区块，保留业务资料、改动资源及外来文件；不是升级或全量重装。
- `recover --resume|--undo --operation-id <uuid> [--package <fixed-source>] [--expected-revision <n>] [--preview]`：明确锁定安装或状态操作；安装须相同来源包，状态须当前准确revision。跨两个日志命名空间只允许唯一可核实的目标，不把新操作当旧操作恢复。
- `recover --refresh --expected-revision <n> --request-id <id> [--preview]`：复用现有语义refresh，仅对结构/位置可核实的书签重绑定basis，不换任务、批准内容或重新执行工作。稳定request-id沿既有重复操作规则。

preview执行相同只读归属/摘要/语义前置检查，只输出目标路径、替换/还原类别、版本/revision及锁处理，不写锁、日志或临时文件。执行时再次读取并校验，预览不成为以后覆盖文件的凭证。为防预览与执行之间的目标变化，恢复核心核对调用方指定operation-id；既有旧入口仍按原行为工作。

恢复后回读实际资源与状态，分别报告本次操作和剩余诊断，不把某项修复成功写成全部问题消失。state损坏、无匹配日志或外部编辑导致无法唯一恢复时保留现场返回阻塞；恢复书签不重试模型、Git、部署或数据库动作。诊断及恢复不建立新的任务/文档存储，不引入新运行依赖。

## 相邻版本升级与回退

版本操作只处理明确支持的相邻路径，保留业务内容和操作历史；当前项目状态和来源包必须能够核对。

### 支持路径

已验证的相邻路径是`0.3.0-dev.5 → 0.3.0-dev.6 → 0.3.0-dev.5`。包身份同时绑定版本和资源清单摘要，同版本不同来源拒绝混用；这条路径不包含当前的新项目试用包。

该路径保持state和workflow-record v1语义。升级只处理框架资源、必要导航/attributes及版本元数据；业务文档、代码、状态和revision保留。回退使用完整前一来源包，并确认它能表达当前状态，保留升级后新增的业务内容和记录。

未知安装、旧手动副本、更早或未登记版本及不兼容数据明确阻断，不按版本号猜迁移。需要改变业务或状态的数据迁移另行确定范围并验证，不隐式重置整个项目。

### 入口与可观察结果

执行升级的来源是完整0.3.0-dev.6外部分发包；当前0.3.0-dev.5安装入口保持原有版本，不能把它伪装成已拥有upgrade命令。外部工具明确指定项目及完整0.3.0-dev.5来源包，先校验两包和项目，再复制受校验的必要来源/恢复依据到项目内受控.local范围。

```powershell
node <dev6-package>/bin/iterlane.mjs upgrade --project <project> --from-package <fixed-dev5-package> --expected-revision <n> --preview --json
node <dev6-package>/bin/iterlane.mjs upgrade --project <project> --from-package <fixed-dev5-package> --expected-revision <n> --json
node <dev6-package>/bin/iterlane.mjs rollback --project <project> --operation-id <completed-upgrade-id> --expected-revision <current-n> --preview --json
node <dev6-package>/bin/iterlane.mjs rollback --project <project> --operation-id <completed-upgrade-id> --expected-revision <current-n> --json
```

rollback选择明确的上一成功升级operation-id及记录中的完整旧包，核对当前安装身份与当前revision，不能按文件时间或最大目录编号挑版本。成功升级返回operation-id、实际from/to版本及来源摘要；成功回退返回实际恢复的版本、保留的当前revision及仍存在的问题。目标身份已经准确匹配时重复upgrade不写；同一成功回退的重复请求，在当前身份/revision仍匹配时返回unchanged，不再次还原。

preview使用与执行相同的路径、归属、兼容、锁、日志和当前文件前置检查，输出新增/替换/删除的管理资源、三个管理区块、manifest及本地历史/备份操作，前后版本/摘要、当前revision和可能的锁处理。预览不建锁、目录、日志、备份、临时文件；执行重新检查全部输入，旧预览不授权覆盖之后的外部改动。

中断恢复通过0.3.0-dev.6外部固定工具的现有recover入口选择确切版本操作。复用`--resume|--undo --operation-id <uuid> --expected-revision <n> --package <fixed-dev6-package> [--preview]`：resume完成当前已记录方向，undo有限还原该次未完成的版本操作。rollback的undo回到该次rollback开始时的0.3.0-dev.6管理资源，保留同一当前业务/state；成功升级后的正式回退必须使用rollback，不能把已提交操作当未完成undo。恢复所需旧包、目标包及前后像须完整并与日志摘要吻合，工具/版本不匹配即停止。

### 前置、兼容检查与项目锁版

- 项目manifest须为严格有效的v2，安装ID/资源归属及0.3.0-dev.5完整来源相符；目标0.3.0-dev.6来源须完整校验、无额外文件、无链接/越界。验证跨版本包使用明确支持路径的校验适配，普通check/init/repair的同版本严格检查保持。
- state与所有当前记录/引用、当前位置及basis须能被当前版本核实。未完成安装/状态/版本操作、未知/损坏日志、活锁或无法确认的锁均阻断新升级/回退。默认须在当前业务任务验收并完成适用收尾后升级；awaiting_user、运行中或暂停未收尾的任务不会因升级而获准前进。
- 初始not_started且未开启业务任务，或已完成任务/迭代且无待收尾位置，可进入升级。当前语义位置的判定复用状态工具；没有可信收尾依据时拒绝，不把空state或目录存在当通过。真正改变默认升级时点需要用户单独指令和对应验证，本条不设置任意force开关。
- 当前已管理资源/区块须完整且与来源相符；缺失先按匹配旧工具repair，用户改动或混合资源明确列差异并停止。未管理的Skills、代码、AGENTS及ignore/attributes区块外内容保留，不自动认领或删除。
- 回退在新的当前state及业务记录上验证旧schema和语义，同时保留当下attributes保护的业务文档集合。兼容性、来源或逆向归属无法确认时返回拒绝，不伪称回退成功。
- 写入前核对expected_revision、当前manifest和全部管理前后像；持锁后再次核对。任何准备后变化停止写入或进入有日志的未完成状态，保留差异及恢复依据。

### 跨版本日志及来源保留

当前`install-journal.mjs`与`workflow-log.mjs`仅接受与运行时同版本的日志；把旧日志package字段改成新版本会改写历史，也不能让回退后的原0.3.0-dev.5工具读懂新版本记录。因此按实际版本保留完整机内历史，调整其活动位置，原日志字节及operation-id保持。

版本操作使用严格的v2版本日志，登记操作ID、方向、from/to完整包身份、当前state读依赖、资源/区块前后像、受控本地历史归属、各阶段及锁nonce。初始日志放在现有`.ai-workflow/.local/operations/<uuid>/journal.json`；0.3.0-dev.5读到不支持的日志协议会明确阻断，0.3.0-dev.6识别并校验版本操作。这一阻断先于任何管理资源替换，避免失败后旧工具在混合资源上继续写入。不能依赖旧客户端理解新命令或新独立目录。

升级前，两类活动日志必须全部完成、版本匹配且没有未知目录。将其完整内容按操作归属保存在该版本操作的受控.local恢复范围，再激活0.3.0-dev.6对应活动历史；原数据不改写。普通0.3.0-dev.6查询/状态写入应识别已提交版本日志，不把有界有效历史当坏日志；未完成版本日志继续阻断。不同版本的历史仅作为历史证据和明确恢复来源，不作为新任务的恢复候选。

rollback前保存升级后产生的活动日志及元数据，恢复原0.3.0-dev.5可读的历史活动位置；新业务文档及记录保留原位。所有v2版本操作日志在旧运行时激活前进入严格的`.local/version-history/<uuid>/`管理位置，原0.3.0-dev.5只看到其能验证的活动日志；外部0.3.0-dev.6仍可按operation-id核查新旧活动位置、已提交残留锁及完整恢复来源。重复请求由显式完成记录及安装身份识别，不按最新目录推断。

跨版本不能仅依赖原样请求的旧revision阻断重复执行：同一request-id换当前revision或其他参数仍须拒绝。为保持旧0.3.0-dev.5入口的既有去重行为，版本迁移在激活目标版本时生成其v1解码器可读的已完成去重投影；原始日志完整归档且字节不改，投影是迁移工具生成的缓存，不宣称原操作由目标旧版本执行。对应版本操作记录原日志路径/ID/摘要、投影路径/独立ID/摘要及原执行包身份，新的doctor可标识派生来源；原0.3.0-dev.5只能读到兼容的去重缓存，原始执行来源须从版本历史核对，真实性字段仍false。

投影仅为经过严格校验且phase=committed的原状态操作建立：保留原request全部字段及其after-state的实际applied revision，在目标活动workflow-operations中写目标版本可验证的v1记录。其files只含同一份原after-state的前/后像，读依赖为空，不写当前state、业务文档或原资源；使用独立UUID、当前迁移时间/nonce及目标包解码身份，来源映射保存在版本日志，不额外塞旧v1不认识的字段。它表示已完成请求的派生去重结果，不是可以重新执行或恢复的语义计划；新工具识别投影并拒绝其resume/undo，正常旧工具对无残留锁的已提交记录亦不提供未完成恢复。

已有限undo的rolled_back请求继续保留阻断，不归为成功投影。迁移生成目标v1可读的撤销标记，保留原请求及实际撤销结果，原日志和当前state不改。原样重试沿INCOMPLETE拒绝，改参复用沿CONFLICT拒绝，避免归档撤销日志后让同一ID再次写入。

相同原request（含旧expected_revision）重试只能返回已经执行的结果或明确旧revision阻断；复用request-id而改变revision/内容须在目标激活后的原生入口返回CONFLICT，不再产生业务/状态写入。恢复目标原始活动历史已包含同request-id时，仅在request及原结果一致时复用原记录，不建立重复投影；存在冲突/多个同ID结果时拒绝迁移并保留现场。rollback须把0.3.0-dev.6期间成功请求也投影为0.3.0-dev.5可读缓存，从而保留跨版本去重，不只覆盖回到0.3.0-dev.5自身的历史请求。投影与活动历史切换、资源写入一同登记、核对、恢复，不能在版本完成后再补一个未受控步骤。

这些是工具恢复元数据，不是另一套业务文档或备份整个项目。完整旧/新来源包仅存受管理.local范围，普通安装资源清单不把.local当框架资源；引用它们前重新验证实际字节和路径。上一可恢复版本的资格由明确成功操作关联；更早操作保留历史但不成为任意回退目标，未解决操作引用的备份必须保留。

目录活动位置转换必须成为版本操作日志的受控阶段：记录准确来源/目标、目录内完整文件清单和摘要，逐步核对已移动/未移动的实际状态。仅能移动本次归属及记录中的日志目录、删除本次已核对为空的目录；新出现或被改文件停止处理。源包/备份/root越界、junction及未知临时内容均保留并拒绝；不从日志自由文本生成shell命令。

### 写入、失败与有限恢复

1. 只读计划后取得现有项目写锁，持久化严格日志及旧/新来源和必要前像；全部恢复依据回读通过后才开始活动历史或资源写入。prepare失败但已产生未知元数据时保留现场，不自动认领。
2. 按日志完成历史切换与资源新增/替换/有限删除，三个管理区块分别核对并替换，仅最后更新安装manifest/version。动态attributes保留当前业务文档保护范围。工具来源在项目外或已完整进入受控备份，运行不能依赖被自己覆盖到一半的安装入口。
3. 每项写入前比较实际当前内容与该项前后像，临时文件按确切operation-id登记、刷新及回读，再替换。删除仅针对完整来源证明归属且仍等于计划前像的旧资源；新增文件与空目录的有限撤销须核对真实归属及内容。区块外修改在有唯一可验证区块时合并保留；区块内变化停止。
4. 资源、manifest、活动历史及当前state/记录按目标版本读回一致后才标记完成，最后清理确切归属的残留锁。upgrade和rollback均不重写state/revision，不倒退进度，不重试模型、Git或业务动作。
5. 未完成操作及准备到提交间的任何故障保持版本操作日志对旧/新正常写入的阻断；不释放唯一阻断后留下混合资源。明确resume/undo先核对原方向、操作ID、日志、完整来源、锁归属/进程终止及当前revision，再按实际前后像继续。undo只处理本次管理写入及活动历史位置，业务文件不列为还原对象。
6. 已提交但清锁/历史激活收口中断，恢复仅完成已核实的收口，不重复业务或资源操作。rollback在旧历史/资源完成并经兼容校验后归档新协议日志，记录其准确完成位置；外部固定新工具可恢复提交后的残留锁，旧工具不得提前误报成功。

这是可检测的多文件协议，不宣称跨目录瞬时原子切换、跨worktree强隔离或断电/磁盘损坏的绝对恢复。来源摘要只校验本地一致性，真实性字段仍false；完整备份不等于用户验收或发布授权。

## 恢复边界

恢复覆盖框架自己管理的文件写入与工作书签，不构成整个业务项目或生产环境的事务系统。状态结构和验收依据见[文档设计](documents.md#第0步状态结构与转换)。

### 写入的一致性方案

推荐每个项目工作目录一把独占写锁，配合revision及文件摘要；不引入数据库、后台服务或多Agent调度。独占锁覆盖本框架工具的写入；不同worktree仍有各自文件，不能把此锁宣称为跨worktree或外部编辑器的强隔离。

1. **先核对**：解析目标根及实际路径，拒绝越界和不支持的文件系统；检查未完成操作、期望revision、当前内容摘要及授权，列出本次具体写入。
2. **持久化准备**：在项目内保存操作标识、目标版本、每项写入前后摘要、归属和必要备份；临时资源校验通过才进入写入。未完成准备时不改目标文件。
3. **逐项写入**：每次写前再核对，先写同目录临时文件、刷新并校验，再执行文件替换；更新操作记录。Windows占用、权限和替换失败均按失败保留现场，不先删目标文件再赌写入成功。
4. **最后提交状态**：相关业务记录更新并回读后，才写新的state revision；安装或升级的有效版本标记在资源校验后提交。中间阶段始终由未完成操作标记阻止误报成功。
5. **回读结束**：全部目标、摘要和状态引用核对一致后标记操作完成，释放锁。启动时先检查未完成日志，不能单凭版本清单或state存在就假定上次成功。

这是一套可检测并恢复的多文件写入协议，不承诺跨目录瞬间原子提交、磁盘损坏恢复或断电绝对不丢数据。非协作编辑器仍可能写入；本框架靠前后比对发现冲突并停止，不声称锁住所有外部进程。

### 哪些可以恢复，哪些必须停止

| 情况 | 推荐处理 |
| --- | --- |
| 只读查询发现状态过时 | 返回过时原因和实际依据，不借查询修复文件；独立恢复在适用授权内执行 |
| 同版本初始化中断 | 依据本次操作日志核对已写/未写项；原授权适用、归属和摘要匹配时继续或有限还原；未知文件不自动认领 |
| 当前文件仍等于本次写入后的内容 | 可按本次已授权范围恢复前像；本次新建且内容未变化的文件才可作为有限还原对象 |
| 文件被用户或外部程序修改 | 停止覆盖与删除，保留当前文件、备份和差异；AGENTS仅比较并恢复本框架区块，保留区块外修改；区块内冲突同样停止 |
| 锁残留或进程异常退出 | 结合操作标识、进程身份和日志判断；不能仅凭锁文件年龄或PID直接删除。无法确定所有者已结束时报告阻塞 |
| state损坏、两份记录矛盾或缺失确认依据 | 不按目录编号/mtime推定；能从已核实的任务、证据及操作记录唯一重建时提交恢复计划，否则保留未知 |
| 升级中断 | 有日志和完整旧资源时恢复一致版本，或在明确兼容及适用授权下继续；禁止混合版本继续工作 |
| 升级后已有新任务或新数据 | 回退先验证旧schema可表达当前状态，保留后来业务修改；不能为了回退框架而恢复整个项目快照 |
| 不可逆迁移或旧版不理解现有状态 | 明确拒绝自动回退，交付差异和可选方案；首版只支持经过测试的相邻兼容版本路径 |
| Git冲突、提交/推送、部署、数据库及生产副作用 | 继续沿既有Git和发布规则；recover不执行reset/clean、自动合并、重新部署或数据库恢复，不把状态恢复当外部动作已撤销 |

备份只覆盖本次管理写入，不备份整个业务目录；未解决操作的日志和前像必须保留，最近一个可回退版本保留至后续成功版本替代且无未结恢复引用。清理由明确的框架管理范围及操作条件决定，不按“临时”二字自动删现场。

恢复后的阶段必须与真实证据一致：原来待验收则仍待验收；已验收但规格未同步则回到收尾；恢复书签不自动重试曾失败的部署。必要恢复无需重复索取已适用授权，但不能从日志中的一段文字发明新的权限。

## 安装与初始化

初始化根据完整固定包生成资源、项目导航和最小状态，保留已存在业务内容。安装检查、客户端调用和业务验收分别判断。

### 成果与操作范围

在用户明确指定、已经存在的本地新项目目录安装资源并生成文档骨架；不全局安装或自动接管旧业务项目。

既定方案是完整原生技能安装，未选用软链接或仅放引用入口：前者增加机器路径与链接安全依赖，后者不满足完整说明直接安装的已选布局。包内运行工具、公共资源放`.ai-workflow/`，11项技能只安装到`.agents/skills/<name>/`；不在公共目录维护另一份技能正文。

### 命令与结果

| 命令 | 行为 |
| --- | --- |
| `init --project <dir> --preview [--json]` | 只读列出拟创建文件、AGENTS区块变化及冲突，不创建目录、锁或日志 |
| `init --project <dir> [--json]` | 从已校验的本命令分发包初始化；项目根必须已经存在，无隐式cwd目标 |
| `init --project <dir> --repair [--json]` | 同版本安装的显式修复；只补可确定缺失的框架资源/导航，不覆盖改变的资源或重建已丢失的业务进度 |
| `init --project <dir> --resume [--json]` | 显式继续同版本、同来源的未完成初始化，逐项核对日志及当前摘要 |
| `init --project <dir> --undo [--json]` | 对未完成初始化做有限还原；仅处理本次归属及摘要匹配的写入，不回退已完成安装 |
| `check --project <dir> [--json]` | 只读检查安装清单、运行时身份、受管理资源、AGENTS区块及未完成操作，单独报告状态结构；不更新文件 |

`--preview/--repair/--resume/--undo`互斥，未知或重复参数返回USAGE/2。分发包`check [--package <dir>]`及`validate --state <file>`保留，`--package`与`--project`互斥。安装后的入口为`node .ai-workflow/bin/iterlane.mjs`，默认check定位其所在项目，不能以其他cwd误判目标；安装版init返回明确失败，不把当前项目当成新分发源。

成功沿用`{ok,command,version,data}`；安装结果明确区分`initialized/unchanged/repaired/resumed/undone`，并返回项目路径、包版本、资源检查和`client_validation: not_run`。冲突错误为CONFLICT/7，未完成操作或无法安全恢复为INCOMPLETE/8，其余退出码沿第1步。成功安装只证明安装检查通过，不写“客户端接入成功”或“任务验收通过”。

### 安装清单与文件归属

- `.ai-workflow/manifest.json`记录`manifest_version=1`、`kind=iterlane-project-installation`、安装UUID、包名/版本、源resource-manifest SHA-256、兼容state schema、受管理文件相对路径/字节数/SHA-256、11个本框架技能根，以及AGENTS管理区块标识/摘要。只读取本运行时支持的清单版本和框架身份，不猜测旧手工副本。
- 分发包技能路径映射到`.agents/skills/<name>/`，其余运行时、模板、schema、来源与许可映射到`.ai-workflow/`；分发清单不复制为安装清单。安装版launcher单独生成并纳入受管理摘要。安装清单自身不递归记录自身摘要；来源摘要不是签名。
- 受管理范围为`.ai-workflow/`公共资源和11个技能根中的明确文件；额外文件、缺失、内容变化均报告。其他技能目录及根目录其他资料保留。`.ai-workflow/.local/`只用于机内锁、操作日志及备份，不纳入可分发资源摘要。
- `AGENTS.md`只管理唯一完整的`<!-- ai-workflow:begin -->`至`<!-- ai-workflow:end -->`区块；区块外说明按字节保留。重复、嵌套或不配对标记、未知来源旧区块、区块内改变都停止；首次无区块时追加最小导航。区块摘要单独核对，不用整份AGENTS摘要认领外部文字；备份前/后像必须满足完整区块追加关系，禁止只凭正确后区块恢复任意前像。生成前后文本上限均1 MiB，超过时预检拒绝。
- 模板生成的`docs/`和state属于业务项目，安装清单不把它们当可覆盖资源。首次目标已有待生成的业务文件、已有state或无依据框架目录时返回冲突，不自动认领、合并或重置。无冲突的AGENTS外部说明和其他Skills可共存。
- 为`.ai-workflow/.local/`接入唯一可识别的Git忽略区块，保留已有`.gitignore`内容；重复/冲突标记停止，不修改实际Git索引或配置。忽略声明不意味着文件已被Git忽略或允许提交。

忽略区块使用`# iterlane:begin`和`# iterlane:end`，内容为`/.ai-workflow/.local/`；它与AGENTS区块分别保存前/后像和摘要。

### 初始文档与状态

`templates/manifest.json`决定既定业务目录，随包/已安装副本与运行时内嵌布局严格比较；普通Markdown允许为空。AGENTS由`templates/navigation.json`渲染实际版本，`templates/project/AGENTS.md`说明生成入口；state示例已采用v1，实际初始化生成UTC和basis。

实际建立`docs/iterations/000-foundation`后生成state v1：`revision=0`，`current_iteration=docs/iterations/000-foundation`，`current_task=null`，`phase=clarify`，`status=not_started`；等待/断点为null，确认/阻塞为空，updated_at为实际UTC时间。basis只记录实际生成并回读的最小业务导航/任务文件摘要，不包含state自身，不预置批准或通过记录。生成后通过现有`validateStateYaml`回读校验。

同版本重跑保留state、全部业务文档、AGENTS区块外内容及其他Skills；完整时返回unchanged，不增加state revision。缺失框架资源先报告，仅显式repair补齐；改变/未知资源不覆盖。state缺失、损坏或进度引用缺失不得按“初始状态”补建，返回未完成/冲突，状态恢复留第4步。不同版本一律停止，升级不通过init隐式完成。

### 写入、中断与有限恢复

1. 只读预检包、现有目录、每级路径、目标冲突及历史操作；拒绝UNC、链接/重解析点越界、大小写/Unicode路径冲突和无支持依据的目标。临时资源准备和校验完成后才进入目标写入。
2. 项目内`.ai-workflow/.local/write.lock`用独占创建；记录操作UUID、该操作稳定的随机nonce、当前持锁PID和时间。恢复重取锁沿用同一操作nonce，避免新锁与旧日志交接中断后永久不匹配。另一工具进程直接失败；残留锁不能按年龄删除。只有关联日志合法且原PID确定不存在时，显式resume/undo才可核对并处理；PID仍存在或权限导致不可判断时保留锁并报告。PID复用导致保守停止，不冒险认定原进程已退出。
3. `.ai-workflow/.local/operations/<uuid>/journal.json`保存日志版本、项目绑定、包身份和源摘要、实际创建目录、逐文件前/后像及状态；以Base64保存本次前/后像，并逐字节与源/当前文件比较，不备份整个项目。日志字段和所有路径严格检查，不从日志中的权限文字推断新授权。
4. 先写可恢复日志和前像，再逐项核对当前内容。目标临时文件路径绑定操作UUID；日志在创建临时文件前登记当前临时写入的路径、镜像、字节数及SHA-256，flush、回读、替换后更新状态。恢复时仅清理该已登记文件且其内容等于完整预期镜像或一次未完成写入的前缀；其他变化停止保留。日志自身未发布的临时文件留在本次`.local/operations/<uuid>/`，后续使用新临时路径，不把机内残留当资源或自动删除。替换失败不先删除原文件；每次处理AGENTS/忽略区块前重新读取外部内容，保留区块外修改，区块内冲突停止。
5. 先写资源和业务骨架，再生成并回读初始state；最后在全部资源/区块及状态检查通过后写正式安装清单并提交操作。操作未提交时check返回INCOMPLETE，清单存在也不能掩盖未完成日志。
6. resume把实际文件与前/后像核对：等于后像则保留，等于前像或本来不存在且尚未写入则继续，其他变化均停止。undo只还原后像仍匹配的本次写入；本次新建且未改的文件才允许删除，新建目录仅在日志归属明确且为空时移除，业务新增内容和项目根始终保留并报告残留目录。部分undo只能继续undo，不能被resume重新创建。撤销未完成repair会回到原安装的不完整状态，不谎称已卸载；正常已结束操作再次resume/undo拒绝，不重写文件。资源已提交但锁清理中断时只完成已核对的锁清理，不重置业务state。

自动resume/undo的起点是完整准备日志已持久化。此前只允许创建机内元数据目录/锁，不允许写资源、管理区块、业务骨架或state；若在此阶段终止且没有有效归属日志，下一次返回未识别残留/阻塞并保留现场，不能自动认领或清理。

本轮实现初始化操作的继续/有限还原，不实现通用state转换、doctor、升级或回退。锁只约束本工具进程；外部编辑的检查与替换仍可能竞争，不宣称强隔离或跨目录原子事务。强制终止、写入错误和占用分别实测，断电/磁盘损坏不作绝对恢复保证。

### 验证与交付门槛

在中文/空格新临时项目，从真实npm包解包后执行初始化；离开源码、无node_modules、禁止网络，安装入口可check和validate。验证初始state未预置验收；同版本重复不改进度/业务/其他Skills；缺失修复、改变拒绝、未知/不同版本停止；AGENTS和.gitignore区块外改动保留。

逐写入阶段注入失败及真实终止子进程，证明未完成操作可识别、resume或undo按摘要执行；并发工具拒绝、残留/损坏锁和日志拒绝、前像/后像之外变化保护、链接越界和路径混淆拒绝均需实际断言。CI新增相关必测文件，继承62项检查全部回归；独立源码审查及必要修复后交用户验收。客户端发现/行为属于第3步，本轮安装结果明确not_run；不拼成完整框架通过。

已对本方案执行一次只读独立实施者检查；唯一需明确的启动中断边界已补入上述规则。检查结论只针对方案可规划性，不是实现、测试或用户确认。


## 客户端接入

采用宿主原生项目导航和技能发现，正常请求按需读取入口与必要参考，不增加后台路由服务或专用hook。

- 项目根AGENTS指向安装资源与业务资料；查询先核对资源及实际任务，不写状态。
- 真实客户端调用与安装检查分别验证，不能从文件齐全推定模型调用成功。
- 读取、路由和等待边界由实际事件与前后文件核对；未知行为或连接失败如实保留。
- 模型验证显式运行并固定条件，普通CI只运行确定性检查。

## Git行尾保护

项目`.gitattributes`管理区块为指定框架、状态及内容依据路径关闭文本转换，保留区块外原文。普通代码和外来技能沿原Git规则，不修改全局Git设置；自定义filter或更高优先级属性需另行核对。

区块纳入预览、同版本repair和中断恢复。日志使用`before_sha256`区分不存在与空文件；写前核对原字节及区块外变化，不认领未知文件，也不通过行尾归一化放宽摘要检查。业务内容依据路径的保护随状态操作更新。

## 项目安装布局

项目根AGENTS引导Agent，`.agents/skills/<name>/`放完整Skill/NOTICE与必要公共参考；`.ai-workflow/`放运行库、清单、schema和恢复元数据。业务资料放`docs/project`、`docs/iterations`、`docs/workflow/state.yaml`与`docs/releases`，由业务流程维护，不是资源repair可覆盖的文件。

## 初始化与失败恢复

采用已实现的第2步协议：从固定完整外部包安装到明确已存在的新项目目录，先预览和归属检查；同版本完整重跑unchanged，缺失须显式repair，改动/混用/无归属冲突停止。恢复只处理合法日志绑定的同一操作，未知锁/日志、外部修改或来源不匹配时保留现场。

## 框架升级

已实现的相邻版本协议见本页第6步：用户主动发起、默认当前任务验收收尾后执行，预览差异，精确绑定revision及operation-id；保留后来业务/state，不通过repair换版本。首个支持路径0.3.0-dev.5→0.3.0-dev.6→0.3.0-dev.5，任意历史版本与复杂迁移另行设计。

普通升级只更新框架资源、必要导航/attributes及机内历史；涉及业务源码/依赖变化先单独说明范围并确认。来源不明、混合版本、改动资源及不兼容情况明确拒绝；成功/失败与用户验收分别记录。

## 规格与验证记录

state仍为v1，workflow-record和语义日志支持v1/v2，旧定义及默认门槛保留。以下扩展处理规格增量、验证政策与同步；实际支持范围见[验证记录](../../tests/README.md)。

### 新接口与确定性操作

| CLI | 输入和输出 |
| --- | --- |
| `spec check [--project <dir>] --json` | 只读格式、身份、生命周期、delta/任务/场景引用；问题列出path、record_id、code及消息 |
| `spec sync [--project <dir>] --iteration <path> --task <id> --request-id <id> --expected-revision <n> [--preview] --json` | 单任务已验收增量；preview返回目标前后摘要/动作且零写，执行返回operation_id、revision及sync_ref；与state/日志一致 |
| `skills check --package <dir> --json` | 只读完整资源、capability映射、包内参考和共享摘要；完整安装check调用同一检查 |

沿现有JSON错误结构：参数错误2、环境3、包/依赖4、格式/记录5、IO6、冲突7、未完成操作8；保持含义，不以退出0掩盖invalid。正常同步状态为applied/already_applied，拒绝无写入；recover继续沿准确operation-id、revision和明确resume/undo模式。

workflow-record v2继续现有JSON围栏与source字段；task/check/review/closeout增加规格或轻重字段，新增spec_delta归scope、spec_sync归verification。spec_sync及progress/checkpoint只由工具生成；所有新属性严格校验，不修改v1定义去接受新语义。对来源和独立性仍不做真实性认证。

v2 sync作为新的语义action进入workflow操作计划，operation_version升级为2；新增v2 workflow日志校验/解码器，v1原日志按原规则恢复。规划器、apply及recover使用同一语义重建，规范化输入后重新计算读集合和精确前后像；state文件仍为每个计划最后一项，revision只递增一次。新action拒绝正在进行的安装/版本/状态操作，共用现有write.lock。

v2计划除文件reads外保存`inventories`：本次扫描的spec/迭代记录路径集合，项为`{root, paths, sha256}`，paths为排序的相对安全路径，sha256为其canonical JSON摘要。准备/执行核对成员变化；虚拟后像检查使用原集合加本计划新文件，恢复重建前像集合时扣除本操作明确新建文件，出现外部新增/删除成员则拒绝恢复并保留。目录枚举与文件read均经过同一虚拟视图，避免新规格在apply/replay时被漏扫或重复解析。

容量在计划阶段核对：新目录与已有目录共同受原1000目录上限约束；v2日志按64MiB读取边界预留临时镜像、有限undo及目录元数据空间。过大的计划拒绝于业务写入之前，日志发布也核对自身长度；不通过写出更大的文件绕过读上限。

收据、spec与生成记录的变化须同步更新basis和精确attributes保护；原始业务内容仅在明确delta范围内写。日志读取先分版本和操作类型，未知版本/未完整准备/来源不明保留并报错，不能用通用refresh掩盖坏收据或未声明spec变化。

### 兼容与交付边界

- 新包安装到明确的新项目；templates继续普通业务Markdown为空，state最小有效，不预置业务ID、确认、任务或示例delta。
- 新运行时支持读取v1及v2记录；v1仍用原门槛，不因资源更新自动升级旧任务或重写验收事实。新sync仅对v2任务有效，v1任务报告需要明确迁移，不自行转换。
- 旧相邻路径及固定包保持原版本；当前新项目包不支持从旧项目直接升级或自动迁移v1任务和旧规格。未知入口或不兼容数据明确拒绝，迁移另行确定范围并验证。
- 新schema、共享manifest和生成参考纳入构建、package/安装完整性检查及同版本repair，固定来源/完整许可随包。不将业务spec_delta或同步结果归资源repair所有。
- runtime路由靠宿主原生发现和Agent判断，skills check验证依赖。未安装的provider、必要参考损坏必须可诊断；不另建服务、hook或权限沙箱。
- 安装包用于内部试用。Git、生产和全局配置操作需要各自授权，版本或资源操作不代替这些授权。

已完成范围与后续边界见[开发路线](../roadmap.md)；新增依赖、路径体系或兼容范围仍按已有规则确认。
