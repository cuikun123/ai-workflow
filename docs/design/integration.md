# 框架接入与运行机制

## 三个层次

1. 框架接入：把入口与完整能力资源接入目标项目，建立可读取的导航和状态。
2. 项目地基：澄清方向、确认方案、建立业务工程并实际验证。
3. 持续迭代：逐轮开发业务能力，更新当前资料和保存历史。

前期讨论曾混淆接入与地基，已明确需要分开设计。

## 当前推进方向

首版 Skills 加轻量脚本，保留演进为独立 CLI 加 Skills 的边界。长期也可研究插件分发。

已确认：每个业务项目保存完整能力包，包含该能力包所需的 Skills、脚本、模板与检查规则。不能只复制 SKILL.md 而遗漏脚本、模板或相对引用。

已确认：项目固定框架版本，日常使用不自动跟随新版；升级由用户主动触发，升级前检查差异与兼容性，并保留业务资料与迭代进度。

D104已确认升级影响边界：普通升级只更新框架管理的资源和必要导航，不顺带修改业务代码；必要导航限于框架接入部分，已有业务说明和用户修改继续保留。更新安装包中的模板资源，不表示覆盖模板生成的真实业务内容，其归属仍按D20。新版Skills及检查规则可能影响之后AI的开发与验证方式，不承诺所有升级完全零影响。确需修改业务代码、依赖或构建配置时，单独说明原因、范围及验证方式，经用户确认后处理，并沿既定验证与验收规则执行。冲突及恢复按D26、D27。D105确认框架升级作为独立任务，便于单独检查、追踪和回退，沿用既定设计、计划、验证、验收和Git流程，检查按实际升级影响选择；任务安排仍遵循默认单轮推进及已有确认规则。

D106确认在升级任务的既有文档中记录升级前后的框架版本，沿任务与验证文档职责保留版本关联，不新增平行记录体系。主Agent核对实际项目版本，将拟升级目标与升级后实际版本按事实区分，无法核实时保留未知；记录不代替版本一致性检查、运行检查或用户验收。具体版本标识、锁定信息与文件清单格式仍待设计，具体升级、迁移及回退机制尚未实现。

D107确认默认等当前任务验收并收尾后再升级框架，避免同一任务中途改变工作规则。待验收时保持等待，按既定流程完成当前任务的适用收尾后，再安排D105的独立升级任务，并核对具体升级范围、前置及已有授权；不自动追随新版。用户明确的新指令或确需改变安排时沿已有确认规则处理，暂停切换的保存与恢复沿既定规则，不据此确认中途升级方案。具体升级及回退机制仍待设计、未实现。

项目顶层安装布局和方案一完整技能直接安装已确认，见下文。能力包内部布局、资源定位与引用、打包形式、依赖布局、版本记录、兼容检查、升级迁移与回滚机制尚未最终定义。这些是设计原则，当前尚无对应实现。

D100确认新个人项目的默认Git远端平台为GitHub，已有项目沿用现有平台；首版优先围绕默认平台验证接入，设计上保留其他平台的适配空间。新建仓库默认可见性按D101，远端及主分支默认命名按D102；具体账户或组织、仓库地址、项目目标、工具及执行权限仍须落实，平台选择不表示Git接入、安装器或真实仓库操作已获实施授权。其余Git约定见[Git设计](git-workflow.md)。

D101确认新个人项目的新建仓库默认私有，用户明确要求公开时才公开；已有仓库保持原可见性。接入设计应沿用此默认值并核对实际项目授权，不能据此创建远端仓库或更改已有设置；本次未实施安装器或Git接入。

D102确认新个人项目默认使用远端名`origin`、主分支名`main`，已有项目沿用实际配置；多个远端时明确同步、推送及PR的目标。接入时沿用默认值或项目实际约定并核对具体仓库和权限，规则确认不自动改名，也不表示已创建远端或实施接入。

框架自身的目录不等于业务项目安装后的目录，两者需由后续接入设计映射。

### 技能入口关联方式的比较（方案一已确认）

已确认采用方案一，见 D25。下表保留比较依据，方案二与目录链接方式未采用。需要区分两层：Codex 从约定位置发现技能，以及触发后读取实际操作说明和所需资源。官方技能文档说明先发现名称和描述，匹配后读取完整 SKILL.md，附加资源按需读取；直接安装不等于启动时加载全部技能全文。

| 方案 | 实际技能说明的位置 | 如何接入 | 本项目需解决的问题 |
| --- | --- | --- | --- |
| 方案一：完整技能直接安装（已采用） | .agents/skills/<skill>/SKILL.md 保存主要流程与约束，专属附件可随技能保存；共享资源放 .ai-workflow/。 | 原生技能入口即实际说明文件。 | 安装与升级统一覆盖技能和共享资源，校验跨目录引用、版本与完整性。 |
| 方案二：生成引用入口（未采用） | .ai-workflow/ 保存实际流程；.agents/skills/<skill>/SKILL.md 保存名称、触发描述及读取实际流程的指令。 | 技能被触发后，按入口指令继续读取集中资源。 | 校验额外的读取步骤、入口和正文一致性、资源定位及路径有效性。引用效果需要实际验证。 |
| 目录链接（未采用） | .ai-workflow/ 保存实际技能目录；.agents/skills/ 下通过文件系统目录链接指向它。 | Codex 官方文档支持技能目录链接；链接关联的是实际文件目录。 | 验证目标平台上的链接创建、保留、迁移及失效检查；不能把支持链接当成跨平台安装已通过。 |

三种方案都可以让每个项目保存完整能力包并固定框架版本；一份能力包可安装到项目内多个受管理目录。完整技能直接安装方案不要求在两处各保存一份相同的 SKILL.md，升级清单需要统一管理相关文件。

选择方案一的理由是首版聚焦 Codex，入口即可读到主要流程，较容易检查实际生效内容，并减少入口指引读取另一份主要流程的关联步骤。仍需校验脚本、模板等资源引用。若以后同时支持多个宿主，可评估统一核心流程并按目标工具组装完整技能的维护方式。这是针对当前范围的已确认设计选择，尚无两种方案效果对比的运行证据，尚未运行接入验证。

依据为上文 OpenAI 官方技能文档及 [Codex 技能文档](https://developers.openai.com/codex/skills/)；项目顶层布局和直接安装方式已确认，具体资源管理与一致性检查机制仍待设计。

### 后续多工具支持的演进考虑（建议，待确认）

需要区分框架源码的维护方式和安装到业务项目后的文件布局：完整技能直接安装是对后者的安排，不要求为每个工具手工维护一套独立核心流程。

建议在框架仓库统一维护核心工作流、公共脚本与模板，把工具特定入口、元数据、调用方式和权限说明集中在适配资源中；安装时按目标工具组装或复制完整技能说明到其约定位置。业务项目里仍使用完整技能，不因此变成只指向外部正文的薄入口。具体源文件组织、组装方式和管理清单尚未设计或实现。

该预留可减少未来重复维护核心流程的需要，但不能消除新增工具的接入成本。仍需核对目标工具的技能发现、路径解析、可用操作、权限与子任务行为，并验证同一工作流的实际执行。Agent Skills 标准定义了通用 SKILL.md 结构，也注明部分字段的支持可能因实现不同；格式共通不代表运行行为一致。依据见 [Agent Skills 规范](https://agentskills.io/specification) 和上文 OpenAI 官方技能文档。

上述多工具演进边界是与方案一相容的建议，具体源码组织与组装机制仍待设计；本次确认方案一不改变首版聚焦 Codex 的范围，也不承诺未来零迁移或固定适配工作量。

## 初始化行为草案

- 检查目标目录、已有规则、工作树与接入状态。
- 安装指定版本的完整能力资源。
- 以可识别的管理区块接入 AGENTS.md，保留原有内容。
- 按最新文档决定创建固定空文件，生成最小有效起始状态。
- 检查资源完整性、内部引用、状态结构，并实际验证入口可用。
- 重复执行不清空进度；冲突和失败明确报告；升级与首次接入分别处理。

接入成功不等于地基完成。当前已有业务模板骨架及十一项 Skill 源码，其中 workflow-guide 提供只读定位与恢复交接；初始化脚本、完整安装器和通用状态运行时尚未实现。

### 初始化中途失败的恢复规则（已确认）

用户参考上游调查后已确认采用临时准备与有限恢复的方案，见 D27：

1. 框架资源先准备再安装：技能、脚本、模板先放临时位置检查，再按安装计划写入目标。
2. 保留业务资料、项目进度与用户修改；已有项目文档和协作说明单独处理。
3. 失败时有限还原：只尝试还原本次安装已授权、归属明确且未被用户或外部修改的写入；有冲突或归属不明时保留现场、报告后按 D26 决定修复。
4. 重新检查后恢复：明确标记接入未完成，下次核对实际文件，通过完整检查后才标记成功。

成功项、失败项、实际写入位置和失败原因需要有恢复依据；具体记录位置、格式及保存机制仍待设计。上述为已确认行为原则，写入与中断一致性、恢复步骤和验证场景尚未实现或运行验证。

### 接入成功的判定原则（已确认，D28）

D28 确认以下四条接入验收原则，具体实现保留设计空间：

1. 最小调用：在真实目标工具中完成一次只读入口调用，能正确读取项目状态，且不修改业务内容；具体调用哪个技能随后设计。
2. 版本一致：按项目锁定版本与受管理文件清单检查完整性及内容变化，发现差异先报告；摘要算法不在此时锁定。
3. 结果如实区分：结构与运行检查分别记录通过、失败或未验证；两层均通过后才标记接入成功。只通过最小调用不能证明所有技能或完整工作流通过。
4. 失败按原因处理：先定位原因，不把入口失败一律视为安装损坏，也不因网络或登录问题就回滚文件；涉及安装写入恢复时按 D27 执行。

以下最小调用示例、清单技术方案和结果表示为实现建议；本节原则已确认，安装器及验收能力尚未实现或运行验证。

#### “一次最小调用”的建议定义

在真实目标 Codex 客户端和业务项目目录中，显式调用已安装的只读状态技能，例如 `$myflow` 请求“报告当前工作流状态”。预期该技能能被选中，读取完整 `SKILL.md`，解析最小有效的 `docs/workflow/state.yaml`，并返回其中的当前阶段、下一任务或“尚未开始”；整个过程不创建、覆盖或修改文件。

这是一个低副作用冒烟场景，能验证入口发现、技能说明读取、项目资源定位和只读路径。它不能证明其他所有技能都触发正确、脚本均可执行、AI 判断普遍正确或完整工作流通过。因此，它应与确定性文件检查、脚本测试和后续端到端场景分开报告。若实际实现不提供只读状态技能，需设计等价的无写入最小场景，不为测试而虚构产品入口。

Codex 官方文档说明技能有名称、描述与完整 `SKILL.md`，可以显式调用，并会在匹配后读取完整说明；项目技能从仓库路径下的 `.agents/skills` 发现。文档也建议用提示验证触发行为。引用：[Codex Skills 文档](https://developers.openai.com/codex/skills/)。

#### “版本一致”的建议检查方式

建议在 `.ai-workflow/` 保存项目锁定的框架版本和一份文件清单。清单覆盖初始化器管理的完整技能文件（位于 `.agents/skills/`）、公共脚本、模板及其他框架资源，为每个文件记录相对路径和内容摘要；SHA-256 是候选算法，尚未锁定。检查器根据项目清单核对版本标识、必要文件是否缺失，以及文件内容是否符合该版本清单；检查范围限于本框架管理内容，不将其他来源的技能当作本框架的冲突文件。

检查结果需要分开表达：

- 版本标识符合且摘要吻合：受管理文件与锁定包一致。
- 版本标识符合，但摘要不同：可能是用户修改或文件损坏；标记内容偏离并先报告，不覆盖。
- 受管理文件缺失或本框架管理范围内出现未登记内容：先报告，必要的修复按 D26 决定。
- 版本信息缺失或格式无法读取：版本状态未知，不能推断当前版本。

摘要清单可以检查内容是否偏离记录的版本，但若清单本身可被一同修改，它不证明来源真实性或防恶意篡改。签名与可信来源校验是否需要，留待发布和安全设计确定。具体清单格式尚未确定。

#### 入口验证失败时的建议处理

如果目标客户端实际调用失败，运行结果记录为失败，不能将其降格为“未验证”或“成功”；保留错误证据和当前文件现场，先定位失败范围与原因。调用失败不证明安装文件已损坏，网络、登录等问题不触发一律回滚。确需恢复安装写入时，按 D27 仅对本次安装已授权、归属明确且未被用户或外部修改的写入有限还原。遇到内容偏离、操作归属不明或还原失败，保留现场并报告，按 D26 先决定修复。修复后重新执行结构检查和同一最小调用，全部通过后才标记接入成功。

如果因没有目标客户端、权限或运行环境而无法执行，记为“运行未验证”，不能声称测试通过；结构检查仍可单独报告为“结构就绪”。

结构与运行是分别记录的检查维度，可以同时出现“结构通过、运行失败”或“结构通过、运行未验证”。只有结构检查与最小调用均通过才是完整接入成功。具体状态字段、枚举名称、状态存储位置、错误分类与最小调用场景仍待设计；不能把原则确认写成状态契约或运行时实现已完成。

普通业务占位文档仍允许为空，接入成功也不表示项目地基完成。具体检查清单、最小调用场景及结果表示尚待设计，接入验收检查尚未执行。

## 入口设计方向

统一入口支持开始、继续、状态；专项入口支持单独阶段或能力。专项入口只补齐必需的前置条件。

`myflow`、`$myflow`、`myflow init/check/status/update` 都是讨论示意，不是现有命令或已确定产品名称。

## 单次运行顺序草案

定位项目与规则 → 读取状态与相关资料 → 核对代码及环境 → 确定任务和确认状态 → 执行并按需委派 → 收集验证证据 → 主 Agent 统一更新正式结果与状态。

状态文件不会自行执行流程。AI 指导、确定性脚本、结构校验与工具权限有不同职责。

## 演进为 CLI

AI 方法与工具操作分离；文件生成、检查、状态读取、升级迁移等操作形成可独立调用的工具逻辑。资源通过明确项目根定位，不绑定开发者机器绝对路径。

版本信息、兼容检查、迁移与回滚需要设计，不能承诺升级完全零改动。
