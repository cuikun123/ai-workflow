# 开发流程

本页回答三个问题：**项目怎么推进、开发者何时参与、什么时候可以继续。**

[第一次开始](#第一次开始项目) · [完成一轮开发](#完成一轮开发) · [遇到问题](#中断或遇到问题时) · [发布与后续](#发布与后续工作)

> 本页说明任务如何推进及用户何时参与。规则依据见[决策记录](../decisions.md)，实际支持范围见[验证记录](../../tests/README.md)。

## 流程总览

```text
首次：建立并验收项目地基
每轮：确定目标 → 设计与计划 → 逐任务实现、检查、验收 → 整轮收尾
后续：继续下一轮，或具备条件时发布；使用反馈进入后续目标
```

- **项目地基**：建立最小可运行工程和基础约定，后续可以演进。
- **小迭代**：每轮围绕一个可验收目标，默认同一时间推进一轮。
- **发布**：可以包含多个已完成迭代，不要求每轮立即上线。

### 开发者与 AI 怎么配合

| 开发者 | AI |
| --- | --- |
| 说明目标和业务预期 | 主动调查，提出方案并解释取舍 |
| 确认关键方案、范围及重要变化 | 在已确认目标和授权内自主处理技术步骤 |
| 逐任务验收成果 | 实现、测试、处理必要问题，提供可检查的成果 |

主 Agent 是统筹工作的 AI，负责当前任务、必要协作、正式记录和恢复依据。

**需要确认的变化**：关键范围、设计、接口、数据、安全、成本和交付。小变更可合并确认点，已有适用确认不重复索取。

> 设计确认、成果验收、Git 操作和生产部署各有条件。“继续”、检查通过或同意实施，都不能代替用户验收。

统一入口负责定位和交接，也支持单独请求规划、执行、测试、审查或诊断。只查询进度时，只核对并报告，不启动工作或改写记录。

## 第一次开始项目

开发者可以从一个想法开始，不必先选好语言、框架或开源方案。

| 步骤 | AI 做什么 | 交给开发者看什么 |
| --- | --- | --- |
| 1. 明确目标 | 利用已有信息，澄清场景、限制与期望 | 对目标和起步范围的理解 |
| 2. 研究方案 | 调查可复用方案，比较技术路线，纳入技术偏好 | 推荐、代价与限制 |
| 3. 确认计划 | 检查可行性和关键风险，安排任务与验收 | 起步范围、方案、任务、验收方式 |
| 4. 建立地基 | 确认和授权具备后，建立工程并实际检查 | 可运行成果、检查证据和验收方法 |

设计和计划可以一并确认，不增加重复审批点。建议先用业务语言解释方案，再按需要展开技术依据。

### 地基需要具备什么

- **产品与体验**：方向、范围、验收目标和首轮方向；布局、视觉、加载、空状态与错误状态。
- **工程**：技术和模块边界、API 与数据库约定、开发规范；实际检查启动、构建、测试命令及必要组件连通、数据库读写。
- **质量与安全**：通用完成标准（DoD）、测试、认证授权、敏感数据、日志禁入信息、AI 文件范围和依赖检查。
- **运行保障**：环境、部署路径、日志位置、错误记录、排查方法、资料保存与恢复。

具体内容按项目需要落实。通用完成标准、功能验收和发布条件分别确定；访问限制写进文档，不等于工具已强制执行。

**继续条件**：必要工程检查、审查和逐任务验收完成后，进入首轮业务迭代。只有文档不能算地基完成。

框架安装与入口初始化另见[接入设计](integration.md)。条件缺失时先说明缺项；文件存在不等于接入成功，接入成功也不等于地基完成。

## 完成一轮开发

### 1. 确定本轮目标

**进入条件**：有明确开轮请求；原轮已完成验收、必要检查和收尾，或开发者明确暂停切换。

- 写清本轮交付什么、暂不做什么、怎样验收。
- 候选获准入轮后，在待办保留原条目并关联去向。
- 仍待验收且没有明确暂停的任务继续等待。

创建迭代目录不批准范围或实施。文件准备及项目方向维护见[开轮与项目方向维护](#开轮与项目方向维护)。

### 2. 设计与安排任务

1. **核对依据**：当前有效规格、公共约定和本轮获准变更。新规则只用于对应行为和版本，草案不能覆盖确认。
2. **检查方案**：需求覆盖、可行性、关键风险；重要设计按需引入独立视角。
3. **拆出成果**：每个任务能独立验收，再拆内部技术步骤。
4. **一并确认**：展示整轮任务的成果、边界、验收要点、依赖与顺序，随设计和计划确认。

例如，“新增待办”包含输入、保存、列表展示、刷新后仍存在。接口、页面和测试是内部步骤，不分别等待验收；示例不构成业务需求。

接口、工程或文档本身可独立交付并检查时，也可以作为任务。

### 3. 逐任务实现、检查和验收

每个任务开始时简述成果与边界；计划、依赖和授权具备后，按下列顺序推进。

#### 实现并持续测试

- 按[Git 工作流](git-workflow.md#普通任务的完整顺序)保存改动、同步主线，建立任务分支和独立目录（worktree）。
- AI 自主处理内部步骤，按需求、验收、DoD 和影响选择必要测试。
- 覆盖正常、关键边界和异常行为，不要求开发者逐条选择技术检查。
- 发现异常时，回到原任务内[调试和重验](#检查失败或验证受阻)。

#### 检查最终候选版本

开发完成后提交候选版本，检查对应的实际内容：

| 检查 | 要求 |
| --- | --- |
| 产品效果 | 实际查看、截图并操作网页或应用，核对交互、动态流程和必要数据结果 |
| 自动化测试 | 执行与本次需求、风险和改动相符的必要组合 |
| 独立审查 | 普通功能默认一次；低影响文案或排版可按实际影响简化，高风险按需专项检查 |

PR 合入前的代码审查使用全新独立上下文 Agent。执行者的测试与自查仍须保留，不能只按改动行数降低审查要求。

> WIP 只是保存断点；截图只证明对应画面。缺少工具、环境或独立审查条件时保留缺项，不能用其他检查冒充。

#### 处理审查发现

- **必须修复**：主 Agent 核验后，在原授权内修复、重验并独立复查。
- **改进建议**：不违反当前要求的命名、重构和优化，默认不改、不建任务、不阻塞交付。
- **待核实**：补查证据，关键验收、安全或数据疑点未排除时不能判通过。

不设最低发现数量，也不因反复修改或达到轮数就自动通过。独立性、证据要求及修复闭环见[审查分工与反馈处理](multi-agent.md#独立审查与反馈处理)。

#### 交付并等待验收

**提交条件**：必要范围已检查、必须修复项已关闭、关键未知已处理，证据适用于当前候选版本。

交付材料包括：

- 成果位置、体验入口或可检查产物。
- 必要准备、操作步骤和预期结果。
- 简短检查结论、证据、已知限制与未验证项。

材料须能实际使用，不虚构服务、账号或结果。按适用权限在交付验收时创建 PR，集中展示候选改动；检查与验收记录见[记录规则](state-contract.md#验证与验收记录)。

> **提交后暂停下一任务，等待开发者明确通过。** 未通过就在当前任务内处理反馈、重验并重交；新增需求或实质变化另行确认。

实施、AI 检查、提交验收、用户验收分别记录。用户验收也不能把必要检查的失败或未执行改为通过。

### 4. 收尾并检查整轮衔接

**每个任务验收后：**

1. 记录对应成果的验收事实，核对必要检查和审查。
2. 只同步实际交付的业务规格变化；无业务变化不机械改规格，公共约定按自身确认和生效时点更新。
3. 仓库、远端、主分支和权限明确时，完成同一范围的[Git 自动收尾](git-workflow.md#验收后的自动收尾)。
4. 收尾完成、后续前置和授权具备后，再接续下一任务。

仅文档收尾补一致性检查；内容、环境或主线变化后补受影响检查，影响已验收行为时重新验证并验收。有效测试事实可复用，旧审查不能替代该轮全新判断。

**整轮结束前：**

- 检查跨任务调用、端到端场景和需求覆盖。
- 核对配置、数据兼容、文档及整体证据。
- 原要求未满足时，回到受影响任务修复、重验并重新验收。

逐项通过不能直接当作整轮通过。收尾受阻时保留验收事实、后续修改和恢复条件；必要检查有缺项时不合入，也不记为全部完成。规格同步步骤见[当前内容与历史](documents.md#当前内容与历史)。

## 开轮与项目方向维护

主 Agent 使用 `clarify-design` 承接明确的资料准备请求；入口只定位交接，计划归 `plan-tasks`，执行收尾归 `execute-task`。

### 准备新一轮

**前置条件：**

- 已有业务项目，用户明确要求开轮或相应资料整理。
- 原轮完成验收、必要检查、规格收尾和整轮衔接检查；或用户明确暂停切换。
- 原任务待验收且未明确暂停时，继续等待；只讨论或查询时不初始化。

**准备顺序：**

1. 核对项目、目标目录和已有确认。
2. 创建既定 `scope.md`、必要的 `design.md`，以及可为空的 `tasks.md`、`verification.md`；计划与证据随后由对应阶段填写。
3. 保留适用确认，未确认部分标作草案；目录创建不批准范围或实施。
4. 候选真正获准入轮后，在 `backlog.md` 保留原条目并关联新范围。

命名沿项目约定；无约定时可建议三位编号加短名称。普通名称冲突在授权内选不覆盖资料的名称，归属歧义先澄清。

### 暂停、切换与返回

1. 在原 `tasks.md` 保存确认依据、日期、目标路径、未完成事项、原验收状态及恢复条件。
2. 先保存现轮暂停，再准备新轮或记录旧轮恢复；新 `scope.md` 关联原轮收尾或暂停依据。
3. 依赖记录写入失败时停止后续切换，分别保留已写现场和未完成部分。
4. 恢复依据是明确确认及实际资料，不能凭“唯一未标暂停目录”、最大编号或修改时间推定。

明确切回旧轮的指令可同时作为现轮暂停和旧轮恢复依据，不重复索取相同确认。部分写入、冲突或缺失保持未知，只澄清受影响部分。

紧急修复沿用同一结构，记录必要范围、方案、任务与证据；可预先约定修复验收、发布、主线处理和清理后返回。条件具备时直接恢复原状态，待验收仍等待。具体顺序见[线上故障处理](#线上故障处理)。

### 维护项目方向

- 项目方向已确认、文档写入授权具备时，首次填写或更新 `overview.md`；没有当前迭代也可响应明确维护请求。
- 文件缺失但项目目录及归属明确时，可创建该文件，不补建整套结构。
- 记录已确认方向无需等功能验收，但不能把未来目标写成已交付能力。
- 未确认方向留在对话、待办或设计；普通迭代不机械改项目概览。

非紧急问题默认进待办，明确纳入本轮时关联范围。原任务未满足要求的问题留在原任务修复，不转入待办推迟。

## 中断或遇到问题时

### 信息不足或范围变化

| 情况 | 怎么处理 |
| --- | --- |
| 资料有缺项 | 在授权内先补查，只问影响本次工作的未知信息；不把代码现状当成业务预期 |
| 开发者拿不准 | 给选项、推荐和影响；建议保持待确认，不依赖缺项的工作可继续 |
| 普通技术调整 | 在当前目标和授权内自主处理 |
| 原要求遗漏或必要修复 | 留在当前任务补齐，不转入待办推迟 |
| 新增目标 | 默认进入待办；纳入本轮前确认范围调整 |
| 任务拆并、成果或验收改变、交付次序受影响 | 先说明原因、前后对比和影响，确认后执行并记录 |

不能合并下一任务来绕过验收等待，受影响的未知结论不能提前判通过。

### 检查失败或验证受阻

**异常调试顺序：**

1. 明确症状并复现，取证并对比正常路径。
2. 用最小实验验证原因，区分事实、假设和已验证原因。
3. 针对原因修复，完成回归与审查，返回原任务。

没有新证据时停止叠加补丁，未复现或修复未验证如实说明。

**检查运行不了时：**

- 先查环境与依赖，在授权内解决准备问题。
- 额外费用、凭据、真实数据、重要环境变更或验收标准调整需要开发者决定。
- 仍受阻则记录未执行项、原因、补齐条件和下一步，继续不受影响的检查。

不能降低标准、把模拟当成真实集成通过，或仅因验证受阻就认定实现已完成。

### 暂停与恢复

| 时点 | 必须保留或核对的内容 |
| --- | --- |
| 明确暂停、切换或遇到需要用户决定的阻塞 | 保存允许入库的改动，记录断点、未完成事项、原验收状态和恢复条件 |
| 远端与推送授权明确 | 备份并核对结果，本地提交与远端备份分别报告 |
| 合并冲突需要用户决定 | 保留现场、暂停该目录继续写入；不强行提交或清理，记录受阻时先在对话交接 |
| 恢复工作 | 核对导航、原任务、已有确认、实际文件和环境，简述目标、位置与下一步 |

`state.yaml` 只是可能过时的书签，不能凭聊天新旧、最大编号或修改时间猜当前轮。明确新指令优先核对；目标冲突先澄清，前置和授权具备才接续。

- 原任务待验收：恢复到等待验收。
- 没有当前轮、下一目标明确：按已有确认接续。
- 目标未定：从项目方向和待办推荐候选，由开发者选择；无候选时主动问清。

保存与替代方案的具体条件见[Git 规则](git-workflow.md#暂停阻塞与方案替换)。“继续”不批准未展示的方案。

### 单独测试、审查或诊断

1. 优先采用指定范围；未指定时结合当前任务和改动定位，存在歧义先澄清。
2. 只补本次必需前置，按实际检查范围给结论。
3. 完成后返回原工作；无适用迭代时在对话交付，不另建迭代或报告体系。

**操作边界：**

- 仅审查：检查并报告；没有适用修复授权时不自动修改。
- 仅诊断：读取获准资料，可在不影响实际项目和真实业务的隔离环境复现，逐步核对副作用。
- 修改代码、配置、真实数据、重启或发起有业务效果的请求：须有对应授权。
- 已有明确修复授权：直接完成修复、验证和验收交接，不重复询问。

## 发布与后续工作

### 发布准备与执行

**先准备好**：目标环境、版本与产物、操作步骤、上线检查、回滚路径及数据恢复方式。

| 条件 | 执行方式 |
| --- | --- |
| 路径明确、可恢复且授权适用 | AI 部署并上线检查 |
| 新环境、费用、重要迁移或授权不清 | 先给具体方案，由开发者决定是否推进及由谁执行 |
| 开发者亲自执行 | AI 提供产物、配置、步骤和检查方法，协助核验实际结果 |

发布使用已验证提交的固定标签和对应产物，标签存在不等于上线成功。发布约定归 `operations.md`，实际结果归 `releases/` 及验证记录；版本保留见[Git 工作流](git-workflow.md#发布版本与线上补丁)。

### 发布失败处理

> **先按事前明确且本次获准的方案回滚并核验，再报告，等待开发者决定是否重试。**

1. 不为完整排障拖延回滚。
2. 报告问题、原因依据、回滚结果、当前状态和建议；未知原因保持未知。
3. 回滚无法执行或失败时及时说明，不宣称已恢复、不继续盲目操作。
4. 不自动重试或重新部署，一般部署授权不能越过重试等待点。

代码回退不代表数据恢复。具体报告格式和诊断工具仍待细化。

### 线上故障处理

**先问清 → 再调查 → 确认方案 → 修复与验证。**

- 先询问必要信息、明确问题和范围，再在访问授权内调查；已知信息不重复问，不能先查到缺项才问。
- 报告证据、假设、未知项和方案；具体方案获同意后才修复。
- 故障反馈不自动批准修复，修复同意不自动覆盖生产部署或数据操作。
- 发布失败的回滚规则，不扩展为所有线上故障一律立即回滚。

**操作建议**：按缺项了解环境、影响、实际与预期、时间规律及近期变化，默认只读调查；有副作用的操作核对授权。可隔离复现时避免让用户在生产反复触发，不设置固定必填表。

**紧急问题**单独开小修复轮，先保存并暂停当前开发，切换时约定返回原轮。补丁从线上实际版本起步：

1. 完成必要测试、独立审查、用户验收和记录。
2. 按授权发布，确认线上恢复。
3. 确保主线覆盖修复，保留实际发布版本与必要产物。
4. 清理后核对返回约定、原状态及授权；无新指令或阻塞、前置满足时恢复。

补丁不夹带主线未发布功能。主线处理受阻时保留现场并分别报告，不能宣布整体完成；原任务待验收则恢复等待。分支与发布细节见 Git 工作流。

非紧急问题默认进入待办，明确要求本轮处理时再调整范围；当前任务未满足原要求的问题仍在原任务修复。

### 使用反馈与下一轮

- 模糊反馈先澄清场景、困扰和期望，整理到待办或本轮范围。
- 不要求用户先写完整需求，也不擅自补成确定功能。
- 理解或记录反馈不批准开发；后续回到目标、设计与计划。

框架版本固定，日常不自动跟随新版。默认当前任务验收收尾后，由用户触发独立升级任务；差异、兼容性、前后版本及保留要求见[框架升级](integration.md#框架升级)。

## 任务轻重与加载方式

本页既有流程仍为当前运行规则；[地基上下文与绑定](state-contract.md#地基上下文与任务绑定草案)和[多客户端接入](integration.md#多客户端与用户包设计草案)已获准实施、实施中；地基与任务门槛尚未启用。

本节说明任务深度和记录校验，供维护者、适配者与执行任务的 AI 核对。日常使用可以先读[使用指南](../usage.md)，无需手工选择或填写内部字段。

### 按任务影响选择流程

AI 根据业务未知、影响范围和恢复代价选择流程，保留适用的测试、业务确认、用户验收和 PR 独立审查。简化读取不取消这些条件。

`execution_mode` 表示这个任务采用的流程深度：

| 取值 | 判断条件 | 执行方式 |
| --- | --- | --- |
| `direct`（直接） | 明确且低影响的文案或排版、已有任务内普通技术步骤，或独立只读请求；容易撤销，无业务、接口、权限或数据规则变化 | 读取最小入口和适用约定，直接处理并必要核对；不强制专项全文、独立方案文件或重复提问 |
| `light`（轻量） | 行为与验收明确的局部功能或普通修复，风险已知且有可执行验证 | 读取相关方法；简短方案与计划可联合表达，补受影响验证 |
| `full`（完整） | 业务不清、跨模块或接口、认证授权、数据迁移、安全、费用、部署或难以恢复的变化 | 按需澄清、设计、计划，执行专项验证与审查 |

不按代码行数或用户说“简单”降级。直接流程发现业务变化时升为轻量；关键未知或高风险出现时升为完整。AI 说明触发原因，必要确认沿用既有边界。显式指定技能时，先读入口，再按条件展开参考。

无适用迭代的独立只读或低影响资料请求在对话交付，不为满足结构创建迭代。业务行为变化必须进入适用迭代并关联需求与增量；已有任务内部步骤沿原授权推进，成果边界保持。新任务仍需真实范围和计划确认，简化流程不能从模糊指令生成批准。

### 任务声明要检查什么

workflow-record v2 是第二版结构化工作记录，和框架包版本、state v1 状态格式分别编号。v2 的 `task` 是任务记录，`definition` 是用于内容绑定的任务定义；进度和检查结果不属于该定义。

任务声明流程深度、选择理由及 `verification_policy`（验证政策）。政策说明这个成果交付验收前必须满足哪些检查和审查：

| 字段 | 含义与约束 |
| --- | --- |
| `execution_mode`、选择理由 | 流程深度和基于实际影响的理由 |
| `scenario_refs` | 本任务关联的需求与场景身份，供检查记录引用 |
| `verification_policy.required_check_types` | 必需的检查类型；非空，至少一种，全部须有适用的通过记录 |
| `verification_policy.required_scenario_refs` | 必测场景，必须是任务 `scenario_refs` 的子集；每项至少由一个适用检查覆盖 |
| `verification_policy.review_mode` | 验收前审查采用 `independent`（独立）或 `simplified`（简化） |

政策随任务定义绑定真实计划确认。政策或定义发生变化时，原确认必须重核对，不能只换字段继续沿用旧批准。

普通业务功能和高风险任务默认独立审查。简化审查仅用于低影响非业务变更；不能称为独立审查。PR 合入前的独立代码审查另外保留。

### 检查和审查记录怎样表达

v2 的 `check` 是检查记录，`check_type` 区分三种检查：

| 类型 | 必须提供 | 通过条件 |
| --- | --- | --- |
| `test_suite`（测试集） | 实际命令、`exit_code` 和 `test_count` | 退出码为 0，测试数至少 1 |
| `command`（命令检查） | 实际命令和退出码，测试数为 `null` | 退出码为 0 |
| `observation`（实际观察） | `method` 方法、`expected` 预期、`actual` 实际结果和 `evidence` 产物证据；命令、退出码和测试数均为 `null` | 有适用的真实观察及证据 |

`result` 区分 `passed`（通过）、`failed`（失败）、`not_run`（未执行）、`not_applicable`（不适用）。必需项失败、未执行或不适用时，不能提交验收。不适用项要给理由，不能用来覆盖必需项。

每类通过记录绑定同一候选 `artifacts`（实际产物及内容摘要）；`covers` 表示实际覆盖的需求和场景身份，非业务检查可为空。记录只覆盖真实证据，不因填入“通过”就证明检查执行。

v2 的 `review` 是审查记录。其 `mode` 必须匹配任务政策，`must_fix_open`（未关闭的必须修复问题数）为 0，结果为 `passed`。独立模式还要有真实独立 `context_id`（来源上下文标识），由主 Agent 核对来源；简化核对不得冒称独立审查。

检查、审查和用户验收分别记录。框架 CI 的非零测试数和必测文件门槛保持，不能用业务观察记录绕过框架测试。

### 旧记录与确认失效

流程深度由 AI 按技能清单和项目事实判断；工具核对声明、确认、记录与证据的一致性，不能证明业务风险判断绝对正确。v1 和未声明新政策的 v2 保留测试集与独立审查默认要求。新模式只对匹配新包且明确声明政策的记录生效，不自动迁移旧项目。

显式验证政策与计划确认的绑定失效时：

- `spec` 和 `status` 报告 `STALE_PLAN_CONFIRMATION`，表示当前政策不再被原计划确认覆盖。
- `status.policy_confirmation_current=false`，诊断位置为 `stale`（依据过时）；缺失或拒绝也说明原因。
- 只读提示不会批准新政策。仍可使用正常登记记录、重新进入检查、等待或登记真实计划确认的路径。
- 实际验收、同步规格和完成任务时，重新核对计划与候选，不能借新增记录绕过旧确认。

实际检查范围见[验证记录](../../tests/README.md)，记录格式和场景身份见[规格契约](spec-format.md)。
