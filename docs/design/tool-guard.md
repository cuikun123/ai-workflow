# 共享工具门槛设计

本页供框架维护者和客户端适配者确定工具操作的前置条件、接口与验证方式。目标是让不同客户端复用同一套判定，拒绝已识别的流程跳步。实施安排见[开发路线中的共享工具门槛安排](../roadmap.md#共享工具门槛实施安排)。

## 方案与范围

本设计采用共享判定内核，客户端只负责取得实际工具参数、调用内核和执行结果。

| 做法 | 取舍 |
| --- | --- |
| 只加强技能说明 | 能指导主动衔接，但原生工具仍可能跳过检查 |
| 共享判定内核与客户端执行包装 | 可统一拒绝已识别的越界操作，适合作为本轮方案 |
| 操作系统与远端强制隔离 | 可以增加更强的限制，需要独立的环境、权限与部署设计 |

本轮只提供共享内核、结构化请求接口、命令行入口、完整包资源和确定性验证。不实施 Pi 或其他客户端扩展，不安装到真实项目，不实现任意命令解析或操作系统沙箱。客户端接入沿[接入设计](integration.md#多客户端与用户包设计草案)另行推进。

共享门槛不创建任务，不批准计划，不登记用户验收，也不执行被检查的操作。技能仍负责主动推进；门槛只检查操作是否具备条件。业务和 Git 规则继续以[工作流](workflow.md)、[状态与记录契约](state-contract.md)及[Git 工作流](git-workflow.md)为准。

## 信任边界

适配者必须把实际执行参数交给内核，不能只提交 AI 自报的操作类别。

项目根目录由受控入口确定，不从模型请求切换。文件参数使用项目相对路径；命令参数使用可执行文件和参数数组。原始 shell 字符串不在本轮允许的接口内。

工具能核对记录、引用和候选是否一致，不能认证消息真实来自用户、检查实际执行或审查真正独立。来自宿主的额外依据也必须标明来源；接口一致不代表来源可信。

允许结果只对当次参数和读取到的事实成立，不是可重复使用的权限令牌。实际执行前必须重新核对参数、文件、状态和 Git 引用。外部编辑与多文件操作的限制见[版本与支持范围](../releasing.md)。

## 记录与授权

本节将操作范围放回既有任务与确认记录，不新增授权文件或状态账本。

任务声明增加可选的 guard_policy，表示供共享门槛核对的执行范围：

| 字段 | 含义 |
| --- | --- |
| workspace | worktree_root、git_common_dir、task_branch、main_branch，分别记录工作目录、仓库公共目录、任务分支和主分支 |
| write_paths | 允许修改的项目相对路径；每项明确是单文件还是整个子目录，不使用自由通配符 |
| closeout_paths | 已批准的普通收尾文档路径；不包含状态、机器记录、有效规格、地基及范围、设计、任务定义 |
| commands | 已约定的工程命令；每项包含 executable、executable_sha256、argv、cwd，分别表示实际可执行文件、文件摘要、参数数组和相对工作目录 |

guard_policy 属于任务定义，必须被计划确认覆盖。修改它使用既有任务修订流程，使受影响的确认和绑定重新核对。不能通过降低流程深度省略它，也不能把参数由模型自报当作范围已确认。

需要独立操作授权时，在既有 confirmation 记录中，为 operation_authorization 增加 operation_scope。其 actions 列出获准操作；git 使用 git_common_dir、worktree_root、source_branch、remote_name、remote_url、target_branch 指定准确对象。binding 明确取 task 或 candidate：task 绑定任务定义与操作范围，candidate 另绑定固定提交。范围不匹配、被拒绝或被取代时，原授权不能使用。

候选变化会使旧 allow 与受影响证据失效，但不会自动取消仍适用的任务范围授权。固定候选授权必须重新核对。仅文档收尾的新提交可以沿原任务授权保存和推送，不把这项许可扩为新增业务行为或主分支直接推送。

没有适用迭代的独立文案请求，不创建 confirmation 或业务迭代。受控宿主通过 independentRequestObserver 提供当前明确请求、项目根、准确路径和前像摘要；只允许非业务文案，受管理记录、规格、地基和协作规则不走这条例外。模型请求不能提供 observer。命令行没有此观察时返回 unknown，不另建许可文件。

### 无任务时的规划与输入准备

规划资料和语义操作输入可以在任务登记前准备，不能要求尚未存在的任务定义、计划确认或绑定。

受控宿主通过 preparationRequestObserver 提供明确准备请求、来源引用、项目根、当前迭代、准确路径和前像摘要。purpose 取 planning 或 workflow_input。该观察只放行准备类资源，不批准实施，也不把规划文本当作已经登记的任务。

- planning 只允许本次明确迭代中的 scope、design、tasks、verification 普通正文初始化或修订。已有机器记录保持原样；已有任务被选定后，不用这条准备分支改变已批准定义。
- workflow_input 只允许在 .ai-workflow/.local/inputs/ 准备单个 JSON 输入文件。内容必须是已有语义操作协议支持的对象，不含可执行脚本；创建文件不等于批准对象或执行其中操作。
- 执行 workflow.apply 时仍使用既有操作的真实前置校验。任务、确认的初次登记不要求任务已启动；start、绑定、验收与收尾各自保留原门槛。原框架计划检查不能被这条准备分支绕开。

这两类请求的 task_ref 为 null，expected 只核对适用的实际 revision 和文件前像，不要求任务定义或绑定快照。准备迭代文件不创建 state、根协作规则或框架资源。未取得宿主观察的命令行返回 unknown。输入目录只保存临时机器输入，不保存另一套批准、任务或进度。

同一条真实用户消息可以形成范围、计划和适用操作授权的不同引用，不增加重复确认点。实施者先核对原消息究竟批准了哪些对象，不能自动生成批准。

guard_policy 和 operation_scope 是既有记录结构的可选扩展，新工具校验声明、修订、定义摘要和确认绑定。旧工具的严格结构可能拒绝新字段，因此使用新字段的项目必须固定匹配的新包；本轮不承诺回到旧工具仍能处理这些新记录。

旧记录保持原格式和原工具含义。共享门槛检查写操作时，缺少机器可核对的范围或授权就返回 unknown，不推断旧文档里的自然语言，也不自动迁移或强制覆盖旧项目。只读诊断继续可用。

### 任务目录与状态

实际执行目录必须与 guard_policy.workspace 匹配，并通过 Git 检查确认所属仓库、分支和 worktree。

任务目录里的安装、导航和操作日志须由既有起步流程准备；门槛不复制这些资源。目录中没有可核对的任务、确认或绑定时返回缺项。同仓库的另一个 worktree、相似分支名或主目录的旧绑定均不代替当前目录的依据。

## 操作请求

GuardRequest 是工具操作请求对象。请求使用严格 JSON，schema_version 表示接口结构代际。未知字段、重复键、超出大小限制或不支持的结构直接拒绝解析。单个请求的 UTF-8 JSON 最大为 16 MiB，文件变化最多 100 项，每项 UTF-8 全文最大为 8 MiB。

| 字段 | 含义 |
| --- | --- |
| schema_version | 请求结构的代际，首个结构取整数 1 |
| operation | 带明确 kind 的操作对象；其参数必须来自实际工具调用 |
| task_ref | 适用任务的文件与记录引用；查询和独立请求可以为空 |
| expected | 任务写操作的 revision、context_snapshot_sha256、task_definition_sha256；独立文案仅要求具体文件前像，查询不要求任务专用字段 |
| authorization_refs | 本次操作适用的既有确认记录引用 |

首轮支持以下结构化操作：

| kind | 实际参数 |
| --- | --- |
| file.mutate | changes 数组；每项含 path、before_sha256、after。删除用 after=null，移动同时列来源和目标 |
| command.run | executable、argv、cwd；不接受 shell 字符串 |
| workflow.query | 明确的查询入口与参数 |
| workflow.apply | 既有语义操作请求及输入文件摘要 |
| git.stage | 明确的 paths 与实际工作目录 |
| git.commit | 实际工作目录、拟提交的路径与当前索引摘要 |
| git.push | 准确远端、目标分支及预期推送提交 |
| git.integrate | 准确仓库、远端、目标分支、PR（合入请求）、候选提交、主线提交和 integration_check_ref |

file.mutate 的 before_sha256 在创建时为 null。after 为 UTF-8 全文或不透明内容的摘要与字节长度。受管理 Markdown 的直接修改必须提供全文，以便比较其中的机器记录；无法取得全文时不能按普通文案修改放行。

共享内核不从命令字符串猜 kind。校验实际可执行文件和参数数组后，已识别的 Git、框架或受保护文件操作采用对应类别，不能借 command.run 的名称取得工程命令许可。可执行文件摘要变化时原命令许可失效。未知操作或未覆盖的参数形态返回 unknown。

## 判定顺序

本节规定同一个操作如何得到判定，所有客户端复用这些步骤。

1. 校验请求结构和受控项目根，规范化路径，拒绝越界、符号链接和大小写别名。
2. 按实际参数识别受保护资源或特定操作；通用命令许可不能覆盖更严格的类别。
3. 读取本次必需的安装身份、导航、任务定义、确认与绑定；只读诊断不因业务前置缺失而被禁用。
4. 读取实际工作目录和 Git 身份，核对任务与操作范围。
5. 根据操作检查阶段、依赖、具体授权及需要的候选证据。
6. 回读使用的依据与引用，发现检查期间变化则拒绝放行。
7. 返回判定和可定位的缺项；不修复文件或状态。

### 文件与命令门槛

| 操作 | 放行条件 |
| --- | --- |
| 项目内只读查询 | 路径安全，属于已识别的只读入口；业务状态无效时允许诊断 |
| 业务代码与任务文件修改 | 当前任务已登记，范围与计划确认有效，绑定有效，目录和路径匹配 |
| 实施中修改 | 任务处于 build 或 execute，且 status 为 running |
| 验证中修复 | 原任务为工程或开发任务，处于 verify/running；候选变化后旧检查不能用于交付 |
| 待验收或已验收后的修复 | 先由明确反馈授权通过既有语义操作重新进入验证；不能用“继续”放行代码写入 |
| 普通规划正文修改 | 只改本次获准范围的正文，机器记录保持不变；不自动视为任务启动 |
| 登记操作输入准备 | 走 preparationRequestObserver 的 workflow_input 分支，不要求任务已启动；执行对象另查前置 |
| 独立低影响文案修改 | 有明确路径与前像对应的独立请求依据；不制造业务迭代 |
| 验收后的普通文档收尾 | closeout/ready 或 closeout/running，验收与原证据仍适用；只改 closeout_paths 内的普通正文，机器记录不变 |
| 状态、机器记录及有效规格修改 | 仅通过已识别的框架语义操作；直接写入拒绝 |
| 工程命令 | 匹配任务确认覆盖的 executable、argv、cwd，且任务与目录前置有效 |

工程命令许可只覆盖该命令在获准环境里的执行。脚本内部的文件、网络或间接 Git 行为不据此宣称全面受控。未知脚本、任意 shell、环境变量拼接和嵌套解释器不作为已保护路径。

收尾阶段的业务代码、验证逻辑或公共约定变化不走普通文档分支，须重新进入验证并核对受影响验收。scope、design、tasks 正文会影响定义摘要，不通过“只改说明”直接放行。进度和完成记录由原语义工具更新，补充说明可写入获准的 verification 正文或交付说明。

### Git 门槛

本节按真实仓库内容区分保存开发成果和合入已验收成果。

- 暂存与开发提交核对实际任务目录、分支、索引和入库范围。开发提交不要求已经完成最终审查，因为审查需要定位候选提交。
- 任务分支推送核对获准远端、准确地址、目标分支、实际推送提交和适用授权。正常候选推送仍按工作流核对检查与审查；暂停时的进度备份按已有保存规则分别判断。
- git.push 直接推送主分支在首轮返回 deny；主分支交付只允许通过 git.integrate 核对实际 PR 与 Squash 前置。不会把直接推送变成 PR 合入的替代方式。
- git.integrate 必须核对当前候选的必要检查、独立审查、必须修复项、用户验收、规格收尾和最终集成检查。推送授权不代替这些条件。
- 最终集成必须同时绑定当前主线提交和候选提交。平台 PR 的目标、候选及当前状态由宿主的只读平台观察提供；缺观察或主线变化返回 unknown 或 deny。
- 清理、强制推送、改写主线历史、初始化仓库、配置作者、创建远端和发布不在首轮允许范围，返回 unknown。它们不会借已有推送授权被允许。

Git 观察只运行结构化的只读命令。清除可改变仓库定位的 Git 环境变量，关闭外部 diff、文本转换和可能写缓存的配置。内核不 fetch、不提交、不推送，不调用远端凭据流程。

平台观察由安装入口配置的只读 provider 提供，不从 GuardRequest 接受“平台检查已通过”的声明。首轮命令行未接入平台 provider 时，git.integrate 不返回 allow。固定本地测试远端用于验证提交与分支事实，平台缺失和候选变化也分别验证。

### 最终集成依据

最终集成检查使用当前迭代 verification.md 中的既有 check 记录，新增可选 operation_context。此字段的 kind 为 git.integration，并明确 git_common_dir、remote_url、target_branch、base_commit、candidate_commit 和 pr。integration_check_ref 引用该记录；两端提交必须与本次 Git 和平台观察一致。

该记录单独用于 Git 集成判定，不混入产品检查的 check_refs，也不改变旧验收对象。仅文档收尾产生新提交时，原产品检查、审查和验收可按原路径范围核对内容是否仍适用，再为实际最终提交补集成检查。业务内容变化则拒绝旧证据，重新检查、审查和验收；不重写旧检查的候选摘要来冒充新运行。

## 返回结果与调用接口

本节让适配者区分通过、违规和证据不足，避免把调用成功当作操作允许。

GuardResult 是判定返回对象。其 decision 取 allow、deny 或 unknown，allowed 仅在 allow 时为 true：

| 字段 | 含义 |
| --- | --- |
| request_sha256 | 本次完整操作参数的摘要 |
| observed | 实际 revision、约定快照、任务定义、仓库与候选引用 |
| read_set | 校验使用的路径和摘要；不返回凭据或无关文件内容 |
| reasons | 原因、相关路径或记录引用、需要补齐的动作 |
| verification | 明确哪些事实已核对，哪些真实性仍未证明 |

deny 表示已确定违反前置。unknown 表示输入或观察不足、接口不支持、来源不兼容或检查异常。两者都不能执行原操作；查询可以返回诊断。正常用户决定缺失只报告缺项，不自动重试或产生更多模型调用。

内核提供以下接口；签名中的 options 只由受控调用方提供：

- inspectOperation(projectRoot, request, options) 异步返回 GuardResult。
- revalidateOperation(projectRoot, request, previousResult, options) 重新判定并核对参数、依据和引用；不得直接复用旧 allowed。
- options.platformObserver 提供只读平台事实。它不是模型请求字段；缺失或异常按 unknown 处理。
- options.independentRequestObserver 提供当前宿主的明确非业务文案请求。它不保存新的批准账本，也不把来源字段当作真实性认证。
- options.preparationRequestObserver 提供当前明确准备请求，只放行上文定义的规划正文和语义输入。

platformObserver 接收 projectRoot、git_common_dir、remote_url、target_branch、pr、base_commit 和 candidate_commit。返回 observed 或 unknown，以及准确仓库地址、目标分支当前提交、PR 地址、状态、目标分支和候选提交。任何对象不匹配均不能放行。

independentRequestObserver 返回 observed 或 unknown，以及来源引用、项目根、准确路径和前像摘要。它免除 task_ref 与任务专用 expected 字段，但不免除路径保护、前像匹配和直接修改机器记录的禁令。

preparationRequestObserver 返回 observed 或 unknown，以及 source_reference、projectRoot、iteration、purpose 和 files。files 每项给准确 path 与 before_sha256；planning 和 workflow_input 的对象和前置按准备分支处理。它不从模型自报“正在规划”推断授权。

命令行提供 guard check --input <请求文件> --json。只有 allow 退出码为 0；deny 使用现有 CONFLICT 退出码，unknown 使用 INCOMPLETE 退出码。请求格式错误保留 USAGE，安装损坏保留 PACKAGE_INVALID 等原错误类别。

完整包提供 runtime/guard.mjs 供适配者导入同一内核，命令行与模块使用同源实现。现有 context guard 保持只检查快照的原含义，不伪装成操作门槛。

客户端必须在最终执行函数内核对实际参数，再调用原生工具。共享内核本轮不提供客户端包装，因此共享检查通过不能被写成 Pi 已拦截成功。

## 验证要求

维护者需要分别验证判定、无写入和完整包接口，不能用模型回答代替工具结果。

判定必须在真实形态上验证：真实 worktree、真实仓库配置（含属性与换行设置）以及框架仓库自身的调用。临时初始化的空仓库只证明逻辑分支，不证明可用；缺真实形态证据的部分按未验证报告。

- 正例覆盖有效任务的代码修改、验证中修复、开发提交、任务分支推送和满足完整前置的集成判定。
- 反例覆盖未登记任务、缺确认或绑定、过时依据、等待验收、缺审查、错误候选、仅获推送授权和跨任务操作。
- 文件反例覆盖越界、符号链接、目录别名、缺前像、不透明的受管理 Markdown，以及通过普通正文修改机器记录。
- 命令反例覆盖伪报类别、实际可执行文件变化、未知参数、任意 shell、嵌套解释器和间接 Git 的支持边界。
- Git 反例覆盖错误 worktree、同名但不同仓库、目标地址变化、索引变化、主线变化和平台观察缺失。
- allow、deny、unknown、请求解析失败、observer 异常和重新校验都比较调用前后文件、状态及 Git 关键内容，确认共享检查没有写入副作用。
- 旧记录仍能按原工具读取和操作，但缺少门槛字段不能取得新的写入许可。新增字段修订后重核计划与绑定。
- 源码、构建模块和命令行对同一组输入给出相同判定，损坏资源与不完整来源不显示正常保护。

同输入比较使用相同观察配置；默认无宿主观察时，源码、构建模块和命令行结果一致。模块配置宿主观察的正例另行验证，不与缺观察的命令行结果混为同一条件。

本轮确定性验证不调用真实模型。实际客户端工具拦截、模型主动衔接和连续迭代留给后续适配验证，成功条件沿[开发路线](../roadmap.md)。
