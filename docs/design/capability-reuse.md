# 成熟能力的吸收与适配

## 已确认原则

以本框架的流程和文档为主，吸收成熟开源方法后统一适配，不把多个上游工作流串起来。D09、D33 管框架能力融合；D49 要求在真实业务需求下继续调查适用开源方案，维护阶段的融合不替代业务调研。具体决定见 [决策记录](../decisions.md)。

能力来源、采用范围及候选状态登记在 [来源目录](../../sources/catalog.yaml)；固定文件、摘要、裁剪、依赖和完整许可由各包 NOTICE.md 保存，本页不重复调查原文或制作过程。上游候选和静态阅读不等于采用或运行验证。

## 协调与文档归属

- 当前主 Agent 保留任务、正式记录及验收责任。入口只定位和交接；专项返回方法与证据，不递归启动执行、不重复审查或争写状态。缺 Skill 或工具就交付材料并说明缺口，不伪称调用。
- 共同交接包括项目与成果、请求模式、目标内容/运行版本、原始要求及具体确认、允许操作、已有证据、未决项和返回位置。实际规则、本轮获准变更、草案与旧版本分开判断。
- 项目方向归overview；反馈候选归backlog；本轮范围和方案归scope/design；任务安排与证据归tasks/verification；公共约定归foundation；发布记录归releases。明确开轮条件满足时，主Agent使用clarify-design建立既定迭代资料，其他专项不为补记录新建迭代；不适用时在对话交付，不建立报告树。
- D62 要求主 Agent 在对应成果验收且必要检查、审查满足后，仅同步该成果实际交付的规格变化；无业务变化不改规格。受阻保留验收事实和恢复依据，未完成收尾不记全部完成。
- 已有适用确认不重复索取。设计与计划可以联合准备，仍不等于批准实施；证据可复用，内容或环境变化后补受影响检查。已提交未验收的成果不因“继续”或沉默自动通过。
- 多视角默认是同一 Agent 分角度分析，应透明说明；独立 Agent 仅在用户或适用协作要求明确需要时使用。讨论不能冒充独立审查或替代用户决定。

D65的开轮、暂停恢复记录和overview维护方法已写入相关Skills，职责见[文档设计](documents.md#开轮与项目方向维护已确认-d65)。只允许明确请求覆盖的操作，暂停保留验收事实；状态定位依据具体确认和实际资料，不能凭未标暂停或编号猜测。来源及运行依赖未增加，实际验证与用户验收仍单独记录。

## 采用与运行边界

每项能力沿用 SKILL.md 和 NOTICE.md 两文件包（D58），必要方法随包，不要求业务项目读取框架 docs。保留完整版权与许可声明；框架整体许可证尚未选定。

未引入上游 CLI、hooks、安装器、固定角色配置、自动会议记录、memlog、ledger、独立 UAT 或平行文档树；不写通用 state.yaml，也不照搬空回复通过、强制委派、到轮数即关闭问题等规则。Git 工作全部归 [Git 专题](git-workflow.md)，其他能力只做必要交接，不决定策略。

Skill 提供方法，由当前 Agent 使用真实可用工具执行，不自动成为进程、服务、另一个模型或权限沙箱。真实环境访问、部署、新依赖及重要范围/数据/安全/成本变化按具体授权处理；不能把方法已融合说成运行条件已齐备。

## 引入与后续维护

引入前核对具体仓库/文件/固定版本、许可证与署名、关联依赖及脚本、写入位置与副作用、权限、保留与裁剪原因，并运行适配验证。新产物先映射既定结构，确有缺口再提调整，不另起体系。

项目使用固定能力版本，日常不临时下载拼接上游。项目级完整包按 D24、D25 接入；安装器、初始化、升级迁移、自动路由、通用状态运行时及强制隔离尚未实现。上游更新先评估差异、重新适配验证，再由用户主动升级项目版本（D23）。其他候选仍以来源目录的实际状态为准。

各轮源码、包检查、隔离场景及独立审查按验证记录分别登记，当前进度见[交接](../handoff.md)；不能推广为真实客户端、完整业务项目、生产部署或用户验收通过。
