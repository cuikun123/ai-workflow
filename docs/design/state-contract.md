# 状态、记录与写入契约

本页说明框架怎么**记住“做到哪了”**、怎么**记录检查和验收**、写文件**写到一半坏了怎么恢复**。给维护状态工具的维护者和需要核对依据的 AI 读；只想知道“文档放哪、各放什么”看[文档管理](documents.md)即可。

<a id="第0步状态结构与转换"></a>

## 状态结构与转换

三类事实分开存，别混：

| 事实 | 存在哪 | 别当成 |
| --- | --- | --- |
| 装了什么框架 | `.ai-workflow/manifest.json` 与安装日志 | 装好了 ≠ 客户端能调用、业务任务完成 |
| 现在停在哪 | `docs/workflow/state.yaml`（轻量“书签”） | 书签写完成 ≠ 证据满足 |
| 目标、进度、验收依据 | scope / design / tasks / verification、specs、发布记录 | AI 自检通过 ≠ 用户验收 |

需求和历史留在 Markdown 正文；只有机器要读的部分用“记录块”（见后一节的“记录与写入保护”）。

### 状态书签（state.yaml）

它只记“当前走到哪”，不囤积需求和历史。关键字段：

- `revision`：每次成功改动 +1；写入要带“我期望的旧值”，对不上就拒绝，防止并发覆盖。
- `current_iteration`、`current_task`：当前在第几轮、哪个任务（可为 null）。
- `phase`（阶段：澄清/计划/地基/执行/检查/验收/收尾/发布/维护）与 `status`（未开始/可开始/进行中/等用户/阻塞/暂停/完成）分开记。
- `waiting_for`：在等什么（等范围确认、等验收、等授权等）。
- `basis`：这个书签依赖的文件摘要，用来发现“依据被改、书签过时”。
- 断点、确认、阻塞的记录引用（只存定位，不塞全部历史）。

字段类型与约束以 [state-v1 结构定义](../../schemas/state-v1.schema.json) 为准；`validate`、`status` 会校验结构和引用，但不认证“是真人批准的”。

**几条铁律**

- 只引用真实存在的目录和任务，不按“编号最大”猜当前轮。
- `current_task=null` 时不能“进行中”；要“暂停”得有断点，“阻塞”得有依据。
- 等用户验收用 `phase=closeout` + 有效验收引用，不提前写“完成”。

### 状态怎么流转

| 从 → 到 | 前提 |
| --- | --- |
| 未开始 → 可开始 → 进行中 | 本阶段该有的确认、授权、资料、依赖都在；进入实施前必须有确认 |
| 执行 / 检查 → 等用户验收 | 必要检查、审查、必修项都满足，并给出成果位置和验收步骤 |
| 等验收 → 收尾 | 用户明确确认了对应成果和内容版本（AI 自检、沉默都不算） |
| 收尾 → 已完成 | 只同步已验收的实际变化，记录和 Git 收尾完成 |
| 任意活动 → 阻塞 | 记下原位置、证据和解除条件 |
| 活动 / 等待 / 阻塞 → 暂停 | 用户明确暂停或切换，先保留断点和原状态 |
| 暂停 / 阻塞 → 恢复 | 回读断点、文件、确认和解除条件，恢复原阶段（原来等验收就仍等验收） |
| 已完成 → 新工作 | 新目标和开轮条件具备后显式更新 |

状态只能通过受控的“语义操作”提交（都带期望 revision），没有“随便设成完成”的后门；涉及多个文件时先按[恢复协议](#记录与写入保护)记账、改文件、回读，最后才更新 state。独立审查、诊断、发布仍可按请求单独进入，不强制从头走一遍。

### 验收绑定到内容

验收记录要绑到**具体成果和内容版本**（优先 Git 提交；有未提交内容就用文件清单加摘要）。成果变了要重新判断原验收是否还适用。`basis` 变了只提示“书签该复核”，不等于把已验收的自动作废。

### 读取、过时与写入中断

- `status` 只读：报告声明状态、引用核对结果和下一步，不偷偷改书签。
- 文档被人工改过后 `basis` 对不上，报“过时”；恢复时读实际资料、保留原验收，能唯一确定才生成新 revision。
- 坏 schema、旧 revision、未完成日志都禁止继续写；原文件和恢复依据保留。
- 这把锁只约束本框架的工具；外部直接改文件仍可能发生，靠前后比对发现冲突并停下，不宣称能锁住一切。

## 记录与写入保护

`tasks.md`、`verification.md` 里用结构化的“记录块”存机器要读的东西，正文仍是中文 Markdown：

| 记录种类 | 放哪 / 记什么 |
| --- | --- |
| task | tasks.md：任务标题、阶段、依赖、需求；进度由工具管 |
| confirmation | verification.md：确认类型、批准或驳回、对象与来源（必须来自用户） |
| check / review | verification.md：实际结果、证据、未关闭的必修项 |
| checkpoint / progress | 工具生成的断点与进度，不许手写冒充 |
| blocker / resolution | verification.md：阻塞原因、解除条件与证据 |
| closeout | verification.md：规格同步或无需同步的理由、Git 收尾结果 |

写法：`<!-- iterlane:record <id> -->`、一段 JSON、`<!-- /iterlane:record <id> -->`，正文保持中文；id 在同一文件内唯一，代码示例里的标记不当运行记录。命令和参数见[命令参考](../../scripts/README.md)。

**写入与恢复（标准做法）**：每个项目工作目录一把独占写锁，配合 revision 和文件摘要；用操作日志记录每个文件的前后像。多文件写入按“先核对 → 持久化日志与前后像 → 逐项写 → 回读 → 最后提交 state”进行，中途失败由未完成标记挡住、不误报成功；坏了能 `resume` 继续或 `undo` 回退，不重做已完成部分、不倒退 revision。它只覆盖框架自己管理的文件与工作书签，不等于整个业务项目或生产环境的事务，也不宣称跨目录瞬时原子、断电绝对恢复或锁住外部编辑器。日志、锁和字节级细节以代码和[命令参考](../../scripts/README.md)为准。

遇到读写异常时：

| 情况 | 处理 |
| --- | --- |
| 只读查询发现状态过时 | 报过时原因，不借查询改文件；独立恢复按授权执行 |
| 文件被用户或外部改过 | 停止覆盖与删除，保留现场和差异 |
| 锁残留或进程异常退出 | 结合操作 ID、进程身份和日志判断，不按锁龄或 PID 删 |
| state 损坏或记录矛盾 | 能唯一核实才重建，否则保留未知 |

## 地基上下文与任务绑定草案

> 本节是设计草案，不是运行保证。

开始任务前，框架要核对两件事：**最新的项目约定（地基）** 和 **当前任务的绑定**；只拿旧绑定不能开工。

- **读取**：把公共启动规则、项目 `AGENTS.md`、`docs/project/foundation/` 全部原文和摘要读出来，算一个快照；规则一改，快照就变。
- **绑定**：`context bind` 把“当前任务 + 当时的地基快照”绑在一起记进 verification；`start`、进验收、收尾前都重新核对，普通刷新不能代替绑定。
- **地基变了**：先重新读取、和用户核对影响，再重新绑定；影响已交付成果的，还要重跑受影响的检查。
- **改任务**：要改任务的验证政策、需求或依赖，用 `task_revise` 走受控修订，不能靠手改正文冒充。

具体字段、错误码和 hook 行为见代码与[多客户端接入](integration.md#多客户端与用户包设计草案)。

## 验证与验收记录

对话给简短结论，文件留可定位依据；没有当前迭代时就在对话交付，不另建迭代或平行报告。

| 记录 | 最少保留 |
| --- | --- |
| 检查 | 对象与范围、执行方式、必要环境、实际结果、关键证据 |
| 缺口 | 失败、未执行或不适用的原因，补齐条件和下一步 |
| 验收 | 对应成果、体验步骤、预期、限制、提交和用户反馈 |
| 进度 | 实施、AI 检查、待验收、用户已验收、未完成收尾分别记 |

- 结果区分通过、失败、未执行、不适用，只覆盖实际范围；不复制完整日志，不写凭据。
- 按完整成果记录任务，技术子步骤完成不等于成果通过验收。

### Git、发布与升级记录

- **暂停保存**：记允许保存的范围、提交断点、远端备份结果和恢复条件。
- **改动归属**：同属当前任务的改动可一起保存；其他任务分开，归属不明保留现场。
- **发布**：关联标签、提交、产物和成功、失败或回滚结果。
- **框架升级**：在既有任务和验证记录里记实际前后版本，计划和已生效分开。

权限和步骤见[Git 工作流](git-workflow.md)与[框架升级](integration.md#框架升级)。
