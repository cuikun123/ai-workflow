# 目标与范围

## 项目定位

建立属于用户自己的 AI 开发工作框架，把成熟开源能力吸收到符合自身使用习惯的流程中。面向个人开发，也应能在工作场景中使用。

用户不希望重写已有成熟方法；也不希望被上游整体流程、并行文档体系或技术预设限制。

## 使用者与 AI 的分工（已确认 D49）

开发者可以只提出想做什么、希望解决什么问题，无需先掌握或决定技术细节。AI 负责主动调查可参考或复用的开源方案，结合实际用途和约束比较语言及技术路线，给出推荐并解释取舍，帮助使用者理解影响和作出关键选择。

有技术背景或已有技术想法的使用者可以参与选型；其偏好应纳入评估，没有偏好时由 AI 提供有依据的建议。技术栈无关也意味着不把熟悉的验证技术栈当成所有项目的默认答案。普通实现细节和关键选择继续遵循既定自主执行与确认规则。

上述要求已有 clarify-design 的方法级适配，实际调研与隔离场景范围见[框架验证](../../tests/README.md)。这不代表完整研究工具、真实客户端接入或真实业务效果已验证；建议呈现与参与深度按具体请求处理。

## 首版范围

- 首版支持 Codex。
- 从零建立个人 Web 项目，建立地基后持续小迭代，支持发布、运行反馈与后续维护。
- Java、React、MySQL 是熟悉的首个验证方向。框架、版本、ORM、构建工具、认证和部署尚未决定。
- 流程本身技术栈无关。技术 profile 提供可验证建议，不限制发现新需求、调研或提出其他方案。
- 用户确认关键范围和取舍，阶段内由主 Agent 自主推进，按需多 Agent 协作。

## 当前不做

- 接手既有业务项目开发新功能：用户计划另做框架。
- 首版同时适配所有编码工具和移动端。
- 从零复制所有上游技能，或只把多个现有框架原样串联。
- 预置无业务依据的登录、支付、多租户等功能。

## 仓库关系

框架仓库保存通用方法、模板、工具和来源记录。各业务项目保存实际代码、真实需求、当前约定、迭代历史与项目状态。

框架的验证技术栈不等于框架自身必须采用的实现语言。
