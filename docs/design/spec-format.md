# 业务规格格式

## 已认可的方向

一份规格描述一个业务能力的当前有效行为，按目的、范围、需求与可验证场景组织。业务规格不是某轮任务清单，也不与迭代一一对应。

正文使用中文；沿用 Purpose、Scope、Requirements、Requirement、Scenario 这类结构标记是当前模板方向。是否要求完全兼容上游解析器仍待决定。

## 内容模板草案

以下占位写法用于说明格式，不是预先作出的业务决定。

```markdown
# 业务能力名称

## Purpose
描述解决的问题与价值。

## Scope
描述覆盖范围、边界及相关规格引用。

## Requirements

### Requirement: CAP-001 需求名称
系统 MUST 满足一项具体且可观察的行为要求。

#### Scenario: 场景名称
- **GIVEN** 前提
- **WHEN** 操作或事件
- **THEN** 预期结果
- **AND** 必要的其他结果
```

需求尽量各表达一项可观察行为。场景按实际风险覆盖成功、异常、边界与权限条件，不机械要求每条填满所有类别。

## 编号与引用

建议使用稳定编号关联范围、任务和验证，例如 EXP-001；编号不因标题文案微调而更换，删除编号不复用。

编号前缀、跨文件移动、拆分与合并、场景定位及自动校验规则未正式定义。

## 按需扩展

术语、状态转换、计算示例、功能特有权限与数据规则可以补充。公共基础约定通过引用复用，技术实现进入相关设计资料。

## 演进

拟修改的行为先记录在本轮迭代资料；按约定验收后同步到当前规格。保留一份当前规格，Git 保存内容历史，迭代解释变更原因。

按 D62，获准的本轮变更用于判断对应候选实现，其余有效规则继续遵守；旧版本环境核对其适用依据。主 Agent 在对应成果验收且必要检查、审查满足后，仅同步实际交付的需求与场景，保留其他规则及编号，不整篇复制本轮范围。无业务变化无需修改规格；部分同步或受阻沿用 tasks/verification 留下范围与恢复依据，具体步骤见 [业务文档管理](documents.md#当前内容与历史)。

第一轮只描述实际交付的能力，未来设想进 backlog。

## 模板与工具的区别

继承表达方法不等于兼容 OpenSpec 命令；若复用其解析、校验、合并逻辑，必须验证路径、标题、内容和变更格式。

格式检查不能证明业务正确。当前尚未实现规格生成器或校验器。
