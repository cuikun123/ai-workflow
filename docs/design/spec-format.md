# 业务规格格式

一份规格描述一个业务能力的**当前有效行为**，按目的、范围、需求和可验证场景组织；它不是某轮任务清单，也不与迭代一一对应。

## 内容格式

正文用中文，结构标记使用 Purpose、Scope、Requirements、Requirement、Scenario。以下只说明格式，不预置业务决定。

```markdown
# 业务能力名称

## Purpose
描述解决的问题与价值。

## Scope
描述覆盖范围、边界及相关规格引用。

## Requirements

### Requirement: CAP-001 需求名称
系统 MUST 满足一项具体且可观察的行为要求。

#### Scenario: S01 场景名称
- **GIVEN** 前提
- **WHEN** 操作或事件
- **THEN** 预期结果
- **AND** 必要的其他结果
```

## 写作与编号

- 每项需求尽量只表达一项可观察行为。
- 场景按风险覆盖成功、异常、边界和权限，不机械填满所有类别。
- 可补术语、状态转换、计算示例及功能特有的数据规则。
- 公共约定通过引用复用，技术实现进入设计资料。

**编号建议**：用稳定编号关联范围、任务和验证，如 `EXP-001`；文案微调不改号，删除后不复用。跨文件移动、需求拆并不自动推断，须声明增量并确认关系。

## 何时更新

1. 拟修改行为先进入本轮范围和设计。
2. 本轮获准变更只用于对应候选版本，其余有效规则继续遵守；旧环境核对旧版本依据。
3. 成果验收且必要检查、审查满足后，只同步实际交付变化，保留其他规则、编号及用户修改。
4. 无业务变化不改规格；中断时保留范围和恢复依据，见[文档管理](documents.md#当前内容与历史)。

保留一份当前规格，Git 保存历史，迭代解释变更原因。第一轮只描述实际交付能力，未来设想进待办。

## 机器同步怎么工作（要点）

程序只校验结构；真正的批准和业务语义由 Agent 或宿主核对。字段、日志和命令的细节以代码、[接入设计](integration.md#规格与验证记录)和[命令参考](../../scripts/README.md)为准。

- **身份**：需求用稳定 ID（如 `CAP-001`），场景用 `S01` 之类；同一需求内场景不重号，文案微调不改号，删除后不复用。旧文档没有编号时只读提示，不自动编号，也不批量迁移。
- **怎么记变化**：本轮对规格的新增、修改、删除，记成本轮 `scope.md` 里的结构化记录（带改动前后摘要），不另建增量目录，也不做第二份任务表。
- **怎么关联**：任务、检查和审查按需求与场景 ID 对应；必测场景由任务和风险决定；验收绑定实际交付的产物，而不是将要被同步改变的后像。
- **怎么同步**：`spec sync` 把**已验收**的变化写进规格，并在同一次可恢复操作里一起写规格、记收据和更新状态；没有业务变化就记“无需同步”。重复请求、内容不一致或未完成操作一律拒绝并保留现场。
- **边界与容量**：只做声明内的新增/修改/删除，不做自然语言合并或整份删除；文档数量与单文件大小有上限，超限在写入前拒绝，不截断后宣称完整。
