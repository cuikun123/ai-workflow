# 业务项目文档管理

本页说明业务项目里**有哪些文档、每个文件放什么、谁维护、什么时候更新，以及“当前内容”和“历史记录”怎么分**。开发怎么一步步走见[开发流程](workflow.md)；状态书签、记录块和写入恢复的机器细节见[状态、记录与写入契约](state-contract.md)。

## 文档结构

业务项目采用以下文档结构；框架自身资料仍放在本仓库 `docs/`。

```text
业务项目/
├── AGENTS.md
└── docs/
    ├── project/
    │   ├── overview.md
    │   ├── backlog.md
    │   ├── foundation/
    │   │   ├── README.md
    │   │   ├── engineering.md
    │   │   ├── experience.md
    │   │   ├── security.md
    │   │   ├── quality.md
    │   │   └── operations.md
    │   └── specs/
    │       ├── README.md
    │       └── 按实际能力创建的规格文件
    ├── iterations/
    │   ├── 000-foundation/
    │   │   ├── scope.md
    │   │   ├── design.md
    │   │   ├── tasks.md
    │   │   └── verification.md
    │   └── 按实际工作创建的后续迭代目录
    ├── workflow/
    │   └── state.yaml
    └── releases/
        └── 按实际发布创建的记录
```

框架资源与技能入口另放 `.ai-workflow/`、`.agents/skills/`，见[项目安装布局](integration.md#项目安装布局)。

### 初始化时先写什么

| 对象 | 初始内容 |
| --- | --- |
| 普通说明文档 | 空文件，由地基和迭代按阶段填充 |
| `AGENTS.md`、`state.yaml` | 最小有效说明与导航 |
| 空目录 | 可用零字节占位文件供 Git 跟踪 |
| 功能规格、后续迭代、发布记录 | 实际发生时创建，不预置示例业务 |

文件存在不等于已填写、确认或验收。阶段检查只要求当时必需的内容，后续文档合法为空不阻碍前一阶段完成。

## 各文件职责

| 文件或目录 | 保存什么 |
| --- | --- |
| `overview.md` | 当前项目方向、目标用户与范围 |
| `backlog.md` | 尚未进入本轮的想法与后续工作 |
| `foundation/README.md` | 基础约定导航 |
| `engineering.md` | 结构、构建、开发与工程约定 |
| `experience.md` | 体验与界面约定 |
| `security.md` | 安全、敏感数据与访问边界 |
| `quality.md` | DoD、测试和通用质量要求 |
| `operations.md` | 环境、启动、部署、日志与排查 |
| `specs/` | 当前有效业务行为与规则 |
| `scope.md` | 本轮范围、验收、相关规格与变更 |
| `design.md` | 方案与关键取舍 |
| `tasks.md` | 唯一任务清单、进度与调整原因 |
| `verification.md` | 检查和验收依据、结果、缺口及恢复条件 |
| `state.yaml` | 当前工作、阶段、确认和任务引用等轻量导航 |
| `releases/` | 实际发布内容、版本、产物和环境结果 |

`state.yaml` 是当前工作的书签，不积累完整需求、任务或验证历史。恢复时回读实际资料，由受校验工具更新；不能单凭书签判断工作或验收已完成。它的字段与转换规则见[状态、记录与写入契约](state-contract.md#状态结构与转换)。

## 当前内容与历史

| 位置 | 时间含义 |
| --- | --- |
| `project/` | 当前有效方向、约定与业务规格 |
| `iterations/` | 每轮变更过程，结束后保留原位 |
| `releases/` | 实际发布历史 |

一个规格可涉及多轮，一轮也可影响多个规格。简单迭代可将必要设计放在 `scope.md`；地基模板保留 `design.md`。

### 验收后同步规格

验收后由主 Agent 只把**实际交付**的变化同步到相关 `specs/`，保留未变规则、其他成果、编号和用户修改；没有业务变化时，记一句“无需同步”即可。不能把整轮 `scope.md` 直接当成有效规格。必要检查还没做完时，先保留验收事实和缺口，补齐后核对原验收是否仍适用，内容变了就重新验收。项目级约定若有变化，按实际生效时间更新，别同时留下互相冲突的两份。具体格式见[规格契约](spec-format.md)，适用不清或两份确认冲突时先澄清。

### 写入中断后恢复

- 写前回读、写后核对，保留用户修改。
- 比对实际文件、验收内容和后续变化，只补未完成部分。
- 不能凭旧记录覆盖文件，也不重复索取同一验收。
- 无法安全写记录时在对话交付断点；收尾未完保持未完成状态。

## 拆分与扩展

- 公共约定按职责分组；业务规格按主题、按需拆分，不强按行数切。
- 只改措辞、不改含义的整理可以直接做；涉及语义、范围或规则变化的，先确认再改。
- 外部来的资料没合适位置时，先商量调整结构，不要硬塞、丢弃，也不要另起一套。
