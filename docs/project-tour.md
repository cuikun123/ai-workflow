# 项目结构导览

这份导览按当前项目结构解释：里面有什么、给谁用、什么时候用、怎么用。你只需要先理解几个目录之间的关系。开始自己的真实项目请读[快速开始](quickstart.md)，开发中的具体对话见[使用指南](usage.md)。

本导览给理解和维护框架的人阅读，留在源码仓库，不安装到业务项目，也不需要每个任务都让 AI 全文读取。

## 先看全貌

```text
ai-workflow/                      框架源码仓库
├─ README.md                     第一次进入的导航
├─ AGENTS.md                     维护本框架的协作规则
├─ docs/                         用户教程、维护资料与设计
├─ skills/                       AI 工作方法与共同规则
├─ src/ + bin/                   确定性的本地工具
├─ templates/ + schemas/         初始化骨架与数据格式
├─ scripts/                      构建、检查和交付
├─ tests/                        工具回归、场景和客户端评测
├─ examples/                     可运行的收藏参考应用
├─ sources/                      上游来源、版本与许可
├─ adapters/ + profiles/         接入说明与技术参考
├─ package.json + package-lock.json  Node 版本、命令和固定依赖
└─ dist/                         构建后的完整工具包，不在 Git 中
```

整体关系是：**文档说明规则，技能教 AI 怎样做，工具核对记录和前置条件，测试验证工具与方法。** 模板用于创建业务项目的资料骨架，示例帮助理解一个可交付成果。

```text
框架源码 ──build──> 完整工具包 ──init──> 你的业务项目
                      │                    ├─ 项目规则与地基
                      └─ 可打成试用 ZIP    ├─ 当前任务与检查记录
                                           └─ 你自己的应用代码
```

框架源码仓库与真实业务项目是两个目录。不要在框架仓库里直接做自己的应用，也不要把维护设计、测试夹具里的内容当成真实业务需求。

## 各部分怎样使用

| 部分 | 里面有什么 | 给谁用 | 什么时候用 | 怎么用 |
| --- | --- | --- | --- | --- |
| 根目录入口 | README 导航、AGENTS 协作规则、CHANGELOG 变化、贡献/安全/许可说明 | 使用者与维护者 | 初次接触、维护框架、查变更和分发 | 使用先进入 quickstart；维护先读 handoff 与 AGENTS |
| `docs/` | 使用教程、当前状态、已确认决定、计划和正式设计 | 使用者、维护者、核对依据的 AI | 使用步骤不清楚、接手维护或修改规则 | 只读与你当前问题有关的文档，见下一节 |
| `skills/` | 十一项技能入口、按需参考、公共契约和许可 | 项目 AI；维护者修改方法 | 澄清、计划、实施、检查、审查或恢复 | 通常用自然语言提出请求；AI 按当前动作选方法 |
| `src/` 与 `bin/` | 安装、状态、上下文、规格、恢复等运行代码；CLI 启动器 | 本地 Node 工具、框架维护者 | 运行命令，或排查实现问题 | 用户运行已安装项目 CLI；维护者在 src 找对应模块 |
| `templates/` | 初始化要创建的项目文档、入口、状态和空目录清单 | 安装器；维护者 | 创建全新项目 | 安装器按清单生成，普通业务文档可以为空，后续按真实需求填写 |
| `schemas/` | state 与业务记录字段、格式和约束 | 校验工具、接口维护者 | 读写结构化状态与记录 | 工具校验；用户不需要手写这些 JSON 字段 |
| `scripts/` | 构建包、CI、测试结果核验、ZIP 交付与文档复制 | 维护者、CI | 改完框架、准备安装包或验证交付 | 常用 build/ci；deliver 要传完整包、来源摘要和新输出目录 |
| `tests/` | 自动化回归、合成项目夹具、真实客户端评测驱动和证据核验 | 维护者、测试运行器 | 修改对应功能后验证，或明确开展客户端评测 | 相关测试用 `node --test`；真实模型驱动单独授权调用 |
| `examples/` | 本地收藏应用、页面、HTTP/存储逻辑与测试 | 想先看效果的使用者、维护者 | 理解可验收成果或参考实现 | 按示例 README 运行；可选 init --example 明确复制业务源码 |
| `sources/` | 固定上游来源、版本、依赖、适配与完整许可 | 维护者、分发者 | 引入、更新或核验第三方能力 | 查 catalog 和 NOTICE，保留许可与署名 |
| `adapters/` | 既有 Codex 接入和自检说明 | 接入维护者 | 排查现有客户端支持 | 是说明与验证入口，不等于全部客户端自动接入已实现 |
| `profiles/` | 技术选型参考的职责说明 | 维护者、选型 AI | 考虑复用技术方案 | 当前没有已验证的现成工程预设，技术栈仍按业务选择 |

### 技能：方法入口，按当前阶段加载

技能大致分为四组：

- **定位和设计**：workflow-guide 定位任务；clarify-design 澄清范围；discuss-design 比较取舍；plan-tasks 整理可验收任务。
- **实施**：build-foundation 建最小工程；execute-task 做当前获准任务；debug-issue 定位并修复问题。
- **验证**：test-work 选择并执行检查；review-work 核对候选和修复证据。
- **发布与故障**：release-work 执行明确获准的发布；handle-incident 处理线上基线和修复范围。

每项技能的 `SKILL.md` 是发现和路由入口，`references/` 是需要时才读取的细节，`NOTICE.md` 保存来源和完整许可。`skills/_shared/` 是共同规则的唯一来源，构建时展开到各技能的 `references/common/`；这些生成副本不需要分别维护。

公共 `manifest.json` 记录能力、规则及资源归属，供工具完整校验。`context inspect` 不再把它的全文返回给 AI，但文件哈希仍参与快照和任务绑定；必要规则、能力信息与最新地基原文继续返回。

### 运行工具：哪些事情由代码核对

`src/` 可以按六个职责理解，不用逐个文件记忆：

| 模块组 | 核对什么 | 你会看到的入口 |
| --- | --- | --- |
| 包与安装 | 文件白名单、摘要、技能完整性、导航与受管区块 | `check`、`skills check`、`init` |
| 上下文与绑定 | 最新规则/地基成员和字节、当前任务定义、专用绑定记录 | `context inspect/guard/bind` |
| 工作流 | 当前任务、等待、确认、验证、验收、收尾与声明修订 | `status`、`transition` |
| 业务规格与证据 | 需求/场景、增量基准、候选摘要、验收后同步收据 | `artifacts inspect`、`spec check/sync` |
| 诊断与恢复 | 未完成操作、锁、前后像、可恢复状态和固定旧版本来源 | `doctor`、`recover`、既有固定路径的 upgrade/rollback |
| 基础安全与可靠写入 | 路径边界、真实文件、写锁、字节一致性和错误分类 | 由上述命令内部使用 |

工具能拒绝过时绑定、坏记录、冲突或提前收尾，不能认证 AI 已理解并遵守约定，也不能替你验收产品。当前还没有全部客户端的原生写前拦截。

### 测试：为什么看起来很多

`tests/runtime/` 验证安装、格式、绑定、恢复等确定性行为；方法场景目录验证技能结构和业务边界；`tests/codex-client/`、`tests/end-to-end/` 保存特定真实会话的驱动与证据识别逻辑；`tests/helpers/`、`fixtures/` 提供共用夹具和固定旧包。

大量用例是为了核对中断、并发、旧版本、外部修改和伪证据，不是每个真实业务项目都要携带或运行的内容。普通 CI 不调用模型。真实客户端驱动可能发请求、创建虚构项目或启动本地服务，不能因为它在 tests 目录就随意运行。测试中的合成确认不代表用户业务批准。

## 构建物和临时目录

| 位置 | 用途 | 怎样处理 |
| --- | --- | --- |
| `dist/` | 自包含工具包，包含 runtime、bin、用户文档、技能、模板、schema及许可 | 不进 Git；克隆/更新源码后 build；不要手改生成代码 |
| `node_modules/` | 按 package-lock 安装的运行与构建依赖 | 不进 Git；用 npm ci 复现，不当框架自写代码 |
| `.artifacts/` | CI原始事件、结果、包及临时副本 | 不进 Git；确认无运行任务且必要证据保留后可清理 |
| ZIP与解包目录 | 分发给使用者的完整工具、教程和示例 | 保留准确 ZIP/来源摘要；重复解包可重新创建 |
| 系统 Temp 测试目录 | 虚构夹具、临时构建和故障场景 | 确认测试结束后清理，活跃进程使用的目录保留 |
| 仓库外验证目录 | 固定候选、失败证据、归档和备份 | 不随源码推送；不是别人克隆后就有的资料 |

`resource-manifest.json` 是包文件清单，项目的 `.ai-workflow/manifest.json` 是安装身份与资源归属，`SHA256SUMS`/`delivery.json` 固定交付文件和来源。它们都不是业务需求，也不需要全部正文进入 AI 请求。摘要证明字节一致，不是来源签名。

## 你的业务项目会长什么样

```text
my-real-project/                 与框架源码分开
├─ AGENTS.md                     项目入口与你的约束
├─ .agents/skills/               已安装的工作方法
├─ .ai-workflow/                 本地工具、资源、安装清单和日志
├─ docs/project/
│  ├─ overview.md                项目方向与概览
│  ├─ foundation/                工程/体验/安全/质量/运行约定
│  ├─ specs/                     已交付的有效业务行为
│  └─ backlog.md                 后续候选
├─ docs/iterations/
│  ├─ 000-foundation/            地基轮
│  └─ 后续迭代/                 scope/design/tasks/verification
├─ docs/workflow/state.yaml      工具维护的当前任务与等待
└─ 你的应用代码与测试            结构由业务技术栈决定
```

你主要关心自己的目标、地基约定、任务成果和验收点；AI 维护记录并使用工具。初始地基文件为空不等于完成，需要第一轮实际建立最小工程、约定和检查。普通 Markdown 正文按授权调整，结构化记录、状态和绑定由工具维护，不手改 JSON 来解除等待。

一次任务的关系是：**读最新规则与地基 → 核对影响和适用确认 → 绑定当前任务 → 实施 → 实际检查/审查 → 你验收 → 同步规格并收尾**。换会话继续从项目规则和当前状态接手，不能凭旧记忆猜下一任务。

开始试用只需要先打开[快速开始](quickstart.md)，按里面的命令安装，再向 AI 描述你的真实目标。
