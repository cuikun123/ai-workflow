# 使用指南

这一页讲安装好以后怎么和 AI 一起开发。还没安装的话，先看[快速开始](quickstart.md)。

## 你和 AI 怎么分工

| 你负责 | AI 负责 |
| --- | --- |
| 说明想要什么 | 调查能查到的信息，问清关键问题 |
| 确认方案和任务 | 设计方案，拆成可验收的任务 |
| 亲自体验成果，说“通过”或指出问题 | 写代码、跑检查、做审查、修问题 |
| 遇到重要取舍时做决定 | 记录进度和结果，验收后更新项目资料 |

平时直接用自然语言交流就行。不需要记住技能名称，也不需要手工改状态文件。

## 先认识几个词

| 词 | 意思 | 例子 |
| --- | --- | --- |
| 地基 | 能运行的最小工程，加上大家共同遵守的约定 | 应用能启动，数据能保存，有一条检查命令 |
| 迭代 | 围绕一个目标的一轮开发，可以包含几个任务 | 让收藏应用能保存和查看收藏 |
| 任务 | 一个能单独交付、检查、验收的成果 | 添加收藏后在列表看到，刷新后还在 |
| 检查 | 实际运行测试、命令或操作来核对结果 | 输入非法地址，看是否有提示 |
| 审查 | 另一个 AI 对照原始要求检查遗漏和风险 | 保存失败时会不会弄丢已有收藏 |
| 验收 | 你亲自试过成果后，明确说通过或不通过 | “保存收藏这个任务验收通过” |
| 规格 | 记录项目**已经交付**的功能行为 | “合法收藏保存后，刷新和重启仍可查看” |

有四个进度很容易混淆，它们是依次发生的：

1. **代码写完了**：还没检查。
2. **检查通过了**：AI 确认能用，交给你验收。
3. **你验收通过了**：只有你明确说“通过”才算。说“继续”、不说话都不算。
4. **收尾完成了**：AI 更新规格和记录，然后才做下一个任务。

## 一轮开发怎么走

```text
你提出目标 → 一起定范围和方案 → 你确认任务计划
    → AI 实施、检查、审查 → 你验收
    → AI 更新资料 → 下一个任务
```

- AI 检查发现问题：它在当前任务里自己修，修完重新检查。
- 你验收不通过：回到当前任务修复，修完重新交给你。
- 你中途想加新功能：先说清是原来要求漏了，还是新的想法。新想法另外安排。

改错字、调排版这类小事，AI 直接做完再告诉你。涉及权限、数据迁移、安全的工作，AI 会先给你看更详细的方案。

## 第一次打开项目

### 1. 确认安装正常

在项目文件夹打开 AI 工具，新建会话，发：

> 查询当前项目状态，不改文件。说明安装是否完整、现在有没有任务，以及下一步可以做什么。

刚装好的项目只有工具和空的资料文件，还没有功能，这是正常的。

### 2. 说明你的目标

> 我想做一个只在本机使用的收藏应用，保存网页标题和地址。先帮我明确第一版范围和技术方案，暂不实施。

还没想好用什么技术，可以说：

> 我还没选技术栈。请给出适合这个目标的选择，解释推荐理由和维护成本。

### 3. 建立地基

新项目的第一轮是建地基（目录名 `000-foundation`），还不做业务功能。顺序是：

1. **确认方案和约定。** AI 一次给你看：起步范围、技术方案、任务、验收方式，以及工程、安全、质量等基本约定。你一起确认，不用逐个文件批准。
2. **准备开工条件。** 正式写代码前，AI 会检查 Git 仓库、远端、主分支这些条件。缺什么它会告诉你，但**不会自己去建仓库、建远端或改作者配置**，这些要你授权。
3. **搭工程并实际运行。** AI 建好最小工程，真的运行启动和检查命令，再把结果记下来。没跑过的检查不会写成“通过”。
4. **你验收地基。** AI 给你体验入口和预期结果。你试过、明确通过以后，才开始做第一个业务功能。

`docs/project/foundation/` 下的 6 个文件刚装好时是空的，不代表地基已经建好。地基完成时，每个文件要么写好了约定，要么写明“暂不适用”的原因。

## 跟着一个例子走完开发

下面是一段**示范对话**，不是真实开发记录。你的项目里，地址、文件和测试结果都要以 AI 实际给出的为准。

假设地基已经验收：应用能启动，数据能保存，检查命令能跑。现在做第一个功能：保存和查看收藏。想先看最终效果，可以运行[收藏示例](../examples/bookmarks/README.md)。

### 1. 提出目标

**你：**

> 开始第一轮业务开发。我想输入网页标题和地址，保存后在列表里看到，刷新和重启后都还在。先讨论范围和方案，暂不实施。

AI 会问几个影响方案的问题，比如：数据只存本机吗？地址允许哪些格式？保存失败时怎么提示？

**你：**

> 第一版只保存本机数据，接受 http 和 https 地址。非法输入要提示原因；保存失败不能丢掉已有收藏。不做账号、标签、搜索和云同步。

写下“这次不做什么”是为了划清边界，以后仍然可以做。

### 2. 确认方案和任务

AI 给出方案和任务计划，例如：

| 项目 | 内容 |
| --- | --- |
| 成果 | 能保存和查看收藏，刷新、重启后还在 |
| 边界 | 只在本机用，手工输入，没有账号和云同步 |
| 内部步骤 | 输入框和提示、保存接口、存储、列表、测试 |
| 检查 | 正常保存、非法输入、保存失败、数据保留，加一次独立审查 |
| 你怎么验收 | 在真实页面里保存一条，看列表，刷新，重启，再试一个非法地址 |

你只需确认整体成果和关键方案，页面、接口这些内部步骤不用逐个批准。

**你：**

> 确认刚才展示的本轮范围、方案、任务计划和验收方式，开始当前任务。

确认方案不包括提交代码、推送、部署这类操作。需要这些时，AI 会另外问你。

### 3. AI 实施和检查

AI 写代码，运行检查，安排审查，修掉发现的问题。这一步一般不用你插手，也不用反复说“继续”。

遇到范围、数据、安全或费用上的变化，AI 会停下来说明影响，让你决定。缺少运行检查需要的环境时，它会告诉你缺什么、怎么补。

### 4. 你来验收

AI 交给你的内容应该包括：

- 成果在哪里，从哪里打开。
- 操作步骤，以及每一步应该看到什么。
- 已经做了哪些检查，结果如何，还有哪些没验证。

在这个例子里，你可以：保存一条收藏，看到它出现在列表；刷新，还在；按步骤重启应用，还在；输入一个非法地址，看到清楚的提示。

自动测试 AI 已经跑过并留了记录，你不用重跑。你只看实际效果是否符合预期。

**发现问题时，你：**

> 当前任务还不能验收通过。保存后列表有记录，但刷新后消失。请按原来的数据保留要求修复，重新检查后再交付。

AI 会在当前任务里修好，再交给你。原来的要求不会被挪到以后。

**符合预期时，你：**

> 我已核对保存、列表、刷新和重启后的保留，以及非法输入提示。当前保存收藏任务验收通过。

只看了一部分时，可以说“刷新保留这一点通过，其他还没看”。AI 不会因此把整个任务记成通过。

### 5. AI 收尾

你验收通过后，AI 把这次真正交付的行为写进规格，保存检查和验收记录。你授权过 Git 操作的话，它还会完成提交、PR 和合入。

想以后再加功能，可以先记下来：

> 把标签和搜索记为后续候选，暂不实施。当前轮收尾后，再和我讨论下一轮范围。

## 项目资料放在哪里

这些文件大多由 AI 维护。想看哪份，直接让 AI 总结或打开。

| 位置 | 内容 |
| --- | --- |
| `docs/project/overview.md` | 项目目标、给谁用、包含哪些范围 |
| `docs/project/backlog.md` | 以后想做的事 |
| `docs/project/foundation/` | 工程、体验、安全、质量、运行等约定 |
| `docs/project/specs/` | 已经交付的功能行为 |
| `docs/iterations/<本轮>/scope.md` | 这一轮的目标和边界 |
| 同目录 `design.md` | 方案和取舍 |
| 同目录 `tasks.md` | 任务和进度 |
| 同目录 `verification.md` | 检查、审查、验收的记录 |
| `docs/workflow/state.yaml` | 当前停在哪一步的书签 |

### 哪些可以自己改

| 内容 | 能不能改 |
| --- | --- |
| 普通的文字、标题、列表 | 可以改。已有的确认和验收记录要保留 |
| `<!-- iterlane:record ... -->` 包住的记录块 | 不要手改，由工具写入和校验 |
| `docs/workflow/state.yaml` | 不要手改，由工具更新 |
| `docs/project/specs/*.md` | 保留原有结构和需求编号，按验收结果更新 |

想改任务描述或验收说明，直接告诉 AI。改文字不会改变任务进度，也不等于批准了新范围。

## 日常可以这样说

| 你想做什么 | 可以这样说 |
| --- | --- |
| 看进度 | “只查询当前状态，说明成果、等待和下一步，不改文件。” |
| 暂停 | “暂停当前任务，保存断点，说明还有什么没做完。” |
| 换会话后接着做 | “恢复之前的任务，先核对实际记录和文件，保留原验收状态。” |
| 比较方案 | “比较这两个方案，解释取舍，暂不实施。” |
| 只要审查 | “只审查当前改动，报告必须修复、建议和待核实项，不修改。” |
| 查问题 | “先定位这个问题，说明原因和修复范围。” |
| 记下新想法 | “这是后续想法，先记为候选，是否纳入本轮再讨论。” |
| 了解升级 | “查看当前框架版本和支持的升级路径，先预览，不执行。” |

一般不用指定技能。想明确从工作流入口开始，可以在支持技能调用的工具里输入 `$workflow-guide`。所有技能见[技能索引](../skills/README.md)。

### 换模型或换会话

- 先让 AI 读 `AGENTS.md`、`docs/project/foundation/`、`docs/project/overview.md` 和本轮资料，再查状态。
- 已有的约定和验收记录要保留，不要让新模型整篇重写。
- 两条约定互相矛盾时，让 AI 指出来，由你决定以哪条为准。
- 新模型写的 `tasks.md` 看不懂，可以说：“按上一轮的写法整理正文，保留当前任务、记录块和实际进度。”

### 地基约定改了以后

改了 `docs/project/foundation/` 里的约定后，可以对 AI 说：

> 先核对最新地基、当前任务绑定和适用确认，再开始实施。

AI 会重新读取约定，说明对当前任务的影响，再继续。工具会拦住用旧约定开始或交付任务的情况。

## 遇到问题怎样处理

| 情况 | 你可以怎么做 |
| --- | --- |
| 不确定 AI 有没有用上框架 | 让它只读查询项目状态 |
| 说了“继续”，AI 却没进下一个任务 | 当前任务在等你验收。先体验成果，再说通过或指出问题 |
| 验收不通过 | 说清你做了什么、看到什么、期望什么 |
| 会话断了或换了会话 | 告诉 AI 是哪个项目，让它先核对断点再恢复 |
| 检查跑不起来 | 让 AI 说明缺什么、有什么影响、怎么补。涉及费用、密钥或重要环境时由你决定 |
| 提示文件冲突或依据过时 | 保留现场，让 AI 先说明冲突在哪、影响什么 |
| 模型连不上、被限流、登录失败 | 先检查 AI 工具自己的网络和账号。这通常不是安装坏了 |
| 做到一半有了新需求 | 说清是原来要求漏了，还是新功能 |

想自己检查安装，在项目根目录的终端运行：

```powershell
node .ai-workflow/bin/iterlane.mjs status --json
node .ai-workflow/bin/iterlane.mjs doctor --json
```

- `status` 显示当前任务和在等什么。
- `doctor` 检查工具、状态、版本、日志和锁。命令运行成功不代表一切正常，要看输出里的 `local_valid` 和 `findings`。

恢复、升级、同步规格这些命令会写文件，让 AI 根据实际记录准备参数。不要自己猜编号、删锁文件或改状态来强行继续。命令说明见[命令参考](../scripts/README.md)。

## 常见误解

| 说法 | 实际含义 |
| --- | --- |
| “方案确认，开始实施” | 批准了 AI 展示过的方案。验收在交付之后才进行 |
| “测试通过” | 只说明这部分检查通过，审查、验收、收尾还要另外完成 |
| “这个任务验收通过” | 只通过这一个成果，不包括没展示过的新功能 |
| “继续” | 按已有授权往下做。当前在等验收时，仍然等着 |
| 技能（Skill） | AI 按需读取的一组工作方法 |
| 主 Agent | 和你对话、统筹任务和记录的那个 AI |
| 独立审查 | 由另一个独立会话做的审查，实施者自查不算 |

工具能核对记录和文件是否一致，不能判断成果在业务上对不对。最终是否符合预期，靠你的验收。

版本和支持范围见[版本与支持范围](releasing.md)。
