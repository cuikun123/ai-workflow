# 使用 Iterlane 开发项目

Iterlane 帮你和 AI 围绕同一份目标推进开发：说明要解决的问题，确认方案和任务，由 AI 实施、检查，你体验成果并验收，最后更新项目资料。

你主要负责业务判断：想要什么、哪些取舍可以接受、成果是否符合预期。AI 负责调查、技术方案、代码、必要检查和记录。通常直接用自然语言交流，不需要先记住十一项技能，也不需要手工填写状态字段。

还没安装时，先按[快速开始](quickstart.md)完成安装和客户端自检。本页从安装成功以后讲起。当前主要用于 Windows 上新建的本地项目；把已有业务项目接入框架，仍需另外确认和验证。

## 先理解几个概念

| 概念 | 在项目中是什么意思 | 例子 |
| --- | --- | --- |
| 项目地基 | 最小可运行工程和共同约定，为后续功能提供基础 | 应用能启动，存储能读写，有检查命令和必要安全约定 |
| 迭代 | 围绕一个目标开展的一轮开发，可以包含多个任务 | 让收藏应用具备最基本的收藏管理能力 |
| 任务 | 一个能交付、检查和验收的成果；内部可有多个技术步骤 | 添加收藏，能在列表看到，刷新后仍保留 |
| 检查 | 用实际执行的测试、命令或操作核对结果 | 测试非法地址，启动应用，核对存储内容 |
| 审查 | 从原始要求和实际产物检查遗漏、风险与实现质量 | 独立审查者检查保存失败是否破坏已有收藏 |
| 用户验收 | 你核对一个具体任务的成果，明确表示通过或给出反馈 | 体验保存和刷新后，确认这个任务满足约定 |
| 规格 | 记录一个业务能力当前已经交付的有效行为 | “合法收藏保存后，刷新和重启仍可查看” |
| 增量 | 本次准备对规格增加、修改或删除的内容 | 本轮新增“保存收藏”，以后再增加“按标签筛选” |

“做完代码”“检查通过”“你验收通过”“收尾完成”是不同的进度。AI 检查通过后会把成果交给你；你明确通过后，AI 才核对规格更新和适用的 Git 收尾，再进入后续任务。

### 一轮工作怎样推进

```text
你提出目标 → 一起明确范围和方案 → 确认任务计划
    → AI 实施、检查和审查 → 你验收当前成果
    → AI 更新规格和记录 → 接续下一任务或结束本轮
```

检查发现问题时，AI 在原任务中修复、重验。你验收不通过时，也返回当前任务。提出额外功能时，再决定放到后续待办还是调整本轮范围。

错字或排版修改可以直接处理并核对；明确的局部功能可以用简短方案；涉及权限、数据迁移、安全或未知业务的工作需要更多设计和验证。AI 应解释采用的深度，你不必自己选择内部流程模式。

## 第一次打开项目

在安装后的业务项目根目录打开 AI 客户端，创建新会话。先发：

> 查询当前项目状态，不改文件。说明安装是否完整、现在有没有任务，以及下一步可以做什么。

AI 应核对项目规则和实际状态。刚初始化的项目有技能、工具和资料目录，但还没有业务功能。空文档是正常的，AI 会在相应阶段填写。

然后说明真实目标，例如：

> 我想做一个只在本机使用的收藏应用，保存网页标题和地址。先帮我明确第一版范围和技术方案，暂不实施。

AI 应问清影响方案的业务问题，并主动调查能查明的技术信息。拿不准技术栈时，可以说：

> 我还没选技术栈。请给出适合这个目标的选择，解释推荐理由和维护成本。

新项目先建立地基。AI 会把起步范围、技术方案、任务和检查方式一起展示。你确认后，它建立最小工程，实际运行必要检查，提供可检查的成果供验收。安装框架和建立地基是两件事。

## 跟着一个例子走完开发

下面是**教学对话**，没有执行真实开发，也不代表任何任务已经通过检查或验收。实际服务地址、文件、测试数和结果必须由 AI 根据你的项目提供。

假设你已在新项目中建立并验收地基：应用能启动，本地存储可用，检查命令已跑通。现在开始第一轮业务开发，目标是保存和查看收藏。试用包中的[收藏示例](../examples/bookmarks/README.md)可以帮助理解最终效果；本教程描述你与 AI 怎样推进自己的项目。

### 1. 提出目标，明确范围

**你：**

> 开始第一轮业务开发。我想输入网页标题和地址，保存后在列表里看到，刷新和重启后都还在。先讨论范围和方案，暂不实施。

**AI 应做的事：**核对地基和当前状态，澄清影响成果的问题。例如收藏是否只保存在本机，地址允许哪些格式，保存失败时怎样反馈。AI 可提出推荐，你确认业务预期。

**你：**

> 第一版只保存本机数据，接受 http 和 https 地址。非法输入要提示原因；保存失败不能丢掉已有收藏。不做账号、标签、搜索和云同步。

这一阶段会形成简短范围和方案。记录“暂不做”的内容是为了明确边界；以后仍可安排。

### 2. 确认方案和任务计划

AI 展示方案、取舍、整轮任务及验收方式。这个目标可以作为一个任务：

| 内容 | 本例约定 |
| --- | --- |
| 成果 | 保存和查看收藏，刷新及重启后保留 |
| 边界 | 本机使用，手工输入标题和地址，无账号与云同步 |
| 内部步骤 | 输入和提示、保存接口、存储、列表展示、必要测试 |
| 必要检查 | 正常保存、非法输入、保存失败、数据保留及适用的独立审查 |
| 用户验收 | 从真实应用入口保存收藏，核对列表、刷新、重启和错误提示 |

页面、接口和存储是内部步骤，不需要你分别批准每个文件或按钮。你需要确认的是完整成果及关键方案。

**你：**

> 确认刚才展示的本轮范围、方案、任务计划和验收方式，开始当前任务。

确认要指向 AI 已经展示的内容。涉及 Git 提交、推送、真实数据、收费服务或部署时，还要具备对应操作授权；确认开发方案不会自动补齐这些权限。

### 3. AI 实施并检查

AI 在获准范围内完成代码和内部步骤，选择并运行必要检查，处理必须修复的问题，安排适用审查。它应报告实际结果与缺项，不能只说“代码看起来没问题”。

这一阶段通常不用你逐条选测试或反复说“继续”。关键范围、数据、安全、成本等发生变化时，AI 会解释影响，请你决定。

如果 AI 需要无法取得的环境或独立审查能力，它应说明缺少什么、已经检查了什么、怎样补齐；未完成的必要检查不能写成通过。

### 4. 收到成果，亲自验收

AI 交付时应提供：

- 当前任务的成果位置和真实体验入口。
- 必要准备、启动或操作步骤，以及可观察的预期结果。
- 已执行的检查和审查结论，已知限制与未验证项。

本例的验收点可以是：保存一个虚构标题和合法地址，确认列表出现；刷新后仍在；按提供的步骤重启应用后仍在；非法地址有清楚提示。

你主要核对体验和业务预期。已经通过的自动检查由 AI 留证，不需要你重复执行整套测试。保存失败等异常若需要专门环境，应由 AI 提供已核对的验证方式和证据。

**如果发现问题，你：**

> 当前任务还不能验收通过。保存后列表有记录，但刷新后消失。请按原来的数据保留要求修复，重新检查后再交付。

AI 应在当前任务内修复、重验并重新交付，不应把未满足的原要求移到后续待办。

**当成果符合约定，你：**

> 我已核对保存、列表、刷新和重启后的保留，以及非法输入提示。当前保存收藏任务验收通过。

只确认一个点时，可以说“刷新保留这一点通过，其他点还没检查”。AI 应保留部分反馈，不能把它登记成整个任务通过。

### 5. AI 收尾，接续后续工作

AI 核对验收对象和必要检查，只把实际交付的行为同步到当前规格；保存任务、检查和验收记录。Git 条件和授权具备时，再完成适用的保存、PR 和合入收尾。

收尾遇到文件冲突时，AI 应保留你的验收事实、现有文件和未完成事项，先解决受影响部分。用户验收通过并不意味着所有收尾已经成功。

本轮只有一个任务时，AI 还会核对整轮衔接并报告结果。有下一任务时，只有收尾和前置条件满足、授权适用才接续。

以后想加入标签和搜索，可以先提出：

> 把标签和搜索记为后续候选，暂不实施。当前轮收尾后，再和我讨论下一轮范围。

## 项目资料放在哪里

大部分记录由 AI 维护。你可以让它概述或打开对应资料，不必先手工填完所有文件。

| 位置 | 你会在这里看到什么 |
| --- | --- |
| `docs/project/overview.md` | 项目目标、面向谁、覆盖什么 |
| `docs/project/backlog.md` | 后续想法和未安排的工作 |
| `docs/project/foundation/` | 工程、体验、安全、质量和运行约定 |
| `docs/project/specs/` | 当前已经交付的业务行为 |
| `docs/iterations/<本轮>/scope.md` | 本轮目标、边界和拟修改的行为 |
| 同目录的 `design.md` | 必要方案和取舍；简单迭代可写在范围里 |
| 同目录的 `tasks.md` | 任务成果、依赖和实际进度 |
| 同目录的 `verification.md` | 检查、审查、验收和未完成事项的依据 |
| `docs/workflow/state.yaml` | 当前工作停在哪里的轻量书签 |

规格描述当前有效行为，迭代资料解释这一轮为何修改、怎样实施。未来想法先留在待办，未验收候选不能提前成为已交付规格。

状态书签可能过时。恢复时 AI 还要读取实际文件和记录，不能只凭一个 `completed` 字段认定完成。请让 AI 使用工具更新状态，避免手改内部字段来解除等待。

### 文档里哪些内容可以改

| 你会看到 | 能否修改 | 说明 |
| --- | --- | --- |
| 普通 Markdown 文字、标题、列表 | 可以 | 这是给人阅读的正文；保留已有确认、进度和验收事实 |
| `<!-- iterlane:record ... -->` 包起来的 JSON 记录块 | 不要直接手改 | 由工具写入和校验；改坏会导致检查失败，不能靠改字段跳过等待 |
| `docs/workflow/state.yaml` | 不要直接手改 | 由工具更新；手改可能与任务和记录不一致 |
| `docs/project/specs/*.md` | 按格式和生效时点改 | 保留 Purpose / Scope / Requirements 结构和需求编号；已交付行为按验收后同步规则更新 |

想调整任务描述或验收说明时，直接告诉 AI 修改正文，并核对相关记录与确认依据，不需要自己动记录块。改正文不会自动批准新范围或改变任务进度。

### 初始化后的地基文件

初始化后 `docs/project/foundation/` 下的 6 个文件为空（0 字节），这是正常的，**不代表地基已经建立**。地基在第一轮迭代 `000-foundation` 中建立：AI 按已确认范围形成工程、体验、安全、质量和运行约定，并实际运行必要检查；README 负责这些约定的导航。

地基验收时请核对这 6 个文件的内容。仍为空的，请让 AI 说明是“当前不适用”还是“待补充”，以及原因和补充阶段；不要求把暂不需要的内容全部填满，但本轮必需的约定和检查尚未落实时，不能认定地基完成。

## 日常可以怎样说

| 你的需要 | 示例表达 |
| --- | --- |
| 看进度 | “只查询当前状态，说明成果、等待和下一步，不改文件。” |
| 暂停 | “暂停当前任务，保存获准范围内的断点，说明未完成事项。” |
| 换会话恢复 | “恢复之前的任务，先核对实际记录和文件，保留原验收状态。” |
| 比较方案 | “比较这两个方案，解释取舍，暂不实施。” |
| 单独审查 | “只审查当前改动，报告必须修复、建议和待核实项，不修改。” |
| 查故障 | “先定位这个问题，核对原因和修复范围。” |
| 提出新功能 | “这是后续想法，先记为候选；是否纳入本轮再讨论。” |
| 检查升级 | “查看当前框架版本和受支持的兼容路径，先预览，不执行升级。” |

通常无需点名技能；需要明确工作流入口时，可在支持技能调用的客户端使用 `$workflow-guide`。其他技能及适用范围见[能力索引](../skills/README.md)。

### 换模型或换会话时

- 先让 AI 读项目 AGENTS.md、`docs/project/foundation/`、`docs/project/overview.md` 和当前迭代资料，再核对实际状态，避免自行推断项目约定。
- 保留已有项目方向、地基约定和验收事实，不因换模型而整篇重写。需要改变有效约定时，先明确变更及适用确认，再更新受影响内容。
- 发现两处适用约定互相矛盾时，让 AI 指出冲突和影响，由你明确以哪条为准，不让它自行择一。
- 新模型写的 `tasks.md` 看不懂时，可以要求“按上一轮的写法整理正文，保留当前任务、记录块和实际进度”。

结构化记录和规格格式受工具校验，普通正文没有强制统一文风；换模型后仍需核对文字是否清楚、约定是否一致。

## 遇到问题怎样处理

| 情况 | 你可以怎样做 | AI 应怎样处理 |
| --- | --- | --- |
| 不知道是否用上框架 | 要求只读查询项目状态；需要实测客户端时，要求客户端自检 | 区分本地安装检查与一次真实客户端调用 |
| 当前待验收，说“继续”没有进入下一任务 | 先体验当前成果，再明确通过或给反馈 | 保留等待，给出成果入口，不猜测你已通过 |
| 验收不通过 | 指出操作、实际结果和预期 | 在原任务修复、重验、重新交付 |
| 会话中断或换了会话 | 指定项目，要求核对断点后恢复 | 核对文件、记录、原确认和外部操作结果，只接续未完成部分 |
| 检查运行不了 | 让 AI 说明缺项、影响及补齐方案 | 处理授权内的准备；费用、凭据或重要环境变化请你决定 |
| 文件冲突或提示依据过时 | 保留输出和文件，要求先说明冲突对象及影响 | 重新核对当前内容；不覆盖用户修改、不伪造新批准 |
| 模型连接、限流或登录失败 | 检查客户端自身连接和账户，保留脱敏错误 | 区分模型服务问题与安装损坏，不因此重做结果未知的操作 |
| 做到一半提出新需求 | 说明是修正原预期还是额外功能 | 原要求遗漏留在本任务；额外功能经确认后调整范围或进入待办 |

需要自己检查本地安装时，在业务项目根目录的终端运行：

```powershell
node .ai-workflow/bin/iterlane.mjs status --json
node .ai-workflow/bin/iterlane.mjs doctor --json
```

`status` 查询当前工作；默认 `doctor` 诊断本地资源、状态、版本、日志和锁。诊断命令退出成功只表示诊断完成，健康情况看 `local_valid` 和 `findings`。可以把脱敏输出交给 AI 分析。

恢复、升级或规格同步会写文件，所需版本、操作编号和确认依据应由 AI 核对实际记录后准备。不要猜编号、删除锁或修改状态来强行继续。命令参数见[工具参考](../scripts/README.md)。

## 常见误解与术语补充

| 表达 | 应怎样理解 |
| --- | --- |
| “方案确认，开始实施” | 批准已展示的方案和工作；成果验收发生在交付之后 |
| “测试通过” | 对应范围的检查通过；仍要核对审查、验收和收尾 |
| “这个任务验收通过” | 明确通过这个成果及对应内容，不批准未展示的新功能 |
| “继续” | 接续已有授权；当前待验收时保留等待 |
| Skill／技能 | AI 按需要读取的一组工作方法；单个技能文件不包含完整运行工具 |
| 主 Agent | 统筹当前任务、协作和正式记录的 AI；你通常与它交流 |
| 独立审查 | 由真实独立上下文进行的审查；实施者自查不能冒充独立审查 |
| DoD／通用完成标准 | 项目共同质量要求，和某个功能的具体验收条件一起适用 |
| 候选版本 | 准备交付检查或验收的具体内容；改动后要重核对受影响证据 |
| PR／任务分支／worktree | Git 协作和保存方式，具体解释与权限见项目 Git 约定 |

框架工具核对本地记录、引用和文件内容的一致性。真实业务判断、检查是否实际执行、批准来源和操作权限还依赖 AI 与宿主核对。一份记录写着通过，并不能证明实际成果正确。

采用当前候选新初始化的项目，会在状态依据中跟踪 `docs/project/foundation/` 的Markdown内容及目录成员。修改、新增或删除会被只读状态查询报告；旧书签显示 `foundation_tracking:untracked` 时尚未采用这项跟踪，不能手改字段冒充迁移。地基约定是否完整、变更影响哪些任务，仍需你和AI核对，过时提示不自动取消历史验收或批准新方案。

需要核对最新约定时，可以让AI运行：

```powershell
node .ai-workflow/bin/iterlane.mjs context inspect --json
```

输出包含必要规则、能力信息、项目规则与地基原文，以及 `snapshot_sha256`。完整共享manifest由工具校验，不返回其正文；文件哈希仍参与快照和任务绑定。后续可把这次摘要交给 `context guard --expected-snapshot <实际SHA256> --json`；`fresh`只说明输入仍匹配，`stale/unknown`需要重新读取并说明影响。当前任务需要自己的有效绑定，之后工具才允许启动、恢复、进入检查、交验收和收尾。同一会话开始T2也要核对T2，不能沿用T1的记录。地基变化后，AI先重新读取、说明影响并核对适用确认，再用context bind绑定最新依据；这一步由工具同次登记说明，不需要你手改JSON。

可以直接告诉AI：“先核对最新地基、当前任务绑定和适用确认，再开始实施。”任务声明要变更时使用task_revise；普通正文仍按既有授权修改。工具能核对资料与记录一致，约束是否理解和落实仍要实际检查。Claude Code/Pi自动注入尚待后续接入，不能把一次查询当作自动遵守的证明。
