# 线上问题调查与修复交接

先明确问题和范围，再取证；诊断结论与修复、部署授权分别判断。方法来源及裁剪见 [NOTICE.md](NOTICE.md)。

## 1. 先收集必要信息

先读用户给出的现象、项目 AGENTS 和已有入口约束，不先运行排障命令、读取线上日志或试探服务。按已有信息补问会影响调查的缺项：目标项目/环境与运行版本、具体操作及实际/预期、开始时间和影响范围、脱敏报错或请求样例、近期变更，以及可用访问边界。已有明确回答不重问，不要求用户填满工单或自己判断根因。

必要信息未齐先询问，独立的方案整理可继续；不能把本地文件中的模糊 TIMEOUT 当作已定位的线上问题。必要信息已明确时，简述问题、目标环境、读取范围、允许操作和停止条件，在已有适用访问授权内直接调查，不重复索取相同确认。

## 2. 按证据调查

读取适用 operations、发布记录、相关要求及实际代码/配置和脱敏日志，识别运行版本和候选修复内容。新候选的要求不能套旧运行版本。原始要求、现象、已证实原因、假设、未知分开。优先用已有可观测数据，比较正常路径，沿组件输入输出定位断点，一次检验一个假设。

默认只读；复现请求可能写数据或产生费用，新增日志、抓取敏感信息、重启、改配置、数据处理及真实环境操作都逐项核对影响和授权。“调查”不自动许可这些操作。可在已获准且不影响真实项目/业务的隔离环境复现，记录真实覆盖；模拟通过不等于线上原因或恢复已证实。

已安装 debug-issue 时读完整说明，传入问题与原始依据、运行/候选版本、具体允许操作及证据，仅使用其调查方法，不因此获得修复权。无工具或访问条件就报告缺项，不能伪称查询或临时安装上游。连续两轮无新证据或反复回退时停止重复尝试、重新取证；仍不明就报告阻塞，不以到限判通过。

## 3. 提出并交接具体方案

报告已知问题与影响、原因依据/假设/未知、方案及代价、涉及的文件/环境/数据、验证与恢复办法及未覆盖风险。用户同意具体方案后在其范围内承接，不重复确认同一方案；故障反馈、调查请求或一般开发授权不能代替该同意。修复同意不自动覆盖生产部署或数据操作。重要范围、数据、安全、成本等变化再按项目规则处理。

由原主Agent保留同一项目/成果、请求模式、目标内容/运行版本、确认依据、允许读写、已有证据、未决项和返回位置。适用修复迭代已有执行主责时返回该任务；execute-task用于实施、验证及用户验收，test-work/review-work提供所需检查方法，不递归启动多条流程或重复整轮审查。没有适用迭代时，只在下述紧急修复条件与具体确认满足后建立修复轮；其余情况交付接续缺项，不自行启动普通新轮。

### 紧急修复、线上基线与返回

1. **判断安排。** 需要立即处理的线上故障，在具体修复方案已获同意后单独开小修复迭代，只包含必要修复；紧急性或方案未明先澄清受影响部分。非紧急问题默认进入已有backlog候选，不打断当前轮，不把候选记成已批准实施；只有记录权限具备才写，保持原始反馈和候选状态。用户明确另作安排时沿用具体确认。
2. **保存原轮。** 有正在推进的开发轮时，按execute-task完整Git方法精选允许内容作WIP并在条件具备时远端备份，原tasks保留暂停依据、未完成项、原验收状态、修复轮去向和恢复条件；冲突按需保留现场，不机械普通提交。暂停不代表通过验收；原成果待验收仍保留其候选与入口。切换时已有“修复收尾后回来”的约定一并记录，未有约定不发明自动返回。保存或记录受阻不假定完整切换成功。
3. **准备修复轮。** 由主Agent按既有命名及实际路径创建scope/design/tasks/verification，沿用原任务编号规则，内容按需要精简；可读clarify-design承接明确路径的资料准备、plan-tasks安排成果。scope引用原轮暂停/返回依据、具体修复确认、线上目标及排除范围。创建资料不批准未确认方案或部署，不写通用state，不另建工单/报告树。已有修复轮或中断重试先核对复用，不重复创建。
4. **固定线上基线。** 通过实际发布记录和目标环境运行证据核实当前线上版本对应的提交/固定标签，不猜用最新main、最大标签或本地HEAD。基线不明暂不创建补丁。按execute-task的路径、归属和合法命名检查，在项目同级worktrees中从该运行提交创建独立修复分支/目录；这是普通任务从同步后main起步的例外。补丁只含线上版本与必要修复，不把main上其他未发布改动Merge进来；目录隔离不自动隔离运行资源。
5. **先恢复线上。** 在补丁分支完成针对该运行版本的修复、必要测试、真实产品验证和全新独立代码审查，按execute-task核对开发提交及PR验收交付时点；用户明确通过后收尾对应记录和规格。在具体部署授权下交release-work为已验证补丁创建并远端保存固定标签，发布指定补丁并核实原故障及必要业务/数据恢复；不能为普通PR合入顺序提前将补丁回合main，也不将PR存在当已合入。若当前PR尚不能准确表达后续主线目标差异，说明条件并保留未完成，不能制造错误合入。发布失败按已获准回退方案先回退、核验、报告并等待重试决定。
6. **按需确保主线覆盖。** 线上恢复后获取并核对当时main与修复：main已经包含等效有效修复则核验并记录，不制造无意义PR；可直接衔接则使用修复分支的同任务PR，按既定验收、收尾及最终集成门槛Squash；只有实际冲突或相关代码不兼容才从同步后main建立必要适配分支/worktree，沿同一修复任务关联原补丁及实际差异，补受影响验证/审查，行为变化重新验收。优先核对并更新已有相关PR，不为同一交付重复创建；主线处理是同次修复收尾，不默认额外适配一轮、不固定cherry-pick或逐一适配所有未发布提交。合入触发上线仍核对部署权限，不能顺带发布其他主线改动。
7. **最后清理和返回。** 线上已恢复、main覆盖修复且实际发布补丁提交的固定远端标签/必要产物已保留后，才按execute-task检查使用者、进程、未跟踪/忽略资料，移除对应临时worktree再清理本地/远端分支，保留发布标签和产物。main已覆盖而无新PR的路径，以实际修复覆盖、验收、发布恢复及版本保留证据核对，不伪造PR合入事实。线上已恢复但主线或清理受阻时分别报告并保留现场，不称整个修复完成。全部适用收尾满足后，主Agent核对预先返回约定、原轮状态/授权及新指令/阻塞；有约定且条件满足直接恢复，原任务待验收则仍等待。无返回约定或条件不满足按已有确认规则交付下一步，不自动推进下一成果。

以上只在具体修复、保存、Git与部署的适用权限内使用真实工具；缺工具就报告条件，不能把规则接入或模拟恢复写成生产验证。每组Git操作后由主Agent报告动作、实际提交/PR/分支、结果与剩余项；重复请求先核对实际仓库、远端/发布状态及原记录，只补获准未完成部分。

修复后核对原失败场景和受影响检查，按必要独立审查及用户验收收尾；需上线再由 release-work 核对具体部署授权。成功上线后的故障不能直接套发布失败规则立即回退；当前发布执行失败则仍由 release-work 按事前获准方案先回退，不重启本项问诊延迟处理。

## 4. 返回与记录

返回问题/环境、实际调查与证据、原因置信边界、执行/未执行操作、方案确认状态、当前运行状态与下一步。只有实际业务与数据核验支持时才称恢复；健康探针通过不证明全部功能恢复。

主 Agent 将必要证据合并适用 verification/tasks 或已有 releases，写前回读并保留历史；仅查询、只读请求或无记录位置时在对话交付。受托者只返回，不争写正式记录。本项不写 state.yaml 或有效规格、不建工单/报告树、不自动重试发布，不把建议当已修复或已验收。

例如只收到“线上导出失败”时先问目标环境、影响和脱敏现象；得到只读范围后查到 TIMEOUT 只算超时事实，需进一步证据才能归因。提出调整超时或重启都仍是待同意方案，不能顺手执行。
