# 任务计划

把已确认要求组织成可验收成果，在成果内部说明实施与验证方法，再检查覆盖与一致性。用中文说明；项目已有术语、编号和文件风格优先。

本 Skill 融合 Spec Kit tasks、Superpowers writing-plans 和 Spec Kit analyze 的适用方法，直接使用项目资料，不调用或安装原版流程。来源、固定版本与许可证见 [NOTICE.md](NOTICE.md)。

## 专项能力协调

接收 workflow-guide、clarify-design 或 discuss-design 的材料时，核对项目与成果、请求模式、原始要求及确认状态、目标内容/运行版本、允许读写、已有证据、未决项和返回位置。讨论推荐不是已确认方案；共同主 Agent 保留记录责任，不重复整轮澄清或启动执行。只在需要且能力真实可用时读对应完整说明，缺能力返回材料，不伪称调用或安装上游。

地基成果可交 build-foundation；发布准备/获准部署可交 release-work；线上问题须由 handle-incident 先明确问题和方案授权。按项目实际风险安排权限、敏感数据、输入边界、依赖来源、运行观察及数据恢复检查；同一成果内的专项方法是技术步骤，不按 Skill 名机械拆成重复验收任务。代码回退与数据恢复分别覆盖，发布前置和失败后等待是否重试不能被一般任务授权覆盖。既有适用证据引用一次，变化后补受影响检查。

## 1. 定位本次计划

从用户明确指定的业务项目根或当前项目开始，读取其 AGENTS.md、已有 docs/workflow/state.yaml，核对当前迭代。用户明确指定的目标优先核对；导航只是线索，不是批准记录。

- 目标须落在该项目docs/iterations/下，结合明确的开轮、暂停、恢复确认与实际资料定位。已有明确依据不重复询问；没有足够依据且存在多个候选时再澄清，不按最大编号、最近修改或唯一未标暂停目录猜选。
- 缺少导航但用户明确指定已有迭代时，可在核对后为该迭代规划，不代替初始化器创建状态。缺少范围或方案时，先补查现有资料；仍不清楚的关键业务意图向用户澄清。
- 框架开发仓库自身的 docs/design/、docs/handoff.md 与 templates/project/ 不是业务迭代。用户没有指定业务目标时，不把模板或示例当作本次业务项目。
- 仅查询进度时读取并报告，不生成、重写任务或状态；尚未选定需求时回到澄清，不凭一句想法编造已确认方案。

读取当前迭代的 scope.md、design.md、tasks.md、verification.md，关联业务规格、项目 overview.md 和适用 foundation 约定。简单迭代的方案可在 scope.md 中。空文件表示资料未填写；后续阶段的合法空文件不要求现在补齐。必要时只读实际工程，核对已有文件、接口、依赖和验证命令。

前置需求或方案需要澄清时，可按请求使用实际可用的 clarify-design；已由它整理的内容直接读取，不重新进行整轮问答。范围及关键业务规则明确、用户要求准备设计与计划联合确认时，可以基于明确标为草案的设计编写计划草案，保留设计和计划的待确认状态，不要求为编写计划先单独批准设计。重要未决事项影响的部分保留，不凭假设补成确定任务。当前有效规格与本轮拟变更要分别识别：明确获准的本轮变更仅在对应行为与目标版本上以 scope 及确认依据为准，其余有效规则继续遵守，未确认备注不能覆盖确认。候选实现与旧版本环境分别核对适用要求；两份适用确认真正冲突时澄清受影响部分。能力不可用时沿用上述资料核对和缺项澄清，不临时安装上游。

## 2. 确定输出与保留范围

尚无适用迭代且用户明确要求开启普通后续迭代并准备资料时，交原主Agent使用可用的clarify-design核对前置和创建既定资料，再接收明确路径与确认依据规划；不能因缺迭代就自动开轮。只讨论、目标不明、记录冲突或线上修复迭代安排时，返回对应缺项和原流程。空tasks仅是占位，不等于计划已确认；本项不负责开轮、overview维护或暂停切换记录，不循环启动入口或执行流程。

默认业务写入只有**当前迭代 tasks.md**。确有必要保存本次计划检查依据时，沿用同一迭代 verification.md，保留原有记录。读取 [任务内容与更新方式](#任务内容与更新方式)，使用其内容要求；不另建 plan.md、分析报告、进度 ledger 或上游目录。

写前核对项目根、当前迭代及目标文件实际位置；遇到链接、路径越界或目标不明确时停止受影响的写入，先澄清。记录已有任务编号、成果、顺序、实施进度、检查结果和用户验收事实。落盘前回读目标，发现其他人改动则基于新内容合并，不覆盖旧快照。

本能力不修改代码、依赖、范围、规格、设计、AGENTS.md 或 state.yaml，不创建新迭代，不提交或推送。发现这些资料需要改变时说明原因并交给对应阶段处理。已有上游同名目录可能是用户资料，不自动删除。临时推理与简短盘点留在对话，不生成新的正式文档。这里的写入规则是 Agent 行为约束，不能当成宿主权限沙箱。

## 3. 按成果组织并细化

1. 从范围和规格提取实际要求、验收条件与排除项。沿用已有编号；没有编号时引用原段落或标题，不新增一套全局需求编号体系。
2. 每项任务交付一个可独立判断的完整成果。普通功能覆盖从用户操作到结果的最小场景；文件、数据表、接口和页面通常是内部步骤。可独立交付的工程、接口或文档也可成任务，不强制页面或用户故事格式。
3. 写明成果边界、依据、验收方法、依赖与顺序，再补充必要技术子步骤。共享准备工作归属相关成果；独立工程成果按实际范围安排，不强制设置固定阶段。
4. 细化会影响协作或正确性的文件职责、输入输出、接口约束和精确业务值。已存在的路径、签名和命令先查实；计划新增的明确标为拟新增。项目尚无工程时可提出必要职责和拟采用路径，不能称已经存在或运行成功。
5. 为各成果安排正常、关键边界和异常验证。验证方式与影响相称，不要求用户先提出测试，也不机械要求每项修改都写测试或采用固定 TDD 序列。可运行命令写明预期；暂不能确定时记录需核对的入口与条件，不能虚构命令或把原始要求移出任务。
6. **普通功能任务在提交用户验收前安排独立审查，并安排有效问题修复、重验与复查。** 低影响修改可按实际影响简化，高风险按需专项检查；整轮交付前检查跨任务衔接。技术子步骤自主推进；每个成果提交验收后等待用户明确通过，不能把审查、测试或整轮计划批准当作用户验收。

开发步骤和检查步骤留在所属成果内。计划中的“将运行”“预期通过”不是执行证据；新任务分别标明实施未开始、AI 检查未执行、用户验收未提交。对已有任务如实保留现状。

Git生命周期是每项完整成果的内部步骤：起步前按归属保存本次涉及目录的改动，fetch并仅快进落后主分支，核对一致后从本地主分支开独立任务分支及同级worktree；恢复同任务复用原位置。开发提交与最终候选的产品验证、全新独立代码审查及必要修复检查通过后，创建PR交用户验收并等待；明确验收后同步对应规格/记录、提交推送并更新同一PR，核对当时主线衔接、最终检查后Squash为一条正式任务提交，再核实PR结果、保留资料、移除对应worktree和两端分支。主线更新以普通Merge进入任务分支；领先/分叉、必要检查或权限缺失、需决策的冲突保留现场，不以清理代替处理。完整操作由执行主Agent读取实际可用execute-task，计划本身不执行Git。

暂停/必要阻塞安排精选本任务WIP、具备远端及推送权限时备份，并分别记录本地/远端结果和原验收状态。紧急线上修复由handle-incident安排保存暂停原轮、独立小迭代、实际线上提交基线、先补丁发布确认恢复再主线覆盖与最后清理；非紧急问题默认候选。发布标签和部署交release-work核对，不能因普通Git收尾自动上线。缺真实工具或项目条件如实列前置，不假定GitHub、远端或生产已经就绪。

涉及业务变化的成果应包含验收后的规格收尾：关联需同步的需求与场景，由执行主 Agent 在验收且必要检查、审查满足后更新；收尾与恢复沿用本任务及 verification，不另拆验收任务或创建报告。无业务变化不安排机械改规格；本技能只规划该步骤，不执行同步。公共约定继续按其确认和生效时点安排。

框架升级按独立任务安排，默认当前任务验收及适用收尾后再做，不自动追随新版。普通升级只更新受管理框架资源和必要导航，保留业务内容、用户修改与进度；确需业务代码、依赖或构建变更时单独说明并确认。计划沿用既定Git、验证与验收流程，在现有任务/验证文档记录升级前实际版本、拟升级目标及升级后实际版本；不能核实时保留未知，不发明锁定文件格式或声称安装/回退运行机制已实现。

## 4. 核对覆盖与一致性

对照原始资料审阅计划，不仅检查计划自己的表述：

- 每项要求和验收条件是否有对应成果及必要工作？有没有遗漏安全、数据、失败恢复或非功能约束？
- 每项任务是否有范围依据？是否因模板多加功能，或把不明确的业务规则当作要求？
- 名称、字段、精确值、接口供需和依赖顺序是否一致？相关成果能否一起工作？
- 验证与审查是否覆盖实际风险，并能给用户提供可执行的验收办法？
- scope/design/tasks 是否对同一成果的验收、规格同步及下一成果前置给出一致安排？每项成果验收收尾后再接续，不能在设计里改成等整轮验收才统一同步。新入口、错误语义或验收行为没有原始依据时，标为待核对或方案建议，不写成既有约定或已确认规则。
- 任务粒度、顺序和已记录进度是否符合原计划与用户确认？

无需固定数量的发现或报告表。问题给出位置、依据、影响和处理建议；没有有效问题可以明确说未发现。未确认备注不能覆盖已确认要求；双方均已确认而互相冲突、或关键意图仍不明确时先澄清，独立部分可继续，整体保留未完成状态。仅由措辞或关键词推断的覆盖关系不能当作确定证据。

## 5. 更新并提交计划

已有计划只修改需要细化的部分，保留编号、已完成步骤、检查和验收历史。普通内部步骤可在授权内调整；拆分、合并成果或影响交付的顺序、依赖、验收变化，先在对话展示原因、前后差异及影响，获确认再修改正式安排。记录调整原因，不通过删除未满足要求或合并下一任务绕过验收等待。

回读本次实际修改，核对只有允许的文件变化，引用可定位且历史事实未被覆盖。输出简短说明：计划位置、成果及顺序、检查结论与保留问题、当前确认状态和下一步。详细依据按需进入 verification.md，不把计划自查记为独立审查或功能测试通过。

新计划按项目已有的设计与计划确认规则交给用户，不重复索取已有适用确认。**仅要求编写或调整计划的请求到此结束；不启动代码实施、上游执行 Skill 或 Git 操作。** 后续由主流程核对具体计划确认与执行授权再接续。Skill 被读取或任务文件存在，不代表计划已批准或任务已完成。

## 任务内容与更新方式

编写或调整当前迭代 tasks.md 时读取。这里约束任务需要表达的信息，不定义全框架状态 schema，不要求迁移已有文件格式。

### 每项成果需要表达什么

| 内容 | 写法 |
| --- | --- |
| 编号与成果 | 沿用原编号；新计划按现有习惯编号。标题说明交付结果。 |
| 依据与边界 | 引用 scope、规格、设计或公共约定中的具体要求，写明本成果做什么。共享约束引用一次即可，不复制整份规格。 |
| 验收方法 | 用户能从哪里、经过哪些必要操作、看到什么结果；接口、工程和文档给可执行检查方式。 |
| 依赖与顺序 | 哪项成果或条件先具备；输入和输出如何衔接。 |
| 技术子步骤 | 必要职责、文件或拟新增位置、接口约束与实施路径；不提前写整份产品代码。 |
| 验证与审查 | 相关正常、边界、异常检查及预期；普通功能的独立审查、修复重验复查；跨任务整体检查按影响安排。 |
| 验收后收尾 | 对应业务变化需同步的规格范围；由执行主 Agent 在本成果验收和必要条件满足后完成，再判断下一成果前置。无业务变化不机械改规格。 |
| 三类事实 | 实施进度、AI 检查结果、用户验收分别表达。历史证据保留日期或引用，不被未来步骤覆盖。 |
| 调整原因 | 修改原安排时记录原因与适用确认，不抹去原任务的历史。 |
| Git位置与条件 | 计划写拟用基线、分支/worktree及项目同步/推送/PR目标；执行后由主Agent记录实际提交、PR、保存备份及收尾结果。名称沿用已有迭代/任务标识，不能把拟执行写成成功。 |

新计划可以用以下虚构例子的表达密度；它不增加任何真实业务要求，也不表示对应代码或服务存在：

```markdown
## T1 用户保存一条书签后，刷新仍可找到

依据：scope.md 的本轮目标与规格“保存书签”。边界：只支持手工输入单条书签。
验收：打开书签入口，输入合法地址并保存，看到新记录，刷新后仍存在。
依赖：既定基础工程与存储入口可用。
实施：未开始；AI 检查：未执行；用户验收：未提交。

- [ ] 核对已有页面、存储接口和验证入口，记录实际改动位置。
- [ ] 完成输入、保存和结果显示，按规格处理非法地址和保存失败。
- [ ] 验证成功、非法输入、保存失败及刷新保留，记录实际结果。
- [ ] 独立审查需求符合性与实现质量；有效问题修复、重验并复查。
- [ ] 提交体验入口、步骤、预期及检查依据，等待用户明确验收。
- [ ] 验收且必要检查、审查满足后，由主 Agent 同步本成果实际交付的业务规格；核对收尾记录，再判断下一成果的接续条件。
```

不要求把最后一项勾选框当作正式状态协议。子步骤勾选不能代替三类事实，也不能在用户尚未通过时把整个任务标为完成。具体状态字段遵循项目已有约定。

### 已有计划的处理

先识别原成果及其内部步骤，然后作局部修改。若一项任务的存储步骤已完成、页面未完成，只细化剩余页面、联调、验证和验收，不重置存储步骤、不将其重新变成新成果。

历史已验收成果不因整理计划而改名、重排或删除。后续真实变更影响它时保留历史验收事实，说明受影响内容并安排必要重验和重新验收。当前计划无法容纳要求时提出安排调整，不先改掉正式边界再让用户追认。

### 检查依据放在哪里

对话先给短结论。需要持久化的计划检查发现和处置进入当前 verification.md，注明检查范围、实际依据、仍未解决的问题与下一步。分析覆盖是计划检查，不是代码测试。已经存在的测试、审查和用户验收记录保留原样，新增记录不声称覆盖本次未执行的检查。
