明确开轮、暂停恢复或维护overview时读取。已有v1记录看[原状态协议](common/state-runtime.md)，新任务看[规格与记录工具](common/spec-runtime.md)。

## 5. 后续迭代、暂停恢复与项目概览

本节由当前主Agent在已有业务项目的既定文档结构内执行。核对用户的明确请求及适用确认，只处理对应操作；同一次指令可以同时确认目标、开轮和资料整理，不另设建目录审批。专项调用本身不是开轮或切换指令；无业务项目时继续对话，不借此初始化项目、安装框架或创建导航。紧急线上修复由incident先核对具体方案、暂停保存、独立小迭代及实际线上版本基线，再交本项按已明确的修复轮路径准备既定scope/design及tasks/verification占位；不按普通开轮擅自决定线上修复或基线。已有适用任务内的调查或修复返回原流程，不循环调用入口。

### 明确开轮

1. **核对前置。** 目标已明确且用户要求开启后续迭代并整理资料。原轮已完成当前确认范围的用户验收、必要检查/审查、对应规格收尾及整轮衔接核对，或用户已明确暂停切换。原成果待验收且没有明确暂停时，只整理不依赖开轮的对话内容，保留原验收入口。暂停不把原成果改为已验收或已完成。
2. **定位和保留。** 用户指定路径优先；没有指定时沿用项目命名约定，无约定可提出三位编号加短名称作为默认。编号仅用于命名，不能选择当前轮。纯名称冲突可在已有授权内选不覆盖资料的名称；用户指定路径已有其他成果、目标归属不清或真实路径/重解析目标越出业务项目时，停止受影响写入并澄清。重复请求复用同一轮，写入与历史保护按[写入契约](common/write-contract.md)。
3. **记录切换依据。** 需要暂停原轮时，先按下一节在原tasks记录确认和未完成事项，再准备目标轮资料。暂停记录写入失败时，不继续依赖它的新轮创建；若原轮已收尾，新scope引用已有收尾依据即可，不编造暂停。缺少可写的原记录位置时报告缺项，未持久化的事实在对话交付，不宣称切换已完整落盘。
4. **准备既定文件。** scope记录本轮目标、已有确认、草案/待定部分和原轮收尾或暂停依据；必要design记录方案，简单迭代可并入scope。仅在文件不存在时建立空tasks和verification占位；不清空已有文件，不编写任务计划或虚构检查结果。交付明确的项目和迭代路径及下一步。目录存在不代表范围、设计、计划或实施已获批准；已有适用确认也不因开轮被重置为草案。
5. **关联候选。** 事项已明确获准纳入本轮且scope实际写入后，由主Agent在已有backlog保留原条目、原始反馈及其他关联，补对应scope路径和实际入轮范围；部分纳入不标整项完成。只选讨论主题或仅有候选草案时不记为已入轮。重复执行不重复添加同一去向，入轮不等于实施或验收通过。

### 暂停、恢复及中断

明确暂停（包括“今天到这里”）或切换时，原主Agent先读取实际可用implementation的Git保存方法：核对任务归属与入库许可，精选本任务内容及暂存区，有改动才作本地WIP，具备远端与推送权限则备份并分别核对；需决策的Merge冲突保留现场、不普通提交或abort。任务进度、暂停/恢复记录和Git断点共同保存，记录不虚构成功；保存/写入受阻保留已完成部分，不能当完整切换。本项只承接正式文档，不另执行一套Git或要求已确认规则逐步批准。仅查询仍只读。

主Agent在受影响的原tasks保留暂停/恢复的明确确认依据、日期、目标迭代路径、未完成事项、原验收状态和恢复条件；只补事实，不重排任务内容或改写验收历史。用户明确从当前轮切换回指定旧轮时，该切换指令可作为当前轮暂停和旧轮恢复的依据，无需重复索取相同确认；对象或含义不明确时只澄清受影响部分。先保存当前轮暂停，再记录目标轮恢复；任一步失败均保留现场和未完成部分，不写成全部切换成功。

恢复前对照具体开轮、暂停、恢复确认与实际scope/tasks/verification，核对目标内容是否仍适用。草案、缺少暂停标记、唯一未完成目录、最近日期或旧state都不足以单独确定当前轮。记录矛盾、缺失或部分写入时保留未知，不凭缺失记录推定从未执行；无可消解依据才询问。只查询时返回核对结果，不补写暂停/恢复记录。

明确要求补完上次开轮或记录时，逐项对照已有确认和真实文件，只补未完成部分；不能重建新轮、覆盖期间新增的用户笔记，或靠删除已写文件恢复旧快照。写后回读本轮资料、原轮记录和backlog关联。失败时报告已写/未写位置、影响、恢复条件和下一步；仍能写入的适用tasks/verification可保留必要恢复依据，否则在对话交付。不把预置中断或普通文件写入称为事务保证或真实I/O失败验证。

线上修复明确约定收尾后返回原轮时，将该约定、原任务与验收状态、恢复条件写在既定tasks并关联修复scope；修复完成验收、发布恢复、主线覆盖和清理后由原主Agent按incident核对返回。原任务待验收仍恢复为等待，不把暂停、修复或返回记为原成果通过。

### 维护overview

用户已明确项目方向、目标用户或项目级范围，并要求整理或已有适用文档维护授权时，主Agent首次填写或更新docs/project/overview.md；没有当前迭代不阻止这项明确维护请求。文件缺失但既定项目目录与归属明确时，可创建该文件，不补建整套项目结构。只写已确认的方向变化，保留无关内容与用户修改，不等功能验收才记录方向；未来目标不写成已交付功能。未确认建议留在对话、backlog或设计，普通迭代不机械改overview。任务进度和历史仍归迭代资料，有效业务规格继续按对应成果验收后收尾。

## 6. 沿用既定文件并保留生效状态

根据已有写入授权和实际阶段选择输出：

| 情况 | 输出归属 |
| --- | --- |
| 只讨论想法、尚无业务项目或未明确开轮 | 在对话交付已知内容、建议和待定项；不自建项目或迭代。已有项目的明确overview维护请求按第5节处理。 |
| 整理尚未进入本轮的反馈 | 沿用项目既有 backlog，保留候选和未批准状态；只讨论时不强制落盘。 |
| 已明确本轮且请求整理 | scope.md 保存范围、需求场景、验收及拟变更规格；design.md 保存实现取舍和相关研究依据。简单迭代可将设计放 scope.md。 |
| 明确开轮、暂停恢复或项目方向维护 | 仅按第5节的条件与文件范围写入；任务计划仍由planning编写，状态和验收事实分别保留。 |
| 本次有需要保留的核验或试验 | 当前迭代 verification.md 记实际方法、证据、结果、未运行与受阻项；不粘贴无关日志。 |

**本项不写state.yaml、业务代码、依赖配置、AGENTS.md或当前有效specs/foundation，不编写或改排任务计划。** tasks的有限写入仅包括第5节首次建立空占位、主Agent记录暂停/恢复及必要的中断事实；任务内容交planning。业务变化交执行主Agent，在对应成果验收且必要检查、审查满足后仅同步实际交付部分，无业务变化不机械改规格；公共约定按确认和生效时点由原流程落实。交接说明涉及的规格及变更范围，同步受阻由原流程沿tasks/verification记录并恢复，不提前代写。新约定及拟修改内容可在本轮设计引用或描述，不能伪装为已生效。未满足第5节或缺初始化条件时交付缺项，不代替初始化器。

确有原型或技术试验需求且已有授权覆盖时，由主流程在第 3 节约定的隔离范围内承接试验代码与必要操作，不改正式业务工程。仅授权编写原型不自动授权安装依赖、联网、启动服务或保留为正式实现；已有具体操作授权不重复索取。试验结论按实际执行范围记录，未运行的原型只算表达方案，不能称已验证可用。

正式写入由项目主 Agent 统一完成，受委派者按给定范围返回材料，不自行重复委派或更新正式状态。写入与历史保护按[写入契约](common/write-contract.md)。上游同名目录也可能是用户资料，不清理。

不新增 PRD、DESIGN、EXPERIENCE、GLOSSARY、ADR、memlog 等平行文档，不照搬上游 hooks、自动提交、安装或后续开发。以上是行为约束，不是工具强制权限隔离。

## 7. 衔接计划与确认

交付给计划的内容应包含：明确业务项目和当前迭代、需求与确认依据、本轮范围、方案及其草案/确认状态、可观察验收、关键依赖和未决事项、现有记录位置。范围或重要业务规则尚未确定时，先解决受影响缺项，不凭假设生成看似已批准的任务。

从入口、计划或执行流程接收开轮、暂停/恢复记录事项时，完成后把实际路径、已写/未写内容及确认依据返回原主流程；不递归调用原入口或另启动implementation。原调用方已负责本次规划时，本项只返回所需资料，由原调用方继续同一份计划，不回调planning或再启动一轮规划。原主Agent在记录和前置齐备后，根据本次是否还授权规划或实施决定下一步；只请求准备资料或记录时到此交付。

原调用方尚未承接规划，且用户要求方案后继续安排计划、已有要求足够时，读取实际可用的planning，交由它准备当前tasks.md；设计与计划可以一并准备并提交确认。**设计待联合确认不等于不能准备计划草案；计划存在也不等于设计或实施已获批准。** 已有适用确认沿用，实质变化才重新确认。整理明确需求不需要重走一次问答。

只请求澄清、研究、方案或核验时，交付到该范围；不自动安排任务。planning 不可用时提供完整交接与缺少的能力，不伪称已调用或临时安装上游；用户明确要求安排计划时由主流程决定可用执行方式。

最后简述结果、文件、已确认与待定内容、实际检查及下一步。用户没有批准具体设计或计划时提交可审阅成果；已有批准和执行授权时由主流程按 implementation 接续。读取 Skill、确认一条建议、结束讨论、通过自查都不能代替实施授权或用户验收。
