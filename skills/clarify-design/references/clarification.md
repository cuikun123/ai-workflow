# 澄清范围与方案的方法

需要厘清需求、比较方案或准备设计时读取。共同判断依[工作契约](common/work-contract.md)，接手/写入/工具条件依[写入契约](common/write-contract.md)。需要专项方法先按[能力表](common/capabilities.json)找到真实提供者；以下能力ID不是原生Skill名称，固定依赖缺失不能用基本方法掩盖。

## 1. 定位意图与已有依据

先利用对话，区分用户是在讨论想法、澄清反馈、检查已有方案，还是要求整理方案并安排计划。只澄清反馈时不自动设计或开发；已经要求方案或计划时，持续完成该范围，不为每个内部步骤另行确认。

有业务项目时，读取其 AGENTS.md、导航、项目方向和相关迭代的 scope/design/tasks/verification，以及涉及的有效规格和 foundation 约定；按问题读实际代码、配置及原始资料。用户明确指定的目标优先核对，state 只作线索，不能代表批准。

- 没有项目也能在对话中澄清想法、研究和提出设计。不为开始讨论要求先安装框架或填齐模板。
- 需要写迭代文件时，核对项目根、明确当前迭代及真实路径；明确开启后续迭代或暂停恢复时按第5节处理。多个候选、链接越界或目标不清时先澄清，继续不依赖定位的讨论，不凭目录号、最近时间猜选。
- 框架仓库的 docs/design、handoff 和 templates/project 是框架资料与模板，不是本次业务项目。
- 既有要求、用户决定、实际实现和 AI 建议分别看待。实现只能证明当前行为；未确认技术备注不能覆盖已确认业务规则。
- 只核验方案时返回有依据的发现和未知项；没有修改授权不改草案。实际故障的诊断与修复按原流程及 diagnosis 处理；线上故障继续遵循先明确必要信息再调查的项目规则。

## 2. 按影响和依赖澄清

先在内部形成最小的决策关系：哪些已经确定，哪些能调查，哪些关键业务选择需要用户回答，以及后续问题依赖什么。无需生成决策树文件或把内部清单整份交给用户。

提问前做三项判断：答案是否改变本轮范围、设计或验收；上下文是否已有答案；是否可由 AI 查明或按已有约定处理。只有仍需要用户决定的关键问题才问。初次模糊反馈先问具体场景、困扰或期望结果，避免把推荐功能塞进用户原意。

独立、简短的问题可分成一小轮一起问；答案相互依赖时，先问前置问题，再按回答更新后续问题。有实际选项时给出推荐、理由和影响，允许自由回答和“不知道”。不固定问题总数，不强迫短答案，也不让每个问题都只能用“是”接受推荐。

可查的事实自己调查；普通技术细节按已有偏好和约定处理，必要时标明“AI 建议”。关键范围、接口、数据、安全和成本等取舍沿用项目确认规则。用户让 AI 推荐不等于允许把未说明的业务假设写成已确认要求。

收到纠正时，更新相关判断和依赖，仅重看受影响内容。双方已确认材料互相冲突时列出出处、冲突及影响，询问关键取舍；未确认草案与明确要求冲突时按要求修正有授权的草案，不重新询问已确定的业务规则。独立可确定部分继续整理。

停止提问的条件：本轮目标、边界、关键行为和验收已足够支撑请求的下一步。未来功能进入候选，不遍历未来所有分支。用户不想继续回答时，交付已知内容与尚受影响的部分；关键未知仍标为未知，不以沉默、超时或终止讨论当作批准。

## 3. 调查开源方案并推荐

对需要选型、复用或验证可行性的目标，主动调查业务开源项目、组件及官方文档；无需用户先指定候选。已有适用技术约定且本次不需改变时沿用，说明复用已有工程的依据，不为凑方案重开技术选型。

对准备推荐或采用的候选，按实际影响核对：官方来源、具体版本或 commit、功能适配、许可证及署名、运行依赖、数据和写文件行为、部署条件、维护负担及可验证方式。调查结论引用可定位来源，区分文档声明、源码阅读和实际运行结果。仓库热度或 Skill 存在不能证明生产可用或优于其他方案。

比较有实质差异的路线，用业务语言说明能否满足目标、开发和维护代价、主要限制及推荐原因。只有一条合理路线时说明理由，不虚构备选。优先考虑用户偏好；与约束冲突时说明影响。技术名称、路径和命令分清已有与拟新增，不把假设接口或未运行命令写成事实。

缺少网络或工具时，先处理可解决的准备问题；仍受阻则报告缺项，继续现有资料能支持的分析，将依赖最新事实的推荐保留为待核对。不能编造版本、许可或搜索结果，也不因调研受阻偷偷安装工具。

文件只读不代表调用无副作用：执行命令、请求接口、下载运行源码、安装依赖、启动服务和接触真实数据分别核对影响与授权。需要原型才能回答的问题，先说明验证目标和所需操作；授权覆盖时在隔离环境验证。原型标为试验，记录实际结论和限制，保留为正式实现须有对应请求与检查。

## 4. 形成足够实施的设计

从原始要求出发，按本轮需要选择以下视角，不要求每次写满模板：

| 视角 | 要说清的内容 |
| --- | --- |
| 范围与验收 | 谁在什么场景下获得什么结果；本轮包含与排除内容；正常、关键边界和失败结果怎样观察；新增建议和待定规则分别标明。 |
| 体验与流程 | 用户从入口到结果的操作顺序；涉及的页面或交互、加载/空/错误状态；恢复和重试是否保留数据；按实际场景考虑键盘、移动端等可访问性与平台要求。沿用已有视觉与组件约定。 |
| 模块与数据 | 哪些职责分开、依赖方向、谁拥有及修改共享数据；关键接口的输入输出和错误约定；数据约束及状态变化。只固定会让分别实施的部分产生不兼容的关键选择。 |
| 工程与运行 | 沿用或拟采用的技术和必要依赖；适用的安全、质量、环境和运行约束；需要怎样的验证，以及当前无法证明什么。 |

每个关键用户需求都有对应行为，每个新增设计点都有需求、技术约束或明确建议作为依据。不凭框架能力表添加账号、云服务、审批、支付等功能。已有完整说明可引用，避免复制公共约定。

复杂实现可保留内部技术细节给 planning 细化，但不能把影响范围或验收的未知业务规则藏在“实施时再定”。对不能可靠实现或验证的承诺说明事实与限制，并提出替代验收方式；若改变用户要求，需要确认该变化，不静默降低标准。

描述接口和验收时核对真实入口及已有行为；拟新增的入口、错误语义或实现建议明确标注，缺少依据时不写成“既定”或“已确认”。设计与计划交接时对照各成果的验收、规格收尾及下一成果前置，保持 scope/design/tasks 一致；按逐任务收尾安排，不在设计中改为等整轮通过才统一同步已验收成果。

交付前对照原始输入检查遗漏、冲突、术语、状态、跨模块衔接和可测试性。必要方案审查沿用项目已有安排；独立审查者读取原始要求和实际草案，可使用可用的 review 返回发现。自查不是独立审查，也不是功能测试通过；不因使用本 Skill 默认委派或增加重复审批。
