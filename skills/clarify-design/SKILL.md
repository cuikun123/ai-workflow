# 需求澄清与方案设计

## 专项能力协调

从 workflow-guide 或 discuss-design 接收材料时，核对项目/成果、请求模式、目标内容/运行版本、原始要求与确认、允许读写、已有证据、未决项和返回位置。讨论建议和少数意见保留原状态，不把推荐写成用户决定；不因接手重复整轮问答。

用户需要多角度比较、或关键取舍确需不同视角检验时，可读真实可用的 discuss-design；它返回推荐、代价、分歧和待确认，不替代本项的范围与方案归属，也不成为强制前置或正式独立审查。仅讨论不写文件；需要落盘仍核对本次整理授权。地基方案交接 build-foundation：先将起步范围、方案、任务和验收方式一并呈现并沿已有确认处理，覆盖适用的安全与数据、DoD及最低可观测性；在实施授权具备后建立最小工程，完成必要组件真实连通和工程验证、审查及逐任务验收，不凭骨架或文档称地基完成。具体组件按项目需要选择。任务与发布分别交原主流程核对，不由本项自动实施或部署。能力缺失给材料，不安装上游或伪称调用。

地基交接分别说明两类生效时点：公共工程约定由原主流程按已确认的落实和生效时点执行，不能一律推迟到功能验收后；业务规格只在对应成果验收且必要检查、审查满足后同步。本项只交接这些依据，不提前代写有效资料。

设计按影响说明必要风险：输入和权限边界、敏感数据与依赖来源、正常/加载/空/错误及可访问体验、运行观察和数据恢复责任。已有要求引用即可，不为凑专项审计增加无关功能；检查点落到可观察验收与现有文档。被调用能力只返回结果，当前主 Agent 保留正式记录和接续责任，不递归启动另一套设计/执行流程。

把用户的想法推进到本次请求所需的深度：理解问题、明确需求、形成设计，或交接任务计划。使用中文和项目已有术语。完整方法在本文件；来源、固定版本、适配范围及许可见 [NOTICE.md](NOTICE.md)。无需安装或调用原版 brainstorming、grilling、clarify 或 BMAD。

## 1. 定位意图与已有依据

先利用对话，区分用户是在讨论想法、澄清反馈、检查已有方案，还是要求整理方案并安排计划。只澄清反馈时不自动设计或开发；已经要求方案或计划时，持续完成该范围，不为每个内部步骤另行确认。

有业务项目时，读取其 AGENTS.md、导航、项目方向和相关迭代的 scope/design/tasks/verification，以及涉及的有效规格和 foundation 约定；按问题读实际代码、配置及原始资料。用户明确指定的目标优先核对，state 只作线索，不能代表批准。

- 没有项目也能在对话中澄清想法、研究和提出设计。不为开始讨论要求先安装框架或填齐模板。
- 需要写迭代文件时，核对项目根、明确当前迭代及真实路径；明确开启后续迭代或暂停恢复时按第5节处理。多个候选、链接越界或目标不清时先澄清，继续不依赖定位的讨论，不凭目录号、最近时间猜选。
- 框架仓库的 docs/design、handoff 和 templates/project 是框架资料与模板，不是本次业务项目。
- 既有要求、用户决定、实际实现和 AI 建议分别看待。实现只能证明当前行为；未确认技术备注不能覆盖已确认业务规则。
- 有效规格与本轮变更分别识别：明确获准的变更只对对应行为与目标版本按 scope 和确认依据处理，其余有效规则继续遵守。候选实现与旧版本环境核对各自要求；草案不能覆盖确认，两份适用确认真正冲突才澄清受影响部分。
- 只核验方案时返回有依据的发现和未知项；没有修改授权不改草案。实际故障的诊断与修复按原流程及 debug-issue 处理；线上故障继续遵循先明确必要信息再调查的项目规则。

## 2. 按影响和依赖澄清

先在内部形成最小的决策关系：哪些已经确定，哪些能调查，哪些关键业务选择需要用户回答，以及后续问题依赖什么。无需生成决策树文件或把内部清单整份交给用户。

提问前做三项判断：答案是否改变本轮范围、设计或验收；上下文是否已有答案；是否可由 AI 查明或按已有约定处理。只有仍需要用户决定的关键问题才问。初次模糊反馈先问具体场景、困扰或期望结果，避免把推荐功能塞进用户原意。

独立、简短的问题可分成一小轮一起问；答案相互依赖时，先问前置问题，再按回答更新后续问题。有实际选项时给出推荐、理由和影响，允许自由回答和“不知道”。不固定问题总数，不强迫短答案，也不让每个问题都只能用“是”接受推荐。

可查的事实自己调查；普通技术细节按已有偏好和约定处理，必要时标明“AI 建议”。关键范围、接口、数据、安全和成本等取舍沿用项目确认规则。用户让 AI 推荐不等于允许把未说明的业务假设写成已确认要求。

收到纠正时，更新相关判断和依赖，仅重看受影响内容。双方已确认材料互相冲突时列出出处、冲突及影响，询问关键取舍；未确认草案与明确要求冲突时按要求修正有授权的草案，不重新询问已确定的业务规则。独立可确定部分继续整理。

停止提问的条件：本轮目标、边界、关键行为和验收已足够支撑请求的下一步。未来功能进入候选，不遍历未来所有分支。用户不想继续回答时，交付已知内容与尚受影响的部分；关键未知仍标为未知，不以沉默、超时或终止讨论当作批准。

## 3. 调查开源方案并推荐

对需要选型、复用或验证可行性的目标，主动调查业务开源项目、组件及官方文档；无需用户先指定候选。已有适用技术约定且本次不需改变时沿用，说明复用已有工程的依据，不为凑方案重开技术选型。

对准备推荐或采用的候选，按实际影响核对：官方来源、具体版本或 commit、功能适配、许可证及署名、运行依赖、数据和写文件行为、部署条件、维护负担及可验证方式。调查结论引用可定位来源，区分文档声明、源码阅读和实际运行结果。仓库热度或 Skill 存在不能证明生产可用或优于其他方案。

比较有实质差异的路线，用业务语言说明能否满足目标、开发和维护代价、主要限制及推荐原因。只有一条合理路线时说明理由，不虚构备选。优先考虑用户偏好；与约束冲突时说明影响。技术名称、路径和命令分清已有与拟新增，不把假设接口或未运行命令写成事实。

缺少网络或工具时，先处理可解决的准备问题；仍受阻则报告缺项，继续现有资料能支持的分析，将依赖最新事实的推荐保留为待核对。不能编造版本、许可或搜索结果，也不因调研受阻偷偷安装工具。

文件只读不代表调用无副作用：执行命令、请求接口、下载运行源码、安装依赖、启动服务和接触真实数据分别核对影响与授权。需要原型才能回答的问题，先说明验证目标和所需操作；授权覆盖时在隔离环境验证。原型标为试验，记录实际结论和限制，保留为正式实现须有对应请求与检查。

## 4. 形成足够实施的设计

从原始要求出发，按本轮需要选择以下视角，不要求每次写满模板：

| 视角 | 要说清的内容 |
| --- | --- |
| 范围与验收 | 谁在什么场景下获得什么结果；本轮包含与排除内容；正常、关键边界和失败结果怎样观察；新增建议和待定规则分别标明。 |
| 体验与流程 | 用户从入口到结果的操作顺序；涉及的页面或交互、加载/空/错误状态；恢复和重试是否保留数据；按实际场景考虑键盘、移动端等可访问性与平台要求。沿用已有视觉与组件约定。 |
| 模块与数据 | 哪些职责分开、依赖方向、谁拥有及修改共享数据；关键接口的输入输出和错误约定；数据约束及状态变化。只固定会让分别实施的部分产生不兼容的关键选择。 |
| 工程与运行 | 沿用或拟采用的技术和必要依赖；适用的安全、质量、环境和运行约束；需要怎样的验证，以及当前无法证明什么。 |

每个关键用户需求都有对应行为，每个新增设计点都有需求、技术约束或明确建议作为依据。不凭框架能力表添加账号、云服务、审批、支付等功能。已有完整说明可引用，避免复制公共约定。

复杂实现可保留内部技术细节给 plan-tasks 细化，但不能把影响范围或验收的未知业务规则藏在“实施时再定”。对不能可靠实现或验证的承诺说明事实与限制，并提出替代验收方式；若改变用户要求，需要确认该变化，不静默降低标准。

描述接口和验收时核对真实入口及已有行为；拟新增的入口、错误语义或实现建议明确标注，缺少依据时不写成“既定”或“已确认”。设计与计划交接时对照各成果的验收、规格收尾及下一成果前置，保持 scope/design/tasks 一致；按逐任务收尾安排，不在设计中改为等整轮通过才统一同步已验收成果。

交付前对照原始输入检查遗漏、冲突、术语、状态、跨模块衔接和可测试性。必要方案审查沿用项目已有安排；独立审查者读取原始要求和实际草案，可使用可用的 review-work 返回发现。自查不是独立审查，也不是功能测试通过；不因使用本 Skill 默认委派或增加重复审批。

## 5. 后续迭代、暂停恢复与项目概览

本节由当前主Agent在已有业务项目的既定文档结构内执行。核对用户的明确请求及适用确认，只处理对应操作；同一次指令可以同时确认目标、开轮和资料整理，不另设建目录审批。专项调用本身不是开轮或切换指令；无业务项目时继续对话，不借此初始化项目、安装框架或创建导航。紧急线上修复由handle-incident先核对具体方案、暂停保存、独立小迭代及实际线上版本基线，再交本项按已明确的修复轮路径准备既定scope/design及tasks/verification占位；不按普通开轮擅自决定线上修复或基线。已有适用任务内的调查或修复返回原流程，不循环调用入口。

### 明确开轮

1. **核对前置。** 目标已明确且用户要求开启后续迭代并整理资料。原轮已完成当前确认范围的用户验收、必要检查/审查、对应规格收尾及整轮衔接核对，或用户已明确暂停切换。原成果待验收且没有明确暂停时，只整理不依赖开轮的对话内容，保留原验收入口。暂停不把原成果改为已验收或已完成。
2. **定位和保留。** 用户指定路径优先；没有指定时沿用项目命名约定，无约定可提出三位编号加短名称作为默认。编号仅用于命名，不能选择当前轮。纯名称冲突可在已有授权内选不覆盖资料的名称；用户指定路径已有其他成果、目标归属不清或真实路径/重解析目标越出业务项目时，停止受影响写入并澄清。回读相关文件，重复请求复用同一轮，保留编号、确认、历史和用户修改。
3. **记录切换依据。** 需要暂停原轮时，先按下一节在原tasks记录确认和未完成事项，再准备目标轮资料。暂停记录写入失败时，不继续依赖它的新轮创建；若原轮已收尾，新scope引用已有收尾依据即可，不编造暂停。缺少可写的原记录位置时报告缺项，未持久化的事实在对话交付，不宣称切换已完整落盘。
4. **准备既定文件。** scope记录本轮目标、已有确认、草案/待定部分和原轮收尾或暂停依据；必要design记录方案，简单迭代可并入scope。仅在文件不存在时建立空tasks和verification占位；不清空已有文件，不编写任务计划或虚构检查结果。交付明确的项目和迭代路径及下一步。目录存在不代表范围、设计、计划或实施已获批准；已有适用确认也不因开轮被重置为草案。
5. **关联候选。** 事项已明确获准纳入本轮且scope实际写入后，由主Agent在已有backlog保留原条目、原始反馈及其他关联，补对应scope路径和实际入轮范围；部分纳入不标整项完成。只选讨论主题或仅有候选草案时不记为已入轮。重复执行不重复添加同一去向，入轮不等于实施或验收通过。

### 暂停、恢复及中断

明确暂停（包括“今天到这里”）或切换时，原主Agent先读取实际可用execute-task的Git保存方法：核对任务归属与入库许可，精选本任务内容及暂存区，有改动才作本地WIP，具备远端与推送权限则备份并分别核对；需决策的Merge冲突保留现场、不普通提交或abort。任务进度、暂停/恢复记录和Git断点共同保存，记录不虚构成功；保存/写入受阻保留已完成部分，不能当完整切换。本项只承接正式文档，不另执行一套Git或要求已确认规则逐步批准。仅查询仍只读。

主Agent在受影响的原tasks保留暂停/恢复的明确确认依据、日期、目标迭代路径、未完成事项、原验收状态和恢复条件；只补事实，不重排任务内容或改写验收历史。用户明确从当前轮切换回指定旧轮时，该切换指令可作为当前轮暂停和旧轮恢复的依据，无需重复索取相同确认；对象或含义不明确时只澄清受影响部分。先保存当前轮暂停，再记录目标轮恢复；任一步失败均保留现场和未完成部分，不写成全部切换成功。

恢复前对照具体开轮、暂停、恢复确认与实际scope/tasks/verification，核对目标内容是否仍适用。草案、缺少暂停标记、唯一未完成目录、最近日期或旧state都不足以单独确定当前轮。记录矛盾、缺失或部分写入时保留未知，不凭缺失记录推定从未执行；无可消解依据才询问。只查询时返回核对结果，不补写暂停/恢复记录。

明确要求补完上次开轮或记录时，逐项对照已有确认和真实文件，只补未完成部分；不能重建新轮、覆盖期间新增的用户笔记，或靠删除已写文件恢复旧快照。写后回读本轮资料、原轮记录和backlog关联。失败时报告已写/未写位置、影响、恢复条件和下一步；仍能写入的适用tasks/verification可保留必要恢复依据，否则在对话交付。不把预置中断或普通文件写入称为事务保证或真实I/O失败验证。

线上修复明确约定收尾后返回原轮时，将该约定、原任务与验收状态、恢复条件写在既定tasks并关联修复scope；修复完成验收、发布恢复、主线覆盖和清理后由原主Agent按handle-incident核对返回。原任务待验收仍恢复为等待，不把暂停、修复或返回记为原成果通过。

### 维护overview

用户已明确项目方向、目标用户或项目级范围，并要求整理或已有适用文档维护授权时，主Agent首次填写或更新docs/project/overview.md；没有当前迭代不阻止这项明确维护请求。文件缺失但既定项目目录与归属明确时，可创建该文件，不补建整套项目结构。只写已确认的方向变化，保留无关内容与用户修改，不等功能验收才记录方向；未来目标不写成已交付功能。未确认建议留在对话、backlog或设计，普通迭代不机械改overview。任务进度和历史仍归迭代资料，有效业务规格继续按对应成果验收后收尾。

## 6. 沿用既定文件并保留生效状态

根据已有写入授权和实际阶段选择输出：

| 情况 | 输出归属 |
| --- | --- |
| 只讨论想法、尚无业务项目或未明确开轮 | 在对话交付已知内容、建议和待定项；不自建项目或迭代。已有项目的明确overview维护请求按第5节处理。 |
| 整理尚未进入本轮的反馈 | 沿用项目既有 backlog，保留候选和未批准状态；只讨论时不强制落盘。 |
| 已明确本轮且请求整理 | scope.md 保存范围、需求场景、验收及拟变更规格；design.md 保存实现取舍和相关研究依据。简单迭代可将设计放 scope.md。 |
| 明确开轮、暂停恢复或项目方向维护 | 仅按第5节的条件与文件范围写入；任务计划仍由plan-tasks编写，状态和验收事实分别保留。 |
| 本次有需要保留的核验或试验 | 当前迭代 verification.md 记实际方法、证据、结果、未运行与受阻项；不粘贴无关日志。 |

**本项不写state.yaml、业务代码、依赖配置、AGENTS.md或当前有效specs/foundation，不编写或改排任务计划。** tasks的有限写入仅包括第5节首次建立空占位、主Agent记录暂停/恢复及必要的中断事实；任务内容交plan-tasks。业务变化交执行主Agent，在对应成果验收且必要检查、审查满足后仅同步实际交付部分，无业务变化不机械改规格；公共约定按确认和生效时点由原流程落实。交接说明涉及的规格及变更范围，同步受阻由原流程沿tasks/verification记录并恢复，不提前代写。新约定及拟修改内容可在本轮设计引用或描述，不能伪装为已生效。未满足第5节或缺初始化条件时交付缺项，不代替初始化器。

确有原型或技术试验需求且已有授权覆盖时，由主流程在第 3 节约定的隔离范围内承接试验代码与必要操作，不改正式业务工程。仅授权编写原型不自动授权安装依赖、联网、启动服务或保留为正式实现；已有具体操作授权不重复索取。试验结论按实际执行范围记录，未运行的原型只算表达方案，不能称已验证可用。

正式写入由项目主 Agent 统一完成，受委派者按给定范围返回材料，不自行重复委派或更新正式状态。写前检查真实路径、回读现有内容；保留编号、历史、用户笔记、并行修改和既有确认事实。发现新改动时基于新内容合并，不覆盖旧快照。上游同名目录也可能是用户资料，不清理。

不新增 PRD、DESIGN、EXPERIENCE、GLOSSARY、ADR、memlog 等平行文档，不照搬上游 hooks、自动提交、安装或后续开发。以上是行为约束，不是工具强制权限隔离。

## 7. 衔接计划与确认

交付给计划的内容应包含：明确业务项目和当前迭代、需求与确认依据、本轮范围、方案及其草案/确认状态、可观察验收、关键依赖和未决事项、现有记录位置。范围或重要业务规则尚未确定时，先解决受影响缺项，不凭假设生成看似已批准的任务。

从入口、计划或执行流程接收开轮、暂停/恢复记录事项时，完成后把实际路径、已写/未写内容及确认依据返回原主流程；不递归调用原入口或另启动execute-task。原调用方已负责本次规划时，本项只返回所需资料，由原调用方继续同一份计划，不回调plan-tasks或再启动一轮规划。原主Agent在记录和前置齐备后，根据本次是否还授权规划或实施决定下一步；只请求准备资料或记录时到此交付。

原调用方尚未承接规划，且用户要求方案后继续安排计划、已有要求足够时，读取实际可用的plan-tasks，交由它准备当前tasks.md；设计与计划可以一并准备并提交确认。**设计待联合确认不等于不能准备计划草案；计划存在也不等于设计或实施已获批准。** 已有适用确认沿用，实质变化才重新确认。整理明确需求不需要重走一次问答。

只请求澄清、研究、方案或核验时，交付到该范围；不自动安排任务。plan-tasks 不可用时提供完整交接与缺少的能力，不伪称已调用或临时安装上游；用户明确要求安排计划时由主流程决定可用执行方式。

最后简述结果、文件、已确认与待定内容、实际检查及下一步。用户没有批准具体设计或计划时提交可审阅成果；已有批准和执行授权时由主流程按 execute-task 接续。读取 Skill、确认一条建议、结束讨论、通过自查都不能代替实施授权或用户验收。
