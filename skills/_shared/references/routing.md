# 选择所需方法与流程深度

目标是完成当前请求，只展开影响判断和执行的内容。先核对项目AGENTS、明确目标和已有适用授权；原生技能元数据用于选择，必要能力才通过[映射](capabilities.json)定位。已经读过且内容未变的资料可复用。不以“可能相关”要求加载全部技能。

## 先判断当前请求

| 判断 | 执行方式 |
| --- | --- |
| direct：目标明确、容易撤销、没有业务/接口/权限/数据规则变化 | 直接处理与必要核对，不强制澄清、独立方案文件、任务计划或专项全文。明确文件的拼写/排版只读取该文件和相关约定；不为了处理它运行check/status或读取所有迭代资料 |
| light：范围、行为和验收明确的局部功能或普通修复 | 简短说明方案与内部步骤，可联合确认；读取相关方法，验证受影响行为，普通功能仍需真实独立审查 |
| full：业务不明、跨模块/接口、认证授权、数据迁移、安全、费用、部署或难以恢复 | 补查及澄清关键未知，展开相关设计、计划与专项验证，保持真实独立审查和操作授权 |

代码行数和用户称“很简单”不是降级理由。direct发现行为变化转light，出现高风险或关键未知转full，说明具体原因。现有任务的普通技术步骤可以直接完成，但不改该任务已确认的验收与验证政策。显式点名技能时读其入口，再依当前动作判断是否需要详细参考。

## 当前任务与独立请求

只问进度就读取必要状态并报告；check/status用于真正需要的安装/工作流核对，输出含糊才读相关记录。无需定位迭代的独立小修改，不为使用框架创建迭代、状态记录或整套资料。修改受管state/progress/有效规格及验收记录必须使用对应工具，不因内容少而手改。

业务变化进入明确的适用迭代，关联需求、场景与增量。新任务方案/计划可以简短并联合确认，真实确认与来源仍须存在；不把明确修改请求之外的新设计自动批准。项目已有测试、PR或操作规则继续适用，direct/light不取消这些条件。

当前成果待验收，单独一句“继续”只报告等待及该成果入口，不验收、不推进下一任务。明确且独立的文件请求可以在原权限内处理，保留原任务位置；影响当前候选或依据则重核对受影响证据，不能让旧验收覆盖新内容。模糊目标只澄清受影响部分，不为所有任务增加问答轮次。

## 验证与审查

具体v2输入见[规格与记录工具](spec-runtime.md)。新任务声明execution_mode、实际理由和verification_policy，类型与必测场景随任务定义绑定计划确认。旧v1及未声明新政策的v2保留test_suite和independent默认值，不从文字或推测自动改政策。

test_suite记录实际测试命令、退出码及非零测试数；command记录实际命令与退出码，test_count=null；observation记录检查方法、预期、实际与证据，执行字段均null。必要检查缺失、失败或未运行就不能交验收，不编造测试数量。未运行项给原因，不作为通过引用。产物及检查证据按[工作契约](work-contract.md)绑定同一当前候选。

普通功能、full、高风险及PR合入前保持真实独立代码审查。simplified只适用于明确direct/light且无业务引用/增量、非发布维护的低影响内容，说明核对范围和实际上下文，不称独立审查。真正的独立审查需宿主提供独立上下文；缺环境就如实受阻。

## 能力交接与缺失

先确定当前caller和需要的方法，再按capability映射找到实际提供者及对应query/prepare/execute模式。沿同一项目、任务、候选、权限和返回位置交接，不把辅助方法变成第二轮完整流程。无需专项时自行完成，不为凑技能调用再委派。

完整包中的提供者/参考缺失是资源问题：skills check/check可能报告包损坏、安装不完整或资源改动，不因退出码不同就降级为可选方法。保留缺项与实际错误；宿主缺工具或独立上下文是环境受阻。只有明确可选的扩展按既定fallback返回基础方法或缺口，不能掩盖固定依赖失效。
