# 核对并执行获准发布的方法

准备发布、执行明确发布或处理失败回退时读取。共同判断依[工作契约](common/work-contract.md)，接手/写入/工具条件依[写入契约](common/write-contract.md)。需要专项方法先按[能力表](common/capabilities.json)找到真实提供者；以下能力ID不是原生Skill名称，固定依赖缺失不能用基本方法掩盖。

## 1. 确定模式和前置

读项目 AGENTS、已有导航、相关 scope/design/tasks/verification、适用 specs 与 foundation/operations、已有 releases 记录和实际发布脚本。发布可包含多个已验收迭代；不要求每轮立即上线，不按最近目录推定目标。定位候选产物/内容、当前运行版本、目标环境、操作者、请求是仅准备还是执行，以及每项操作的授权。

核对用户验收、必要检查与审查、规格收尾和发布条件；旧证据要对应当前内容与环境，改变后只补受影响检查。测试通过不等于验收或发布批准，目录存在不等于产物可用。前置缺失仍可做独立准备，但不称已就绪。

## 2. 形成可执行准备

给出：具体产物/配置及去向、部署顺序、敏感配置提供方式、健康与关键业务检查、失败判断、回退目标/步骤/核验和停止条件。按影响核对迁移兼容、备份及恢复、数据丢失风险、费用和权限。代码回退不代表数据恢复；无法逆转的数据动作没有可恢复方案时不执行。先读脚本副作用，再决定是否运行。

已有明确可恢复路径且授权覆盖本次目标和操作时直接推进，不重复询问相同许可。新环境、费用、重要迁移、恢复方案或授权不清时，提交具体方案与影响供用户决定。仅准备请求不执行部署、回退、重启、迁移或会改变真实环境的检查。用户亲自执行时，提供已核对步骤及回传证据要求，协助核验；无法观察不能称部署成功。

## 3. 执行、检查与失败

### 固定发布版本

仅准备时只核对提交、拟用标签及条件，不创建/推送标签或部署。具体发布和Git权限具备后，主Agent固定已验证、准备发布的提交与对应产物，沿项目版本约定选择合法标签；没有统一版本递增默认值，`v1.2.1`只是示例。核对实际仓库、目标远端、同名本地/远端标签及解引用后的提交；不能凭名称相同推定内容相同。已有标签指向本次目标则核对并复用，指向别的提交则保留原标签，按项目约定确定新版本，重要取舍不明才请用户决定；不移动、强推或删除重建同名发布标签。远端状态未知先查询，无法确认则不宣称已保存或发布就绪。

创建`git tag <版本> <已验证提交>`后核对实际指向，再只推送对应标签到已明确远端，核对远端标签及其提交。标签创建、远端保存、部署和业务恢复分别报告，任一步失败保留已成功部分及原始证据；发布以该固定标签和对应产物为准，内容再变化必须用新版本标签并补受影响验证。标签推送或PR合入可能触发部署时，先核对自动化配置及本次适用部署授权，不把Git权限当上线许可。缺工具/账户/远端条件就保留未完成，不临时安装CLI或虚构结果。

### 部署与结果

执行前再次核对目标和当前状态，避免恢复会话后重复部署。外部操作结果未知时先在访问授权内查询，不把未知视为没执行。依准备顺序操作，读取退出码及实际环境结果，核对健康与关键业务、版本、配置及相关数据。发布完成与业务用户验收分开记录。

| 实际情况 | 行动 |
| --- | --- |
| 部署与必要上线检查通过 | 报告实际产物/版本、环境、证据与限制；不据局部健康检查宣称所有功能通过。 |
| 发布执行或关键上线检查失败 | **先按事前明确且本次授权覆盖的方案回退并核验，再报告。** 保留首次失败证据，不因根因未知延迟获准回退。 |
| 回退未获具体授权、无法执行或失败 | 报告失败点、当前状态/未知、数据风险和所需操作；不称已恢复，不擅改方案或盲目补救。 |
| 已回退或仍故障 | 报告原因依据、事实/假设、回退及数据核验结果、解决建议；等待用户决定是否重试。原部署授权不覆盖失败后的再次部署。 |

失败调查按已有只读授权和 diagnosis 方法取证；超出允许范围的修复另核对具体方案。不将本次发布失败处理替换为 incident 的另一套问诊而延迟已获准回退；成功运行后的独立故障才走该入口。

## 4. 返回原流程

当前主Agent统一维护已有releases中的本次发布记录及适用verification/tasks，关联实际发布标签、解引用提交、产物、环境与部署/失败/回滚结果；标签存在不等于已上线。只准备且不许写时在对话交付，无适用位置不自动建迭代或新报告树。不写state.yaml、不改有效规格替代验收。普通任务分支/PR/目录收尾交原主Agent按implementation处理，不由发布专项顺手清理。重复发布/标签请求先核对实际状态，只接续获准剩余步骤；失败后的再次部署仍等用户决定。

线上补丁标签固定实际发布的补丁提交，不改指后来Squash进入main的提交。按incident先完成补丁必要检查、用户验收及记录，在具体部署授权具备后发布并核实业务恢复，再确保main覆盖修复，最后由原主Agent清理临时目录/分支；保留发布标签及必要产物。线上恢复与主线同步受阻分别记录，不能因为同步main而额外上线未发布改动；发布失败先沿本项获准方案回退并核验，不提前清理或自动重试。

交接包含项目/成果、候选与运行内容/版本、原始确认、请求模式、允许操作、当前环境状态、真实执行与证据、未决项和返回位置。testing、diagnosis、review 仅提供所需方法及结果，读真实可用说明，不递归启动 implementation 或重复整轮审查；原主责继续统筹。缺工具/能力如实报告，不临时安装上游或伪称执行。

例如获准在本地演练部署 v2、失败回退 v1：部署退出失败后运行已核对的回退，查询 v1 健康及适用数据状态，再报告失败和恢复证据，等待是否重试；单有“发布吧”而缺环境和恢复方案时先补齐具体条件。
