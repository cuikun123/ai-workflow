# 取证并修复问题的方法

复现故障、查明原因或验证修复时读取。共同判断依[工作契约](common/work-contract.md)，接手/写入/工具条件依[写入契约](common/write-contract.md)。需要专项方法先按[能力表](common/capabilities.json)找到真实提供者；以下能力ID不是原生Skill名称，固定依赖缺失不能用基本方法掩盖。

## 1. 明确问题与操作范围

接手Git相关失败或有Git版本的任务时，先在允许的只读范围核对真实仓库/worktree、当前分支/HEAD、暂存与冲突、目标提交/远端及原始失败命令；工作区内容与最终候选分开。普通故障修复保留原任务分支，不因报错另开方案。需要人类决策的Merge冲突保留现场和已处理部分，暂停该目录写入，不自动abort、reset、普通WIP或清理；网络/权限失败保留本地提交及远端未知，不能用重试成功覆盖首次失败。Git变更由原主Agent读取implementation的真实方法和既有授权后执行；本项不因诊断取得同步、推送或历史改写权。

读取目标项目 AGENTS.md、已有导航、用户指定问题、相关规格和工程约定，按需读当前任务、范围、设计、验证记录及实际代码。确认预期、实际表现、输入、环境与复现入口；先补查可得信息，只问影响判断的缺项。没有适用迭代但目标明确时直接调查，在对话交付，不创建迭代或导航。框架源码设计和业务模板不是本次业务项目。

共同依据按[工作契约](common/work-contract.md)核对。将故障实际版本与预期对应；关键歧义保留未知，不靠修改实现消除歧义。

| 请求或角色 | 允许推进到哪里 |
| --- | --- |
| 只查原因、解释报错 | 读取与必要的隔离复现，返回原因依据、未知项和建议；不修改真实项目代码、配置或数据。 |
| 明确要求修复，或当前任务已有适用修复授权 | 在该范围调查、修复和重验，不重复索取同一授权；重要范围、设计、数据、安全、成本变化另行确认。 |
| implementation 中的问题 | 当前主 Agent 继续管理任务、授权、记录及验收；本项提供调查和修复方法，完成后回到同一任务。 |
| 受委派的调查者或实施者 | 遵守分配的读写范围，返回证据与实际改动，不自行再委派或更新正式进度。 |
| 线上运行故障 | 按项目线上规则先取得必要信息、明确问题和范围，再按访问授权调查；修复依据具体方案及适用确认。本项不提供部署、重启或回滚入口。 |

每次实验前核对实际路径、命令、输出位置和外部影响。添加诊断日志、运行测试、发送复现请求也可能写入，不能等到“修复阶段”才检查授权。只查原因时，需要写入的实验放在不影响真实项目与业务的隔离环境；无法隔离则说明缺项。只读取和展示定位所需、可脱敏的信息，不整体输出环境变量、凭据或业务数据。

## 2. 复现并找到故障边界

先阅读完整错误、堆栈及必要日志，核对实际执行环境、工作目录、版本和近期改动。运行能暴露原问题的最小检查，记录输入、预期、实际结果及退出码；测试另记录执行数量与跳过情况。退出 0 但零测试、全部跳过或运行错项目，不能作为通过证据。没有提交或旧版本证据时只判断当前内容，不虚构变更历史。

找到同项目的正常路径，逐项比较输入、配置、调用顺序和依赖。在多组件边界检查值或状态的进入与输出，优先利用已有可观测信息；新增日志和检查仍受上节范围限制。

**沿调用链向上追踪：** 从报错位置找直接原因，再追问谁传入了这个值、谁创建或更改了状态。直到找到最早偏离要求的环节，而不只在最终报错处加兜底。可以对比“直接调用下层”与“经过上层构造”的结果，区分下层算法错误与上层输入错误。

例如，配置允许 `maxRetries=0`，实际却执行三次：分别核对原始配置、构造后的选项、执行器收到的值及实际调用次数。若直接传 0 行为正确、经过选项构造变成 2，调查重点就应转向构造环节，不能仅调整执行器或延长等待。该例只说明追踪方式，不预设真实项目的重试要求或修复表达式。

不能稳定复现时记录已检查的输入、环境和缺少的历史证据；当前检查通过只说明本次未复现，不能据此否定过去的故障或宣布已修复。

## 3. 验证一个具体原因

提出可被推翻的假设：“因为观察到 A，怀疑 B；若 B 成立，实验 C 应得到 D。”一次尽量只改变一个因素，读取实际结果后决定保留还是否定假设。实验输入先核对接口约束，为可能循环、等待或反复调用的探针设置次数或时间上限；绕过正式入口的对照结果要单独解释。优先使用无写入检查或隔离对照，避免把多个补丁一起试到偶然通过。

按问题选择补充方法：

- **异步或不稳定测试：** 明确要等待的事件或状态，优先使用现有 Promise、事件或等待工具；轮询时每次读取新状态，并保留超时、失败原因和资源清理。判断“条件满足”与取结果分开，合法的 0、false 或空值不应误判为尚未完成。不要靠增大固定 sleep 掩盖错误。防抖、节流和其他真实时间要求仍需按规格验证，不能把等待完成的方法替换时间语义。
- **测试间污染：** 先检查初始状态，再在隔离环境比较单独与组合执行、必要的顺序；逐次保留退出结果、数量和观察值。只逐个运行仍可能漏掉组合污染；不把“未找到”写成“已经排除”，也不运行会吞掉失败输出的上游脚本。
- **输入或状态越过边界：** 原因明确后核对实际入口、业务与环境约束，只补对当前问题有依据的校验，保留原调用语义；不一律给每层增加相同检查或承诺问题永不发生。

无新证据时停止重复补丁和相同实验，回看假设、证据缺口及可行的新调查路径。缺少必要条件时报告受阻和补齐办法；重要设计变化交用户决定。失败次数本身不证明架构错误，暂未找到原因也不自动授权重试、降级或重构。审查修复中的两轮无进展按项目已有规则处理，不设统一的诊断尝试次数。

## 4. 在授权内修复、重验与审查

只诊断的请求到原因与建议即结束。适用修复授权具备时，针对有证据支持的原因作必要改动，优先用原有失败检查或补充回归用例暴露问题，再验证修复。检查选择按规格与影响；无法自动复现时给可执行的替代办法并保留限制，不伪造红灯到绿灯记录。

重跑原问题和受影响的正常、边界及异常检查；不要删断言、改预期或降低标准来获得通过。必要环境缺失时先在授权内解决准备问题，仍受阻则继续独立可做检查，如实报告；模拟结果不替代真实集成。代码或环境变化后，重查受影响的旧结论。

修复需要的独立审查由主 Agent 组织。已安装 review 时使用其实际入口；未安装时向真实独立审查者提供原要求、原因证据、实际改动与检查结果，请其核对修复是否满足要求、原问题是否消失及是否引入回归。没有必要的独立审查条件时如实保留未完成，自查不冒充独立审查。

在 implementation 中，返回结果后由原执行流程统一安排审查、有效问题修复复查和验收，不重复启动一轮全量审查。独立修复请求也要交付可核验结果，不能以缺少 implementation 跳过必要检查。后续修复影响已验收成果时保留历史，重验并重新提交受影响部分；本项不自动开始下一任务。

## 5. 返回结果与记录

简短结论先说明“已定位”“已修复并完成哪些检查”或“仍无法确定”，随后给出：

1. 问题范围、预期与实际行为，以及可定位的当前内容。
2. 事实、假设和原因证据；关键对照实验的输入、命令、工作目录、退出结果及测试数量。
3. 实际修改或仅建议的修复、原问题与关联回归的结果、审查及未执行项。
4. 未解决问题、必要补齐条件、下一步；修复交付给出可执行的验收入口、步骤和预期。

主 Agent 有适用迭代时，将必要依据合并到 verification.md，实际进度写入 tasks.md；写入按[写入契约](common/write-contract.md)。无适用迭代时在对话交付；受委派者只返回结果。实施、AI 检查与用户验收分别记录，必要检查或审查缺失不称全部完成。

发现规格需随已交付变化更新时，返回涉及行为、确认依据、目标版本和待同步范围，不在诊断或修复中自行改规格。验收后由原主流程负责收尾：必要检查与审查满足后仅同步该成果实际交付的业务变化；无业务变化不改规格，受阻沿 tasks/verification 留恢复依据并核对实际文件后补齐。可交实际可用的 implementation 承接；未安装时原主 Agent 仍履行这些责任，不临时安装或虚构调用。

需要维护机器状态时由主Agent使用真实语义工具，保留原位置和历史。Git版本、保存断点及操作结果返回原主Agent，普通任务按implementation处理精选WIP、远端备份、PR与验收后收尾；线上修复按incident核对实际线上基线、补丁范围和发布后主线处理。只诊断或受托修复不自行执行Git写入。运行依赖实际宿主工具与项目环境；上述行为约束不是权限沙箱。来源脚本与原版Skill未被安装或串行调用。
