# 审查、反馈与验收

需要组织审查、修复反馈或提交验收时读取。已有适用证据复用，具体确认与独立性依[工作契约](common/work-contract.md)。Git动作已有明确授权时才创建提交/推送/PR；否则交付可查候选，不伪称已完成。

## 4. 独立审查与修复关闭

明确低影响非业务任务按已确认政策进行simplified核对，说明实际范围和上下文；普通功能任务在验收前需要独立审查，分别核对需求符合性与质量。每个交付PR的代码规范性检查使用全新的独立上下文Agent，只交需求、相关修改/新增及可定位候选，不传开发对话和实现推理；审查者可自行只读项目规范、必要调用方、依赖及证据。低影响修改可简化检查深度，高风险按需增加视角，整轮还检查跨任务衔接；简化不取消PR所需的新独立判断。代码行数少不等于低影响。

审查者读取原始要求、实际产物、必要上下文与可核对的验证证据，默认只读业务代码和正式记录。工具不能提供独立审查者时说明能力缺失；自查可以完成但不记成独立审查。仅有格式正确的报告、角色名或实施者自报不能证明独立审查发生。

审查中的内容保持稳定；修改后重新核对受影响结论。主 Agent 核验发现是否成立，有效问题在已有授权内修复、重验并由审查者复查原问题和新增回归；误报给出具体依据，业务关键取舍交用户决定。

后续任务或整轮审查的修复影响已验收成果时，保留原验收历史，明确当前内容及受影响结论已变化；按范围修复、重验和复查后，将受影响成果重新提交用户验收。旧验收不覆盖修改后的内容，不能只让用户验收当前任务而沿用受影响前项的旧结论。

必须修复的问题或影响必要判断的未知项未解决时，不能提交为已满足验收条件。先核验意见的必要性与证据，非必要意见不进入当前修复列表、不阻塞合入；复查聚焦原问题和实际修复影响，新增必要项须有同等证据。改进建议可保留但不擅自扩展任务。同一问题连续两轮无新证据或反复回退时，停止重复修改、重新取证；仍不能解决则报告阻塞和已尝试内容。不得因轮数、时间或预算耗尽，把真实问题记为已关闭或任务已完成。

## 5. 核对证据，交给用户验收

开发阶段结束前，主Agent精选本任务允许入库的代码、测试及相关文档，核对暂存差异后创建开发提交。必要产品效果验证、全新独立代码审查和修复检查对应最终候选提交；Web成果真实查看页面、截图并操作关键流程，接口、工程或文档用对应实际入口验证，不能用静态页面或局部自动测试冒充体验。适用测试可复用，内容变化补受影响检查；WIP不算开发完成。必要检查通过后，按已明确的推送和平台权限推送候选、创建PR并交用户验收，提供准确head/base、提交号与PR入口。已有同任务PR更新它；不提前合入，不为同一候选重复创建。GitHub或其他平台工具/API缺失时如实保留PR未创建，不能用本地Squash或假CLI冒充。

提交前核对当前内容：要求是否实现、必要检查是否实际通过、审查及必须修复项是否关闭、历史证据是否仍适用、实际改动是否在范围内。当前没有变化且证据仍适用时不因再次回复机械重跑；代码或环境改变影响结论时重验。需要重跑却无法执行时如实保留未验证。

主 Agent 沿用项目现有格式更新 tasks.md 和 verification.md，分别记录实施、检查、审查及用户验收。保留命令、必要环境、退出结果、关键证据、内容范围或可定位版本、未解决项和下一步；不用复制完整日志，不新建平行报告。未记录用户明确通过前保持“待用户验收”，不能用普通完成勾选冒充最终完成。

交付说明必须包含当前成果及位置、真实体验入口或可查产物、必要准备、操作步骤、预期结果、已知限制和未验证项。接口或工程任务可给已核对的调用/检查命令；不虚构在线服务、账号或测试结果。

把本成果整理为简短的“操作 → 可观察预期 → 当前检查/用户反馈”验收点，自动检查与用户判断分开；不把已有通过检查重复交用户手工执行。中断后沿原 tasks/verification 核对已反馈项、未反馈项及内容变化，只恢复仍待确认部分。逐点确认仅覆盖该点，全部所需内容明确通过才记录成果验收；空回复、沉默或含糊的“下一步”不算通过。验收点涉及启动、写数据或清理时先核对项目操作授权，不能照搬上游冷启动清理真实环境。

**提交后停止推进下一任务，等待用户明确验收。** 用户拒绝时在原范围修复再提交；用户明确通过后进入第 6 节收尾。普通查询、沉默、AI 检查通过或既有阶段授权均不能越过等待点。写入约束依靠当前 Agent 和实际工具能力，不是已实现的权限沙箱。


## 验收后的规格收尾

原主Agent核对真实验收、适用检查与当前内容，然后按[规格工具](common/spec-runtime.md#同步与完成)预览、同步及登记closeout/complete。无业务变化也由工具核对not_needed；不手工修改spec或编造收据。保留未变规则、其他任务及历史，收尾完成后才核对下一任务。Git收尾另读[Git方法](git-workflow.md)。

## 协作与证据参考

主 Agent 在委派实施者、接收结果或安排独立审查时读取。没有子 Agent 工具时不得编造调用；主 Agent 自己实施与独立审查的要求分别判断。

### 任务交接

提供当前成果的稳定编号、目标与验收、原始 scope/spec/design 及 tasks.md 中对应位置、公共约束、允许读写范围、依赖接口和已完成事实、必要验证与停止条件。按需给上下文，不复制全部会话。原始资料与摘要矛盾时先回报，不自行覆盖用户要求。

实施者只处理分配的当前工作，返回：

- 实际实现或尝试了什么、哪些文件改动、哪些原要求尚未完成。
- 运行过的命令、必要环境、退出结果、关键输出和未运行检查及原因。
- 自查发现、阻塞、缺项及需要主 Agent 决定的问题。

可以用完成实现、存在疑点、需要资料、受阻等短语描述返回情况；它们是实施者自报，不是框架状态枚举或用户验收。详细依据随返回传给主 Agent，不自行创建 report.md 或更新正式 tasks/verification/state。不自行再派实施者或审查者，也不提交、合并或清理文件。

主 Agent 接收后检查实际文件、差异与证据，确认必要内容可读，不用子 Agent 的“完成”替代核验。报告缺证据时要求补齐；技术资料能自行查到就补查，关键业务意图才向用户确认。委派期间主 Agent 不同时改相同范围。

### 独立审查输入

给独立上下文的审查者以下资料：

| 输入 | 要求 |
| --- | --- |
| 原始依据 | 当前任务、已确认范围、规格、设计和质量要求；提供具体位置。 |
| 实际内容 | 改动文件、必要调用方与依赖，以及可定位的内容状态。 |
| 实施者返回 | 主Agent接收时只作导航；给全新独立代码审查者仅提供原始要求与实际候选/差异，不传实施者的解释、开发对话或推理。 |
| 检查证据 | 真实命令、退出结果与关键输出；失败、未执行、限制及已有问题一起提供。 |
| 操作边界 | 默认只读代码和正式文档；必要检查仅在允许环境运行，注明可能产生的临时产物。 |

过程中的方案、计划和定位审查不要求为审查专门创建提交，可用当前文件、实际差异或快照说明覆盖范围；最终交付PR的检查仍须对应已创建的实际候选提交。diff不完整时补读原文件和必要上下文，不用模板读取次数限制阻止核验。等待审查期间冻结其检查范围；其后变化必须重查受影响部分。

### 审查者返回

先判断是否满足原要求，再检查可靠性、安全/数据、兼容、边界异常与可维护性；按实际风险核验测试能否证明要求，不机械套完整清单。证据不清先回读已有记录；确有新疑点时做有针对性的检查，不无故重复昂贵测试。

每条发现说明位置、触发条件、预期与实际差异、影响与依据，必要时给最小复现。区分必须修复、改进建议、待核实；没有有效问题可以为零。关键未知尚未排除时，不用“没有证明有错”当作通过。审查者返回覆盖范围、结论、未判断事项及原因，并说明是否影响已验收成果；审查者不写正式进度、不直接修复或再委派。主 Agent 据此组织修复、更新正式记录并处理重新验收。

### 修复与复查

主 Agent 核验发现后决定授权内的修复安排，可以自己修复，也可交回原实施者；问题与证据一起传递。每轮保留发现、处理、受影响检查和结果，再由审查者复查。新回归按实际影响处理，不因它晚出现就一律列为可忽略建议。

关闭问题必须有原问题已解决及受影响内容已核验的依据。审查者误报时保留驳回依据；必要业务选择由用户决定。两轮无新证据或反复回退时按主说明停止重复修补并重新调查，不“停放”必须修复的问题后继续下一任务。

### 记录与交付

主 Agent 把经过核验的返回内容合并到当前 verification.md，按事实更新 tasks.md。保留实施、AI 检查与用户验收的区别，避免重复粘贴原始规格或全部命令日志。记录可以简短，但必须能定位本次内容、实际检查与未解决事项。

完整交付还需可执行的用户验收方式。自查、测试、独立审查和用户验收分别成立，不能相互替代。工具限制或预算不足导致任一必要环节缺失时明确保留未完成状态，不伪造审查记录来满足模板。
