# 实施方法

仅在开始、恢复或修复当前已获准成果时读取。共同依据与写入规则见[工作契约](common/work-contract.md)和[写入契约](common/write-contract.md)。需要专项方法通过[能力表](common/capabilities.json)找到真实提供者，固定依赖缺失先报告包错误。

## 1. 核对入口、确认和当前任务

先读用户指定项目的 AGENTS.md、已有 docs/workflow/state.yaml、当前迭代的 scope.md、design.md、tasks.md、verification.md，关联规格、overview 与适用 foundation 约定，再核对实际代码、环境与工具。简单迭代的方案可在 scope.md 中；合法空文档不要求现在补齐。

框架源码仓库的docs/design和templates/project不是业务迭代。结合明确的开轮、暂停、恢复确认及实际资料定位；已有明确依据不重复询问，无法确定时再澄清，不按最大编号、最近修改、空state或唯一未标暂停目录选择。明确指定已有迭代时可核对，本项不创建导航或迭代。

请求明确开启普通后续迭代、暂停切换或恢复记录时，由原主Agent先按本项Git保存方法保留当前任务，再使用真实可用的clarify核对条件并处理最小文档，把实际路径、确认依据及已写/未写结果带回同一流程；不递归重启implementation。没有适用迭代本身不触发开轮；紧急线上修复的迭代、运行版本基线和返回约定按incident的专门方法承接，不能套普通开轮。资料、Git保存或切换记录未完成时不假定前置已满足；只请求记录或资料整理时不继续实施，固定能力缺失用skills check报告包问题。

| 当前事实 | 行动 |
| --- | --- |
| 用户只问进度、问题或下一步 | 只读核对并报告，不写文件、不启动新工作。 |
| 用户明确暂停切换或恢复指定旧轮 | 先由主Agent按上述交接保存当前任务、原验收状态及切换依据；不把暂停/恢复当作验收通过，记录完成后再按本次请求判断接续。 |
| 计划缺失、仅为未展示草案，或关键要求/授权不清 | 补查已有资料；仍缺关键前提则说明具体缺项，交回计划或澄清。不能把“继续”补成批准。 |
| 当前成果已提交，用户尚未明确验收通过且没有明确暂停切换请求 | 保持等待，提供验收入口与未解决事项；不开始下一任务。 |
| 用户明确通过指定成果 | 由主 Agent 按[验收后的规格收尾](common/spec-runtime.md#同步与完成)记录验收、核对检查并同步对应业务变化；收尾完成后才按前置、计划与授权判断接续。 |
| 已有验收，规格同步未完成或曾中断 | 核对实际文件及既有验收范围，按收尾步骤补未完成部分；不重做已完成工作、不重复索取同一验收。 |
| 已有适用的具体计划确认、当前任务前置与实施授权 | 简述本次成果和边界，直接推进内部步骤，不重复询问已有确认。 |
| 用户要求修复当前任务验收反馈 | 在原范围和授权内调查、修复、重验及复查，再提交；新增目标或重要变化另行确认。 |

实施前检查关键方案及任务之间的文件、接口供需和公共约束是否一致，核对依赖是否真实满足。已确认资料冲突、关键验收或业务意图不明时先处理；能在原目标与授权内解决的普通技术细节自主处理并说明依据，不让执行悄悄改变计划的成果或交付安排。

实施或恢复前按[每任务读取与绑定](common/state-runtime.md#每任务读取与绑定)实际读取context inspect原文，核对最新地基、当前任务定义及committed绑定；缺绑定或摘要过时先核对影响/确认并context bind，成功后再start/resume。context guard fresh和同一会话T1已完成均不能替代T2绑定。任务声明变更使用v3 task_revise，不先手改JSON或verification解锁。已有有效绑定、授权与内容不变可复用。

## 2. 固定本次读写与分工

记录当前成果的编号、依据、范围、验收条件、依赖与未完成步骤，核对涉及文件和实际路径。允许修改当前任务及已有授权覆盖的代码、测试和交付文档；主 Agent 将正式进度写到本轮 tasks.md、依据写到 verification.md。写入与历史保护按[写入契约](common/write-contract.md)。

state及机器记录通过已安装的语义工具维护；位置冲突先读取真实证据。不得为满足上游模板而创建 ledger、report、brief、隐藏工作目录或另一套计划。用户已有的这些同名资料不自动删除。构建或测试确需生成产物时先核对实际输出位置与影响，不将已声明的构建产物误当作正式文档。

不默认修改 scope、spec、design 或公共规则来迁就实现。当前任务明确授权的文档交付可按范围完成；涉及重要范围、设计、数据、安全、成本或交付安排变化时先说明原因和影响并确认。Git由主Agent按下文的任务起步、保存、提交和有条件自动收尾执行，核对项目目标、实际权限与工具；已确认且适用的动作不逐步重问。初始化仓库、配置身份、创建远端及生产发布另核对具体授权。

按项目已确认的验收后同步规则，主 Agent 可在第 6 节条件满足后更新该成果涉及的业务规格；这是落实已交付行为，不是为实现降低标准或扩大本轮范围。其他专项 Skill 的独立调用不因此获得规格写入权。

主 Agent 可自己实施；只有目标、输入、边界和前置清楚且工具真实支持时才派实施者。默认最多三个子 Agent，不默认递归委派；并行仅用于当前成果内可隔离的工作，不提前实施下一待验收成果。委派、接收或审查前读取 [协作与证据参考](review-and-acceptance.md#协作与证据参考)。

## 3. 实施并持续验证

按当前任务的技术步骤推进，遵循既有工程约定。已完成部分先核对，避免重新实现；缺少当前证据时补做必要检查，不将旧通过结论直接覆盖改动后的内容。普通内部步骤可自行调整，原要求的遗漏与修复留在当前任务；改变成果边界、依赖或交付顺序时按计划调整规则处理，不能拆走未满足的要求后称完成。

验证来自规格、验收条件、DoD 和实际影响。先确认命令和环境，再运行并阅读退出码与关键输出。测试、构建、接口及端到端验证按需要选择；测试必须证明行为，不为通过而删断言、改预期或降低标准。不强制所有改动采用统一 TDD 序列；项目已有 TDD 或测试约定适用时遵守。

失败时读取错误并复现，区分事实、假设与已证实原因，对比正常路径，用最小实验验证原因，在授权内针对原因修复后重跑原失败场景与受影响检查。重要方案变化不能由试错自行决定；无新证据时不叠加补丁。

环境不足时先在授权内处理已声明的本地准备问题；缺少凭据、真实数据、重要环境变更或额外费用且无授权时说明条件和影响。继续独立可做检查，记录必要检查的失败或未执行、原因与下一步；模拟结果不替代真实集成，不能凭本地测试通过宣布全部完成。
