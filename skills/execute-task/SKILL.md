# 任务执行与协作

读取已确认计划，推进当前可验收成果的实施、必要验证、独立审查与修复复查，提交用户验收并等待。主 Agent 统筹，实施可自行完成或按需委派；用中文说明，沿用项目术语。

本项融合 Superpowers executing-plans、subagent-driven-development 与 verification-before-completion 的适用方法，补充 GSD 的可观察验收及检查点恢复方法。来源、版本、保留与排除范围见 [NOTICE.md](NOTICE.md)。不调用原版流程，不依赖未安装的专项 Skill。

## 专项能力协调

从 workflow-guide 或其他能力接手时，核对同一项目、当前成果、请求模式、目标内容/运行版本、原始依据与确认、允许读写及副作用、已有证据、未决项和返回位置；不重建一份任务来源。原主 Agent 继续统筹记录、审查和验收。受托专项返回结果，不递归启动本项；能力不存在时给交接材料，不伪称调用。

地基任务可读 build-foundation 提供最小工程与真实连通方法；方案分歧按需读 discuss-design，讨论结论仍是建议。发布是 release-work 的单独请求与授权判断，任务通过不自动发布。线上问题先按 handle-incident 明确必要信息与调查范围，再按获准方案承接修复；一般执行授权不能代替线上修复确认。已有测试和审查仍适用时复用，只补内容或环境变化影响的部分。

## 1. 核对入口、确认和当前任务

先读用户指定项目的 AGENTS.md、已有 docs/workflow/state.yaml、当前迭代的 scope.md、design.md、tasks.md、verification.md，关联规格、overview 与适用 foundation 约定，再核对实际代码、环境与工具。简单迭代的方案可在 scope.md 中；合法空文档不要求现在补齐。

框架源码仓库的docs/design和templates/project不是业务迭代。结合明确的开轮、暂停、恢复确认及实际资料定位；已有明确依据不重复询问，无法确定时再澄清，不按最大编号、最近修改、空state或唯一未标暂停目录选择。明确指定已有迭代时可核对，本项不创建导航或迭代。

请求明确开启普通后续迭代、暂停切换或恢复记录时，由原主Agent使用真实可用的clarify-design核对条件并处理最小文档，再把实际路径、确认依据及已写/未写结果带回本流程；不递归重启execute-task。没有适用迭代本身不触发开轮，线上修复迭代安排仍归独立Git专题。资料或切换记录未完成时不假定前置已满足；只请求记录或资料整理时不继续实施，缺技能如实交接。

| 当前事实 | 行动 |
| --- | --- |
| 用户只问进度、问题或下一步 | 只读核对并报告，不写文件、不启动新工作。 |
| 用户明确暂停切换或恢复指定旧轮 | 先由主Agent按上述交接保存当前任务、原验收状态及切换依据；不把暂停/恢复当作验收通过，记录完成后再按本次请求判断接续。 |
| 计划缺失、仅为未展示草案，或关键要求/授权不清 | 补查已有资料；仍缺关键前提则说明具体缺项，交回计划或澄清。不能把“继续”补成批准。 |
| 当前成果已提交，用户尚未明确验收通过且没有明确暂停切换请求 | 保持等待，提供验收入口与未解决事项；不开始下一任务。 |
| 用户明确通过指定成果 | 由主 Agent 按[验收后的规格收尾](#6-验收后的规格收尾)记录验收、核对检查并同步对应业务变化；收尾完成后才按前置、计划与授权判断接续。 |
| 已有验收，规格同步未完成或曾中断 | 核对实际文件及既有验收范围，按收尾步骤补未完成部分；不重做已完成工作、不重复索取同一验收。 |
| 已有适用的具体计划确认、当前任务前置与实施授权 | 简述本次成果和边界，直接推进内部步骤，不重复询问已有确认。 |
| 用户要求修复当前任务验收反馈 | 在原范围和授权内调查、修复、重验及复查，再提交；新增目标或重要变化另行确认。 |

导航、勾选框和子 Agent 自报不是批准或完成证据。确认针对具体内容；计划/范围实质变化后重新核对。用户本次明确的具体批准可作为依据，不因旧文档尚未更新而重复索取；“继续”“看一下”或空回复不自动批准未展示方案或验收成果。

分别识别当前有效规格、本轮变更及具体确认：明确获准的变更只在对应行为和目标版本上按 scope 与确认依据执行，其余有效规则继续遵守；草案、备注和建议不能覆盖确认。核对候选实现与旧版本环境各自适用的要求，不把候选的新预期套用于旧版本，也不以尚未同步的旧规格否定获准变更。两份适用确认真正冲突时先澄清受影响部分。委派或交给测试、调试、审查时一并传递这些依据和目标版本。

实施前检查关键方案及任务之间的文件、接口供需和公共约束是否一致，核对依赖是否真实满足。已确认资料冲突、关键验收或业务意图不明时先处理；能在原目标与授权内解决的普通技术细节自主处理并说明依据，不让执行悄悄改变计划的成果或交付安排。

## 2. 固定本次读写与分工

记录当前成果的编号、依据、范围、验收条件、依赖与未完成步骤，核对涉及文件和实际路径。允许修改当前任务及已有授权覆盖的代码、测试和交付文档；主 Agent 将正式进度写到本轮 tasks.md、依据写到 verification.md。保留原任务顺序、已完成工作、历史检查和用户验收事实，落盘前回读以避免覆盖并发修改。

本版不写 state.yaml，不定义通用状态 schema；若导航与事实不一致，说明差异，以实际资料核对当前位置。不得为满足上游模板而创建 ledger、report、brief、隐藏工作目录或另一套计划。用户已有的这些同名资料不自动删除。构建或测试确需生成产物时先核对实际输出位置与影响，不将已声明的构建产物误当作正式文档。

不默认修改 scope、spec、design 或公共规则来迁就实现。当前任务明确授权的文档交付可按范围完成；涉及重要范围、设计、数据、安全、成本或交付安排变化时先说明原因和影响并确认。不自动初始化 Git、切换分支、提交、合并、推送、发布或清理工作区；相关操作必须有具体适用授权与方案。

按项目已确认的验收后同步规则，主 Agent 可在第 6 节条件满足后更新该成果涉及的业务规格；这是落实已交付行为，不是为实现降低标准或扩大本轮范围。其他专项 Skill 的独立调用不因此获得规格写入权。

主 Agent 可自己实施；只有目标、输入、边界和前置清楚且工具真实支持时才派实施者。默认最多三个子 Agent，不默认递归委派；并行仅用于当前成果内可隔离的工作，不提前实施下一待验收成果。委派、接收或审查前读取 [协作与证据参考](#协作与证据参考)。

## 3. 实施并持续验证

按当前任务的技术步骤推进，遵循既有工程约定。已完成部分先核对，避免重新实现；缺少当前证据时补做必要检查，不将旧通过结论直接覆盖改动后的内容。普通内部步骤可自行调整，原要求的遗漏与修复留在当前任务；改变成果边界、依赖或交付顺序时按计划调整规则处理，不能拆走未满足的要求后称完成。

验证来自规格、验收条件、DoD 和实际影响。先确认命令和环境，再运行并阅读退出码与关键输出。测试、构建、接口及端到端验证按需要选择；测试必须证明行为，不为通过而删断言、改预期或降低标准。不强制所有改动采用统一 TDD 序列；项目已有 TDD 或测试约定适用时遵守。

项目已安装 test-work 时，读取其完整说明，传入当前要求、验收、实际改动、允许读写与已有证据，按需选择测试层次、补充用例并执行检查。它返回各层结果与缺口，本项继续管理正式记录、失败后的调试、独立审查及验收，不因多个技能均提到测试而重复运行相同检查。未安装时使用本项基本验证方法。

失败时读取错误并复现，区分事实、假设与已证实原因，对比正常路径，用最小实验验证原因，在授权内针对原因修复后重跑原失败场景与受影响检查。重要方案变化不能由试错自行决定；无新证据时不叠加补丁。

环境不足时先在授权内处理已声明的本地准备问题；缺少凭据、真实数据、重要环境变更或额外费用且无授权时说明条件和影响。继续独立可做检查，记录必要检查的失败或未执行、原因与下一步；模拟结果不替代真实集成，不能凭本地测试通过宣布全部完成。

若已安装且适用的专项测试、调试或审查 Skill 可用，可按其真实入口使用。遇到需要调查原因的问题且项目已安装 debug-issue 时，读取其完整说明，传入当前问题、原始要求、已有证据和允许操作范围，按其方法调查、修复与重验，再返回当前任务；本项继续管理正式记录、独立审查与验收。项目已安装 review-work 时，审查者读取其完整说明完成专项检查，主 Agent 用其方法核验反馈；不另启动重复的全量审查。没有这些技能时，本项仍可用实际工具完成上述基本验证与调查，并用配套参考组织审查；不声称已调用不存在的能力，也不临时安装另一套框架。

## 4. 独立审查与修复关闭

普通功能任务在验收前需要独立审查，分别核对需求符合性与质量。低影响修改可按真实影响简化并说明依据；高风险内容按需增加专项视角，整轮还检查跨任务衔接。代码行数少不等于低影响。

审查者读取原始要求、实际产物、必要上下文与可核对的验证证据，默认只读业务代码和正式记录。工具不能提供独立审查者时说明能力缺失；自查可以完成但不记成独立审查。仅有格式正确的报告、角色名或实施者自报不能证明独立审查发生。

审查中的内容保持稳定；修改后重新核对受影响结论。主 Agent 核验发现是否成立，有效问题在已有授权内修复、重验并由审查者复查原问题和新增回归；误报给出具体依据，业务关键取舍交用户决定。

后续任务或整轮审查的修复影响已验收成果时，保留原验收历史，明确当前内容及受影响结论已变化；按范围修复、重验和复查后，将受影响成果重新提交用户验收。旧验收不覆盖修改后的内容，不能只让用户验收当前任务而沿用受影响前项的旧结论。

必须修复的问题或影响必要判断的未知项未解决时，不能提交为已满足验收条件。改进建议可保留但不擅自扩展任务。同一问题连续两轮无新证据或反复回退时，停止重复修改、重新取证；仍不能解决则报告阻塞和已尝试内容。不得因轮数、时间或预算耗尽，把真实问题记为已关闭或任务已完成。

## 5. 核对证据，交给用户验收

提交前核对当前内容：要求是否实现、必要检查是否实际通过、审查及必须修复项是否关闭、历史证据是否仍适用、实际改动是否在范围内。当前没有变化且证据仍适用时不因再次回复机械重跑；代码或环境改变影响结论时重验。需要重跑却无法执行时如实保留未验证。

主 Agent 沿用项目现有格式更新 tasks.md 和 verification.md，分别记录实施、检查、审查及用户验收。保留命令、必要环境、退出结果、关键证据、内容范围或可定位版本、未解决项和下一步；不用复制完整日志，不新建平行报告。未记录用户明确通过前保持“待用户验收”，不能用普通完成勾选冒充最终完成。

交付说明必须包含当前成果及位置、真实体验入口或可查产物、必要准备、操作步骤、预期结果、已知限制和未验证项。接口或工程任务可给已核对的调用/检查命令；不虚构在线服务、账号或测试结果。

把本成果整理为简短的“操作 → 可观察预期 → 当前检查/用户反馈”验收点，自动检查与用户判断分开；不把已有通过检查重复交用户手工执行。中断后沿原 tasks/verification 核对已反馈项、未反馈项及内容变化，只恢复仍待确认部分。逐点确认仅覆盖该点，全部所需内容明确通过才记录成果验收；空回复、沉默或含糊的“下一步”不算通过。验收点涉及启动、写数据或清理时先核对项目操作授权，不能照搬上游冷启动清理真实环境。

**提交后停止推进下一任务，等待用户明确验收。** 用户拒绝时在原范围修复再提交；用户明确通过后进入第 6 节收尾。普通查询、沉默、AI 检查通过或既有阶段授权均不能越过等待点。写入约束依靠当前 Agent 和实际工具能力，不是已实现的权限沙箱。

## 6. 验收后的规格收尾

由主 Agent 执行，子 Agent 只返回材料。独立修复等原流程交来已验收成果时，同样先核对项目、成果、授权与以下条件；没有适用迭代时返回交接需要，不为收尾创建迭代或导航。

1. **核对验收与检查。** 沿用 tasks/verification 记录用户明确通过的具体成果及内容范围，核对必要检查、审查和未关闭问题。检查缺失或失败时保留用户验收事实，记录缺口，暂不将受影响变化同步为有效规格，也不称整体完成。补齐后核对内容是否仍受原验收覆盖；修改影响已验收内容时，重验、复查并重新提交受影响成果。
2. **确定实际同步范围。** 从获准变更、实际交付及该成果验收范围定位相关需求与场景，可涉及多个 spec。只更新已交付业务变化，保留未变规则、其他任务内容、稳定编号和用户修改；不将整轮 scope 复制到规格。无业务变化时记录“不需同步”。公共 foundation 约定仍按其独立的确认、落实和生效时点维护，不能等业务验收才一律生效。
3. **写入并核对。** 检查真实目标路径，写前回读并合并后续修改；新业务能力确需新规格时只在既定 specs 目录按项目约定创建。写后核对实际内容、相关引用及未受影响规则，按影响补必要检查；不机械重跑未受影响测试，不把修改规格当成发布或更新旧环境。
4. **记录结果并恢复。** tasks.md 记收尾进度，verification.md 留验收依据、已同步与待同步的需求/文件范围、实际核对及受阻原因、补齐条件和下一步。中断后对照实际文件、验收内容及后续修改，只补未完成部分，不盲目重放或覆盖新内容；语义冲突先处理受影响部分。无法写记录时在对话交付同样信息，不声称已落盘。保留验收事实，收尾未完成时不将任务记为全部完成或推进下一任务。
5. **判断接续。** 收尾完成或确实无需同步后，核对下一成果的依赖、具体计划及已有授权再接续；用户要求停止或只查询时遵守该请求。无需再为原已确认规则下的同一同步索取批准；新增或实质变化仍按确认规则处理。

例如本轮 T1 获准将标题上限 60 改为 120，T2 拟改导出条数：T1 验收且必要条件满足后，只同步标题及其相关场景；标签等未变规则照旧，T2 尚未验收的导出变化不进入有效规格。

## 协作与证据参考

主 Agent 在委派实施者、接收结果或安排独立审查时读取。没有子 Agent 工具时不得编造调用；主 Agent 自己实施与独立审查的要求分别判断。

### 任务交接

提供当前成果的稳定编号、目标与验收、原始 scope/spec/design 及 tasks.md 中对应位置、公共约束、允许读写范围、依赖接口和已完成事实、必要验证与停止条件。按需给上下文，不复制全部会话。原始资料与摘要矛盾时先回报，不自行覆盖用户要求。

实施者只处理分配的当前工作，返回：

- 实际实现或尝试了什么、哪些文件改动、哪些原要求尚未完成。
- 运行过的命令、必要环境、退出结果、关键输出和未运行检查及原因。
- 自查发现、阻塞、缺项及需要主 Agent 决定的问题。

可以用完成实现、存在疑点、需要资料、受阻等短语描述返回情况；它们是实施者自报，不是框架状态枚举或用户验收。详细依据随返回传给主 Agent，不自行创建 report.md 或更新正式 tasks/verification/state。不自行再派实施者或审查者，也不提交、合并或清理文件。

主 Agent 接收后检查实际文件、差异与证据，确认必要内容可读，不用子 Agent 的“完成”替代核验。报告缺证据时要求补齐；技术资料能自行查到就补查，关键业务意图才向用户确认。委派期间主 Agent 不同时改相同范围。

### 独立审查输入

给独立上下文的审查者以下资料：

| 输入 | 要求 |
| --- | --- |
| 原始依据 | 当前任务、已确认范围、规格、设计和质量要求；提供具体位置。 |
| 实际内容 | 改动文件、必要调用方与依赖，以及可定位的内容状态。 |
| 实施者返回 | 只作导航，所有实现与设计理由都需核对。 |
| 检查证据 | 真实命令、退出结果与关键输出；失败、未执行、限制及已有问题一起提供。 |
| 操作边界 | 默认只读代码和正式文档；必要检查仅在允许环境运行，注明可能产生的临时产物。 |

不要求为了审查先创建 Git 提交。已有适用差异可以使用；没有提交范围时读取实际文件和已有快照等可用证据，说明覆盖范围。diff 不完整时补读原文件和必要上下文，不用模板的读取次数限制阻止核验。等待审查期间冻结其检查范围；其后变化必须重查受影响部分。

### 审查者返回

已安装 review-work 时，以下要求作为交接与接收约定，具体检查和反馈核验采用该技能；未安装时使用下列基本方法。无论哪条路径，一次实际审查只记录一次，不因两份说明均含审查规则重复派发。

先判断是否满足原要求，再检查可靠性、安全/数据、兼容、边界异常与可维护性；按实际风险核验测试能否证明要求，不机械套完整清单。证据不清先回读已有记录；确有新疑点时做有针对性的检查，不无故重复昂贵测试。

每条发现说明位置、触发条件、预期与实际差异、影响与依据，必要时给最小复现。区分必须修复、改进建议、待核实；没有有效问题可以为零。关键未知尚未排除时，不用“没有证明有错”当作通过。审查者返回覆盖范围、结论、未判断事项及原因，并说明是否影响已验收成果；审查者不写正式进度、不直接修复或再委派。主 Agent 据此组织修复、更新正式记录并处理重新验收。

### 修复与复查

主 Agent 核验发现后决定授权内的修复安排，可以自己修复，也可交回原实施者；问题与证据一起传递。每轮保留发现、处理、受影响检查和结果，再由审查者复查。新回归按实际影响处理，不因它晚出现就一律列为可忽略建议。

关闭问题必须有原问题已解决及受影响内容已核验的依据。审查者误报时保留驳回依据；必要业务选择由用户决定。两轮无新证据或反复回退时按主说明停止重复修补并重新调查，不“停放”必须修复的问题后继续下一任务。

### 记录与交付

主 Agent 把经过核验的返回内容合并到当前 verification.md，按事实更新 tasks.md。保留实施、AI 检查与用户验收的区别，避免重复粘贴原始规格或全部命令日志。记录可以简短，但必须能定位本次内容、实际检查与未解决事项。

完整交付还需可执行的用户验收方式。自查、测试、独立审查和用户验收分别成立，不能相互替代。工具限制或预算不足导致任一必要环节缺失时明确保留未完成状态，不伪造审查记录来满足模板。
