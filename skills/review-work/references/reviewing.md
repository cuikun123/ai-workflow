# 核对候选与发现的方法

审查需求符合性、质量或核验反馈时读取。共同判断依[工作契约](common/work-contract.md)，接手/写入/工具条件依[写入契约](common/write-contract.md)。需要专项方法先按[能力表](common/capabilities.json)找到真实提供者；以下能力ID不是原生Skill名称，固定依赖缺失不能用基本方法掩盖。

## 定位范围与角色

先读目标项目 AGENTS.md 和已有导航，结合用户指定范围定位本次任务、迭代或文件，区分方案/计划审查、实现审查和修复后复查；读取相关 scope/spec/design/tasks、适用质量约定和已有检查。提交者摘要只用于导航，不能代替原始依据及受审草案、代码或实际输出。当前范围内没有某类资料时，先查可得信息，只把影响判断的缺项保留为待核实，不强制补齐整套文档。

用户指定的范围优先；未指定时结合当前任务和实际改动简述范围。多个合理目标、互相冲突的确认或关键业务意图不明时，澄清受影响部分，其余可独立检查的内容继续推进。无当前迭代但目标文件明确时可以审查，不按最大目录编号猜测目标，也不为审查创建迭代或导航。框架源码的 docs/design 与 templates/project 不作为业务迭代。

| 当前角色或请求 | 工作边界 |
| --- | --- |
| 主 Agent 组织审查 | 实现前检查关键方案，普通方案和计划按影响及项目安排检查，不因本技能新增逐份独立审查门槛。普通功能任务按项目规则安排独立审查；低影响改动可简化并说明，高风险按需补充视角，整轮检查跨任务衔接。原实施者自查不能冒充独立审查。 |
| 已委派的审查者 | 自己读取依据、检查并返回发现；不再委派、不修改实现和正式记录。必要检查仅在给定环境与范围内运行。 |
| 主 Agent 核验已有反馈 | 逐项理解和核验反馈；已有独立审查不因读取本技能再自动派一轮全量审查。修复后的独立复查按实际需要安排。 |
| 用户只请求审查 | 交付问题和建议；该请求本身不授权修改代码。已有适用修复授权则由主 Agent 按原流程处理，不重复询问。 |

主 Agent 委派时提供：原始要求位置、任务及验收条件、实际文件与必要上下文、可定位的内容状态、已有检查及限制、允许操作与返回要求。使用真实可用的工具，独立上下文不包含实施者推理历史；默认最多三个子 Agent，不递归委派。工具无法提供必要独立审查时如实报告，自查结论与独立审查分别标明。

交付PR的代码规范性检查必须是全新独立上下文，只交需求、相关修改/新增和可定位候选，不传开发对话、实现推理或以实施者解释替代核验；审查者可自行只读规范、必要调用方、依赖和验证证据。普通测试证据仍适用时可引用，但旧审查不替代本轮独立判断。每轮检查固定候选内容；修复后检查实际影响，必要内容未查不能算通过。

Git审查输入包含真实仓库/worktree、候选提交、PR的head/base及当前获取的目标主线，核对工作区差异与未入提交内容，不能只看同名分支或旧diff。准备合入发现普通任务尚未包含新主线时，由主Agent按implementation先保存再普通Merge同步，重查受影响衔接；审查者不自行合并。线上补丁例外保持实际运行提交基线，不要求将未发布主线全部并入。最终集成须核对已验收范围、对应规格/记录收尾、必要检查和PR实际待合入内容；GitHub状态/权限缺失如实保留，不能用本地合并预置证明真实PR通过。

已有有效 diff 可作入口；没有提交或基线时读取当前文件和必要调用方，说明只能判断当前内容，不虚构“本次新增”或自动创建提交、分支、工作树。主 Agent 保持受审范围稳定；内容后来变化时，重新核对受影响结论。

## 检查实际产物

**方案或计划审查：** 从原始要求与适用确认检查受审草案，已有有效确认继续作为依据，未确认建议不能变成需求。按实际影响检查：

- **覆盖与约束：** 每个已确认需求是否有对应方案、成果及验收方式；是否遗漏、超范围或违反已有体验、数据、安全、成本和技术约定。明确拟新增入口与已有能力，关键未知保留为待验证。
- **依赖与顺序：** 前置资料、组件与任务是否可获得，接口和共享约定是否兼容；scope/design/tasks是否对验收、逐成果规格收尾及下一成果前置给出一致安排。
- **可验证性：** 验收是否可观察，所需环境和工具是否可得；影响方案成立的关键假设若确需原型或实验，核对已有证据及缺口。只读审查不自动获得编写原型、安装或运行服务的授权。

尚未进入实施阶段时，没有实现代码或运行测试属于阶段事实，不单独作为方案缺陷；明确要求的可行性证据仍缺失时，保留相应结论为证据不足。结论只覆盖受审方案/计划，不称实现、测试或用户验收通过，也不将审查通过当作范围或实施批准。例如计划要求T1验收后立刻启动T2，却把T1规格同步推迟到整轮结束，应指出与逐成果收尾约定的冲突，而不是要求先写T1代码再审计划。

**实现审查及修复后复查：** 核对已确认要求和本轮获准变更是否得到实现，再判断实现与测试是否可靠。沿实际调用与数据流选取检查视角：

- **需求与范围：** 对应验收场景及接口，检查遗漏、超范围实现、与设计或约束的偏离；区分实现错误和方案本身的问题。
- **行为与质量：** 对照正常、边界和异常输入，追踪状态变化、错误处理及资源生命周期。按影响检查权限、数据完整性、接口与配置兼容、迁移、性能和可维护性，不机械要求每项改动完成全部专项审计。
- **测试与证据：** 检查断言是否能暴露需求失败，是否遗漏关键分支或只证明替身行为；测试通过只说明实际覆盖场景。实现者说“已通过”或旧日志不能代替对当前内容的核验。
- **跨任务衔接：** 整轮审查核对调用方、共享约定和端到端路径，不能只汇总各任务曾经通过的结论。

读必要调用方、依赖和测试以验证发现，不因只看改动行而漏掉实际行为；重要范围变化仍按项目规则处理。通用正确性或安全问题应给出具体依据；规格未说明的业务偏好列为待核实，不能凭“合理用户应该想要”发明需求。

按疑点运行最小且有意义的检查。先读命令和配置，核对输出位置与副作用；优先使用现有无写入检查或不影响项目的隔离复现。构建缓存和临时产物应说明，不把测试视为任意改代码、安装依赖、访问真实环境或写报告的授权。读取真实退出码和关键输出；不能运行则说明原因、影响和补齐条件，继续独立可做检查。模拟结果不替代真实集成结果。

## 核验反馈与修复后复查

收到反馈时先理解全部意见及其关联，再对每项核对：原要求是什么、受审方案/计划或代码实际怎样、触发条件是否成立、建议是否适合项目并会不会破坏已有行为。补查原始依据或最小复现后，给出采纳依据、驳回依据或仍缺的信息。技术分歧凭实际产物、约定和实验解决；重要业务取舍交用户决定。意见不清只阻塞依赖它的工作，独立且有授权的部分可以继续。

先筛必要性再安排修复；非必要建议不进入本轮修复列表、不阻塞合入，也不驱动反复润色。必须修复项与影响判断的关键未知仍按证据关闭。复查聚焦原发现与实际修复影响，新增必要项给出同等触发条件、影响和依据；不能因晚发现就忽略真实回归。主Agent按implementation组织内部修复、重验及独立复查，用户侧报告简短结果；审查通过不授权合入，用户验收和最终门槛仍分别核对。

主 Agent 在原执行流程或明确修复请求的授权内安排有效修复；审查者保持检查职责，不顺手改实现。implementation 可承接已有任务的修复与重验，但不是本项的硬依赖。仅核验意见时不把建议直接记成修复完成，也不根据未发现内部调用就删除公开接口。

复查对照原发现、实际修改和受影响检查，确认原问题消失且没有新增回归；同一原因合并说明，不凑问题数量，也不把晚发现的回归自动降为建议。两轮没有新证据或反复回退时停止重复修补、重新调查；仍未解决则报告阻塞，不能到限即通过。

修复影响已验收成果时，主 Agent 保留原验收历史，说明当前内容及结论已变化；修复、重验和复查后重新提交受影响成果验收。审查通过不代替测试、用户验收或发布授权，不自动接续下一任务。

## 返回结论与记录

返回以下内容，篇幅按发现多少决定：

1. **范围与结论：** 审查对象及可定位内容，已检查的要求，结论为通过、需修复或证据不足；仅对实际覆盖范围成立。
2. **发现：** 每项包含位置、触发条件、预期与实际差异、影响和依据；可复现时给最小复现，静态判断说明推导路径。按“必须修复”“改进建议”“待核实”区分，有效问题可以为零。
3. **检查证据与限制：** 命令或检查方式、必要环境、退出结果和关键输出；区分通过、失败、未执行、不适用。列出未判断事项及原因，重要未知不能按“没有证实有错”算通过。
4. **处理与下一步：** 反馈采纳或驳回依据、原问题是否已关闭、受影响成果、尚需修复或补齐的条件。必要范围未查、必须修复项未关、必要检查失败或未执行时，不能宣布整体通过。

例如，需求要求“去空白后不能为空”，代码只检查原始空字符串，而现有测试只验证普通名称：应给出纯空白输入的实际结果、对应要求及位置，说明测试覆盖缺口；不能只报告“缺少测试”或因为现有测试通过就接受实现。

审查者将结果返回主 Agent，不落盘正式记录。主 Agent 有明确适用迭代时，沿用现有格式将必要依据合并到 verification.md、必要进度写入 tasks.md，写入按[写入契约](common/write-contract.md)。没有适用迭代时在对话交付结果，不自建报告或完整迭代。需要维护机器状态时由主Agent使用真实语义工具，保留原位置和历史。

本技能不附运行脚本、不自动安装工具、不发送外部审查评论、不执行 Git 写操作。上述是 Agent 行为约束；实际工具权限与隔离条件需另行核对，不能宣称具有权限沙箱。
