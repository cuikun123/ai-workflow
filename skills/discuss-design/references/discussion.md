# 比较方案与取舍的方法

存在真实设计分歧或需要多个视角比较时读取。共同判断依[工作契约](common/work-contract.md)，接手/写入/工具条件依[写入契约](common/write-contract.md)。需要专项方法先按[能力表](common/capabilities.json)找到真实提供者；以下能力ID不是原生Skill名称，固定依赖缺失不能用基本方法掩盖。

## 明确议题和事实

先读用户问题与已有材料；存在业务项目时读 AGENTS、相关目标、范围、设计、有效规则及本轮获准变更，按需核对实际产物。没有项目也可以在对话讨论，不创建迭代或让用户先填文档。区分事实、已确认约束、建议默认值和未知，不重开已定且仍适用的决定。

用一句话确定本次要决定什么、主要约束及讨论深度；只追问会改变推荐的关键缺项。能查的事实主动查，外部来源按实际权限、具体版本和原始依据核对，未查不能冒充已研究。关键未知不妨碍独立可做比较，但保留有条件结论。Git议题先核对项目已确认规则和实际资料，普通任务Git方法由implementation、发布标签由release、线上补丁由incident承接；不把已定规则重新当未决选项。仅讨论Git方案不执行提交、分支、PR或清理；改变已确认范围或策略仍交用户决定，推荐不成为操作授权。

## 按议题选择视角

选择能改变判断的角度，不机械凑齐角色或重复同一观点：

| 视角 | 关注的问题 |
| --- | --- |
| 产品 | 谁在什么场景受益、价值和范围、是否值得现在做？ |
| 体验 | 用户路径、加载/空/错误/冲突状态、可访问性、理解及恢复成本？ |
| 技术 | 既有工程适配、组件边界、依赖方向、数据归属、兼容和可验证性？ |
| 运行与数据 | 费用、权限、安全、敏感信息、可观测性、备份恢复与维护责任？ |

先给各角度的核心论点与依据，再让冲突互相检验：一个选择增加价值时，会带来什么数据、体验或维护代价？哪些不同意见来自事实差异，哪些来自优先级？不虚构用户研究、实验或共识，不凭角色名提高证据等级。

默认由当前 Agent 分视角分析，并明确这是同一 Agent 的分析。只有用户要求或本次适用协作要求明确需要实际独立 Agent、且工具可用时才委派；给相同原始问题和约束、各自关注点与只读边界，默认不递归委派。说明哪些视角实际独立产生；工具不足则透明报告，不静默冒充。无论几位 Agent，多视角讨论都不能代替正式独立审查或用户决定。

## 收敛并返回原流程

简短交付：**推荐及适用条件 → 主要理由与代价 → 保留分歧/未知 → 需要用户决定的关键点或最小验证办法**。用户要继续深挖时针对分歧推进；请求已答清则收敛，不强制无限轮次或制造一致意见。推荐不是已确认原则，结束讨论或沉默不算批准。

仅讨论时不写文件、不改状态或范围，不自动保存会议、记忆、角色配置或 HTML。用户明确要求整理方案时，由当前主 Agent 把获准内容交 clarify 沿 scope/design 归属处理；tasks 交 planning，证据按需归 verification；无适用位置在对话交付。写入依[写入契约](common/write-contract.md)，不能提前改有效 specs/foundation 来迁就新建议。

被原流程调用时，保留同一项目/成果、请求模式、目标内容/版本、原始要求及确认、允许读写、已有证据、未决项和返回位置。只返回讨论结果，主 Agent 统一记录和接续，不递归调用执行或另起审查；能力不存在时给材料，不安装上游或伪称调用。

例如比较本地存储与跨设备同步时，核对真实使用频率、账号/费用意愿、冲突和恢复责任；信息不足可以推荐先保留本地并写明改判条件，不能把同步建议直接加入本轮实施。
