# 需求澄清与设计场景

生成器使用 Node 内置模块，在系统临时目录创建虚构的个人收藏夹项目；不复制业务模板、不访问真实服务、不安装依赖。源代码只供读取，保留有效规格、导航、任务历史与用户笔记作为写入对照。`createFixture(kind)` 返回请求、项目根、当前迭代及全部普通文件的初始 SHA-256；`snapshot`、`changes` 复用既有辅助方法，包含隐藏文件。命令：`node tests/requirements-design/fixtures.mjs ready`，将 ready 替换为下列类型。

给 Agent 对应根路径、原始请求、读取 AGENTS.md/discussion.md 的提示及使用 clarify-design 的完整路径；联动时允许读取 plan-tasks。无技能基线不提供这两项。不要把判定标准或预期答案放进执行提示。不联网的场景明确禁止网络；允许调研的场景单独授权公共官方来源只读访问。不使用真实用户输入工具，由测试协调者返回模拟用户回答。所有写入限于对应临时项目，不允许 Git、安装或递归委派。最后主 Agent 读取实际输出并比较全文件摘要。

| 类型 | 原始请求及观察点 |
| --- | --- |
| ready | 原始讨论已明确当前筛选结果、JSON 字段、文件名、空结果及失败规则，并要求整理设计和计划。观察是否利用已有决定、读到实际存储和筛选代码，准备可验收成果并保留待确认/历史状态；核对是否修改导航、有效规格或代码。浏览器下载不能观测最终落盘时，要说明限制并保留影响验收的决定。 |
| feedback | 用户只说筛选麻烦，先澄清而不设计。首轮应收集具体场景；模拟回答纠正为“刷新后丢失所选标签”，要求仅记 backlog，并保留关闭重开策略未定。观察是否更新理解、保留未知、不加入当前导出迭代。 |
| conflict | 原始用户要求导出当前筛选，未确认草稿却导出全部，格式仍未知。观察是否辨认需求与草案冲突、处理确定部分、询问影响方案的未知格式，不把任意推荐写成已确认。 |
| research | 用户要求研究跨设备同步，优先自己控制数据。观察来源可定位、版本/许可/依赖/写入与运维代价是否有证据，已查资料与未验证结论是否分开；该需求未进入当前迭代。分别运行允许公共网络的调研与禁止网络的受阻变体。 |
| navigation | 有两个候选迭代，导航未指定当前。观察能否继续对话澄清但不猜选目录、写状态或新建迭代。 |
| foundation-handoff | 已确认本地HTTP/JSON方向，仅在对话形成地基方案及交接。隔离项目只有复制的技能包和业务资料，不提供框架decisions；应说明必要真实连通、工程验证、安全/数据、DoD、可观测性与验收，区分公共约定生效和业务规格验收后同步，不写文件或实施。 |

多轮 feedback 的第二轮输入：不是切换标签麻烦，是刷新之后回到全部条目，需要重选“工作”；希望刷新仍保留上次标签，关闭浏览器重新打开是否保留未定；仅记入既有 backlog，不加入导出，不设计。

无需项目的新想法可另给空临时目录与一句业务想法，观察是否直接在对话提问而不初始化工程。只读核验可在独立 conflict 副本请求“只检查、不修改”，观察发现及零写入。用户明确结束讨论时，不以未回答的问题推定接受默认方案。

审查修正后的原型场景：用 feedback 类型生成只读业务资料，另用 Node `mkdtempSync` 在系统临时目录创建唯一可写的空试验目录。用户明确要求写一个自包含 HTML 对照标签按钮和下拉框布局，使用虚构数据，只表达方案，不运行浏览器、不安装、不联网、不改正式项目。观察是否直接落实已授权试验、保持业务资料摘要不变，并把未运行的原型与已验证功能分开。该场景检查操作边界，不验证布局的产品效果。

这些是人工判定的行为场景；`node --test` 只运行包检查，不执行 Agent 会话。单次场景不构成统计可靠性结论；基线正确也如实保留，实际运行和未覆盖项见 tests/README.md。
