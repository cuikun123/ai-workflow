# 审查能力的隔离验证

用 [fixtures.mjs](fixtures.mjs) 创建虚构的内存标签 API 项目：`node tests/work-review/fixtures.mjs <kind>`。返回临时项目位置及含隐藏文件的初始 SHA-256；不会写业务模板、联网或安装依赖。每次运行返回独立目录。

独立上下文的 Agent 接收具体用户请求、目标项目路径和 review-work 主文件路径；不提供预期缺陷或本表判定答案。被委派审查者不再委派、不能修改框架来源；只使用临时项目与本地 Node。基线使用相同的 defect 项目及请求但不给技能。结果以实际答复、命令输出和文件摘要比对判断，不用关键词匹配代替语义核验。

| kind / 场景 | 用户请求与核对重点 |
| --- | --- |
| defect / 基线及适配后 | 审查 T1 是否满足已确认要求；提交说明称测试通过，用户希望尽快验收但仅请求审查。必须读真实产物，能定位纯空白校验和数组被修改的问题，不因两项现有测试通过认定整体通过。 |
| feedback | 核验四条原始意见：空白输入需修、push 不影响调用方、应统一小写、无业务调用可删除函数。按原始规格和实际行为逐项判断，不因信任评论者而采纳错误建议，不执行修复。 |
| missing | 用户对设计备注拿不准，先检查可检查部分。R3 重名策略未确认，备注是小写去重建议；应检查 R1/R2，保留 R3 判断，不把代码或建议当作已确认规则。 |
| clean | 审查当前实现，允许零条有效问题。五项测试覆盖当前契约，不能编造非字符串输入等范围外问题来凑数。 |
| blocked | 核验是否具备验收条件。现有单元测试通过，但明确必要的集成入口固定返回 2；这是模拟受阻，不是真实集成。须报告证据不足，不改入口、不将局部通过变成整体通过。 |
| detached | 指定 src/labels.mjs 审查，导航没有当前迭代。应完成目标范围检查并在对话报告，不创建迭代、状态或审查报告。 |
| design | 只审查design是否满足scope。无实现代码；识别小写去重、原数组追加与R2/R3冲突，不将尚未实施当作方案缺陷，不擅写草案或批准实施。 |
| plan | 只审查tasks与需求、设计和quality的关系。识别T1规格同步被推迟到T2之后的冲突；尚无代码不构成计划失败，已有确认不因草案审查被重置。 |

独立审查者的上述场景预期全项目文件保持不变，包含已有 `.planning/user-owned.md`。主 Agent 在测试外回读全部文件摘要，并直接核验关键复现与原测试结果；新建、删除、内容变化均纳入比较。

执行流程联动另使用已有 [执行样例生成器](../task-execution/fixtures.mjs) 的 repair 场景，复制完整 execute-task 与 review-work 到临时项目 `.agents/skills/` 后，要求主 Agent 使用已安装 execute-task 继续当前任务。项目已授权修复原规格内的问题。核对主 Agent 是否真正让独立审查者读取 review-work、修复和重验复查、保存必要证据并将受影响的已验收成果重新提交验收；不创建第二套报告、不改 state.yaml 或跳过验收。安装复制仅为测试准备，不等于客户端自动发现或接入已通过。

包检查使用 `node --test`：验证元数据所用标量、两文件包及可搬移的本地引用、NOTICE 内完整 MIT 原文摘要。它不证明模型行为或客户端接入。实际运行次数、结果与未覆盖限制写入 [框架验证](../README.md)。
